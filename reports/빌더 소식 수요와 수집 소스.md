# 새 소식보다 내 스택의 변화를 수집하라

Tidwyn이 새 제품과 GitHub 트렌딩 다음으로 더할 것은 또 다른 소식 목록이 아니라 **"내가 쓰는 도구에 무슨 일이 생겼고 언제까지 무엇을 해야 하나"**를 알려 주는 항목이다. 우선순위는 코딩 에이전트 변경, 모델 지원 종료·가격·한도, 고영향 보안 사고, 프레임워크·런타임 릴리스 순이고, 이 넷을 매일 2~4건 이내로 싣되 사건이 없는 날은 "오늘은 없음"이라고 쓴다. 투자, YC, 인디 사례, 채용, 논문은 주간이나 월간 묶음으로 충분하다. 근거는 세 가지다. 설문에서 코딩 에이전트 일상 사용과 비용 압박이 뚜렷하고, 커뮤니티의 가장 큰 불만은 AI 소식 과잉이며, "무슨 일이 있었나" 요약은 GeekNews의 GN⁺와 한국어 AI 뉴스레터가 이미 채운 반면 시간 축과 영향 판단을 붙인 한국어 일간 서비스는 이번 조사에서 찾지 못했다. 수집 비용도 낮다. 대부분 공식 RSS·JSON·마크다운으로 얻을 수 있고, 추가로 필요한 것은 어제 사본을 저장해 비교하는 기능이다. 다만 계획에 있는 두 소스부터 조건이 붙는다. GitHub Trending 페이지는 공식 API가 없어 검색 API로 대체하는 편이 맞고, Product Hunt API는 상업 사용이 금지되어 있어 광고를 달기 전에 허가를 받거나 뺄 수 있어야 한다. 이 순위는 여러 간접 근거를 묶은 판단이며, 범주 선호를 직접 물은 설문과 한국 독자 측정 자료는 없다.

## 수요는 제품 발견보다 도구 변화와 비용에 몰려 있다

가장 강한 근거는 사용 강도다. Stack Overflow 2026 설문에서 코딩 에이전트·보조 도구 사용자의 **73%가 매일 쓰고**, 매일 쓰는 사람의 31%는 하루 4시간 이상 쓴다([SO 2026 블로그](https://stackoverflow.blog/2026/10/06/the-results-of-the-2026-developer-survey-are-here/)). 이 정도면 도구의 기본 동작이나 요금 변화는 뉴스가 아니라 작업 환경 변경이다. Amplify·Notion·Vercel 설문(1,053명)에서는 **81%가 여러 모델을 쓰고**, 비용이 AI 활용 수준을 정기적으로 제한한다는 응답이 40%, 가끔 제한한다는 응답이 36%였다([Amplify 2026](https://www.notion.com/lp/ai-engineering-survey)). 같은 설문에서 에이전트에 쓰기 권한을 주는 사용자는 90%로 전년 52%에서 늘어, 공급망 사고의 피해 범위도 커졌다.

뉴스레터의 구성도 같은 방향을 가리킨다. JavaScript Weekly는 Releases와 Code & Tools를 고정 칸으로 두고([JS Weekly](https://javascriptweekly.com/latest)), Console은 도구마다 좋은 점과 아쉬운 점을 적는 리뷰로 3만 명 이상을 모았다([Console](https://console.dev/)). 반면 논문은 실무자 수요가 가장 약했다. 이론 연구에는 관심 없다는 반응이 있고 구체적으로 추천되는 곳은 Hugging Face daily papers 정도였다([HN 44575422](https://hn.svelte.dev/item/44575422)).

주 독자는 현직 8년차이면서 Claude Code로 직접 만드는 사람이라 시니어와 인디의 교집합이다. 시니어는 도구의 깊이, 팀 도입, 비용, 커리어를 찾고 인디는 유통과 첫 사용자를 찾는데, 1~5위는 양쪽에 공통이다. 그래서 1~5위를 본문으로 두고 유통·수익 사례는 작은 주간 묶음으로 두는 구성이 맞다. 한국 고유 항목(규제, 지원사업)은 수요 근거가 없지만 해외 소식지와 겹치지 않는다.

두 번째 수요는 양이 아니라 필터다. "Ask HN: How do you keep up with HN these days?"(93점·148댓글)는 AI 글 때문에 따라가기 어려워졌다는 글이고, 사람들은 키워드 차단과 시간 제한으로 대응하며 중요한 소식은 어차피 다시 온다고 말한다([Zeli 요약](https://zeli.app/story/49308059)). 2026년 6월에는 AI를 뺀 기술 뉴스가 필요하다는 스레드가 80점·41댓글을 얻었고, 반대로 지난 12개월이 직업을 더 많이 바꿨다는 반론도 나왔다([AI Weekly 요약](https://aiweekly.co/alerts/hacker-news-thread-reveals-split-over-ai-coverage-volume)). 신뢰 조건도 명확하다. SO 2026에서 AI 결과를 **쉽게 검증할 수 있을 때만 믿는다는 응답이 48.0%**이고 출처 표시가 매우 중요하다는 응답이 52.1%다([SO 2026](https://survey.stackoverflow.co/2026/)). 공식 변경 내역에 근거한 항목은 이 요구를 그대로 만족한다.

## 요약은 포화 상태이고 빈자리는 시간 축과 영향 판단이다

한국어 "무슨 일이 있었나"는 GeekNews가 기준선이다. 사람 투고와 AI 번역 요약 GN⁺가 일간으로 돌고([GeekNews](https://news.hada.io/)), 주간 메일 구독자는 약 19,000명이다([GN Weekly](https://news.hada.io/weekly)). 트렌딩 레포 한국어 설명도 빈자리가 아니다. 깃밥은 2026-11-01 기준 제270호까지 왔고 신뢰도 점수, 난이도, 라이선스 신호등까지 제공한다([깃밥](https://gitbap.com/)). 그러므로 Tidwyn이 GitHub 트렌딩을 레포별 요약으로 내면 깃밥보다 약하고, 해외 글을 번역 요약하면 토론이 없는 GN⁺가 된다. 레포 항목은 "이번 주 스택에 영향이 있는 것"만 골라 이슈에 연결하는 쪽이 맞다.

| 기능 | 한국어 | 영어 |
|---|---|---|
| 무슨 일이 있었나(요약) | 포화: GN⁺, 뉴스레터 | 포화 |
| 트렌딩 레포 설명·신뢰 라벨 | 있음: 깃밥 | 있음: Trendshift 등 |
| "내가 신경 써야 하나" 판단 | 찾지 못함 | Console이 부분적 |
| 마이그레이션 영향·기한 | 찾지 못함 | 은퇴 달력은 있음 |
| 한 도구를 시간순 추적 | 찾지 못함 | 데이터 추적기는 있고 해설은 드묾 |
| 제품 소식을 업계 이슈 흐름과 연결 | 찾지 못함 | 미확인 |

한국어 Claude Code·Cursor 비교 글은 많지만 날짜 없는 정적 가이드나 업체 블로그가 대부분이고, 검색에서 지원 종료나 가격 인상을 다룬 소식형 글은 나오지 않았다([wavespeed](https://wavespeed.ai/blog/ko/posts/cursor-vs-claude-code-comparison-2026/), [braindetox](https://braindetox.kr/posts/ai_coding_tools_2026_comparison.html)). 영어권에는 303개 모델의 은퇴 일정과 90·30·7일 전 알림을 주는 BenchLM이 있고([BenchLM](https://benchlm.ai/newsletter/issues/2026-08-27)), Vorp Labs는 업체마다 날짜 신뢰도가 다르다고 적는다([Vorp Labs](https://vorplabs.com/models/deprecations)). 데이터를 새로 만들 이유는 없고, 한국어로 된 영향 판단과 기존 기능 연결이 차별점이다.

Tidwyn에는 경쟁자에게 없는 구조가 이미 있다. 이슈, 인물·기관, 용어집, 일정 달력, 지표, 정정 표시다. 모델 은퇴일과 요금 시행일은 달력에 올리고 확정·잠정을 구분한다. API 단가는 지표로 쌓는다. 도구별 변경은 엔티티 페이지에 쌓아 "Claude Code의 지난 석 달"을 만든다. 한 번 쓴 요약은 복제가 쉽지만, 몇 달 쌓인 도구별 기록과 판단은 복제가 느리다.

AI 다이제스트의 실패 원인도 형식을 정해 준다. 불만의 핵심은 AI라는 사실보다 내용이 없다는 점이다. HN 토론에서는 빠른 선별과 과장 뺀 제목을 좋아했고, 장황함과 상투적 도입부를 싫어했다([HN, 2023](https://news.ycombinator.com/item?id=37427127)). 제목을 되풀이하는 자동 요약 사례도 있다([ai-radar](https://github.com/HuggerHustle/ai-radar/issues/58)). 그래서 항목 틀은 "무엇이 바뀌었나, 누가 영향받나, 지금 할 일(없음 포함), 기존 대안, 기한"으로 고정한다. AINews가 10월 20일 호 제목을 "not much happened today"로 낸 것처럼([AINews](https://www.latent.space/s/ainews)), 건수를 채우지 않는 태도가 신뢰가 된다.

## 넷은 매일, 나머지는 주간으로 돌려야 2~4건이 유지된다

주기 기준은 "그 날짜를 놓치면 독자가 손해를 보는가"다. 시행일·마감일·종료일이 있는 것만 매일 싣고, 범주별 고정 칸은 두지 않는다. 종료·정책·라이선스 소식은 없는 날이 많기 때문이다. 아래 표의 순위는 수요, 차별성, 수집 난이도를 합친 추천이다.

| 10 | 채용·해고 | 월간 | [HN Who is hiring](https://hn.algolia.com/api/v1/search_by_date?tags=story,author_whoishiring&hitsPerPage=3) | 건수 추이 정도 |

코딩 도구는 릴리스 단위로 실으면 안 된다. Claude Code는 피드의 10개 항목이 모두 10월 20일 이후였고([실측](https://github.com/anthropics/claude-code/releases.atom)), Codex에는 알파가 섞여 온다([실측](https://github.com/openai/codex/releases.atom)). 실을 것은 기본 모델, 요금·사용량 구조, 자동 실행·권한 동작, 호환성 파괴, 새 작업 흐름이다.

보안은 심각도만으로 거르면 양을 줄이지 못한다. 10월 이후 npm critical만 56건이었고, critical이면서 주간 다운로드 100만 이상도 28건(패키지 중복 포함)으로 여전히 하루 약 1건이다([GHSA 실측](https://api.github.com/advisories?per_page=100&ecosystem=npm&severity=critical&published=%3E=2026-10-01)). 그래서 "기본 설정에서 도달 가능한 RCE·인증 우회·비밀 유출인가"는 AI가 판단해야 한다. 공급망 공격은 CVE보다 벤더 블로그가 빠르다. 조사일 Socket 최신 글은 Cursor 마켓플레이스의 악성 Claude Code 확장 제거였다([Socket](https://socket.dev/api/blog/feed.atom)). 악성코드 공지는 `type=malware`를 줘야 나오고([GitHub 문서](https://docs.github.com/en/rest/security-advisories/global-advisories)), EPSS는 신규 공지 대부분에 값이 없어 필터로 쓸 수 없다. 독자 행동 문구가 가치의 핵심이다. 영향 버전, 고친 버전, lockfile 확인, 토큰 회전 필요 여부를 적는다. 예컨대 Next.js는 10월 긴급 패치 뒤 11월 보안 릴리스를 예고했는데([Next.js 피드](https://nextjs.org/feed.xml)), 이것은 달력에 올릴 수 있는 사전 공지다.

플랫폼 변경은 원본을 그대로 쓸 수 없다. 10월에 Cloudflare 140건, Vercel 119건이 나왔고 AWS는 하루 약 8건이다([Cloudflare](https://developers.cloudflare.com/changelog/rss/index.xml), [Vercel](https://vercel.com/atom), [AWS](https://aws.amazon.com/about-aws/whats-new/recent/feed/)). 키워드만으로 Vercel 10월분은 "Deployment Storage billing begins for existing Pro teams" 등 4건으로 줄었다. 장애는 하루 뒤 브리핑이 이미 늦으므로 실시간 알림으로 쓰지 않는다. 대형 사건의 사후 분석이 나왔을 때만 교훈을 싣되, 상태 API에서 `postmortem_body`가 채워진 사건은 0건이었으니 공식 블로그 쪽을 봐야 한다([Vercel 상태](https://www.vercel-status.com/api/v2/incidents.json)).

의도적으로 빼는 것도 정해야 한다. MRR 순위, 매일의 벤치마크 변동, 신규 MCP 서버 목록, 구글 급상승어, 레포 점수 경쟁이다. 가짜 MRR 차트 생성기가 공개적으로 팔리고([Tom's Guide](https://www.tomsguide.com/ai/if-this-22-year-old-made-usd400-000-over-the-weekend-why-cant-i-inside-the-fake-ai-entrepreneur-boom)), TrustMRR 수치도 스스로 연결한 표본이며 MRR $5,000 초과로 보인 390건 중 37건은 만료됐거나 동기화가 끊겨 있었다([Tech Startups](https://techstartups.com/?p=138900)). 벤치마크는 추적 공급사 신규 모델이 코딩·종합 상위에 진입할 때만 싣는다. SaaS 가격 추적기 구독도 값이 낮다. 2분기에 146개 도구에서 실제 움직임은 6건뿐이었다([Q2 보고서](https://www.saaspricepulse.com/blog/state-of-saas-pricing-q2-2026)).

## 장벽은 비용이 아니라 약관이고 숫자 소스가 가장 안전하다

모든 공식 API의 한도는 하루 1회에 충분하고, 비용 벽은 X(포스트 읽기당 $0.005)와 Crunchbase뿐이다([X 가격](https://docs.x.com/x-api/getting-started/pricing), [Crunchbase API](https://data.crunchbase.com/docs/using-the-api)). "AI 요약 게시"를 명시적으로 금지한 약관은 찾지 못했고 대부분 학습 금지였다. 그러나 수집 주체가 Claude이므로 AI 입력을 거부하는 소스는 우회하지 않고 제외한다. 이 절은 법률 자문이 아니며 도구 요약을 거친 판단이므로, 구현 전에 핵심 조항 원문을 사람이 확인해야 한다.

계획 중인 두 소스는 먼저 손봐야 한다. GitHub AUP는 자동 추출을 스크래핑으로 정의하고, robots.txt는 `/trending`을 금지하지 않지만 크롤링은 문의하고 API를 쓰라고 안내한다([AUP](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies), [robots](https://github.com/robots.txt)). Trending 페이지 대신 검색 API나 [OSS Insight](https://ossinsight.io/docs/api/), [Hugging Face 트렌딩](https://huggingface.co/api/models?sort=trendingScore&limit=3)을 쓴다. OSS Insight는 베타이고 약관이 명시되지 않아 끊겨도 되게 둔다. Product Hunt는 소스별 끄기 스위치를 둔다. 광고 없는 무료 사이트가 "상업"이 아니라는 공식 확인은 없고, 후원 링크도 해석이 갈릴 수 있다. 광고를 켤 때 재검토할 곳은 Product Hunt, HN, dev.to다([YC 약관](https://www.ycombinator.com/legal/), [dev.to 약관](https://dev.to/terms)).

Reddit은 넣지 않는다. 여러 매체가 **RSS가 2026-11-13에 끝난다**고 전했고([TechRepublic](https://www.techrepublic.com/article/news-reddit-rss-public-api-shutdown/), [Decrypt](https://decrypt.co/379892/reddit-killing-rss-feeds-and-public-api-access-to-fight-ai-scrapers)), 공개 API도 2027년 3월 종료로 보도됐다([PPC Land](https://ppc.land/reddit-to-halt-public-data-api-access-in-march-2027-as-14-000-apps-register/)). 새 API 신청이 10월 31일에 닫혔다는 대목은 조사 메모 사이에 신뢰도 평가가 갈리고 Reddit 원문은 읽지 못했다. 어느 쪽이든 결론은 같다.

조사 메모가 엇갈린 지점이 둘 더 있다. 기술 메모는 Artificial Analysis를 무료 소스로 꼽았지만 약관 메모는 공개 게시를 피하라고 했다. 공개 사이트이므로 약관 쪽을 따른다. 같은 이유로 OpenRouter `/benchmarks`가 모아 주는 Artificial Analysis 점수를 그대로 재게시하는 것도 허가 전까지는 피하는 편이 안전하다. 이는 이번 조사의 추론이다. 또 기술 메모의 공식 문서·보안 소스 대부분은 접근만 실측했고 약관은 보지 않았다. 사실과 수치를 짧게 재서술하고 원문 링크를 다는 범위로 제한하고, 문장 재현은 하지 않는다.

## 수집기는 넷이면 되고 어제 사본이 핵심이다

새 크롤러는 거의 필요 없다. 기존 `feeds` 명령에 피드를 더하는 것으로 절반이 끝나고, JSON 읽기, 스냅샷 비교, 드문 HTML 추출을 추가하면 된다. 문서 사이트가 마크다운 원본을 내주는 경우가 많다. OpenAI 지원 종료 문서는 `### 2026-10-14: GPT-4 series model deprecations` 같은 날짜 머리글이라 파싱이 쉽다([OpenAI](https://developers.openai.com/api/docs/deprecations.md)). 다만 가격과 한도는 피드에 잘 나오지 않아, Anthropic의 2026년 7월 한도 상향은 X 계정으로 전해졌다는 제3자 보도가 있다([aicatchup](https://aicatchup.com/news/claude-platform-api-rate-limits-tier-simplification), 원문 미확인). 조용한 변경을 잡으려면 [OpenAI pricing](https://developers.openai.com/api/docs/pricing.md), [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing.md), [rate limits](https://platform.claude.com/docs/en/api/rate-limits.md), [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing.md.txt)을 매일 저장하고 숫자를 비교해야 한다. 재배치로 인한 거짓 경보를 줄이려면 본문 비교보다 숫자 추출 비교가 낫다. 페이지 변경과 실질 변경의 차이가 크다는 점은 1분기 271개 중 218개 페이지가 바뀌었다는 수치와 2분기 6건의 대비에서 드러난다([Q1](https://www.saaspricepulse.com/reports/saas-pricing-q1-2026), [Q2](https://www.saaspricepulse.com/blog/state-of-saas-pricing-q2-2026)). LiteLLM과 models.dev는 비공식이라 교차 확인에만 쓴다.

구현 순서는 세 묶음을 권한다. 첫째는 피드와 JSON만으로 되는 코딩 도구, 프레임워크, 보안이다. 둘째는 스냅샷이 필요한 모델 지원 종료·가격·한도로, 달력과 지표에 연결한다. 셋째는 주간 묶음과 추세다. 기술 메모는 보안을 첫 순서로 두고 수요 메모는 도구 변경을 첫 순서로 두는데, 첫 묶음에 함께 넣으면 충돌이 사라진다.

공통 처리도 세 가지가 필요하다. 같은 CVE·패키지·모델을 다시 싣지 않도록 기억하고, 필터 통과 이유를 항목에 남겨 AI 판단을 검증 가능하게 하고, 소스별 실패를 감지한다. 마지막이 중요한 이유는 피드 주소가 실제로 자주 바뀌기 때문이다. Windsurf 변경 기록은 docs.devin.ai로 옮겨 갔고 옛 피드는 2026-05-12에 멈춰 있다([실측](https://windsurf.com/feed.xml)). `cursor.com/rss.xml`처럼 200을 주지만 HTML인 함정도 있어, 형식 검사가 필요하다. 프로젝트는 폰 알림을 두지 않기로 했으므로 실패는 브리프 실행 결과에 드러나게 하면 된다. Copilot 변경 피드는 10건뿐이고 모두 10월 28일이어서 공지가 몰리면 하루 1회 수집으로도 놓칠 수 있다([실측](https://github.blog/changelog/label/copilot/feed/)). 이 소스는 항목 수 한도에 닿았는지 확인해야 한다.

## 증명되지 않은 가정이 네 가지 남아 있다

첫째, 수요 순위는 판단이다. 설문마다 표본과 질문이 다르고 비교할 수 없으며, 한국 웹 개발자가 판단형 항목을 원한다는 직접 자료는 없다. 일부 근거는 2023년 HN 토론이나 요약본에 기댄다. 둘째, 필터가 실제로 하루 2~4건을 만드는지는 측정하지 않았다. 이번 수치는 대부분 조사일 단면이고, GHSA high 표본은 100건에서 잘렸다. 2~4주치 과거 데이터로 재현해 본 뒤 임계값을 정해야 한다. 셋째, "한국어로 아무도 안 한다"는 부재 증거다. 검색 도구가 메일리 같은 곳의 작은 개인 뉴스레터를 잘 잡지 못한다. 넷째, 문서의 `.md` 제공은 OpenAI 외에 공식 약속인지 확인하지 못했고, Reddit, X, Stack Overflow, Indie Hackers의 약관 원문과 Hugging Face 트렌딩 API의 문서화 여부도 미확인이다. Vercel·Supabase 요금 페이지는 숫자 추출 가능성을 시험하지 않았으므로, 플랫폼 가격은 첫 단계에서 공식 변경 피드 키워드로만 잡는다.

## Conclusion

이번 조사로 질문이 바뀐다. "무엇을 더 모을까"가 아니라 "무엇을 대신 봐 주고 무엇을 안 봐도 된다고 말해 줄까"다. 독자에게 필요한 것이 소식이 아니라 변화의 영향이라면, 수집 범위를 넓히는 것보다 추적 대상을 좁게 정하는 일이 제품 결정이다. 시작 목록을 Claude Code, Codex, Cursor, Copilot, 주요 모델 공급사, Node, TypeScript, React, Next.js, Vite, Vercel, Supabase, Cloudflare로 제한하면 사용자 본인의 스택과 일치하고 품질을 직접 검증할 수 있다.

두 번째 함의는 시간이다. 지금 수집을 시작해야 할 이유는 기능보다 이력에 있다. 변경 기록은 공식 CHANGELOG로 어느 정도 되살릴 수 있지만, 가격·한도 스냅샷은 저장하지 않은 날을 되살릴 수 없다. 몇 달 뒤의 "지난 석 달" 화면은 이 기록 위에 선다. 따라서 화면을 설계하기 전에 스냅샷 저장부터 켜는 것이 비용 대비 가장 큰 선택이다.
