- 작성일: 2026-10-28
- 요약: DB에 쌓인 브리프와 이슈를 폰에서 보는 공개 정적 사이트로 만든다. `/brief` 끝에 사이트를 빌드해 Vercel(`tidwyn.vercel.app`)에 배포하고, 원본 저장소에 main과 백업 브랜치를 푸시한다. 원본 저장소는 머지 뒤 공개한다(P14).
- 종류: 변경 건 (1·1.5·2단계의 `/brief`, 백업, 저장소 운영을 바꾸고 사이트를 새로 더한다. 실제 데이터가 매일 쌓이고 있다)
- 단계: [`docs/plan.md`](../../plan.md)의 3단계(공개 사이트). 1, 1.5, 2단계를 참조한다.
- 이 문서는 기획과 요구사항만 담는다. 설계(스키마, 라이브러리, 폴더 구조)와 작업 계획은 구현하는 AI가 정한다.
- 공개 여부: 사이트는 배포하면 공개다. 원본 저장소는 구현 중에는 비공개로 push만 하고, 머지 뒤 공개한다(plan D2, P14). 배포 저장소는 두지 않는다(P1).

## 1. 목표

- **지금 상태:** `/brief`가 매일 브리프를 모아 DB에 저장하고, 뉴스를 이슈에 연결하고, 로컬 마크다운(`data/briefs/`, `data/issues/`)을 만들고, 로컬 `data` 브랜치에 백업한다. 원격 저장소는 없고, 폰에서는 볼 수 없다. 기존 클라우드 예약 브리프(매일 03:45 KST 푸시)가 병행 중이다(D10).
- **바꾸려는 이유:** 폰으로 어디서든 매일 브리프와 이슈 흐름을 본다. 사이트가 생기면 기존 예약 브리프를 끌 수 있다.
- **쓰는 사람:** 프로젝트 주인 한 사람. 사이트는 공개라 누구나 볼 수 있다.
- **충분한 수준:** 실제 DB의 복사본으로 빌드한 사이트가 `tidwyn.vercel.app`에 배포되어, 폰 폭(375px)에서 날짜별 브리프, 펼친 뉴스 카드, 이슈 페이지, 카테고리 필터, 검색이 동작한다. `/brief` 한 번 실행으로 저장부터 배포와 백업 push까지 이어진다. 원본 저장소(비공개)에 main과 백업 브랜치가 push되고 공개 전 점검을 통과해, 머지 뒤 바로 공개할 수 있다(P14). 사용자가 폰에서 확인한다(5장).

## 2. 확정된 결정과 제약

### 2.1 계획과 앞 단계에서 가져온 결정 (다시 묻지 않는다)

- plan D1~D14와 2.2 제약, 1단계 S1~S14, 1.5단계 R1~R7, 2단계 I1~I8을 따른다. 특히 다음이다.
  - **D1:** 수집부터 배포와 백업까지 `/brief` 한 번 실행으로 이어진다. 사이트는 로컬 DB에서 로컬로 빌드한다. 다시 돌려도 안전해야 한다.
  - **D2(P1로 바뀜):** 원본 저장소는 공개다. 비밀 값과 SQLite 파일은 커밋하지 않는다. 호스팅은 GitHub Pages 대신 Vercel이고 배포 저장소는 두지 않는다(P1).
  - **D3:** 사이트는 Vite + React SPA다. 화면 틀 하나에 데이터를 필요할 때 불러온다. 브리프 데이터는 월별 JSON이다. 검색은 인덱스를 잘게 나누는 도구(Pagefind)다. 뉴스마다 HTML을 만들지 않는다.
  - **D6:** 이미지는 원문 주소로만 연결하고 파일은 올리지 않는다. 사이트의 글은 이미 바꿔 쓴 브리프·이슈 글이다.
  - **D7:** 비용은 월 100달러 이내다. 이 단계는 무료 플랜만 쓴다(7장 사전 승인의 비용 0원).
  - **D8:** 디자인은 Kagi News를 참고하고 이 명세서의 확정 시안(P13)을 4~10단계가 따른다.
  - **D10:** 기존 예약 브리프는 사용자가 폰에서 확인한 뒤 끈다(P12).
  - **D12:** 백업 브랜치(`data`)는 원본 저장소에 push한다. main에 머지하지 않는다.
  - **D14:** 개발과 확인은 실제 DB의 복사본이나 테스트 DB로만 한다. 실제 `data/`에는 쓰지 않는다. 예외는 7장 사전 승인에 적은 `refs/heads/data` 이력 다시 쓰기(P2)뿐이다.
  - **S12:** 매일 실행은 main 체크아웃에서 변경이 없을 때만 한다. 구현 중에는 실제 `/brief`가 실행 조건에 걸려 멈춘다(6장 사용자에게 알릴 것).
  - **2단계:** 이슈 식별자는 정수이고 다시 쓰지 않는다. 흡수된 이슈는 남는 이슈를 가리키고, 되돌리면 다시 살아난다. 이전 전개와 전개 순서는 2단계 코드가 계산한다(사이트도 같은 코드를 쓴다, CLAUDE.md).
- **plan 3.4의 사실:** 출처 이미지 주소가 지금은 모두 비어 있다(P3로 푼다). 1·1.5·2단계의 "`dependencies`가 비어 있다"는 수집 스크립트의 관례다. 사이트 도구는 `devDependencies`에 둔다. `test/condition.test.ts`의 검사(`dependencies` 없음, `src/`의 import가 `node:`·상대 경로뿐)는 바꾸지 않는다. 그래서 사이트 코드는 `src/` 밖에 둔다.

## 3. 범위

### 넣는 것

- 사이트 데이터 만들기: DB에서 사이트용 JSON과 검색 색인을 만든다(4.1)
- 사이트 화면: 날짜별 브리프, 뉴스 카드, 이슈 목록과 이슈 페이지, 날짜 목록, 카테고리 필터, 검색, 없는 페이지, 사이트 소개(4.2, 4.3)
- 원문 이미지 주소 얻기와 지난 날짜 채우기(P3, 4.4)
- `/brief`에 빌드·배포·push 단계 넣기, 시험 모드(4.5)
- Vercel 배포와 배포 뒤 점검, 방문 통계(4.6)
- 커밋 이메일 바꾸기와 이력 다시 쓰기, 공개 전 점검, 원본 저장소 push(비공개)와 머지 뒤 공개 절차(4.7)
- README 두 언어, 라이선스, 운영 문서와 스킬 문서 갱신, plan 갱신(4.8)

### 넣지 않는 것

- 인물·용어·일정·지표 화면과 이슈 페이지의 지표 그래프: 4~6단계
- 추천 영상: 7~8단계
- 흐름 리포트: 10단계
- 데이터에 질문하기: 9단계
- 이슈를 손으로 고치는 기능, 이슈 나누기: 2단계 명세서 "넣지 않는 것"
- 기존 예약 브리프 끄기: 사용자가 폰에서 확인한 뒤 한다(P12, D10)
- 개인 도메인 연결, Vercel 유료 플랜: P1. 한도에 가까워지면 그때 정한다
- Vercel의 빌드 기능과 Git 연동(push하면 자동 배포): P1. 빌드는 로컬에서만 한다
- 이미 수집한 날짜의 뉴스 내용(제목, 요약, 분류, 출처 목록)을 다시 조사하는 것: 이미지 주소 채우기(P3)만 한다
- 사이트에서 로그인, 댓글, 알림 같은 사용자 기능: 혼자 읽는 공개 사이트다
- 다국어 사이트: 한국어만 쓴다

### 해당 없음

- 인증과 권한: 로그인이 없다. 누구나 모든 화면을 본다.
- 남용 방지와 입력 제한: 입력은 검색어뿐이고, 검색은 브라우저 안에서 정적 색인으로 한다. 서버가 없다.
- 개인정보 보관: 사이트는 개인정보를 모으지 않는다. 방문 통계(P10)는 쿠키 없이 익명 집계이고, 사이트 소개에 그렇게 적는다(4.3-4).
- 서버, DB 원격 접속, 예약 작업: 사용자가 `/brief`를 직접 실행한다(D1).

## 4. 요구사항

요구사항마다 확인 방법을 붙인다. "자동 테스트"는 `pnpm verify`에 들어가는 테스트다. 자동 테스트는 네트워크를 쓰지 않고, 실제 `data/`를 읽지 않는다. 예시 데이터(뉴스 제목, 이슈 이름)는 지어내서 만든다. "화면 확인"은 사이트를 로컬에서 띄워 Claude Code의 내장 브라우저로 폰 폭(375×812)에서 보고 스크린샷을 명세서 폴더의 `screenshots/`에 남기는 것이다. 화면의 동작 중 자동화할 수 있는 것은 자동 테스트로 둔다(도구는 AI 재량, 4.9-1).

**용어**

- **사이트 데이터:** 빌드할 때 DB에서 만드는, 사이트가 불러오는 JSON 파일들이다.
- **결과물:** 빌드가 만드는, Vercel에 올리는 폴더 전체다(HTML·JS·CSS·사이트 데이터·검색 색인·호스팅 설정 파일).
- **뉴스 키:** 2단계의 뉴스 키(`<섹션>-<순위>`, 짧은 소식은 `<섹션>-s<위치>`)다.
- **공개 전 점검:** 원본 저장소에 push하기 전과 공개하기 전에 돌리는 검사다(4.7-3).
- 데이터 폴더, 실제 DB, 실행 조건, 시험 모드, 실행 기록은 1단계 명세서 4장 용어와 같다.

### 4.1 사이트 데이터와 검색 색인

1. **사이트 데이터:** DB에 저장된 모든 날짜의 브리프와 모든 이슈를 사이트 데이터로 만든다. 브리프는 월별 파일로 나눈다(D3). 한 달을 목록용과 본문용처럼 여러 파일로 나누는 것은 된다(4.3-7). 이슈 목록과 이슈별 데이터의 파일 단위는 AI 재량이되, 4.1-3의 파일 수 한도를 지킨다. 뉴스마다 다음을 담는다: 섹션, 순위(짧은 소식은 위치), 뉴스 키, 제목(짧은 소식은 요약), 한 줄 요약, 왜 중요한가, 배경, 핵심, 비유, 전망, 확인 정도, 분류(새 소분류 표시 포함), 출처(매체명, 원문 주소, 발행 시각과 추정 표시, 대표 여부, 이미지 주소가 있으면 이미지 주소), 주 이슈와 추가 이슈, 그날 기준 이전 전개(P5, 최대 3건, 없으면 새 이슈), "어제에 이어" 표시(4.2-3). 브리프마다 헤드라인과 키워드를 담는다. 이슈마다 식별자, 이름, 별칭, 분류, 상태, 시작일·최근 업데이트일, 지금까지 요약, 전체 전개(날짜, 뉴스 키, 제목), 관련 이슈, 흡수된 이슈면 남는 이슈의 식별자를 담는다.
   - 이전 전개, 전개 순서, 흡수 이슈 따라가기는 2단계 코드를 공통으로 쓴다. 같은 계산을 사이트 쪽에 따로 만들지 않는다(CLAUDE.md).
   - 확인: 자동 테스트로 지어낸 DB(날짜 3개 이상, 이슈 여럿, 합쳐진 이슈 1개, 이미지 주소가 있는 출처 1개)에서 사이트 데이터를 만들면 위 항목이 모두 나오고, 같은 DB에서 2단계 브리프 마크다운이 보이는 이전 전개와 사이트 데이터의 이전 전개가 같다.
2. **같은 DB, 같은 결과:** 같은 DB로 두 번 만들면 사이트 데이터와 검색 색인의 내용이 같다(시각 같은 값이 섞이지 않는다). 만들 때마다 결과물 폴더를 비우고 다시 만든다.
   - 확인: 자동 테스트로 두 번 만들어 파일 목록과 내용이 같다.
3. **파일 수 한도:** 결과물 전체 파일 수는 5년치 데이터(하루 뉴스 40건, 이슈 1년 3,000개)에서도 10,000개 이하다. Vercel의 CLI 배포 파일 수 한도(15,000개, 2026-10-28 공식 문서)보다 넉넉히 작게 둔다. 검색 색인의 파일도 센다. 그래서 검색 레코드의 단위(뉴스 하나, 날짜 하나, 이슈 하나 등)는 이 한도 안에서 AI가 정한다. 단, 결과에서 뉴스를 누르면 그 뉴스 카드로 간다(4.3-3). Pagefind는 레코드마다 파일을 하나씩 만들므로 뉴스·이슈 하나 단위의 레코드는 이 한도를 넘는다(1년 뉴스 약 14,600건). 그래서 여러 뉴스·이슈를 한 레코드로 묶고, 걸린 레코드에서 개별 뉴스·이슈를 찾아내는 방법(레코드 안의 위치 정보, 브라우저에서 다시 거르기 등)은 AI 재량이다. 레코드는 `addCustomRecord`로 넣는다(P6).
   - 확인: 자동 테스트(또는 검증 명령)로 지어낸 5년치 데이터를 만들어 빌드하고 결과물 파일 수가 10,000개 이하다. 보고서에 그때의 결과물 크기와 파일 수, 지금 실제 데이터 복사본의 크기와 파일 수, 1년 뒤 예상 크기를 적는다.
4. **결과물에 들어가면 안 되는 것:** DB 파일, 실행 전 사본, 실행 기록, 작업 파일, 후보 목록, 백업 파일, 비밀 값, 홈 폴더 절대 경로(`$HOME`의 값), 개인 메일 주소(메일 주소 모양 중 4.7-3 허용 목록 밖의 것으로 찾는다). 결과물은 사이트 데이터와 화면 파일, 검색 색인, 호스팅 설정 파일뿐이다.
   - 글자 모양 검사(메일, 홈 경로, 토큰, 개인 키 머리)는 텍스트 파일(HTML·JS·CSS·JSON 등)에만 하고, 바이너리·압축 파일(Pagefind 색인 조각과 wasm, 글꼴, 이미지)은 건너뛴다(4.7-3과 같다. 같은 글이 사이트 데이터 JSON에 그대로 있다). DB 파일은 이름과 파일 머리로 찾는다.
   - 사이트 데이터 파일 이름은 백업 파일 이름(`YYYY-MM.json`, `issues.json`, `meta.json`)과 겹치지 않게 짓는다(검사가 둘을 구분할 수 있게).
   - 확인: 자동 테스트로 빌드한 결과물에 `.db` 파일, 백업 파일 이름, 위 문자열이 없다. 배포 명령이 올리기 전에 같은 검사를 하고, 걸리면 배포하지 않는다(일부러 걸리는 파일을 넣어 배포가 거부되는지 자동 테스트).

### 4.2 날짜별 브리프와 뉴스 카드

1. **첫 화면과 날짜 이동:** `/`는 가장 최근 날짜의 브리프를 보인다. 브리프 주소는 `/<YYYY-MM-DD>`다(P4). 브리프 위에 날짜와 이전·다음 날짜 이동이 있고, 날짜 목록 화면(`/dates`)으로 갈 수 있다. 날짜 목록은 저장된 모든 날짜를 최근 순으로 보인다(달별 묶음은 AI 재량). 저장되지 않은 날짜 주소는 없는 페이지(4.3-5)를 보인다.
   - 확인: 화면 확인으로 `/`, 날짜 주소, 이전·다음 이동, 날짜 목록이 시안 A대로 보인다. 자동 테스트로 라우팅이 없는 날짜를 없는 페이지로 보낸다.
2. **브리프 화면:** 헤드라인과 키워드, 카테고리 필터(대분류 칩, "전체" 기본), 섹션 탭(한국·세계·IT·AI, 아래)을 둔다. 고른 섹션의 주요 뉴스를 순위대로 보이고, 그 아래 짧은 소식을 보인다. 주요 뉴스 줄에는 카테고리(대분류·소분류, 대분류마다 정한 색), 제목, 이어지는 이야기 줄(주 이슈 이름, 또는 "새 이슈"), "어제에 이어" 표시가 나온다. 짧은 소식 줄에는 요약, 카테고리, 주 이슈 이름(링크)이 나온다. 카테고리 필터는 고른 섹션 안의 주요 뉴스와 짧은 소식을 함께 거른다. 거른 결과가 없으면 "이 분류의 뉴스가 없다"는 빈 상태를 보인다.
   - 확인: 화면 확인(필터 전·후, 빈 상태 포함). 자동 테스트로 필터와 섹션 전환의 결과 목록이 맞다.
3. **"어제에 이어" 표시(P11):** 뉴스의 주 이슈에 바로 앞 저장일(그 날짜보다 앞선 가장 늦은 저장일)의 뉴스가 있으면 표시한다. 앞 저장일이 하루 전이면 "어제에 이어", 그보다 앞이면 "<M월 D일>에 이어"로 쓴다. 이슈가 없는 뉴스나 첫 저장일의 뉴스에는 붙이지 않는다.
   - 확인: 자동 테스트로 앞 저장일이 하루 전인 경우, 이틀 이상 전인 경우, 앞 저장일에 그 이슈 뉴스가 없는 경우를 본다.
4. **펼친 뉴스 카드:** 주요 뉴스를 누르면 그 자리에서 펼쳐진다. 카드에는 시안 A의 순서대로 카테고리, 제목, 이미지(있을 때만, 4.4-3), 이어지는 이야기 상자(주 이슈 이름과 이슈 페이지 링크, 이전 전개 최대 3건의 날짜·제목과 그 날짜 브리프의 해당 뉴스 링크, 없으면 "새 이슈"), 한 줄 요약, 왜 중요한가, 배경, 핵심, 비유(있을 때만), 전망, 확인 정도, 함께 엮인 이슈(추가 이슈 링크), 출처(매체명, 원문 링크는 새 탭, 대표 출처를 앞에, 발행 시각이 추정이면 표시)가 나온다. 펼친 카드의 주소는 `/<날짜>#<뉴스 키>`이고, 이 주소로 들어오면 그 카드가 펼쳐진 채 그 위치로 간다.
   - 확인: 화면 확인(이미지 있는 카드와 없는 카드). 자동 테스트로 `#<뉴스 키>` 주소가 해당 카드를 펼친다.

### 4.3 이슈, 검색, 그 밖의 화면

1. **이슈 목록(`/issues`):** 모든 이슈(흡수된 이슈 제외)를 최근 업데이트일 순으로 보인다. 이슈마다 이름, 분류, 상태, 최근 업데이트일, 전개 수가 나온다. 대분류와 상태(진행 중·종료)로 거를 수 있다. 화면 아래 탭이나 머리 메뉴에서 갈 수 있다.
   - 확인: 화면 확인. 자동 테스트로 정렬과 거르기 결과가 맞다.
2. **이슈 페이지(`/issues/<식별자>`):** 시안 A대로 분류·상태, 이름, 별칭, 시작일·최근 업데이트일·전개 수, 지금까지 요약 상자, 타임라인(모든 전개를 최근 순, 날짜와 제목, 누르면 그 날짜 브리프의 해당 카드로), 관련 이슈 링크가 나온다. 흡수된 이슈의 주소로 들어오면 남는 이슈 페이지로 바꾸고 "이 이슈는 <날짜>에 <남는 이슈>에 합쳐졌다"를 한 줄 보인다. 없는 식별자는 없는 페이지를 보인다.
   - 확인: 화면 확인. 자동 테스트로 흡수된 이슈 주소가 남는 이슈로 가고, 합치기를 되돌린 DB로 다시 빌드하면 그 주소가 원래 이슈를 보인다.
3. **검색(`/search?q=<검색어>`, P6):** 머리의 검색 버튼으로 연다. 뉴스(제목, 한 줄 요약, 본문)와 이슈(이름, 별칭, 지금까지 요약)를 찾고, 결과를 "이슈"와 "뉴스"로 나눠 보인다. 뉴스 결과는 날짜·제목을 보이고 누르면 그 날짜 브리프의 해당 카드가 펼쳐진다. 이슈 결과는 이름·분류를 보이고 누르면 이슈 페이지로 간다. 결과가 없으면 빈 상태, 색인을 불러오는 동안 대기 표시를 보인다. 한국어 낱말로 찾아진다.
   - 확인: 자동 테스트로 지어낸 데이터의 검색 색인에서 뉴스 본문 낱말, 이슈 별칭으로 각각 찾아지고, 본문에 조사가 붙은 낱말(예: "반도체가")이 조사 없는 검색어("반도체")로 찾아진다. 화면 확인(결과, 빈 상태).
4. **사이트 소개와 바닥글:** 모든 화면 아래(또는 메뉴)에 사이트 소개로 가는 길이 있다. 사이트 소개에는 Tidwyn이 무엇인지(AI가 매일 모아 바꿔 쓴 뉴스 요약이라는 것, 틀릴 수 있다는 것), 원문 저작권은 각 매체에 있다는 것, 글의 저작권과 코드 라이선스(P9), 쿠키 없는 방문 통계를 모은다는 것(P10), 원본 저장소 링크를 적는다(저장소는 머지 뒤 공개되므로 그 전까지 링크가 열리지 않는 것은 괜찮다, P14).
   - 확인: 화면 확인.
5. **없는 페이지와 오류:** 없는 주소는 "없는 페이지"와 첫 화면 링크를 보인다. 사이트 데이터를 불러오지 못하면(네트워크 오류) 다시 시도 버튼이 있는 오류 상태를 보인다. 데이터를 불러오는 동안 대기 표시를 보인다.
   - 확인: 화면 확인(없는 페이지, 오류 상태는 데이터 요청을 막아서 본다).
6. **화면 공통:** 폰 폭(375px)을 먼저 맞추고, 넓은 화면에서는 가운데 정렬된 한 단(최대 폭은 AI 재량)으로 보인다. 다크 모드는 기기 설정을 따른다(P13). 키보드로 모든 링크와 버튼을 쓸 수 있고, 본문 글자 색 대비는 WCAG AA(4.5:1) 이상이다. 문서 언어는 한국어(`lang="ko"`)다. 날짜는 KST 대상일 그대로 쓴다. 페이지마다 제목(`<title>`)이 그 화면을 나타낸다.
   - 확인: 화면 확인(375px 라이트·다크, 넓은 화면 1장). 대비는 시안 색으로 계산해 보고서에 적는다.
7. **첫 화면 속도:** 가장 최근 날짜의 첫 화면(펼치지 않은 목록)을 보는 데 필요한 파일(HTML, JS, CSS, 사이트 데이터)의 전송 크기 합이 글꼴과 이미지를 빼고 gzip 기준 300KB 이하다. 한 달이 가득 찬 경우(하루 뉴스 40건 × 31일)에도 지킨다. 그래서 월별 사이트 데이터를 목록용과 펼친 카드 본문용처럼 여러 파일로 나눠도 된다. 나누는 방법은 AI 재량이되, 파일 단위는 달로 두고(D3) 파일 수는 4.1-3 한도 안에 둔다.
   - 확인: 지어낸 데이터(하루 40건 × 31일, 출처·이전 전개 포함)로 빌드한 뒤 크기를 재는 명령이나 테스트가 300KB 이하다. 보고서에 그 값과 실제 데이터 복사본의 값을 적는다.

### 4.4 원문 이미지 (P3)

1. **새 날짜:** 날짜마다 후보 목록을 만들 때(`feeds`) 공식 RSS(연합뉴스, BBC) 항목의 이미지 주소(미디어 태그)를 함께 읽어 둔다. 저장(`save`)할 때 출처의 원문 주소가 그 날짜 후보 목록의 공식 RSS 항목과 같으면 스크립트가 그 이미지 주소를 출처에 넣는다. Claude가 이미지 주소를 짐작해 쓰지 않는다. 브리프 작업 파일 형식은 바꾸지 않되(작업 파일에 `imageUrl`이 있어도 검사는 받아 준다), 저장할 때 작업 파일의 `imageUrl`은 쓰지 않고 스크립트가 찾은 값만 저장한다. 버리는 곳은 `save` 명령 단계이고, 검사(`validateBrief`)와 저장(`saveBrief`) 함수의 동작과 그것을 보는 기존 테스트는 바꾸지 않는다. 스킬 문서에서 Claude에게 `imageUrl`을 쓰라는 안내와 예시는 지운다(문서 속 예시를 보는 테스트도 맞춘다). 주소 비교 방법(정규화)은 AI 재량이고 1.5단계의 주소 규칙(구글 뉴스 중간 주소 금지 등)을 지킨다.
   - 확인: 자동 테스트로 지어낸 연합뉴스·BBC RSS(미디어 태그 있음)와 구글 뉴스 RSS(없음)에서 후보 목록을 만들고, 저장한 출처 중 공식 RSS와 주소가 같은 것만 이미지 주소가 들어간다.
2. **지난 날짜 채우기:** `/brief`가 실행마다 이미지 주소가 없는 저장된 출처를 공식 RSS를 다시 받아 채운다(아직 남아 있는 항목과 원문 주소가 같은 것만). 이미지 주소만 바꾸고 다른 값은 바꾸지 않는다. 받지 못한 피드는 실행 요약에 알리고 실행은 계속한다. 백업과 복원에 이미지 주소가 들어간다(지금 백업 형식에 있으면 그대로).
   - 확인: 자동 테스트로 이미지가 없는 출처가 있는 DB에 가짜 RSS로 채우기를 하면 맞는 출처만 이미지 주소가 생기고, 다시 해도 바뀌지 않으며, 백업·복원 뒤에도 남는다.
3. **화면:** 이미지가 있으면 펼친 카드에만 보인다(목록에는 보이지 않는다, P13). 외부 이미지는 지연 로딩하고 리퍼러를 보내지 않는다. 불러오지 못하면(깨진 주소, 외부 차단) 이미지 자리를 숨기고 깨진 이미지 아이콘을 보이지 않는다. 이미지가 하나도 없어도 빌드와 배포는 끝까지 된다.
   - 확인: 자동 테스트나 화면 확인으로 깨진 이미지 주소의 카드가 이미지 없이 보인다. 4.1-1의 테스트 DB 대부분이 이미지 없이 빌드된다.

### 4.5 `/brief` 흐름 (P7, P8)

1. **실행 순서:** 지금의 실행 순서(2단계 스킬 문서 15단계)에서 백업과 커밋 뒤, 대화창 출력 전에 다음을 넣는다: 사이트 빌드 → 배포와 배포 뒤 점검(4.6) → 원본 저장소에 `data` 브랜치 push. 지난 날짜 이미지 채우기(4.4-2)의 위치는 AI 재량이되 백업 전이다. 각 단계는 스크립트 명령이 하고, Claude가 직접 git·vercel 명령을 치지 않는다(1단계 스킬 규칙).
   - `data` push 전에는 push할 커밋에 공개 전 점검(4.7-3)을 돌린다. 걸리면 push하지 않고 요약에 걸린 내용(값은 가리고 파일·종류만)을 알린다. 실패 처리는 4.5-2와 같고, 다음 실행이 다시 점검하고 push한다. 걸린 내용을 고치는 일은 사용자가 한다(운영 문서에 적는다).
   - 확인: 스킬 문서(4.8-3)에 순서와 명령이 있다(읽어서 확인, 2단계처럼 문서 속 명령 이름이 실제 명령과 같은지 자동 테스트). 4.9-2 시험 실행(데이터 폴더 지정이라 배포·push가 없다)에서 이미지 채우기 → 빌드 → 요약 순서를 보고, 빌드 → 배포 → push 순서는 4.5-2의 자동 테스트(실제 실행으로 판정되는 임시 저장소, 가짜 배포 명령)로 본다.
2. **실패 처리:** 빌드, 배포, 배포 뒤 점검, push 중 하나가 실패해도 나머지 단계(가능한 것)와 요약은 계속한다. 빌드가 실패하면 배포하지 않는다. 실패는 실행 기록에 남기고 요약에 이유와 함께 보인다. 다음 실행은 이전 결과와 상관없이 사이트 전체를 다시 빌드·배포하고, 원격보다 앞선 `data` 브랜치 커밋을 모두 push한다. 배포할 바뀐 것이 없어도 배포 명령은 같은 결과를 다시 올려도 안전하다.
   - 확인: 자동 테스트로 빌드 실패, 배포 실패(가짜 배포 명령), push 실패(원격이 없는 저장소), push 전 점검 실패(허용 목록 밖 메일 주소가 든 백업 커밋)를 각각 만들면 요약에 실패가 나오고 종료 코드와 이후 단계가 위 규칙대로다. 원격보다 앞선 커밋 두 개가 다음 실행에서 함께 push된다(로컬 bare 저장소를 원격으로 둔 테스트).
3. **시험 모드:** 시험 모드와 데이터 폴더를 지정한 실행에서는 빌드만 하고 배포와 push를 하지 않는다. 결과물은 그 데이터 폴더 아래에 두고, 요약에 결과물 경로와 로컬에서 열어 보는 명령을 보인다. 실제 실행으로 판정되는 경우(1단계 S12)만 배포·push한다.
   - 확인: 자동 테스트로 시험 모드 실행에서 배포·push 명령이 불리지 않고 결과물이 시험 폴더에 생긴다.
4. **실행 요약:** 요약에 사이트 줄을 더한다: 빌드 결과(브리프 날짜 수, 이슈 수, 결과물 크기와 파일 수), 배포 결과(운영 주소, 배포 뒤 점검 결과) 또는 실패 이유, push 결과. 결과물 크기가 80MB를 넘거나 파일 수가 12,000개를 넘으면 Vercel 무료 한도(100MB, 15,000개)에 가깝다는 경고를 보인다. 지난 날짜 이미지 채우기 결과(채운 출처 수)도 한 줄 보인다.
   - 확인: 자동 테스트로 요약 출력에 위 줄이 나오고, 한도 경고가 문턱에서 나온다.
5. **의존성:** 사이트 도구는 `devDependencies`에 두고 버전을 고정한다(lockfile). `start`의 의존성 맞추기(`pnpm install --frozen-lockfile`)로 설치된다. 실행 조건 확인과 복원은 의존성 없이 돈다(1단계 테스트 그대로).
   - 확인: `test/condition.test.ts`가 바뀌지 않고 통과한다. `package.json`의 `dependencies`가 없다.

### 4.6 배포와 방문 통계 (P1, P10)

1. **배포:** 배포 명령은 결과물 폴더만 Vercel 프로젝트 `tidwyn`(계정 `mivomad33`, 6장)에 운영 배포한다. Vercel에서 빌드하지 않는다(정적 파일 그대로 올림). 저장소의 다른 파일(코드, 문서, 백업, DB)은 올리지 않는다. Vercel 인증은 사용자의 Vercel CLI 로그인을 쓰고, 토큰을 저장소나 결과물에 두지 않는다. 배포는 대화형 질문 없이 끝난다.
   - 연결 정보 폴더(`.vercel/`)와 실제 실행의 결과물 폴더는 git 무시 목록에 들어가게 둔다(데이터 폴더 아래에 두거나 `.gitignore`에 더한다). 다음 실제 실행이 실행 조건(S12)의 "추적되지 않은 파일"에 걸리지 않게 하기 위해서다.
   - 배포는 항상 Vercel 프로젝트 `tidwyn`을 명시해 겨냥한다(연결 정보를 결과물 폴더 밖에 두고 쓰거나 프로젝트 ID 환경 변수를 쓰는 등, 방법은 AI 재량). 결과물 폴더는 빌드마다 비우므로 그 안의 연결 정보에 기대지 않는다. 다른 Vercel 프로젝트를 만들지 않는다(예: `vercel deploy <결과물 폴더> --scope mivomad33 --project tidwyn --prod --yes`처럼 겨냥하고 `--create-if-missing`은 쓰지 않는다. CLI 65.5.0 도움말 기준).
   - Vercel 프로젝트에 Git 저장소를 연결하지 않는다(P1). `vercel link`나 배포가 Git 연결을 묻거나 시도하면 연결하지 않는 쪽을 고른다. 실수로 연결되면 끊는다(사전 승인). `vercel git disconnect`는 연결(link)된 폴더에서만 동작하므로, 저장소 밖 임시 폴더를 연결해 끊거나 같은 API를 쓴다(방법은 AI 재량).
   - 확인: 4.9-2에서 실제 배포 뒤 운영 주소의 결과물 밖 경로(`/package.json`, `/src/cli.ts`, `/data/tidwyn.db`, `/.git/HEAD`)가 404이거나 화면 틀(`index.html`)이고, 응답 본문이 저장소 파일 내용이 아니다(예: `"name": "tidwyn"`, `ref: refs/heads/`, SQLite 머리가 없음). `vercel deploy <결과물 폴더> --scope mivomad33 --project tidwyn --dry --json`이 보이는 올릴 파일 목록이 결과물 파일 목록과 같다. 결과물 맨 위에 `public/` 폴더를 두지 않는다(프로젝트 설정의 Output Directory가 "`public`이 있으면 그것"이라서). 프로젝트 정보(`vercel api /v9/projects/tidwyn --scope mivomad33` GET 응답 등. `project inspect`는 Git 연결을 보이지 않는다)에 Git 연결(`link`)이 없고, `vercel project ls`에 이번 작업으로 생긴 다른 프로젝트가 없다. Vercel CLI 설정 폴더(로그인 파일)는 읽지 않는다. 배포 뒤 `git status --porcelain`이 비어 있다. 자동 테스트로 배포 명령이 결과물 폴더 밖을 올리지 않게 만든 것(올릴 폴더 인자)을 본다(가짜 vercel 명령).
2. **주소 처리:** 모든 화면 주소(`/`, `/<날짜>`, `/dates`, `/issues`, `/issues/<식별자>`, `/search`)를 새로 고치거나 직접 열어도 화면이 나온다. 호스팅의 SPA 대체 경로 설정으로 하고(P4), 사이트 데이터·색인·화면 파일 주소는 대체 경로로 가지 않는다. 설정 파일 하나만 바꾸면 다른 정적 호스팅으로 옮길 수 있게 둔다.
   - 확인: 4.9-2에서 운영 주소의 각 화면 주소를 직접 요청해 200과 화면 틀이 오고, 없는 데이터 파일 주소는 404다.
3. **배포 뒤 점검:** 배포가 끝나면 운영 주소에서 첫 화면과 가장 최근 날짜의 사이트 데이터를 받아, 그 날짜가 DB의 가장 최근 저장일과 같은지 본다. 다르거나 받지 못하면 점검 실패로 기록한다. 자동으로 이전 배포로 되돌리지 않는다(다음 실행이 다시 배포한다). 되돌리는 방법은 운영 문서에 적는다(4.8-4).
   - 확인: 자동 테스트로 가짜 응답(맞음, 날짜 다름, 받지 못함)에서 점검 결과가 맞다. 4.9-2에서 실제 점검이 통과한다.
4. **방문 통계:** Vercel Web Analytics 스크립트를 화면 틀에 넣어 화면 이동마다 페이지 보기를 남긴다(SPA 경로 바뀜 포함). 사용자 정의 이벤트, 쿠키, 다른 분석 도구는 넣지 않는다. 주소의 검색어(`q`)는 통계로 보내지 않는다. 시험 모드의 로컬 결과물에서는 통계를 보내지 않는다. 통계를 켤지는 빌드 모드가 아니라 실행 중의 접속 주소로 정한다(운영 주소 `tidwyn.vercel.app`일 때만 켠다). 그래서 4.9-2처럼 시험 흐름으로 만든 결과물을 운영에 올려도 통계가 나간다.
   - 공식 문서의 plain React용 "route support 없음"은 동적 경로 묶기(`/issues/[id]`)가 없다는 뜻이다. 화면 이동마다 페이지 보기가 남는 것은 지켜야 한다.
   - 확인: 4.9-2 뒤 운영 사이트를 브라우저로 열어 통계 요청(`/<고유 경로>/view` 같은 요청)이 나가고, 앱 안 링크로 다른 화면에 가면 두 번째 요청이 나가는지 네트워크 기록으로 본다. 시험 모드로 빌드한 결과물을 로컬에서 열면 통계 요청이 없다. 검색 화면에서 보낸 요청에 검색어가 없다. 대시보드에 숫자가 보이는 것은 사용자가 확인한다(5장).

### 4.7 이메일, 공개 전 점검, 원본 저장소 공개 (P2, D2, D12)

1. **커밋 이메일:** 이 저장소의 로컬 git 설정(`user.email`)을 GitHub noreply 주소(6장)로 바꾼다. 이름은 그대로 둔다. 앞으로의 커밋(작업 브랜치, `/brief`의 백업 커밋)은 이 주소를 쓴다.
   - 확인: 이 저장소에서 `git config user.email`과 `git var GIT_COMMITTER_IDENT`가 noreply 주소다. 바꾼 뒤 작업 브랜치에 만든 커밋의 작성자·커미터 이메일(`%ae %ce`)이 noreply 주소다. (시험 모드는 커밋하지 않고, 데이터 폴더 지정 실행의 테스트 저장소는 이 저장소의 설정을 쓰지 않으므로 그것으로 확인하지 않는다.)
2. **이력 다시 쓰기:** main과 `refs/heads/data`의 모든 커밋의 작성자·커미터 이메일을 noreply 주소로 바꾼다. 내용(트리)과 날짜, 메시지, 이름은 바꾸지 않는다. 다시 쓰기 전에 모든 브랜치를 담은 git 번들을 저장소 밖의 사라지지 않는 곳(저장소와 같은 상위 폴더의 `../tidwyn-history-backup-<날짜>.bundle`)에 남긴다. 작업 브랜치도 같은 다시 쓰기에 넣는다(rebase만으로는 작성자 이메일이 남는다). 번들 검증 뒤 다시 쓰기 도구가 남긴 백업 참조(`refs/original/*` 등)는 지운다. 다른 로컬 브랜치와 태그가 있으면 그것도 같은 방식으로 바꾸고 보고서에 적는다.
   - 확인: 다시 쓴 뒤 `git log --all --format='%ae %ce'`에 noreply 주소만 나온다. 다시 쓰기 전과 뒤의 커밋을 차례로 맞대어 트리 해시, 작성 날짜, 메시지가 모두 같다(명령 결과를 보고서에 적는다). 번들에서 원래 브랜치를 꺼낼 수 있다(`git bundle verify`).
3. **공개 전 점검:** 원본 저장소에 push할 모든 커밋(main과 `data`의 이력 전체)과 지금 파일을 검사하는 명령을 둔다. 다음 중 하나라도 있으면 실패한다.
   - noreply 주소가 아닌 작성자·커미터 이메일
   - 실행하는 사람의 홈 폴더 절대 경로(`$HOME`의 값). 이 명세서들처럼 경로 모양을 설명하는 글(예: `/Users/...`)은 실제 경로가 아니므로 걸리지 않게 실제 값으로 찾는다
   - 비밀 값 모양(GitHub·Vercel 토큰 접두사, 개인 키 머리, `.env` 파일), SQLite 파일, 실행 전 사본
   - 메일 주소 모양의 글 중 허용 목록에 없는 것. 허용 목록은 이 저장소의 GitHub noreply 주소, 커밋 메시지의 `Co-Authored-By`에 쓰는 `noreply@anthropic.com`, `example.com`·`example.org` 같은 예시용 주소다
   - "지금 파일"은 git이 추적하는 파일(작업 트리와 index)이다. git이 무시하는 파일(`data/`, `.test-data/`, `node_modules/` 등)은 push 대상이 아니라 검사하지 않는다. 그 밖에 검사에서 빼는 경로는 없다(테스트 폴더 포함). 글자 모양 검사(메일, 홈 경로, 토큰, 개인 키 머리)는 바이너리 파일(스크린샷 PNG 등)을 건너뛴다(`git grep -I`처럼). SQLite 파일과 실행 전 사본은 이름과 파일 머리로 찾는다. 테스트에 쓰는 걸리는 값(허용 목록 밖 메일, 토큰 접두사, 개인 키 머리)은 소스에 그대로 적지 않고 실행할 때 조립한다. 문서·진행 기록·보고서에는 홈 폴더 절대 경로 대신 저장소 기준 상대 경로(번들은 `../tidwyn-history-backup-<날짜>.bundle`)를 쓴다.
   - 확인: 자동 테스트로 위 경우를 하나씩 넣은 임시 저장소에서 점검이 실패하고, 깨끗한 임시 저장소에서는 통과한다. 실제 저장소에서 push 전(4.7-4)과 구현 끝(보고서 작성 직전)에 돌린 결과를 보고서에 적는다. 머지 직전 점검은 4.7-5가 맡는다.
4. **push (비공개, P14):** 공개 전 점검을 통과한 뒤 다시 쓴 main을 먼저, 그다음 `data`를 비공개 원본 저장소(`mivomad33/tidwyn`)에 push한다(처음 push한 브랜치가 GitHub 기본 브랜치가 되므로 main이 기본 브랜치가 되게 한다). `gh repo edit`로 저장소 설명, 홈페이지 주소(`https://tidwyn.vercel.app`), 주제(topics)를 넣는다. 저장소는 공개로 바꾸지 않는다(4.7-5에서 머지한 세션이 한다). 작업 브랜치는 push하지 않는다. 그 뒤 `/brief`의 매일 `data` push는 이 비공개 저장소로 간다.
   - 확인: `gh repo view mivomad33/tidwyn --json visibility,defaultBranchRef,description,homepageUrl`이 비공개, 기본 브랜치 main, 설명·홈페이지 주소가 들어 있음을 보인다. `git ls-remote origin`의 main·`data`가 로컬과 같다.
5. **머지 뒤 main push와 공개:** 이 단계의 작업 브랜치를 사용자 승인 뒤 main에 squash merge하면, 머지한 세션이 공개 전 점검을 다시 돌리고 main을 push한다. 3단계 머지 때만 그다음 저장소를 공개로 바꾸고(`gh repo edit --visibility public --accept-visibility-change-consequences`), 공개 주소가 로그인 없이 열리는지(`curl`로 200) 본다. 점검이 실패하면 push와 공개를 하지 않고 사용자에게 알린다. 공개로 바꾼 뒤에는 main과 `data`를 강제 push하지 않는다. 이 절차를 운영 문서와 CLAUDE.md의 작업 규칙에 적고(앞으로의 단계도 머지 뒤 점검하고 main을 push한다), 보고서의 머지 승인 항목에 "머지를 승인하면 원본 저장소가 공개된다"를 적는다.
   - 확인: 운영 문서와 CLAUDE.md에 머지 뒤 점검, push, (3단계만) 공개 전환이 적혀 있고, 보고서의 머지 승인 항목에 공개 안내가 있다(읽어서 확인). 실제 머지·push·공개는 사용자 승인 뒤의 일이라 이 구현의 확인 범위가 아니다.

### 4.9 기존 기능 유지와 시험 실행

1. **기존 테스트와 검증:** 1·1.5·2단계 테스트가 통과한다. 기존 테스트에서 허용하는 변경은 2단계 명세서 4.8-1과 같다(버전 숫자에 묶인 줄, 새 테스트와 import). 사이트 테스트(화면 동작 포함)는 `pnpm verify`에 들어가고 네트워크 없이 돈다. 브라우저를 쓰는 테스트를 둘지와 도구는 AI 재량이되, 넣는다면 `pnpm verify`에서 돌고 브라우저 내려받기가 첫 설치 뒤에는 필요 없게 한다.
   - 확인: `pnpm verify` 통과. `git diff main -- test/`에서 기존 줄의 변경이 허용 범위뿐이다.
2. **시험 실행:** 실제 `data/tidwyn.db`를 읽기만 해서 `.test-data/` 아래 새 폴더에 복사하고, 그 복사본으로 다음을 한다. 실제 `data/`와 실제 DB에는 쓰지 않는다.
   - 데이터 폴더 지정(`TIDWYN_DATA_DIR`=복사 폴더) `/brief` 흐름으로 지난 날짜 이미지 채우기와 빌드까지 돌려 요약을 확인한다. 시험 모드는 늘 새 빈 폴더를 만들어 복사본을 쓰지 않으므로 쓰지 않는다. 새 날짜 수집, 소급 연결, 합치기는 건너뛰어도 되고 요약에 미처리로 나와도 된다(하고 싶으면 1·2단계 흐름대로 해도 된다).
   - 그 결과물(복사본의 데이터)을 운영으로 배포하고(사전 승인), 배포 뒤 점검과 4.6-2·4.6-4의 확인을 한다. 배포는 4.5의 배포 명령으로 하되, 시험 모드가 배포를 막으므로 배포 명령을 직접 부르는 방법(운영 문서에 적는 수동 배포)으로 한다.
   - 운영 주소를 폰 폭으로 열어 4.2·4.3의 화면 확인 스크린샷을 남긴다.

### 사전 승인

묻지 않고 해도 되는 것:

- 비용 0원. 무료 플랜 안에서만 쓴다.
- `devDependencies` 설치와 lockfile 갱신(npm 레지스트리 공개 패키지). 브라우저 테스트 도구를 넣는다면 그 브라우저 내려받기.
- Vercel 프로젝트 `tidwyn`에 운영 배포(횟수 제한 없음, 하루 100번 한도 안). 4.9-2의 실제 데이터 복사본 결과물 배포 포함. 운영 배포를 이전 배포로 되돌리기. 실수로 생긴 Vercel Git 연결 끊기(`vercel git disconnect`).
- 이 저장소의 로컬 git 설정 바꾸기(`user.email`, `origin` 등록).
- 4.7-2의 main·`refs/heads/data`(와 다른 로컬 브랜치·태그) 이력 다시 쓰기. 반드시 번들을 먼저 남긴다.
- `mivomad33/tidwyn`에 main과 `data` push. 공개로 바꾸기 전에는 강제 push도 된다.
- 공개 전 점검을 통과한 뒤 `mivomad33/tidwyn`에 `gh repo edit`로 설명·홈페이지 주소·주제(topics)를 넣기. 공개 전환은 구현이 하지 않는다(4.7-5, P14).
- `.test-data/` 아래 시험 폴더 만들기와 정리(AI가 만든 것만).

### 멈추고 물을 것

- 비용이 드는 것(유료 플랜, 유료 기능, 도메인).
- 공개 전 점검이 이메일 말고 다른 것(비밀 값, 홈 경로, 공개하면 안 될 글)을 찾아, 이력에서 내용을 지우거나 고쳐야 할 때. 그 부분만 보류하고 공개하지 않는다.
- 저장소를 공개로 바꾼 뒤 main이나 `data`를 강제 push해야 할 때.
- 이력 다시 쓰기 결과가 4.7-2의 비교를 통과하지 못할 때(번들로 되돌리고 보류).
