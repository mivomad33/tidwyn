## 작업 계획

1. 사이트 데이터 형식(`src/siteTypes.ts`)을 먼저 정한다(백엔드와 화면이 함께 쓰는 약속).
2. 병렬: (가) 사이트 데이터 만들기·이미지(`src/`) / (나) 사이트 화면과 빌드 스크립트(`site/`, 격리 작업 공간).
3. (다) `/brief` 연결: 빌드·결과물 검사·배포·배포 뒤 점검·공개 전 점검·push 명령, 요약, 스킬 문서.
4. 커밋 이메일 바꾸기 → 시험 실행(복사본 빌드, 운영 배포, 스크린샷).
5. 이력 다시 쓰기(번들) → 공개 전 점검 → 비공개 push, `gh repo edit`.
6. 문서(README 두 언어, LICENSE, 운영 문서, CLAUDE.md) → 마지막 검증 → 보고서.

## 재량 결정

- 사이트 데이터는 결과물의 `site-data/`에 둔다: `dates.json`, 달마다 `list-YYYY-MM.json`(목록)과 `detail-YYYY-MM.json`(펼친 카드), `issue-list.json`, 이슈 상세는 식별자 100개씩 `issue-<n>.json`. 첫 화면 크기(4.3-7)와 파일 수(4.1-3)를 함께 지키기 위해서다.
- 사이트 코드는 `site/`(src 밖, condition 테스트 때문), DB에서 사이트 데이터를 만드는 코드는 `src/`(node:sqlite와 2단계 계산 코드를 그대로 쓰기 위해서).

- "어제에 이어"는 바로 앞 저장일에 주 이슈가 같은(합친 이슈는 남는 이슈로 따라가서) 뉴스가 있을 때만 붙인다. 추가 이슈 연결은 보지 않는다(주 이슈가 "이어지는 이야기"의 기준이라서).
- 검색 레코드는 날짜 하나(뉴스)와 이슈 100개 묶음 하나(이슈) 단위로 묶고, 화면이 그날·그 묶음 데이터를 불러 낱개 결과를 다시 거른다(4.1-3).
- 작업 파일의 `imageUrl`은 검사를 통과한 뒤 `save`에서 버린다(검사 결과가 validate와 save에서 같게).
- 원문 주소 비교: http/https, `www.`/`m.`, 끝 `/`, `#`, 추적 질의 값을 무시하고 `bbc.co.uk`=`bbc.com`. 구글 뉴스 주소는 비교하지 않는다.
- 공개 전 점검·결과물 검사의 토큰은 접두사 뒤에 충분히 긴 영숫자가 붙을 때만 잡는다(검사 코드·문서 자신이 걸리지 않게). Vercel 접두사는 공식 변경 기록(2026-02-09) 기준 `vcp_ vci_ vca_ vcr_ vck_`.
- 메일 모양 검사에서 끝이 파일 확장자인 글(`logo@2x.png` 등)은 메일로 보지 않는다(화면 파일의 가짜 걸림 방지).
- 한도 경고 문턱은 10진 80,000,000바이트·12,000개를 넘을 때. 로컬 보기 명령은 `pnpm site:preview <결과물>`(Vercel과 같은 주소 규칙의 `site/dev/serve.ts`. 처음엔 `vite preview`였으나 없는 데이터 파일도 화면 틀을 줘서 바꿨다).
- 스킬 실행 순서: 13 합치기 → 14 `images` → 15 `backup` → 16 `site` → 17 `deploy` → 18 `push` → 19 `summary`.
