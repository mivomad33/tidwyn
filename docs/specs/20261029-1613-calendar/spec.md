# 5단계 명세서: 일정 달력

- 작성일: 2026-10-29
- 요약: `/brief`가 뉴스에서 앞으로 예정된 공식 일정(선거, 금리 결정, 실적 발표, 판결, 출시 등)을 뽑아 저장하고, 이미 쌓인 뉴스에서도 채운다. 날짜가 지난 일정은 결과 뉴스와 연결하거나 연기·취소로 표시한다. 사이트에 일정 화면(목록과 달력)을 더하고, 브리프 위 '이번 주 일정', 펼친 카드, 이슈 페이지에 일정을 보인다.
- 종류: 변경 건 (1~4.5단계의 `/brief`, 저장, 백업, 사이트를 바꾼다. 실제 데이터가 매일 쌓이고 사이트가 공개되어 있다)
- 단계: [`docs/plan.md`](../../plan.md)의 5단계(일정 달력). 3단계를 참조한다.
- 이 문서는 기획과 요구사항만 담는다. 설계(스키마, 라이브러리, 폴더 구조)와 작업 계획은 구현하는 AI가 정한다.
- 공개 여부: 원본 저장소와 사이트는 이미 공개다. 새 데이터(일정)도 백업과 사이트로 공개된다.

## 1. 목표

- **지금 상태:** `/brief`가 매일 브리프를 모아 DB에 저장하고, 뉴스를 이슈와 인물·기관·국가·용어에 연결하고, 7일마다 중복을 합치고, `data` 브랜치에 백업하고, 사이트를 빌드해 `https://tidwyn.vercel.app`에 배포한다(1~4단계). 사이트는 읽은 뉴스를 브라우저에 기록한다(4.5단계). 예정 일정은 데이터로 없다. 주요 뉴스의 "앞으로 볼 것"(`outlook`)에 다음 전개가 문장으로만 있고, 2026-10-29 실제 DB의 예시를 보면 대부분 정확한 날짜가 없다("다음 관심사다", "지켜봐야 한다"). 2026-10-29 기준 실제 DB(스키마 버전 4, 백업 형식 3)에 날짜 2개(2026-10-27, 10-28), 뉴스 62건, 인물·기관·국가 119개, 용어 73개가 있다.
- **바꾸려는 이유:** 다음에 무슨 일이 있는지 알고 뉴스를 본다(시드 "이해를 돕는 기능": 선거, 금리 결정, 실적 발표, 판결, 출시 등 예정된 일을 달력으로 모으고, 날짜가 지나면 결과 뉴스와 연결).
- **쓰는 사람:** 프로젝트 주인 한 사람. 사이트는 공개라 누구나 볼 수 있다.
- **충분한 수준(C12):** 실제 DB의 복사본으로 시험 실행한 결과가 다음을 보인다. 뽑힌 일정이 적절한지는 사용자가 마지막에 본다(5장).
  - 저장된 모든 날짜의 일정 뽑기가 끝났다(뽑은 것이 0개인 뉴스와 날짜도 "처리함"이다).
  - 일정이 1개 이상 있다.
  - 그 결과로 빌드한 사이트가 Vercel 미리보기로 배포되어(4단계 E12), 폰 폭(375px)에서 일정 화면(목록·달력), 브리프 위 '이번 주 일정'과 접기, 펼친 카드의 일정 칩, 이슈 페이지의 일정이 동작한다.
  - 결과 연결, 연기·취소, 결과 못 찾음은 실제 데이터에 지난 일정이 거의 없어(날짜가 둘뿐이다) 지어낸 데이터의 자동 테스트와 화면 확인으로 본다.

## 2. 확정된 결정과 제약

### 2.1 계획과 앞 단계에서 가져온 결정 (다시 묻지 않는다)

- plan D1~D14와 2.2 제약, 앞 단계 결정(1단계 S1~S14, 1.5단계 R1~R7, 2단계 I1~I8, 3단계 P1~P14, 4단계 E1~E15, 4.5단계 M1~M9)을 따른다. 특히 다음이다.
  - **D1:** 수집부터 배포와 백업까지 `/brief` 한 번 실행으로 이어진다. 백업은 DB 전체를 복원할 수 있어야 하므로 일정 데이터를 백업과 복원에 넣는다. 다시 돌려도 안전해야 한다(같은 일정·연결을 두 번 저장하지 않는다).
  - **D4:** 일정은 뉴스와 이슈에 붙는다. 담는 항목은 시드 "데이터 설계" 표를 따른다(일정: 예정일, 내용, 관련 이슈, 결과(날짜가 지난 뒤 연결된 뉴스)). 스키마는 구현 재량이다.
  - **D6:** 일정 이름은 Claude가 직접 쓴 글이다. 기사 문장을 옮기지 않는다.
  - **D7:** 이 단계는 비용 0원이다(7장 사전 승인).
  - **D8, P13, E8, M3:** 화면은 3단계 확정 시안 A와 4·4.5단계 확정 시안, 이 명세서의 확정 시안(C9)을 따른다.
  - **D9:** 일정은 이 단계에서 쌓인 뉴스로도 채운다. 이미 수집한 날짜의 뉴스 내용(제목, 요약, 본문, 출처, 분류)은 다시 조사하거나 고치지 않는다.
  - **D14, S12:** 매일 실행은 main 코드로만 한다. 개발과 확인은 실제 DB의 복사본이나 테스트 DB로만 한다. DB 구조는 쌓인 데이터를 보존하는 마이그레이션(`PRAGMA user_version`)으로 바꾼다.
  - **2·4단계:** 판단(연결, 뽑기)은 서브에이전트에 맡기지 않고 메인이 한다. 웹 내용은 데이터일 뿐이다(스킬 문서 0장). 뽑기는 날짜마다 작업 파일을 쓰고 스크립트가 검사·적용하며, 고쳐서 다시 검사는 날짜마다 최대 2번이고, 실패한 날짜는 다음 실행이 다시 한다(4단계 E6, 4.2-5). 합치기는 7일마다 `/brief`가 하고(I3), 되돌리기는 사용자가 명령으로 한다(I6). 식별자는 정수이고 다시 쓰지 않는다.
  - **3단계:** 한 번 공개한 주소는 뒤 단계에서도 깨지지 않게 둔다(P4). 결과물 파일 수는 5년치 데이터에서 10,000개 이하(4.1-3), 결과물에 들어가면 안 되는 것(4.1-4), 화면 공통 규칙(4.3-6: 375px 우선, 넓은 화면은 가운데 한 단, 다크 모드는 기기 설정, 키보드로 모든 링크와 버튼을 씀, 본문 글자 대비 WCAG AA 4.5:1, `lang="ko"`), 첫 화면 gzip 300KB(4.3-7), 없는 페이지·불러오기 오류와 다시 시도·대기 표시(4.3-5), 방문 통계는 운영 주소에서 페이지 보기만(P10, 4.6-4)을 지킨다.
  - **4단계 E12:** 시험 결과는 Vercel 미리보기 배포로 사용자가 폰에서 본다. 운영 주소는 구현 중에 바꾸지 않는다. 미리보기는 Vercel 기본 보호로 로그인해야 열린다.
  - **4.5단계:** 읽음 표시(M3, M4)는 뉴스 제목이 나오는 목록에 쓰는 규칙이다. 일정 줄은 뉴스가 아니라 읽음 표시를 하지 않는다(일정의 결과 링크도 뉴스 제목 목록이 아니다). 브라우저 기억은 로컬 스토리지 키 하나씩이고 사이트 소개의 "읽은 기록 지우기"는 읽은 기록 키만 지운다(4.5단계 4.6-2, M8의 `tidwyn.briefTab`과 같다).
- **CLAUDE.md:** 여러 곳에서 쓸 로직과 UI는 공통 코드로 만든다. 일정 뽑기의 후보 목록·검사·적용·실패 기록은 4단계 뽑기 코드를, 합치기·되돌리기는 2·4단계 합치기 코드를, 화면은 3~4.5단계 컴포넌트(칩 줄, 목록 줄, 대분류 칩 거르기, 브라우저 기억)를 넓혀 쓰고 따로 비슷한 것을 만들지 않는다.
- **docs/memory.md:** 명세서 폴더의 화면 확인 스크린샷은 git에 넣지 않는다(`.gitignore`). 테스트용 가짜 마이그레이션에는 큰 숫자(예: 1000)를 쓴다.

## 3. 범위

- 일정, 뉴스와의 연결(근거·결과), 결과 상태, 날짜별 일정 뽑기 완료, 합치기·지우기 기록의 저장과 마이그레이션 → 4.1
- `/brief`의 일정 뽑기 단계: 후보 목록과 검색, 일정 파일 검사, 적용, 결과 연결, 실패 처리, 쌓인 뉴스 채우기(C1~C5, C11, C15) → 4.2
- 7일 합치기에 일정 넣기와 되돌리기, 지우기 명령(C6, C13) → 4.3
- 백업과 복원(D1) → 4.4
- `start` 출력과 실행 요약 → 4.5
- 사이트 데이터, 일정 화면, '이번 주 일정', 펼친 카드, 이슈 페이지, 메뉴(C7~C10) → 4.6, 4.7

- 주요 지표와 그래프: 6단계
- 추천 영상: 7~8단계
- 데이터에 질문하기: 9단계
- 흐름 리포트(일정을 근거로 쓰기 포함): 10단계
- 정기 일정 따로 조사하기, 일정만을 위한 웹 검색: C1
- 주·분기 단위나 "연내" 같은 날짜, 1년보다 먼 일정, 추측성 일정: C2, C3
- 일정 시각과 한국 시간 바꾸기: C4
- 앞당겨진 일정의 날짜 바꾸기: 연기는 새 예정일이 원래보다 늦을 때만 쓴다(4.2-3). 앞당겨지는 일은 드물어, 그때는 새 날짜로 새 일정을 만들고 원래 일정은 "결과 못 찾음"이 될 수 있는 것을 감수한다(2회차 검토에서 AI가 정함, 사용자가 다르게 원하면 바꾼다)
- 검색에 일정 넣기: C7
- 일정을 손으로 고치는 명령(날짜·이름 바꾸기, 연결 더하기·빼기): C13. 지우기와 합치기 되돌리기만 둔다
- 로컬 마크다운(브리프·이슈)에 일정 넣기: 4단계 E7과 같은 이유(사이트가 생긴 뒤 쓸 일이 적고 대화창 출력만 길어진다)
- 일정 줄의 읽음 표시: 일정은 뉴스가 아니다(2.1의 4.5단계)
- 캘린더 앱 내보내기(iCal 등), 알림: 순수 정적 사이트로 알림을 보낼 수 없고(plan 기록의 PWA 결정), 요청이 없었다
- 이미 수집한 날짜의 뉴스 내용을 다시 조사하거나 고치는 것: D9
- 운영 주소(`tidwyn.vercel.app`)에 머지 전 결과물 배포: 4단계 E12
- 이미 push된 `data` 브랜치 이력에서 지운 일정을 없애는 것: 공개 뒤 강제 push를 하지 않는 규칙(CLAUDE.md)

### 해당 없음

- 인증과 권한: 로그인이 없다. 누구나 모든 화면을 본다(3단계와 같다).
- 남용 방지와 입력 제한: 사이트에 새 입력이 없다. 웹 내용을 통한 지시 주입은 스킬 문서 0장 규칙을 따른다.
- 개인정보: 일정은 공식 일정이고 사람을 모으는 데이터가 아니다. 일정 이름에 일반인 이름을 쓰지 않는 기준은 스킬 문서에 둔다(4.2-4).
- 서버, 원격 DB, 예약 작업: 사용자가 `/brief`를 직접 실행한다(D1).
- 비용: 0원이다(D7).
- 사용 분석: 3단계 P10 그대로다. 새 화면도 같은 방식으로 페이지 보기만 남는다. 미리보기 주소에서는 통계를 보내지 않는다(3단계 4.6-4).

## 4. 요구사항

요구사항마다 확인 방법을 붙인다. "자동 테스트"는 `pnpm verify`에 들어가는 테스트다. 자동 테스트는 네트워크를 쓰지 않고, 실제 `data/`를 읽지 않는다. 예시 데이터(일정 이름, 이슈 이름, 뉴스 제목)는 지어내서 만든다(저장소가 공개다). "E2E"는 4단계에서 둔 `pnpm e2e`(Playwright)다. "화면 확인"은 앞 단계와 같다: 사이트를 로컬에서 띄워 Claude Code의 내장 브라우저로 폰 폭(375×812)에서 보고 스크린샷을 명세서 폴더의 `screenshots/`에 남긴다(git에 넣지 않는다). 화면 동작 중 자동화할 수 있는 것은 자동 테스트나 E2E로 둔다.

**용어 정의**

- **일정:** 앞으로 예정된 공식 일정 하나다(C3).
- **예정일:** 일정의 날짜다. 일 단위(YYYY-MM-DD) 또는 달 단위(YYYY-MM)다(C2). 현지 날짜다(C4).
- **근거 뉴스:** 그 일정을 말한 뉴스다. 일정 하나에 여러 개일 수 있다. 처음 근거 뉴스는 그중 날짜가 가장 이른 것이다.
- **알려진 날:** 처음 근거 뉴스의 날짜다(C8).
- **결과:** 일정의 상태다. "결과 연결"(결과 뉴스 하나 이상), "연기"(새 일정을 가리킴. 가리키던 일정을 지웠으면 "연기(새 날짜 모름)"), "취소", "결과 기다림"(결과가 없고 기다리는 기간 안이거나 아직 예정일 전, 화면에 표시 없음), "결과 못 찾음"(기다리는 기간이 지남) 중 하나다. 연기·취소는 예정일 전에도 정해질 수 있다(C15).
- **기다리는 기간:** 일 단위는 예정일부터 예정일 + 14일까지, 달 단위는 그 달 1일부터 다음 달 14일까지다(C5).
- **"결과 못 찾음"의 기준일:** 사이트 데이터를 만들 때 DB의 가장 최근 저장 날짜다. 결과가 없고 기다리는 기간의 끝이 기준일보다 앞이면 "결과 못 찾음"이다. 저장하지 않고 계산한다(늦게 재시도한 날짜가 결과를 찾으면 바뀔 수 있게).
- **일정 뽑기:** 한 날짜의 뉴스에서 새 일정을 정하고, 기존 일정에 근거를 더하고, 결과를 정하는 일이다.
- **일정 파일:** 한 날짜의 일정 뽑기 결과를 Claude가 쓰는 작업 파일이다. 데이터 폴더의 `work/` 아래에 둔다.
- **일정 뽑기 완료:** 한 날짜의 일정 파일이 검사를 통과해 적용된 상태다. 뽑은 것이 0개인 날짜도 완료다.
- **다가오는 일정 / 지난 일정(화면):** 보는 사람 브라우저의 오늘(KST) 기준이다. 일 단위는 예정일이 오늘 이후(오늘 포함)면 다가오는 일정이다. 달 단위는 그 달이 이번 달 이후(이번 달 포함)면 다가오는 일정이다.
- **합치기, 흡수, 되돌리기:** 2단계 4.3과 같은 뜻을 일정에도 쓴다.
- 데이터 폴더, 실제 DB, 실행 조건, 시험 모드, 실행 기록, 뉴스 키, 사이트 데이터, 결과물, 본문은 1~4단계 명세서의 용어 정의와 같다.

### 4.1 데이터와 저장

1. **일정 항목:** 일정마다 고정된 정수 식별자(다시 쓰지 않는다), 이름(40자 이하의 짧은 명사구, 예: "가짜 중앙은행 기준금리 결정"), 예정일(일 또는 달 단위), 대분류(plan D5의 7개 중 하나), 결과(상태와 결과 뉴스 또는 연기 대상 일정)를 저장한다. 근거 뉴스, 알려진 날, 관련 이슈는 연결에서 계산한다(저장할지는 구현 재량). 관련 이슈는 근거 뉴스와 결과 뉴스의 주 이슈들이다(흡수된 이슈는 남는 이슈로 본다). 흡수된 일정은 남는 일정을 가리킨다.
   - 확인: 자동 테스트로 일정을 만들고 여러 날짜의 뉴스를 근거로 연결한 뒤 읽으면 위 항목이 나오고, 알려진 날이 가장 이른 근거 뉴스의 날짜이며, 관련 이슈가 근거·결과 뉴스의 주 이슈와 맞다(흡수된 이슈는 남는 이슈로). 합치거나 지운 뒤 새로 만든 일정의 식별자가 앞의 것과 다르다.
2. **연결과 완료 표시:** 뉴스-일정 근거 연결과 결과 연결을 저장한다. 같은 뉴스와 같은 일정의 같은 종류 연결은 하나만 둔다. 날짜마다 일정 뽑기 완료 여부를 남긴다(뽑은 것이 0개여도 완료).
   - 확인: 자동 테스트로 같은 일정 파일을 두 번 적용해도 연결이 하나씩만 남고, 뽑은 것이 없는 날짜도 완료로 나온다.
3. **마이그레이션:** 지금 형식(버전 4)의 DB를 열면 새 버전으로 마이그레이션되고, 기존 브리프·뉴스·이슈·대상·용어·연결·합치기·지운 이름 기록은 그대로 남으며, 모든 날짜가 "일정 뽑기 안 함"이 된다. 마이그레이션 전에 실행 전 사본이 남는 순서(1단계)는 그대로다.
   - 확인: 자동 테스트로 버전 4 스키마의 DB(브리프, 이슈, 대상, 용어, 합치기 기록 포함)를 새 코드로 열면 마이그레이션되고, 기존 데이터를 그대로 읽으며, 모든 날짜가 일정 뽑기 대상으로 나온다.
4. **기존 저장과의 관계:** 브리프 작업 파일, 이슈 연결 파일, 인물·용어 뽑기 파일의 형식에 일정 항목을 더하지 않는다(C11). 1~4단계의 저장·검사·연결·뽑기 동작은 바꾸지 않는다.
   - 확인: 1~4.5단계 테스트가 통과한다(4.9-1).

### 4.2 일정 뽑기 단계 (C1~C5, C11, C15)

1. **실행 순서와 입력:** `/brief`에서 일정 뽑기는 다음 순서로 돈다.
   - 4단계 채우기 뽑기(스킬 문서 7-1단계)를 마친 뒤, 새 날짜를 조사하기 전에 "일정 뽑기 안 함"인 저장된 날짜를 오래된 날부터 뽑는다(이미 쌓인 날짜와 지난 실행에서 실패한 날짜). 그 날짜의 이슈 연결이나 인물·용어 뽑기가 실패 상태여도 일정 뽑기는 한다.
   - 새 날짜마다 그 날짜의 인물·용어 뽑기(스킬 문서 12-1단계)를 마친 직후 그 날짜의 일정을 뽑는다. 앞 단계가 실패했어도 한다. 저장하지 못한 날짜는 뽑지 않는다.
   - 입력은 DB에 저장된 그 날짜 뉴스의 글이다. 새로 수집하는 날짜는 그 날짜를 조사하며 이미 읽은 기사에서 확인한 예정일도 쓴다. 채우기·재시도 날짜는 저장된 글만 쓴다. 일정을 찾으려고 따로 웹 검색을 하거나 원문 페이지를 읽지 않는다(C1).
   - 일정 뽑기는 서브에이전트에 맡기지 않고 메인이 한다(앞 날짜에서 생긴 일정과 결과 후보를 읽어야 하기 때문이다).
   - 날짜 단위로 적용한다. 검사를 통과하면 그 날짜의 새 일정, 근거 연결, 결과를 한 번에 적용하고 일정 뽑기 완료로 둔다. 통과하지 못하면 아무것도 적용하지 않는다.
   - 확인: 스킬 문서(4.8-1)에 이 순서와 각 단계가 부르는 명령이 있다(읽어서 확인, 문서 속 명령 이름이 실제 명령과 같은지 자동 테스트). 4.9-2 시험 실행에서 채우기 날짜가 이 순서대로 진행된다. 새 날짜의 순서(12-1단계 직후)는 시험 실행에서 새 날짜를 수집하지 않으므로 스킬 문서를 읽어서 확인한다.
2. **후보 목록과 검색:** 날짜마다 뽑기 전에 스크립트 명령이 다음을 데이터 폴더의 `work/` 아래 파일로 쓴다.
   - 뉴스: 뉴스 키, 섹션, 종류(주요 뉴스·짧은 소식), 대분류, 제목, 본문(짧은 소식은 요약), 주 이슈 이름.
   - 기존 일정 후보(중복 막기, C6, 예정일 전 연기·취소 C15): 아직 다가오는(예정일이 그 날짜 이후이거나, 달 단위로 그 날짜의 달 이후) 일정 중 그날 뉴스의 주 이슈에 관련된 것과, 이름의 낱말이 그날 뉴스 글에 나오는 것. 낱말 일치에서 흔한 낱말("발표", "결정" 등)은 뺄 수 있다(범위는 AI 재량). 항목마다 식별자, 이름, 예정일, 대분류, 관련 이슈 이름, 알려진 날, 결과(연기·취소면).
   - 결과 후보(C5): 예정일이 그 날짜이거나 지났고, 결과가 "결과 기다림"이며, 그 날짜가 기다리는 기간 안인 일정. 항목마다 식별자, 이름, 예정일, 관련 이슈 이름, 근거 뉴스 제목 하나.
   - 목록에 없는 기존 일정은 검색 명령(이름의 낱말, 예정일 범위)으로 찾는다. 검색 결과에 지운 일정과 이름·날짜가 같으면 "지운 일정과 같음"이 보인다.
   - 일정이 늘어도 목록 길이가 전체 일정 수에 비례해 커지지 않는다.
   - 확인: 자동 테스트로 지어낸 DB에서 그날 뉴스의 주 이슈에 관련된 다가오는 일정과 이름이 본문에 나온 일정이 기존 후보에 들고, 관계없는 일정과 지난 일정은 들지 않으며, 기다리는 기간 안의 결과 기다림 일정만 결과 후보에 든다(기간 밖, 결과 있음, 연기·취소된 것은 들지 않음. 달 단위 일정은 다음 달 14일까지 든다). 일정 5,000개를 넣어도 목록 줄 수가 그 날짜에 관계된 것만큼이다. 검색 명령이 낱말과 날짜 범위로 일정을 찾고, 지운 일정과 같은 이름·날짜면 "지운 일정과 같음"이 나온다.
3. **일정 파일과 검사:** Claude는 날짜마다 일정 파일에 뉴스별로 일정(기존 식별자, 또는 새 일정의 이름·예정일·대분류)을 쓰고, 결과(결과 후보의 식별자와 "결과 뉴스 키" / "연기: 알린 뉴스 키와 새 예정일 또는 기존 일정 식별자" / "취소: 알린 뉴스 키")를 쓴다. 새 예정일로 연기하면 스크립트가 원래 일정의 이름·대분류로 새 일정을 만들고(알린 뉴스가 그 근거 뉴스다) 원래 일정이 그것을 가리킨다. 이렇게 만드는 새 일정도 새 일정과 같은 검사(예정일 범위, 이름 겹침, 지운 일정)를 받고, 겹치면 기존 일정 식별자를 쓰라고 알린다. 달 단위 기존 일정이 그 달 안의 정확한 날짜로 정해졌으면 근거 뉴스 키와 함께 날짜 확정을 쓸 수 있다(다른 달이면 연기다). 스크립트가 검사해 다음을 거부한다.
   - 없는 뉴스 키, 그 날짜의 모든 뉴스가 파일에 나오지 않음(일정이 없는 뉴스는 빈 목록으로 적는다)
   - 주요 뉴스 한 건에 일정 4개 이상, 짧은 소식 한 건에 일정 2개 이상(C3). 기존 일정에 근거를 더하는 것도 센다
   - 예정일 형식이 일·달 단위가 아님, 일 단위 예정일이 뉴스 날짜 다음 날보다 이르거나 365일을 넘음, 달 단위가 뉴스 날짜의 달보다 이르거나 12달 뒤 달을 넘음(C2, C3)
   - 대분류가 7개 밖, 이름이 비었거나 40자를 넘거나 문장 끝 부호로 끝남
   - 없는 식별자, 흡수된 일정의 식별자(남는 것을 쓰라고 알린다), 지운 일정의 식별자
   - 새 일정이 같은 예정일(달 단위는 같은 달)의 기존 일정이나 같은 파일의 새 일정과 이름이 겹침(띄어쓰기·대소문자·가운뎃점 같은 표기 차이 무시, 정규화 방법은 AI 재량). 지운 일정과 이름·예정일이 겹침(C13)
   - 결과 연결의 대상이 그 날짜의 결과 후보가 아님, 연기·취소의 대상이 결과 후보도 아니고 "결과가 없고 예정일이 그 날짜 뒤(달 단위는 그 날짜의 달 뒤)인 일정"도 아님(C15. 후보 목록에 없어도 검색으로 찾은 일정이면 된다), 결과 뉴스 키나 연기·취소를 알린 뉴스 키가 그 날짜 뉴스가 아님, 같은 일정에 결과를 두 번, 연기의 새 예정일이 원래 예정일보다 이르거나 같음(달 단위는 같은 달), 연기 대상 기존 일정이 자기 자신·흡수·지운 일정임
   - 날짜 확정의 대상이 달 단위가 아니거나, 새 날짜가 그 달 밖이거나, 근거 뉴스 키가 그 날짜 뉴스가 아님
   - 같은 뉴스에 같은 일정이 두 번
   - 확인: 자동 테스트로 위 거부 경우를 하나씩 넣은 파일이 거부되고 DB가 바뀌지 않으며, 맞는 파일(새 일정, 기존 일정에 근거 더하기, 결과 연결, 연기(새 예정일로 새 일정이 생기고 원래 일정이 그것을 가리킴), 연기(기존 일정을 가리킴), 취소, 날짜 확정, 예정일 전의 연기와 취소(C15))은 통과해 적용된다. 거부 경우에는 41자 이름, 366일 뒤 예정일, 예정일 전 일정에 결과 뉴스 연결, 이미 연기·취소된 일정에 다시 연기도 넣는다.
4. **뽑기 기준(스킬 문서에 적는다):** 판단 기준은 스킬 문서(4.8-1)에 적고 Claude가 따른다. 기계로 검사할 수 없어 사용자가 마지막에 본다(C12).
   - 날짜가 정해졌다고 보도된 공식 일정만 뽑는다(C3의 종류). 추측, 전망, "~할 수도"는 뽑지 않는다.
   - 날짜를 모르면 뽑지 않는다. 달까지만 알면 달 단위로 쓴다. "연내", "곧", 주·분기 단위는 뽑지 않는다(C2).
   - 해외 일정은 기사가 말하는 현지 날짜로 쓴다(C4).
   - 이름은 무엇이 일어나는지 알 수 있는 짧은 명사구로 직접 쓴다(D6). 일반인 이름을 쓰지 않는다(공인·기관 이름은 쓴다).
   - 대분류는 그 일정이 속한 분야로 고른다(보통 근거 뉴스의 대분류).
   - 새로 만들기 전에 기존 일정 후보와 검색으로 같은 일정이 있는지 보고 있으면 그 식별자를 쓴다(C6).
   - 결과 후보마다 그날 뉴스에 그 일정의 결과(결정, 발표, 선고, 개표 결과 등)가 있으면 그 뉴스를 결과로 잇는다. 미뤄졌다고 보도되면 연기(새 날짜를 알면 새 예정일, 이미 있는 일정이면 그 식별자), 취소되었다고 보도되면 취소로 쓴다. 해당 뉴스가 없으면 그대로 둔다.
   - 아직 예정일 전인 기존 일정이 연기·취소되었다고 보도되면 그 일정에 연기·취소를 쓴다. 새 날짜로 새 일정만 따로 만들지 않는다(C15).
   - 확인: 스킬 문서에 위 기준이 모두 있다(읽어서 확인). 4.9-2 시험 결과의 적절함은 사용자가 마지막에 본다(5장).
5. **고쳐서 다시 검사와 실패:** 위반이 나오면 Claude가 일정 파일을 고쳐 다시 검사한다. 날짜마다 최대 2번이다. 그래도 위반이 남으면 그 날짜는 적용하지 않고 실행 기록에 실패로 남긴다. 다음 실행이 그 날짜를 다시 뽑는다(C11). 일정 뽑기 실패는 그 실행의 다른 날짜, 합치기, 백업, 빌드, 배포, 요약을 멈추지 않는다.
   - 확인: 자동 테스트로 실패로 기록된 날짜가 다음 실행의 "일정 뽑기 안 함" 날짜에 다시 나오고, 그 날짜의 뉴스·이슈 연결·대상·용어 연결은 바뀌지 않는다(데이터 폴더 지정 실행으로 확인한다). 시험 모드 실행에서는 일정 뽑기 실패가 실행 기록과 요약에 남고 다른 단계를 멈추지 않는다.

### 4.3 합치기, 되돌리기, 지우기 (C6, C13)

1. **7일 합치기에 함께 넣기:** 2·4단계의 7일 합치기(같은 점검일, 같은 실행 위치)에서 비슷한 일정 쌍 후보를 함께 뽑는다. 후보는 예정일이 같거나(달 단위와 그 달 안의 일 단위 포함) 이틀 안이고 이름이 비슷한 쌍이다(비슷함 기준은 AI 재량). 쌍마다 이름, 예정일, 대분류, 관련 이슈, 근거 뉴스 몇 건(날짜·제목), 결과를 담는다. 흡수된 것, 지운 것, 되돌려서 "합치지 않음"이 된 쌍, 한쪽이 다른 쪽을 연기 대상으로 가리키는 쌍(연기로 생긴 일정은 이름이 같다)은 뺀다. Claude가 같은 일정인지 판단해 합치기 파일에 쓰고 스크립트가 검사·적용한다. 판단 기준은 스킬 문서에 적는다. 점검일 규칙은 이슈·대상·용어·일정을 함께 한 번으로 본다(4단계 4.3-1과 같다).
   - 확인: 자동 테스트로 같은 날짜의 이름이 거의 같은 두 일정과 달 단위·일 단위로 같은 달인 두 일정이 후보에 나오고, 날짜가 먼 쌍, 관계없는 쌍, "합치지 않음" 쌍, 연기 관계인 쌍, 지운 것은 나오지 않는다. 점검일 규칙이 4단계 테스트와 같이 동작한다.
2. **합치기 적용:** 흡수되는 일정의 근거·결과 연결을 남는 일정으로 옮긴다(같은 뉴스에 둘 다 있으면 하나로). 예정일은 합치기 파일에 쓴 남는 것의 예정일로 한다(없으면 남는 것 그대로. 하나가 일 단위면 일 단위를 쓴다). 결과는 남는 것에 결과가 없고 흡수되는 것에 있으면 그것을 쓰고, 둘 다 있고 다르면 거부한다. 흡수된 일정은 남는 것을 가리키고, 그것을 연기 대상으로 가리키던 일정은 남는 것을 가리킨다. 합치기 기록에 날짜, 둘, 이유, 되돌리기에 필요한 합치기 전 상태를 남긴다. 거부: 없는 것, 이미 흡수되거나 지운 것, 같은 것끼리, 이유 없음, 결과 충돌.
   - 확인: 자동 테스트로 적용 결과(연결 이동과 중복 정리, 예정일, 결과, 흡수 표시, 연기 대상 갱신, 기록)가 맞고, 거부 경우마다 거부되며 DB가 바뀌지 않는다.
3. **되돌리기:** 일정 합치기 기록 하나를 되돌리는 명령을 둔다(4단계 `ref-unmerge`를 넓히든 새 명령을 두든 AI 재량, 공통 코드를 쓴다). 규칙은 4단계 4.3-3과 같다: 흡수된 일정을 합치기 전 상태로 되살리고, 남는 것은 합치기 전 연결·예정일·결과로 되돌리되 그 뒤에 더해진 것은 둔다. 그 쌍은 "합치지 않음"이 된다. 연달아 합쳐진 경우와 이미 되돌린 기록은 거부한다. 실제 데이터 폴더에서는 실행 조건(S12)을 따르고 바꾸기 전에 DB 사본을 남긴다. `/brief`는 이 명령을 실행하지 않는다. 합치기 기록 목록을 보는 명령(`merges`) 출력에 일정 합치기도 나온다.
   - 확인: 자동 테스트로 합친 뒤 되돌리면 둘이 합치기 전과 같아지고, 합친 뒤 새 근거가 붙은 경우 새 연결이 남는 것에 남으며, 되돌린 쌍이 다음 후보에 나오지 않고, 연달아 합쳐진 경우와 실제 데이터 폴더 조건 위반(임시 git 저장소의 다른 브랜치)이 거부되고 DB가 바뀌지 않는다.
4. **지우기 명령(C13):** 사용자가 부르는 명령 하나로 일정 하나를 식별자로 지운다. 흡수된 식별자를 주면 거부하고 남는 것의 식별자를 알린다.
   - 그 일정의 근거·결과 연결을 모두 지우고, 식별자는 다시 쓰지 않는다. 그 일정을 연기 대상으로 가리키던 일정은 "연기(새 날짜 모름)"로 보인다. 이름과 예정일을 "지운 일정"으로 기록해 다음 뽑기에서 같은 이름·예정일의 새 일정을 거부한다(4.2-3). 지운 일정에 흡수되어 있던 일정도 지운 것으로 본다.
   - 다음 빌드·배포부터 사이트에서 빠지고, 그 일정 주소는 없는 페이지가 된다(4.7-6).
   - 실제 데이터 폴더에서는 실행 조건(S12)을 따르고 바꾸기 전에 DB 사본을 남긴다. `/brief`는 이 명령을 실행하지 않는다. 출력에 지운 일정, 끊은 연결 수, 다음 `/brief`가 백업·배포한다는 것, 이미 push된 `data` 브랜치 이력과 뉴스 본문에는 남는다는 것, 바로 내리려면 운영 문서의 손으로 하는 배포를 쓰라는 것을 보인다.
   - 지우기는 되돌리지 않는다(사본으로 복원은 운영 문서에 적는다).
   - 확인: 자동 테스트로 지운 뒤 연결이 없고, 사이트 데이터에 그 일정이 없으며, 같은 이름(띄어쓰기만 다른 표기 포함)·같은 예정일의 새 일정을 만드는 일정 파일이 거부되고(다른 날짜면 통과), 흡수된 식별자로 지우면 거부되고 출력에 남는 것의 식별자가 나오며, 연기 대상으로 가리키던 일정이 "연기(새 날짜 모름)"가 되고, 실제 데이터 폴더 조건 위반이 거부된다.

### 4.4 백업과 복원 (D1)

1. **백업 형식:** 백업에 일정, 근거·결과 연결, 결과 상태, 날짜별 일정 뽑기 완료, 일정 합치기 기록과 "합치지 않음" 쌍, 지운 일정 기록을 넣는다. 날짜에 묶이지 않는 데이터는 이슈·대상처럼 날짜 밖 파일에 둔다(파일 나누기는 AI 재량이되 백업 파일 이름 규칙은 3단계 4.1-4의 구분이 유지되게 한다). 일정 데이터가 하나도 없는 DB의 백업은 형식 버전 숫자와 날짜별 일정 뽑기 완료 표시 말고는 지금과 같은 파일과 키를 낸다(4단계 4.4-1과 같은 이유). 형식 버전을 올리고(지금 3), 복원은 지금 형식(1, 2, 3)과 새 형식을 모두 읽는다. 옛 형식 백업을 복원하면 모든 날짜가 "일정 뽑기 안 함"이 된다.
   - 확인: 자동 테스트로 일정·연결·결과·합치기·지우기가 있는 DB를 백업하고 빈 곳에 복원하면 같은 데이터가 나오고(왕복), 가장 큰 식별자의 일정을 지운 DB를 백업·복원한 뒤 새로 만든 일정의 식별자가 지운 것과 다르며, 형식 3 백업을 복원하면 모든 날짜가 일정 뽑기 대상으로 나온다.
2. **공개 데이터 검사:** 새 백업 데이터도 3단계의 push 전 공개 전 점검과 결과물 검사를 그대로 받는다. 결과물에 들어가면 안 되는 파일 이름 목록(`src/siteCheck.ts`)에 이 단계의 새 백업 파일, 일정 파일·후보 목록 파일 이름을 더한다(3단계 4.1-4).
   - 확인: 기존 공개 전 점검 테스트가 통과하고, 4.9-2 시험 결과물이 결과물 검사를 통과한다.

### 4.5 `start` 출력과 실행 요약

1. **`start` 출력:** 지금 출력에 "일정 뽑기할 저장된 날짜(채우기·재시도)" 줄을 더한다.
   - 확인: 자동 테스트로 일정 뽑기 안 한 날짜가 있는 DB에서 그 줄에 날짜가 나오고, 없으면 "없음"이다.
2. **요약:** 실행 요약에 다음을 더한다: 일정 뽑기한 날짜마다 새 일정 수, 근거를 더한 기존 일정 수, 결과 연결·연기·취소 수. 일정 뽑기에 실패한 날짜와 남은 위반. 아직 일정 뽑기 안 한 날짜 수. 합치기 줄에 일정 합치기(남는 것, 흡수된 것, 이유)와 되돌리는 명령. 사이트 빌드 줄에 일정 수(다가오는 일정 수 포함). 요약과 보고서의 다가오는 일정 수는 실행한 날의 KST 날짜 기준이다(사이트 데이터는 시계를 쓰지 않는다(4.6-3). 테스트에서는 날짜를 넣어 준다).
   - 확인: 자동 테스트로 요약 출력에 위 줄이 나온다.

### 4.6 사이트 데이터 (C7, C8)

1. **사이트 데이터:** 빌드할 때 DB에서 다음을 사이트 데이터에 더한다. 흡수된 것과 지운 것은 목록에서 빼고, 흡수된 것의 식별자는 남는 것으로 가는 정보만 남긴다.
   - 일정 목록: 일정마다 식별자, 이름, 예정일(일·달 단위 구분), 대분류, 관련 이슈(식별자·이름), 알려진 날, 처음 근거 뉴스(날짜, 뉴스 키), 결과(상태, 결과 뉴스의 날짜·뉴스 키·제목, 연기 대상 일정의 식별자·예정일). "결과 기다림"과 "결과 못 찾음"은 빌드할 때의 기준일(가장 최근 저장 날짜)로 계산한다.
   - 브리프 날짜마다 '이번 주 일정'(C8): 그 날짜 다음 날부터 7일 안의 일 단위 일정 중 알려진 날이 그 날짜 이하인 것, 예정일 순.
   - 펼친 카드 본문에 뉴스마다 그 뉴스를 근거로 한 일정(식별자, 이름, 예정일).
   - 이슈 데이터에 관련 일정(다가오는 일정은 예정일 가까운 순, 지난 일정은 최근 순, 결과 포함). 다가오는·지난의 구분은 화면이 보는 사람의 오늘로 한다(4.7-1).
   - 확인: 자동 테스트로 지어낸 DB(날짜 10개 이상, 일 단위·달 단위 일정, 결과 연결·연기·취소·결과 기다림·결과 못 찾음 일정, 합친 일정 1개, 지운 일정 1개, 합친 이슈 1개)에서 위 항목이 나오고, '이번 주 일정'이 브리프 날짜 기준(알려진 날 조건 포함)이며, 흡수된 이슈의 일정이 남는 이슈 쪽에 붙고, 지운 것은 어디에도 없다.
2. **파일 수와 크기:** 3단계 4.1-3의 파일 수 한도(5년치 데이터에서 결과물 10,000개 이하)를 일정을 더한 5년치에서도 지킨다. 5년치는 4단계 측정 조건(1,826일, 하루 약 42건, 이슈 15,000개, 대상 15,000개, 용어 5,000개)에 일정 15,000개(하루 평균 약 8개, 그중 달 단위 2할, 근거 연결 평균 2개, 결과 연결 6할)를 더한 것이다. 3단계 4.3-7의 첫 화면 크기(브리프 첫 화면, '이번 주 일정' 포함 gzip 300KB 이하)를 그대로 지킨다. 일정 화면이 처음 받는 사이트 데이터(목록의 다가오는 일정, 달력의 이번 달)도 gzip 300KB 이하다. 나누는 방법(달별 파일 등)은 AI 재량이다. 단, 결과물 파일·폴더 이름이 결과물 검사(`src/siteCheck.ts`)의 이름 규칙 전체(백업 파일 이름 `YYYY-MM.json`·`issues.json`·`refs.json`·`meta.json`, 실행 기록·작업 파일 이름 `YYYY-MM-DD.json`·`merges.json` 등, 데이터 폴더 이름 `work`·`runs`·`backup` 등)에 걸리지 않게 한다(지금 사이트 데이터의 `list-2026-10.json`처럼 앞에 이름을 붙인다).
   - 확인: 지어낸 5년치로 빌드해 결과물 파일 수가 10,000개 이하이고, 위 화면들이 처음 받는 데이터 크기가 300KB 이하다(명령이나 테스트). 보고서에 결과물 크기·파일 수와 4단계 보고서 값과의 차이, 실제 데이터 복사본의 값, 1년 뒤 예상 크기(Vercel 무료 한도 100MB에 닿는 예상 시점 포함)를 적는다.
3. **같은 DB, 같은 결과:** 3단계 4.1-2를 새 데이터에도 지킨다. 단, "결과 못 찾음"은 DB의 가장 최근 저장 날짜로 계산하므로 같은 DB면 같다(빌드한 날의 시계를 쓰지 않는다).
   - 확인: 3단계의 같은 결과 테스트가 일정이 있는 DB로도 통과한다.

### 4.7 화면 (C7~C10)

화면은 [design/site.html](design/site.html)(확정 시안)을 따른다. 시안의 설명 글과 이 명세서가 다르면 명세서를 따른다(예: '이번 주 일정'의 결과 문구는 링크가 아니다, 달 단위 상자는 그 달 날짜 일정들의 앞이나 뒤다). 시안에 없는 것은 3단계 확정 시안 A와 지금 사이트의 색·글꼴·간격·컴포넌트를 쓴다. 3단계 4.3-5(없는 페이지, 불러오기 오류와 다시 시도, 대기 표시)와 4.3-6(화면 공통)을 모든 새 화면과 동작에 지킨다.

1. **일정 화면: 목록(기본):** 제목 '일정' 오른쪽에 '목록 | 달력' 보기 전환, 그 아래 "날짜는 현지 기준" 한 줄, '다가오는 일정 / 지난 일정' 탭, 대분류 칩(전체와, 일정이 있는 대분류)을 둔다. 다가오는 일정은 가까운 날부터, 지난 일정은 최근 날부터 날짜별로 묶는다(날짜 머리에 요일). 달 단위 일정은 그 달의 "N월 중 (날짜 미정)" 상자에 모아 그 달 날짜 일정들의 앞이나 뒤에 둔다(어느 쪽인지는 AI 재량). 줄마다 대분류(색 글자), 이름, "이슈: <대표 이슈 이름>"을 보인다. 대표 이슈는 처음 근거 뉴스의 주 이슈이고(흡수된 이슈는 남는 이슈), 없으면(이슈 연결이 실패한 뉴스) 이슈 줄을 보이지 않는다. 지난 일정은 결과("결과: <결과 뉴스 제목> ›", "연기 → <새 예정일>", "연기(새 날짜 모름)"(링크 없음), "취소", "결과 못 찾음". 결과 기다림은 표시 없음)를 붙인다. 다가오는 일정도 연기·취소되었으면 같은 문구를 붙인다(C15). 이름을 누르면 처음 근거 뉴스(그 날짜 브리프의 해당 카드나 줄), 결과를 누르면 결과 뉴스, 이슈를 누르면 이슈 페이지, 연기를 누르면 새 일정으로 간다. 다가오는·지난의 구분은 보는 사람 브라우저의 오늘(KST)로 한다. 다가오는 일정이 많으면 처음에 일부를 보이고 이어서 더 보인다(방식은 AI 재량, 4.6-2의 크기 안).
   - 확인: 자동 테스트로 다가오는·지난 구분(오늘 경계, 달 단위의 이번 달 포함), 정렬, 달 단위 묶음, 대분류 거르기, 결과 문구와 링크 주소가 맞다. 화면 확인(다가오는 일정, 지난 일정, 다크, 1440px).
2. **일정 화면: 달력:** '달력'을 누르면 월 격자(일요일 시작)를 보인다. 일정 있는 날에 점(지난 날은 회색 점), 오늘은 강조색 글자다. 날짜를 누르면 격자 아래에 그날 일정(목록과 같은 줄 모양, 지난 일정이면 결과 포함)이 나오고, 그 달의 달 단위 일정은 격자 아래 "N월 중 (날짜 미정)" 상자에 나온다. ‹ ›로 달을 넘긴다(일정이 있는 첫 달부터 마지막 달까지, 오늘이 든 달이 그 밖이면 범위에 넣는다). 처음 열면 오늘이 든 달과, 오늘(오늘 일정이 없으면 그 달에서 오늘 뒤 첫 일정 날, 그것도 없으면 오늘)을 고른다. 대분류 칩은 격자의 점과 목록 모두에 적용된다. 날짜 칸은 키보드로 고를 수 있고(화살표나 Tab, 방식은 AI 재량) 고른 날을 보조 기술에 알린다.
   - 확인: 자동 테스트로 격자의 날짜 배치(달 첫날 요일), 점 표시(지난 날 회색), 처음 고르는 날, 달 넘기기 범위, 거르기가 맞다. E2E로 날짜를 눌러 그날 일정이 나오고 키보드로 날짜를 고를 수 있다. 화면 확인(이번 달, 지난 달의 지난 날을 고른 상태, 다크, 1440px).
3. **보기 기억(C9):** 마지막으로 고른 보기(목록·달력)를 로컬 스토리지 키 하나에 기억한다(키 이름은 AI 재량, `tidwyn.` 접두사). 처음엔 목록이다. 저장할 수 없거나 값이 깨졌으면 오류 없이 목록으로 시작한다. 사이트 소개의 "읽은 기록 지우기"는 이 키를 지우지 않는다. 사이트 소개의 브라우저 기억 설명(4.5단계)에 이 키와 4.7-4의 키를 더한다.
   - 확인: 자동 테스트(또는 E2E)로 달력을 고른 뒤 새로 고치면 달력이고, 저장할 수 없는 상태에서 목록으로 시작하며, 읽은 기록 지우기 뒤에도 보기가 남는다.
4. **브리프 위 '이번 주 일정'(C8, C10):** 오늘의 한 문장 아래, 카테고리 칩 위에 상자를 둔다. 4.6-1의 '이번 주 일정'을 예정일 순으로 최대 5개 보이고(줄마다 "MM-DD 요일"과 이름. 결과 문구는 4.7-1과 같고 작게 보인다. "결과 못 찾음" 포함, 결과 기다림은 표시 없음), 제목 줄 오른쪽에 '일정 전체 ›'(일정 화면 목록으로)를 둔다. 줄을 누르면 일정 화면의 그 일정으로 간다(4.7-6). 결과 문구는 링크가 아니다(줄 전체가 일정 화면 링크다. 링크 안에 링크를 두지 않는다). 섹션 탭('전체', 한국, 세계, IT·AI)과 대분류 칩에 관계없이 같다. 일정이 없으면 상자도 접은 줄도 보이지 않는다. 상자 제목 '이번 주 일정 ▴'가 토글 버튼이다: 누르면 상자가 접혀 배경 없는 한 줄 '이번 주 일정 N ▾'(N은 그 주 일정 전체 수)만 남고, 다시 누르면 편다. 버튼은 열림 상태를 보조 기술에 알린다(`aria-expanded`). 접은 상태는 로컬 스토리지 키 하나에 기억해 다른 날짜와 다음 방문에도 이어진다(처음엔 펼침, 저장할 수 없으면 펼침, 읽은 기록 지우기는 이 키를 지우지 않는다).
   - 확인: 자동 테스트로 상자의 일정이 브리프 날짜 기준이고 최대 5개이며 N이 전체 수다. E2E로 제목을 눌러 접고 펴며, 새로 고치거나 다른 날짜로 가도 접은 상태가 이어지고, 키보드(Enter·Space)로 토글하며 `aria-expanded`가 바뀐다. 화면 확인(펼침, 접음, 다크, 일정 없는 날짜).
5. **펼친 카드와 이슈 페이지:** 펼친 카드에서 '앞으로 볼 것' 아래, '인물·기관·국가' 칩 줄 위에 '일정' 칩 줄(칩마다 예정일 "MM-DD" 또는 "N월 중"과 이름)을 둔다. 누르면 일정 화면의 그 일정으로 간다. 그 뉴스를 근거로 한 일정이 없으면 칩 줄을 보이지 않는다. 이슈 페이지에서 타임라인 아래, '등장 인물·기관·국가' 위에 '일정'을 둔다: 다가오는 일정(가까운 순) 다음에 지난 일정(최근 순). 결과 문구는 4.7-1과 같다. 줄마다 예정일, "다가오는 일정"/"지난 일정", 이름이고, 누르면 일정 화면의 그 일정으로 간다. 없으면 보이지 않는다. 일정이 많으면 다가오는 일정 최대 5개와 지난 일정 최대 5개를 보이고 '일정 전체 ›'로 일정 화면에 간다(그 이슈로 거르지 않는다).
   - 확인: 자동 테스트로 칩 순서와 링크, 이슈 페이지의 순서·최대 개수가 맞다. 화면 확인(카드, 이슈 페이지, 다크).
6. **일정 주소:** 일정 화면과 일정 하나를 가리키는 주소는 깔끔한 경로나 그 화면의 고정된 표시(경로 이름과 방식은 AI 재량, 3단계 P4와 같은 방식)이고, 한 번 공개한 주소는 뒤 단계에서도 깨지지 않게 둔다. 일정 하나의 주소로 들어오면 목록 보기의 그 일정이 든 탭(다가오는·지난)으로 가서 그 일정 위치로 이동하고 잠깐 강조한다(시안의 강조, 기억한 보기가 달력이어도 이때는 목록을 보인다. 기억한 보기는 바꾸지 않는다). 흡수된 일정 주소는 남는 일정으로 가고, 지운 일정과 없는 식별자는 없는 페이지를 보인다. 직접 열거나 새로 고쳐도 화면이 나온다(3단계 4.6-2의 대체 경로 설정에 더한다).
   - 확인: 자동 테스트로 일정 주소가 그 일정을 가리키고, 흡수·지운·없는 일정 주소가 위 규칙대로다. E2E로 일정 주소에서 그 일정이 강조된다. 로컬 보기 서버(`pnpm site:preview`)에서 새 주소를 직접 요청해 200과 화면 틀이 온다.
7. **메뉴:** 머리 메뉴에 '일정'을 더한다(위치는 AI 재량). 바닥글에 더할지는 AI 재량이다. 사이트 소개(`/about`)에 일정도 AI가 뉴스에서 뽑은 것이라 틀릴 수 있고 날짜는 현지 기준이라는 것을 한 줄 더한다.
   - 확인: 화면 확인(메뉴 연 상태, 사이트 소개).
8. **화면 확인의 상태:** 위 화면을 375px 라이트로, 일정 화면(목록·달력)·'이번 주 일정'·이슈 페이지는 다크로도, 일정 화면은 넓은 화면(1440px)으로도 확인한다. 빈 상태(일정이 하나도 없음, 다가오는 일정 없음, 거른 결과 없음, 일정 없는 달)와 데이터를 불러오지 못한 오류 상태(3단계 4.3-5)도 하나씩 본다. 가로 스크롤이 없다. 새 화면의 글자 색 대비가 WCAG AA(4.5:1) 이상이다(강조된 일정 배경, 결과 표시 배경, 달력의 고른 날 위 글자 포함).
   - 확인: 스크린샷을 보고서에 링크한다. 대비는 시안 색으로 계산해 보고서에 적는다. 가로 스크롤 없음은 E2E로 375px에서 본다.

### 4.9 기존 기능 유지와 시험 실행

1. **기존 테스트와 검증:** 1~4.5단계 테스트(`pnpm verify`, `pnpm e2e`)가 통과한다. 기존 테스트에서 허용하는 변경은 4단계 명세서 4.10-1과 같다(버전 숫자에 묶인 줄, 새 테스트와 import, 사이트 데이터·결과물의 파일 목록 단언에 이 단계의 새 파일 이름 더하기). 새 항목(펼친 카드의 일정, 이슈의 일정, 브리프의 '이번 주 일정')은 비어 있으면 빼서 기존 통째 비교 단언을 바꾸지 않는다. 브리프 첫 화면 구조를 보는 기존 E2E가 새 상자 때문에 깨지면, 일정이 없는 데이터에서는 상자가 없으므로 그 데이터로 통과해야 하고, 일정이 있는 데이터의 E2E는 새로 둔다. 스킬 문서·요약·`start` 출력의 바뀐 줄을 보는 기존 테스트는 바뀐 동작에 맞게 고쳐도 되고, 고친 줄과 이유를 보고서에 적는다.
   - 확인: `pnpm verify`와 `pnpm e2e` 통과. `git diff main -- test/`(E2E는 `test/e2e/`)의 기존 줄 변경이 허용 범위뿐이다(보고서에 목록).
2. **시험 실행:** 실제 `data/tidwyn.db`를 읽기만 해서 `.test-data/` 아래 새 폴더에 복사하고, 그 복사본으로 다음을 한다. 실제 `data/`와 실제 DB, `refs/heads/data`에는 쓰지 않는다.
   - 데이터 폴더 지정(`TIDWYN_DATA_DIR`=복사 폴더) `/brief` 흐름으로 `start`를 돌려 마이그레이션과 "일정 뽑기할 저장된 날짜"를 확인한다.
   - 그 모든 날짜를 스킬 문서의 일정 뽑기 절차대로 뽑는다. 구현하는 AI가 Claude의 역할(일정 파일 쓰기)을 스킬 문서 기준(4.2-4)대로 한다. 채우기 날짜라 저장된 글만 쓴다. 새 날짜 수집은 하지 않는다.
   - 합치기 주기가 되었으면 합치기도 한다. 이어서 백업(지정 폴더라 커밋 없음), 빌드까지 돌리고 요약을 확인한다.
   - 그 결과물을 미리보기로 배포하고(4단계의 `deploy --dir <결과물> --preview`, 사전 승인) 4단계 4.8-1과 같은 확인을 한다: `vercel inspect <미리보기 주소> --scope mivomad33`가 Ready이고, 로그인 없이 `curl`로 요청하면 사이트 내용이 아닌 응답(401·403 또는 Vercel 로그인으로 보내는 응답)이 오며, 미리보기 배포 직후 운영 배포 ID가 시작 때 진행 기록에 적은 것과 같다.
   - 같은 결과물을 로컬 보기 서버로 띄워 4.7의 화면 확인 스크린샷을 남긴다(미리보기는 로그인이 필요해 AI가 열지 않는다). 지난 일정·결과가 실제 복사본에 거의 없으므로, 결과 연결·연기·취소·결과 못 찾음 화면은 지어낸 데이터로 찍는다. 실제 복사본에 '이번 주 일정'이 하나도 없으면(브리프 날짜 다음 7일 안의 일정이 뽑히지 않음) 그 화면도 지어낸 데이터로 확인하고, 그 사실을 보고서와 5장 사용자 확인 1번 안내에 적는다.
   - 백업 결과를 빈 폴더에 복원해 다시 빌드하면 같은 사이트 데이터가 나온다.
   - 확인: 보고서에 시험 폴더 경로, 일정 뽑기한 날짜 수, 일정 수(일 단위·달 단위, 다가오는·지난), 결과 상태별 수, 실패와 고친 횟수, 합치기 결과, 빌드 결과(일정 수, 크기, 파일 수), 미리보기 주소와 확인 결과, 복원 비교 결과, 스크린샷 링크, 뽑힌 일정 전체 목록(이름, 예정일, 대분류, 근거 뉴스 제목)이 든 검토 파일 경로(git이 무시하는 시험 폴더 안)(검토 전 목록이 공개 main에 들어가지 않게 보고서에는 경로와 수만 적고, 합치기 결과도 수만 적는다. 진행 기록에도 일정 이름 목록을 적지 않는다)가 있다. 1장 "충분한 수준"이 모두 보인다.
3. **실제 데이터 보호:** 구현을 시작할 때 `data/tidwyn.db`의 해시와 `git rev-parse refs/heads/data`를 진행 기록에 적고 끝날 때 다시 본다. 다르면 `data/runs/`로 사용자의 실제 실행 때문인지 확인해 보고서에 적는다.
   - 확인: 비교 결과를 보고서에 적는다.
