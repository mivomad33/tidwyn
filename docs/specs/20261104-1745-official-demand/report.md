# 9.96단계 결과 보고서: 공식 수요 데이터

## 사용자가 할 일

보류는 없다. 공식 소스 묶음 여섯이 모두 실제로 받았고, 국회를 뺀 다섯 묶음(권익위, 1372, DART, SEC, Wikimedia)이 지난 날짜를 받았다.

1. [source-terms.md](source-terms.md)의 판정을 보고 그대로 둘지 정한다. 특히 볼 것:
   - OpenDART의 '조항 없음'을 저장·AI 입력이 되는 것으로 본 것
   - 민원빅데이터의 비상업 조건(광고를 달기 전에 다시 본다)
   - 소비자 위해정보를 뺀 것

   빼기로 정한 곳은 `src/demandSources.ts`의 끄기 값(`DEMAND_SOURCES_OFF`)과 [판정 문서](../../demand-sources.md)를 worktree에서 고쳐 커밋한다. 이어서 `pnpm verify`를 다시 돌린 뒤 머지한다.
2. 머지를 승인한다. 직접 머지하지 않는다. 사용자 확인이 끝나면 `/review-done`으로 이 보고서를 검토한다. 통과와 머지를 승인하면 `review-done`이 메인 폴더에서 다음을 한다.
   - squash merge, 공개 전 점검, main push
   - worktree와 브랜치 지우기
   - `docs/specs/README.md`의 상태를 '완료'로 바꾸기

   머지에 관해 알아 둘 것:
   - CI는 없다. 사이트는 바뀌지 않는다.
   - 머지는 00:00~05:49에 한다. 05:50 뒤라면 그날 예약 실행이 push를 끝낸 뒤에 한다.
   - 머지 뒤 첫 `/brief`가 할 일:
     - 실제 데이터 폴더의 `demand.db`를 v2로 마이그레이션한다. 9.95 첫 실행이 만든 것이 있으면 그것을 쓴다.
     - 18-1단계에서 지난 기간 채우기를 시작한다. 9분씩 두 번이다.
3. 머지 뒤에 할 일(머지 승인의 조건은 아니다): 처음 며칠의 실행 요약에서 `남은 채우기 대상`이 줄어드는지 본다. 시험 실행으로 보면 사흘쯤이면 끝난다. 막힘이나 키 없음이 이어지면 [운영 문서](../../operations.md)의 "공식 수요(9.96단계)" 절대로 한다.

## 만든 것

- `node src/cli.ts demand-official --run <실행 기록>`이 공식 소스를 9.95와 같은 전용 DB(`<데이터 폴더>/demand.db`)에 쌓는다. 소스는 6묶음 19개다.
  - 국회 청원 3목록
  - 권익위 민원정책 질의응답·공개제안·민원빅데이터 오늘의 이슈
  - 1372 소비자상담
  - DART 공시검색
  - SEC Form D(일별 인덱스의 `D`·`D/A` 줄과 각 신고의 `primary_doc.xml`)
  - Wikimedia 인기 문서 10개 위키
- 지난 기간 채우기:
  - 2026-09-30부터 받는다. 국회 목록은 받은 날의 상태다.
  - 소스끼리 값 날짜를 하나씩 번갈아 받고, 오래된 날부터 받는다.
  - 한 번 부를 때 상한은 9분이다. 상한에 닿고 남은 대상이 있으면 출력에 `공식 수요 상한: 닿음, 남은 대상 있음`이 나오고, 스킬이 같은 명령을 한 번 더 부른다. 한 실행에서 두 번까지 부른다.
  - 같은 실행의 뒤 호출은 앞 호출이 받은 것과 실패한 값 날짜를 다시 받지 않고, 결과를 합친다.
  - 1372는 진행 중인 달을 7일마다 다시 받는다. 끝난 달은 2달까지 건수가 바뀌면 다시 받는다.
- 저장(마이그레이션 v2):
  - 값 날짜마다 스냅샷 하나에 응답을 gzip으로 담는다. 고치기·지우기는 트리거가 막는다.
  - 하루 요청 수, 상한에 끊긴 값 날짜, 민원빅데이터 마지막 요청 시각을 표로 둔다.
  - 저장하는 주소에서는 키 파라미터를 뺀다. 본문의 키 값은 가린다.
  - 개인 칸을 버린다: 청원인, 제안자, DART 제출인, Form D 관계자·서명·중개인·발행사 전화·거리 주소.
- 받는 규칙:
  - 같은 호스트 요청 사이는 1초를 띄운다. SEC는 0.2초다.
  - 민원빅데이터는 2분을 띄운다. 일시 오류 뒤 다시 시도할 때도, 명령 호출과 실행 사이에도 지킨다.
  - 하루 한도의 90%에서 멈춘다. 같은 날 앞 실행의 요청 수도 더한다.
  - 일시 오류는 한 번 더 시도한다.
  - 한도·간격 응답과 키 거부는 다시 시도하지 않는다. 그 실행에서 그 범위를 멈추고, 공공데이터포털은 서비스별로 멈춘다.
  - 요청 하나의 상한은 60초, 크기 상한은 16MB다.
  - robots는 소스 종류마다의 정책(4.2-3)으로 매번 본다.
- 실패 격리:
  - 소스가 실패해도 종료 코드는 0이다. 전용 DB를 열거나 쓰지 못하면 1이다.
  - 실행 전 사본은 14-1과 합쳐 실행마다 하나다.
- 스킬과 문서:
  - `/brief` 18-1단계(push 뒤, 요약 앞)와 0장 금지 줄
  - [판정 문서](../../demand-sources.md)의 공식 소스 절
  - [운영 문서](../../operations.md)의 "공식 수요(9.96단계)" 절과 "9.96단계 이전 코드로 돌아갈 때" 절
  - README 두 파일의 수요 신호 줄

## 제안 (범위 밖이라 하지 않은 것)

- 1372 한 달치 본문을 쪽마다 바로 압축한다. 그러면 메모리(약 75MB)와 저장 때의 동기 gzip(이벤트 루프 1~2초)을 줄인다.
- 요청 틀 `makeOfficialFetch`를 `src/feeds.ts`의 `makeFetchText`에 크기 상한 옵션으로 합친다.
- `dropFields`와 9.95 `dropAuthorFields`를 합친다.
- `demandStore`의 `getMeta`·`setMeta`를 이름이 겹치지 않게 바꾼다. 지금은 본 DB의 `src/issues.ts` 함수와 이름이 같다.
- 두 수요 명령(`demand-fetch`, `demand-official`)의 열기·사본·기록 뼈대를 공용 함수 하나로 모은다. 사본 책임도 전용 DB 열기 하나로 모은다.
- 소스별 스케줄 규칙(간격, 맨 앞에 받기, 지난 측정 시간)을 소스 정의의 칸으로 옮긴다. 앞 호출 결과 합치기는 상태 객체 하나로 한다.
- robots 요청 수가 같은 호스트의 첫 소스 묶음에만 잡힌다(1372 묶음의 robots 요청 수가 0으로 나온다). 묶음별 수 보고만 다르고 받기에는 영향이 없다.
