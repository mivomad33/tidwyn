# 2단계 명세서: 이어지는 이야기

- 작성일: 2026-10-28
- 요약: `/brief`가 저장한 뉴스를 이슈로 엮는다. 뉴스는 기존 이슈에 붙거나 새 이슈를 만들고, 이슈마다 지금까지 요약과 관련 이슈를 둔다. 브리프의 뉴스에는 이전 전개가 함께 나온다. 1단계 동안 쌓인 뉴스도 이슈에 붙이고, 7일마다 중복 이슈를 찾아 합친다. 잘못 합친 것은 명령으로 되돌린다.
- 종류: 변경 건 (1·1.5단계의 `/brief` 스킬, 저장, 백업, 마크다운, 실행 요약을 바꾼다. 실제 데이터가 이미 쌓이고 있다)
- 단계: [`docs/plan.md`](../../plan.md)의 2단계(이어지는 이야기). 1단계를 참조한다.
- 이 문서는 기획과 요구사항만 담는다. 설계(스키마, 라이브러리, 폴더 구조)와 작업 계획은 구현하는 AI가 정한다.
- 공개 여부: 원본 저장소는 3단계에서 공개된다(plan D2). 이 단계에서는 push하지 않는다. `data` 브랜치 백업과 코드는 나중에 공개되므로 공개되어도 되는 내용만 담는다.

## 1. 목표

- **지금 상태:** `/brief`는 날짜마다 뉴스를 조사해 DB에 쌓는다(1·1.5단계). 하지만 뉴스끼리 연결이 없다. 같은 사건의 어제 뉴스와 오늘 뉴스가 따로 놓이고, 브리프를 읽어서는 이전 전개를 알 수 없다. 2026-10-28에 첫 실제 실행으로 2026-10-27 브리프(주요 뉴스 17건, 짧은 소식 10건)가 `data/`에 저장되었고, 그 뒤로 사용자가 매일 실행한다.
- **바꾸려는 이유:** 시드가 꼽은 가장 큰 문제, "이어지는 이야기를 따라가지 못한다"를 푼다. 3단계(공개 사이트)의 이슈 페이지와 뉴스 카드의 이전 전개가 이 데이터를 그대로 쓴다.
- **쓰는 사람:** 프로젝트 주인 한 사람.
- **충분한 수준(I8):** 실제 데이터의 복사본에서 시험 실행을 한다. 그 결과로 다음 네 가지가 보여야 한다. 사용자는 마지막에 이슈 목록을 보고 묶음이 적절한지 판단한다(5장).
  - 모든 뉴스가 이슈에 연결된다.
  - 이미 쌓인 뉴스도 소급해서 연결된다.
  - 새로 수집한 날짜(2일 이상) 중 가장 늦은 날짜의 주요 뉴스 1건 이상이 기존 이슈에 붙는다.
  - 합치기가 1회 실행된다.

## 2. 확정된 결정과 제약

### 2.1 계획과 앞 단계에서 가져온 결정 (다시 묻지 않는다)

- plan D1~D14, 1단계 명세서의 S1~S14, 1.5단계 명세서의 R1~R7을 그대로 따른다. 특히 다음이다.
  - **D1:** 수집부터 백업까지 `/brief` 한 번 실행으로 이어진다. 백업은 DB 전체를 복원할 수 있어야 하고, 데이터를 더하는 단계는 그 데이터를 백업과 복원에 넣는다. 다시 돌려도 안전해야 한다(같은 연결을 두 번 저장하지 않는다).
  - **D4:** 사건 연결의 매개는 이슈다. 모든 뉴스는 하나 이상의 이슈에 속하고, 이슈끼리 관계를 가진다. 담는 항목은 시드 "데이터 설계" 표를 따르고, 스키마는 구현 재량이다. 표의 항목은 다음과 같다.
    - 이슈: 이름, 별칭 목록, 대분류·소분류, 시작일, 최근 업데이트일, 상태(진행 중·종료), 지금까지 요약
    - 뉴스-이슈 연결: 어떤 뉴스가 그 이슈의 몇 번째 전개인지
    - 이슈 관계: 관련 이슈
  - **D5:** 소분류는 정해진 목록(1단계 S3)에서만 고르고, 새로 만들면 표시를 남긴다. 연결할 때 기존 이슈 목록과 별칭을 먼저 읽는다. 주 1회 중복 이슈를 합친다(I3).
  - **D6:** 이슈 요약도 기사 문장을 바꿔 쓴다. 직접 인용은 15단어 미만이다.
  - **D7:** 이 단계는 유료 서비스가 필요 없어 비용 0원으로 한다.
  - **D14:** 매일 실행은 main 코드로만 한다(S12). 개발과 확인은 실제 DB의 복사본이나 테스트 DB로만 하고, 실제 `data/`와 `refs/heads/data`는 건드리지 않는다. DB 구조는 쌓인 데이터를 보존하는 마이그레이션으로 바꾼다.
  - **S9·S13:** 권한 건너뛰기 모드를 전제로 한다. 멈추면 그대로 끝낸다.
- **이슈별 지금까지 요약(시드 "이해를 돕는 기능"):** 5줄 안팎으로 무슨 일인지, 현재 상황, 핵심 인물·국가, 다음에 볼 것을 담는다. 새 뉴스가 붙을 때마다 고쳐 쓴다. 이 명세서는 이것을 "5줄 이하"로 검사한다(4.2-3).

## 3. 범위

### 넣는 것

- 이슈 데이터, 뉴스-이슈 연결, 이슈 관계, 합치기 기록의 저장과 마이그레이션(4.1)
- `/brief`의 연결 단계: 후보 이슈 목록과 이슈 검색, 연결 파일 검사, 적용, 실패 처리, 소급 연결(I1, 4.2)
- 7일마다 합치기와 되돌리기 명령(I3, I6, 4.3)
- 브리프 마크다운의 이전 전개, 이슈 마크다운과 목록, 실행 요약(I4, I5, 4.4)
- 백업과 복원에 이슈 데이터를 넣는 것(D1, 4.5)
- 스킬 문서와 운영 문서 갱신(4.6)
- 실제 데이터 복사본에서 시험 실행(I8, 4.7)

### 넣지 않는 것

- 사이트, 이슈 페이지 화면, push·배포: 3단계다.
- 인물·기관·국가, 용어, 일정, 지표: 4~6단계다(D9). 이슈 요약의 "핵심 인물·국가"는 요약 문장으로만 쓰고, 따로 데이터로 뽑지 않는다.
- 이미 수집한 날짜의 뉴스 내용(제목, 요약, 출처, 분류)을 다시 조사하거나 고치는 것: 이슈 연결만 더한다.
- 이슈를 나누는 기능(한 이슈를 둘로 쪼개기): 합치기 되돌리기(I6)로 충분한지 사용자가 써 본 뒤 정한다.
- 사용자가 이슈 이름·요약·연결을 손으로 고치는 명령: 요구가 생기면 다음 명세서에서 다룬다.
- 기간이 지나면 이슈를 자동 종료하는 것: I7.
- 데이터에 자연어로 질문하기: 9단계다.
- 1단계 report의 다른 개선 제안: 이 단계 범위 밖이다.

### 해당 없음

- 인증과 권한, 사용 분석, 사용자 입력의 남용 방지: 사용자도 화면도 없는 로컬 도구다. 웹 내용을 통한 지시 주입은 1단계 규칙을 그대로 따른다(4.6-1).
- 배포, 운영 중 관측: 3단계부터다. 실패는 실행 요약에 알린다(4.4-4).
- 예약 작업: 사용자가 직접 `/brief`를 실행한다. 합치기도 그 실행 안에서 한다(I3).
- 규모와 성능: 하루 뉴스 30~40건이라 1년이면 이슈가 수천 개다. 그래서 연결할 때 이슈를 모두 읽지 않게 한다(4.2-2). 그 밖의 성능 요구는 두지 않는다.
- 비용: 0원이다(D7).

## 4. 요구사항

요구사항마다 확인 방법을 붙인다. "자동 테스트"는 `pnpm verify`에 들어가는 테스트다. 자동 테스트는 네트워크를 쓰지 않고, 실제 `data/`를 읽지 않는다. 예시 데이터(이슈 이름, 뉴스 제목)는 지어내서 만든다. 저장소가 3단계에서 공개되기 때문이다(D2, D6).

**용어**

- **뉴스**: 저장된 주요 뉴스와 짧은 소식 모두를 말한다(D4).
- **연결**: 뉴스 한 건과 이슈의 관계다. 뉴스마다 주 이슈 연결이 정확히 하나 있고, 추가 이슈 연결은 0개 이상이다.
- **전개 순서**: 한 이슈에 연결된 뉴스의 순서다. 대상일, 섹션 순서(한국 → 세계 → IT·AI), 주요 뉴스 → 짧은 소식, 순위(짧은 소식은 위치) 순으로 정한다. 저장하지 않고 계산해도 된다(구현 재량).
- **연결 파일**: 한 날짜의 연결 결과를 Claude가 쓰는 작업 파일이다. 데이터 폴더의 `work/` 아래에 둔다.
- **합치기**: 이슈 하나(흡수되는 이슈)를 다른 이슈(남는 이슈)에 넣는 것이다.
- 데이터 폴더, 실제 DB, 실행 조건, 시험 모드는 1단계 명세서 4장 용어와 같다.

### 4.1 이슈 데이터와 저장

1. **이슈 항목:** 이슈마다 다음을 저장한다.
   - 고정된 식별자: 한 번 쓴 식별자는 다른 이슈에 다시 쓰지 않는다. 3단계 이슈 페이지 주소와 I6이 이 식별자에 기댄다.
   - 이름(한국어 짧은 명사구), 별칭 목록(다른 표기, 영어 이름, 하위 사건 이름 등. 0개 이상)
   - 대분류·소분류(D5, S3). 소분류가 S3 목록 밖이면 새 소분류 표시를 남긴다(1단계 뉴스와 같은 방식).
   - 상태(진행 중·종료), 지금까지 요약
   - 시작일과 최근 업데이트일: 연결된 뉴스의 가장 이른·늦은 대상일이다. 연결에서 계산해 Claude의 입력에 기대지 않는다(저장할지 계산할지는 구현 재량).
   - 확인: 자동 테스트로 이슈를 만들고 뉴스를 붙인 뒤 읽으면 위 항목이 나오고, 시작일·최근 업데이트일이 연결된 뉴스 날짜와 맞는다. 이슈를 합친 뒤 새로 만든 이슈의 식별자가 흡수된 이슈의 식별자와 다르다.
2. **연결과 관계:** 뉴스-이슈 연결(주 이슈 여부 포함)과 이슈 관계(두 이슈의 쌍, 방향 없음, 자기 자신과는 없음, 같은 쌍은 하나)를 저장한다. 같은 뉴스와 같은 이슈의 연결은 하나만 둔다.
   - 확인: 자동 테스트로 같은 연결이나 관계를 두 번 적용해도 하나만 남고, (A, B)와 (B, A)가 같은 관계로 저장된다.
3. **마이그레이션:** 이슈 데이터를 위한 마이그레이션을 더한다(1단계의 `PRAGMA user_version` 방식). 지금 형식(버전 2)의 DB를 열면 마이그레이션되고, 기존 브리프와 뉴스는 그대로 남으며 모두 "이슈 없음"이 된다.
   - 확인: 자동 테스트로 버전 2 스키마의 DB에 브리프를 넣고 새 코드로 열면 마이그레이션되고, 그 브리프를 그대로 읽으며, 모든 뉴스가 이슈 없음으로 나온다.
4. **브리프 저장과의 관계:** 이미 저장된 날짜를 다시 저장하는 기능은 없다(1단계). 1단계 저장·검사 동작은 바꾸지 않는다. 브리프 작업 파일 형식에 이슈 항목을 더하지 않는다(연결은 연결 파일이 맡는다, I1).
   - 확인: 1단계·1.5단계 테스트가 통과한다(4.8-1).

### 4.2 연결 단계 (I1, I2, I7)

1. **실행 순서:** 연결 단계는 `/brief`에서 다음 순서로 돈다.
   - 시작(`start`)을 마친 뒤, 새 날짜를 조사하기 전에 "이슈가 없는 뉴스가 있는 저장된 날짜"를 오래된 날부터 연결한다. 1단계 동안 쌓인 뉴스와 지난 실행에서 연결이 실패한 날짜가 여기에 든다.
   - 새 날짜마다 저장(`save`)이 성공한 직후 그 날짜를 연결한다.
   - 연결은 날짜 단위다. 한 날짜의 연결 파일이 검사를 통과하면 그 날짜의 연결, 새 이슈, 요약, 관계, 상태 변경을 한 번에 적용한다. 통과하지 못하면 아무것도 적용하지 않는다.
   - 확인: 스킬 문서(4.6-1)에 이 순서와 각 단계가 부르는 명령이 있다(읽어서 확인). 4.7 시험 실행에서 이 순서대로 진행된다.
2. **후보 이슈 목록과 검색:** 날짜마다 연결하기 전에, 스크립트 명령이 그 날짜의 연결할 뉴스와 후보 이슈 목록을 데이터 폴더의 `work/` 아래 파일로 쓴다.
   - 연결할 뉴스: 그 날짜에서 이슈가 없는 뉴스. 뉴스마다 연결 파일에서 가리킬 키, 섹션, 종류, 제목(짧은 소식은 요약), 분류를 보인다.
   - 후보 이슈: 최근에 업데이트된 이슈다(기간은 AI 재량). "최근"은 대상일이 아니라 DB의 가장 늦은 대상일을 기준으로 재고, 대상일보다 뒤에 업데이트된 이슈도 넣는다(연결 실패 뒤 다시 연결, 4.7-2 다). 이슈마다 식별자, 이름, 별칭, 분류, 상태, 시작일·최근 업데이트일, 최근 전개 몇 건(날짜·제목), 요약의 앞부분을 보인다. 이슈가 늘어나도 목록 길이가 이슈 전체 수에 비례해 커지지 않게 한다. 목록에 없는 오래된 이슈와 종료된 이슈는 검색 명령으로 찾는다.
   - 검색 명령: 낱말로 이슈의 이름과 별칭(요약을 넣을지는 AI 재량)을 찾아, 후보 목록과 같은 형식으로 출력한다.
   - 확인:
     - 자동 테스트로 최근 이슈와 오래된 이슈(예: 100개)를 만든 DB에서 목록에 최근 이슈만 나온다.
     - 오래된 이슈는 이름이나 별칭 낱말로 검색하면 나온다.
     - 이슈가 없는 뉴스만 연결할 뉴스로 나온다.
3. **연결 파일과 검사:** Claude는 연결 파일에 다음을 쓴다.
   - 뉴스마다 주 이슈 하나와 추가 이슈(0개 이상): 기존 이슈의 식별자나, 같은 파일에서 만드는 새 이슈.
   - 새 이슈: 이름, 별칭, 대분류·소분류, 지금까지 요약
   - 이번에 뉴스가 붙는 기존 이슈마다 고쳐 쓴 지금까지 요약(시드: 새 뉴스가 붙을 때마다 고쳐 쓴다)
   - 상태 변경(I7: 종료로 바꿀 이슈)과 이슈 관계 추가

   스크립트 명령이 연결 파일을 검사하고, 위반마다 위치와 이유를 보인다. 거부할 경우는 다음과 같다.
   - 연결할 뉴스가 빠졌거나 두 번 나온다. 그 날짜에 없는 뉴스를 가리킨다.
   - 주 이슈가 없거나 둘 이상이다. 같은 뉴스에 같은 이슈가 두 번 나온다.
   - 없는 이슈 식별자나 흡수된 이슈를 가리킨다(흡수된 이슈를 가리키면 이유에 남는 이슈를 알린다).
   - 새 이슈에 이름이나 요약이 없다. 대분류가 7개 밖이다. 이슈 관계가 자기 자신을 가리킨다.
   - 새 이슈의 이름이나 별칭이 기존 이슈(흡수된 이슈 제외)나 같은 파일의 다른 새 이슈의 이름·별칭과 같다. 대소문자와 공백은 무시하고 비교한다. 이유에 그 기존 이슈를 알려 붙이게 한다. D5의 중복 생성을 기계적으로 막기 위해서다.
   - 뉴스가 붙는 기존 이슈에 고쳐 쓴 요약이 없다.
   - 요약이 비었거나 6줄 이상이다(줄은 줄바꿈으로 나눈 빈 줄 아닌 줄).
   - 요약이나 이름에 15단어 이상의 직접 인용이 있다(D6. 1단계의 인용 검사를 다시 쓴다).
   - 상태 값이 진행 중·종료 밖이다.
   - 확인: 자동 테스트로 위 거부 경우마다 틀린 연결 파일이 거부되고 위치와 이유가 나온다. 올바른 연결 파일은 통과한다.
4. **적용:** 검사를 통과한 연결 파일을 적용하는 명령은 적용 전에 같은 검사를 한 번 더 한다. 적용하면서 다음이 함께 일어난다.
   - 종료된 이슈에 후속 뉴스(대상일이 그 이슈의 최근 업데이트일과 같거나 뒤인 뉴스)가 붙으면 진행 중으로 바꾼다. 앞선 날짜의 뉴스만 붙으면 상태를 바꾸지 않는다(I7, 4.2-6). 같은 파일이 그 이슈를 다시 종료로 바꾸면 종료가 이긴다.
   - 브리프 마크다운과 이슈 마크다운을 새 데이터로 다시 만든다(4.4).
   - 같은 날짜를 다시 적용해도(이미 연결된 뉴스) 연결이 두 번 생기지 않는다(D1). 재실행 때는 이슈가 없는 뉴스만 다룬다.
   - 확인: 자동 테스트로 다음을 본다.
     - 연결 파일을 적용하면 뉴스 연결, 새 이슈, 요약, 관계, 상태가 저장된다.
     - 종료 이슈에 후속 뉴스를 붙이면 진행 중이 되고, 같은 파일이 종료로 바꾸면 종료로 남는다. 앞선 날짜의 뉴스만 붙이면 종료로 남는다.
     - 같은 파일을 두 번 적용하면 두 번째는 바뀌는 것이 없다.
     - 검사에 실패하는 파일을 적용하면 DB가 바뀌지 않는다.
5. **고쳐서 다시 검사와 실패:** 위반이 나오면 Claude가 연결 파일을 고쳐 다시 검사한다. 날짜마다 최대 2번이다(1단계 4.2와 같다). 그래도 위반이 남으면 그 날짜의 연결은 적용하지 않고 실행 기록에 실패로 남긴다. 뉴스는 저장된 채로 두고, 다음 실행이 다시 연결한다(I1). 연결 실패는 그 실행의 다른 날짜, 백업, 요약을 멈추지 않는다.
   - 확인: 자동 테스트로 연결 실패를 기록한 실행의 요약에 실패한 날짜와 남은 위반이 나오고, 그 날짜의 뉴스가 저장된 채로 이슈 없음으로 남아 다음 실행의 연결 대상에 든다.
6. **연결 기준(스킬 문서):** 스킬 문서에 다음 판단 기준을 적는다.
   - 이슈 크기는 이어지는 사건 단위다(I2). 큰 주제(예: 중동 정세)나 한 번의 회담 같은 개별 사건으로 만들지 않는다.
   - 단발성 뉴스는 한 건짜리 새 이슈로 만든다.
   - 새 이슈를 만들기 전에 후보 목록을 읽고 검색 명령으로 이름·별칭·핵심 낱말을 찾아 본다.
   - 주 이슈는 그 뉴스가 가장 직접 이어지는 이야기다. 추가 이슈는 그 뉴스가 다른 이슈에도 뚜렷한 새 전개일 때만 붙인다.
   - 이슈 관계는 한 이슈의 전개가 다른 이슈에 영향을 주는 경우에 붙인다(예: 미국-이란 갈등 ↔ 국제 유가).
   - 종료 기준은 I7을 따른다.
   - 붙는 뉴스가 그 이슈의 최근 업데이트일보다 앞이면(연결 실패 뒤 다시 연결, 시험 실행 4.7-2 다), 요약의 현재 상황은 최신 전개 기준으로 두고 그 뉴스는 경과에만 반영한다. 종료로 바꾸는 것은 그 뉴스가 이슈의 가장 최근 전개일 때만이다.
   - 요약은 5줄 이하로(검사가 6줄 이상을 거부한다. 스킬 문서에도 "5줄 이하"로 적는다) 무슨 일인지, 현재 상황, 핵심 인물·국가, 다음에 볼 것을 담는다. 기사 문장을 바꿔 쓴다(D6). 붙은 뉴스와 기존 요약에 없는 사실을 지어내지 않는다.
   - 이슈 이름은 한국어 짧은 명사구로 쓰고, 다른 표기는 별칭에 넣는다.
   - 확인: 스킬 문서에 위 기준이 있다(읽어서 확인).

### 4.3 합치기와 되돌리기 (I3, I6)

1. **주기:** 마지막 합치기 점검일(처음에는 첫 연결 적용일)에서 7일이 지났으면, `/brief`가 그 실행의 연결이 모두 끝난 뒤 백업 전에 합치기를 한다. 점검을 마치면(합친 것이 없어도) 점검일을 그 실행의 날짜로 바꾼다. 합치기 검사가 2번 고쳐도 실패하면 점검일을 바꾸지 않아, 다음 실행이 다시 한다.
   - 확인: 자동 테스트로 점검일에서 6일 뒤에는 합치기 단계가 "할 일 없음"이고 7일 뒤에는 "할 일 있음"이다. 합친 것이 없어도 점검일이 바뀌고, 검사 실패로 끝나면 바뀌지 않는다.
2. **후보 뽑기:** 스크립트 명령이 비슷한 이슈 쌍 후보를 데이터 폴더의 `work/` 아래 파일로 쓴다. 쌍마다 두 이슈의 이름, 별칭, 분류, 기간, 전개 목록, 요약을 담는다. 비슷함을 정하는 방법(이름·별칭의 낱말 겹침, 분류, 기간 등)은 AI 재량이다. 흡수된 이슈와, 되돌려서 "합치지 않음"이 된 쌍(I6)은 후보에서 뺀다.
   - 확인: 자동 테스트로 이름이 거의 같은 두 이슈가 후보에 나오고, 관계없는 이슈 쌍과 "합치지 않음" 쌍은 나오지 않는다.
3. **합치기 파일과 적용:** Claude는 같은 이야기라고 판단한 쌍마다 남는 이슈, 흡수되는 이슈, 이유, 남는 이슈의 고쳐 쓴 요약을 합치기 파일에 쓴다. 판단 기준(I2의 이어지는 사건 단위로 같은 이야기인지)은 스킬 문서에 적는다. 스크립트가 검사하고 적용한다. 적용하면 다음이 일어난다.
   - 흡수되는 이슈의 연결을 남는 이슈로 옮긴다. 한 뉴스가 두 이슈에 모두 붙어 있으면 하나로 줄이고, 둘 중 하나가 주 이슈였으면 남는 이슈가 주 이슈가 된다.
   - 흡수되는 이슈의 이름과 별칭을 남는 이슈의 별칭에 더한다.
   - 관계를 옮긴다. 자기 자신과의 관계와 겹치는 관계는 없앤다.
   - 상태는 둘 중 하나라도 진행 중이면 진행 중이다.
   - 흡수된 이슈는 지우지 않고 "흡수됨"과 남는 이슈를 가리키게 둔다. 식별자를 다시 쓰지 않고(4.1-1), 3단계에서 옛 주소를 새 이슈로 보낼 수 있게 한다.
   - 합치기 기록에 날짜, 두 이슈, 이유, 합치기 전 상태(I6에 필요한 것 전부)를 남긴다.
   - 한 번의 합치기 안에서 이슈가 연달아 흡수되는 경우(A→B, B→C)도 처리하거나, 검사에서 거부한다(방법은 AI 재량).
   - 검사에서 거부할 경우: 없는 이슈, 이미 흡수된 이슈, 같은 이슈끼리, 이유나 요약이 없음, 요약 규칙 위반(4.2-3과 같다).
   - 확인: 자동 테스트로 위 적용 결과(연결 이동과 중복 정리, 주 이슈 유지, 별칭 추가, 관계 정리, 상태, 흡수 표시, 기록)가 맞고, 거부 경우마다 거부되며, 거부된 파일은 DB를 바꾸지 않는다.
4. **되돌리기 명령:** 합치기 기록 하나를 골라 되돌리는 스크립트 명령을 둔다. 사용자가 직접 실행한다. `/brief`는 이 명령을 실행하지 않는다.
   - 흡수된 이슈를 되살린다. 합치기 전의 이름, 별칭, 분류, 상태, 요약, 연결, 관계로 되돌린다.
   - 남는 이슈는 합치기 전의 별칭, 연결, 관계로 되돌린다. 단, 그 합치기 뒤에 남는 이슈에 더해진 것(새로 붙은 연결과 관계, 다른 합치기로 더해진 별칭·연결·관계)은 그대로 둔다.
   - 남는 이슈의 요약과 상태는 그 합치기 뒤 남는 이슈에 더해진 것이 없으면 합치기 전 값으로 되돌리고, 있으면 지금 값을 둔다(흡수됐던 이슈의 내용이 남을 수 있고, 다음에 뉴스가 붙을 때 고쳐 쓰인다).
   - 되살린 관계의 상대 이슈가 그사이 다른 이슈에 흡수됐으면 그 남는 이슈를 가리키게 한다(자기 자신이 되면 뺀다).
   - 되돌린 뒤에도 뉴스마다 주 이슈는 정확히 하나다. 겹치면(예: 뉴스가 A의 주 이슈, C의 추가 이슈였고 A→B, C→B 뒤 A→B만 되돌림) 되살린 이슈의 합치기 전 연결이 주 이슈가 되고, 남는 이슈의 연결은 추가 이슈로 남는다.
   - 그 쌍을 "합치지 않음"으로 기록한다.
   - 그 합치기 뒤에 남는 이슈가 다시 다른 이슈에 흡수되었으면, 거부하고 먼저 되돌릴 합치기를 알린다.
   - 실제 데이터 폴더를 쓸 때는 1단계의 실행 조건(S12)을 따르고, 바꾸기 전에 DB 사본을 남긴다(1단계 실행 전 사본과 같은 곳, 같은 보관 규칙). 끝나면 마크다운을 다시 만든다. 백업은 다음 `/brief` 실행이 한다.
   - 이미 되돌린 합치기를 다시 되돌리려 하면 거부한다. "그 뒤 다시 흡수됨" 판정에서 되돌린 합치기는 세지 않는다.
   - 합치기 기록 목록을 보는 방법(명령 출력이나 이슈 목록 파일)을 둔다.
   - 확인: 자동 테스트로 다음을 본다.
     - 합친 뒤 되돌리면 두 이슈가 합치기 전과 같아진다.
     - 합친 뒤 남는 이슈에 새 뉴스를 붙이고 되돌리면, 새 연결은 남는 이슈에 남는다.
     - A→B 뒤 C→B를 합치고 A→B만 되돌리면, C에서 온 별칭과 연결이 B에 남는다. 그 경우에도 모든 뉴스의 주 이슈가 정확히 하나다.
     - 되돌린 쌍은 다음 후보에 나오지 않는다.
     - 연달아 합쳐진 경우의 거부가 동작한다.
     - 실제 데이터 폴더 조건을 어기면(임시 git 저장소의 다른 브랜치) 거부되고 DB가 바뀌지 않는다.

### 4.4 마크다운과 실행 요약 (I4, I5)

1. **브리프 마크다운의 이전 전개(I5):**
   - 주요 뉴스마다 주 이슈 이름(그 이슈 마크다운으로 가는 상대 링크)과, 그 이슈에서 이 뉴스보다 앞선 전개 최대 3건(가까운 것부터, 날짜·제목(짧은 소식은 요약), 그 날짜 브리프로 가는 링크)을 보인다.
   - 앞선 전개가 없으면 "새 이슈"로 표시한다. 추가 이슈가 있으면 이름만 함께 보인다.
   - 짧은 소식에는 주 이슈 이름(링크)만 보인다.
   - 이슈가 없는 뉴스는 지금(1·1.5단계)과 같게 보인다.
   - "앞선 전개"는 전개 순서로 이 뉴스보다 앞인 것이다. 그래서 오래된 날짜의 브리프는 그 날짜 기준의 이전 전개를 보인다.
   - 확인: 자동 테스트로 다음을 본다.
     - 앞선 전개 4건이 있는 이슈의 뉴스에 가까운 3건이 나온다.
     - 첫 전개인 뉴스에 "새 이슈"가 나온다.
     - 짧은 소식에 이슈 이름만 나온다.
     - 이슈가 없는 브리프의 마크다운은 1단계 예시(`test/fixtures/brief-2026-10-27.md`)와 같다.
2. **이슈 마크다운과 목록(I4):** 데이터 폴더의 `issues/` 아래에 다음을 둔다.
   - 이슈마다 파일 하나: 이름, 별칭, 분류, 상태, 시작일·최근 업데이트일, 지금까지 요약, 타임라인(전개 순서로 날짜, 섹션, 제목이나 요약, 대표 출처 링크(대표 출처가 없는 짧은 소식은 첫 출처), 그 날짜 브리프 링크), 관련 이슈(링크)
   - 흡수된 이슈의 파일: 남는 이슈로 가는 링크와 합친 날짜만 담는다.
   - 목록 파일 하나: 진행 중 이슈를 최근 업데이트일 순으로, 이어서 종료된 이슈를 보인다. 이슈마다 이름, 분류, 전개 수, 기간을 보인다. 최근 합치기 기록(되돌리기 명령에 쓸 값 포함)도 보인다.
   - 마크다운은 DB만으로 만든다. 연결 적용, 합치기, 되돌리기, 복원 뒤에 영향을 받는 이슈 마크다운과 브리프 마크다운(이슈 이름과 앞선 전개가 바뀌기 때문이다)을 다시 만든다(모두 다시 만들어도 된다). 같은 DB에서는 같은 내용이 나온다.
   - 확인: 자동 테스트로 다음을 본다.
     - 이슈 둘과 뉴스 셋인 예시 DB에서 이슈 파일과 목록 파일의 내용이 기대 예시 파일과 같다.
     - 합친 뒤 흡수된 이슈 파일이 남는 이슈를 가리킨다.
     - 같은 DB로 두 번 만들면 내용이 같다.
3. **대화창 출력:** 실행 요약이 보여 주는 가장 최근 브리프 마크다운에 이전 전개가 들어간다(4.4-1을 따르므로 따로 만들지 않는다).
   - 확인: 4.7 시험 실행의 요약 출력에 이전 전개가 보인다.
4. **실행 요약에 더할 것:** 1단계·1.5단계 요약 내용은 그대로 두고 다음을 더한다.
   - 연결한 날짜마다 연결한 뉴스 수, 기존 이슈에 붙은 뉴스 수, 새로 만든 이슈 수
   - 연결에 실패한 날짜와 남은 위반, 아직 이슈가 없는 뉴스 수
   - 합치기를 했으면 합친 쌍(남는 이슈, 흡수된 이슈, 이유)과 되돌리는 명령. 점검했는데 합친 것이 없으면 그렇다고 보인다. 합치기 검사가 2번 고쳐도 실패했으면 남은 위반과, 다음 실행이 다시 한다는 것을 보인다.
   - 이슈 목록 파일의 경로
   - 확인: 자동 테스트로 위 경우마다 요약에 해당 줄이 나오고, 1단계 요약 테스트가 통과한다.

### 4.5 백업과 복원 (D1)

1. **백업에 넣는 것:** 이슈, 연결, 관계, 합치기 기록(합치기 전 상태 포함), "합치지 않음" 쌍, 마지막 합치기 점검일을 백업 JSON에 넣는다. 백업만으로 DB 전체를 다시 만들 수 있어야 한다. 이슈 데이터는 날짜에 묶이지 않으므로 파일을 어떻게 나눌지는 AI 재량이다(월별 파일과 따로 두어도 된다). 백업은 날짜와 식별자 순서로 정렬해, 바뀐 것이 없으면 내용도 같게 한다. 이슈 데이터가 하나도 없는 DB의 백업은 형식 버전 숫자 말고는 지금과 같은 파일과 키를 낸다(빈 이슈 파일이나 빈 값 키를 쓰지 않는다). 그래야 기존 백업 테스트(`test/backup.test.ts`의 파일 목록·meta.json 단언)가 4.8-1 범위 안에서 통과한다.
   - 확인: 자동 테스트로 이슈·연결·관계·합치기 기록(되돌린 것 포함)이 있는 DB를 백업하고 빈 곳에 복원하면 같은 데이터가 나오고, 같은 DB를 두 번 백업하면 파일 내용이 같다.
2. **이전 형식:** 형식 버전을 올린다. 이전 형식(버전 1) 백업도 복원되고, 그 경우 모든 뉴스가 이슈 없음이 된다(다음 실행이 연결한다, I1).
   - 확인: 자동 테스트로 형식 버전 1 백업 예시가 복원되고, 뉴스가 이슈 없음으로 나온다.
3. **복원 뒤 마크다운:** 복원 명령으로 DB를 만들면 브리프와 이슈 마크다운을 다시 만들 수 있다(복원 명령이 함께 하거나, 다음 실행이 만든다. 방법은 AI 재량이고 운영 문서에 적는다).
   - 확인: 자동 테스트로 복원한 데이터 폴더에서 정한 방법대로 하면 이슈 마크다운이 생긴다.

### 4.7 시험 실행으로 끝난 상태 확인 (I8)

1. **복사본 준비:** 실제 `data/tidwyn.db`를 읽기만 해서 `.test-data/` 아래 새 시험 데이터 폴더에 파일로 복사한다(마이그레이션 전 형식 그대로여야 4.8-4를 시험 실행이 보일 수 있다). `data` 브랜치 백업 복원은 DB 파일이 없을 때만 쓰고, 그때는 4.8-4를 시험 실행이 대신 보이지 못했다고 보고서에 적는다. 실제 `data/`와 `refs/heads/data`에는 아무것도 쓰지 않는다. 시험 폴더를 가리키는 방법(1단계의 데이터 폴더 지정 환경 변수, 시험 모드 확장 등)은 AI 재량이다. 단, 그 방법이 실제 데이터 폴더를 가리키면 1단계처럼 실제 실행으로 판정되어야 하고, 이 저장소의 `data` 브랜치에 커밋하지 않아야 한다.
   - 확인: 시험 폴더의 DB에 실제 DB와 같은 날짜가 있다(조회). 실행 설정 출력에 시험 폴더와 "커밋 안 함"(또는 이 저장소가 아닌 백업 저장소)이 나온다.
2. **새로 수집할 날짜 정하기:** 소급 연결(4.7-3) **전에** 복사본에서 새로 수집할 날짜가 2일 이상 되게 맞춘다. 아래 순서로 처음 맞는 것을 쓴다. 바꾸는 것은 모두 복사본뿐이다(실제 DB가 아니므로 허용한다. 방법은 AI 재량).
   - 가. 복사본의 가장 최근 저장일 다음 날부터 KST 어제까지 빠진 날짜가 2일 이상이면 그대로 둔다. 빠진 날짜를 모두 수집한다.
   - 나. 아니고 복사본의 저장일이 2일 이상이면, 가장 최근 저장일부터 복사본에서 지워 빠진 날짜를 2일 이상으로 만든다. 저장일은 1일 이상 남긴다. 남길 수 없으면 다로 간다.
   - 다. 그 밖(예: 저장일이 2026-10-27 하루뿐이고 빠진 날짜가 2일 미만)이면 지우지 않는다. 복사본의 첫 수집일 기록을 가장 이른 저장일보다 이틀 앞으로 옮겨, 그 앞의 두 날짜를 수집 대상으로 만든다. 이때 새 날짜가 기존 뉴스보다 앞이므로, 전개 순서상 새 뉴스가 기존 이슈의 앞쪽 전개가 된다. 가장 최근 저장일 뒤에 빠진 날짜가 있으면 그것도 함께 모은다(대상 날짜 계산을 그대로 따른다).
   - 확인: 보고서에 가~다 중 어느 것을 썼는지와 새로 수집할 날짜가 있다. 소급 연결 전에 복사본의 저장일이 1일 이상이다(조회).
3. **소급 연결:** 복사본에서 `/brief` 흐름을 따라 이슈가 없는 저장된 뉴스를 모두 연결한다.
   - 확인: 복사본의 모든 저장된 뉴스가 주 이슈를 하나씩 가진다(조회).
4. **새 날짜 수집:** 스킬 문서대로 4.7-2에서 정한 날짜를 오래된 날부터 수집·저장·연결한다. 뉴스 조사는 1.5단계 방식 그대로다.
   - 확인: 새 날짜가 저장되고 모든 뉴스가 연결된다. 새 날짜 중 가장 늦은 날짜의 주요 뉴스 1건 이상이, 그 날짜를 연결하기 전에 있던 이슈(소급 연결이나 앞 날짜가 만든 이슈)에 붙는다(조회. 보고서에 그 뉴스와 이슈를 적는다). 요약 출력의 브리프에 이전 전개 표시(앞선 전개나 "새 이슈")가 나온다.
5. **합치기 1회:** 복사본의 마지막 합치기 점검일을 7일 전으로 두거나(복사본만) 합치기 단계를 직접 불러 1회 실행한다. 합칠 것이 없으면 그 결과(후보와 Claude의 판단)를 보고서에 적는다.
   - 확인: 합치기 기록이나 "합친 것 없음" 점검 기록이 남는다(조회). 합친 것이 있으면 합친 뒤의 시험 폴더를 다른 시험 폴더로 복사하고, 그 복사본에서 되돌리기 명령을 1회 실행해 되돌아가는지 본다. 사용자가 보는 시험 폴더(5장)는 합친 상태로 둔다.
6. **기준 미달:** 위 확인을 통과하지 못하면 원인을 보고 스킬 문서나 명령을 고쳐 다시 한다. 시험 실행(2~5)은 최대 3번이다. 다시 할 때는 4.7-1의 새 복사본부터 시작한다. 3번 모두 못 넘으면 구현을 끝내되 보고서에 "기준 미달"과 회마다의 결과, 원인, 시도한 것을 적는다.
   - 확인: 보고서에 시험 실행 횟수와 회마다의 결과가 있다.

### 4.8 기존 기능 유지와 실제 데이터 보호

1. **기존 테스트:** 1단계·1.5단계 테스트가 통과한다. 1단계·1.5단계 테스트에서 허용하는 변경은 다음뿐이다.
   - 스키마 버전·백업 형식 버전 숫자에 묶인 단언과, 그 숫자를 쓰는 테스트 준비 줄(테스트용 마이그레이션 번호, `test/backup.test.ts`의 "모르는 형식 버전" 테스트가 바꿔 넣는 버전 문자열 등)을 새 버전에 맞게 고치는 것
   - 새 테스트를 기존 테스트 파일에 더하는 것과, 그에 필요한 import 줄 변경
   - 확인: `git diff main -- test/`에서 기존 줄의 변경이 위 두 가지뿐이다.
2. **실제 데이터:** 구현 중에는 실제 `data/`에 쓰지 않고(4.7-1의 읽기는 허용), `refs/heads/data`를 바꾸지 않는다. 테스트는 임시 폴더만 쓴다.
   - 확인: 구현을 시작할 때 `data/tidwyn.db`의 해시와 `git rev-parse refs/heads/data`를 진행 기록에 적고, 끝날 때 다시 본다. 다르면 `data/runs/`의 실행 기록으로 사용자의 실제 실행이 바꾼 것인지 확인해 보고서에 적는다. 구현하는 AI가 바꾼 것이면 보류로 적는다.
3. **커밋하는 파일의 경로:** 보고서, 진행 기록, 스킬·운영 문서, 테스트 기대 파일에는 홈 폴더 절대 경로(`/Users/...`)를 쓰지 않고 프로젝트 기준 상대 경로만 쓴다. `start`가 출력하는 절대 경로를 옮길 때도 상대 경로로 바꾼다. 이슈·합치기 데이터와 백업 JSON에도 절대 경로를 넣지 않는다. 저장소가 3단계에서 공개되기 때문이다(1단계 4.6-3과 같다).
   - 확인: 마지막 커밋에서 `git grep -n "/Users/"`가 비어 있다.
4. **머지 뒤 첫 실제 실행:** 머지 뒤 사용자의 첫 실제 `/brief`가 실제 DB를 마이그레이션하고 쌓인 뉴스를 모두 소급 연결할 수 있어야 한다. 실행 전 사본(1단계)이 마이그레이션 전에 남는다.
   - 확인: 4.7 시험 실행이 실제 DB 복사본(마이그레이션 전 형식)에서 시작해 이것을 대신 보인다. 새 자동 테스트로 버전 2 스키마의 DB가 있는 데이터 폴더에서 `start`를 실행하면, 실행 전 사본은 버전 2이고 DB는 새 버전이다(지금의 실행 전 사본 테스트는 최신 버전 DB에서 돌아 이것을 보지 않는다).

## 5. 완료 정의

### AI가 확인하고 끝낸다

- `pnpm verify`가 통과한다.
- 4장의 모든 확인이 통과한다(4.7-6으로 끝낸 경우는 보고서에 미달을 적는다).
- `package.json`의 `dependencies`가 없거나 비어 있다(1단계처럼 런타임 의존성이 없다).
- 명세서 폴더에 `report.md`를 쓴다. 다음을 담는다.
  - 바꾼 것과 새 명령 사용법(연결, 검색, 합치기, 되돌리기)
  - 시험 실행 결과: 시험 데이터 폴더 경로, 소급 연결한 뉴스 수, 새로 수집한 날짜 목록, 기존 이슈에 붙은 뉴스의 예, 이슈 수(새로 만든 것, 한 건짜리 이슈 비율), 합치기 결과
  - 4.8-2의 실제 데이터 확인 결과, 남은 한계

### 사용자가 마지막에 확인한다

1. 보고서에 적힌 시험 데이터 폴더의 `issues/` 목록 파일과 이슈 파일 몇 개를 읽고, 이슈 크기와 묶음이 적절한지 본다(I2, I8). 같은 이야기가 여러 이슈로 쪼개졌거나, 다른 이야기가 한 이슈에 섞였는지 본다.
2. 시험 데이터 폴더의 새 날짜 브리프 마크다운에서 이전 전개(I5)가 읽기에 도움이 되는지 본다.
3. 합친 이슈가 있었으면 합치기 기록과 이유가 납득되는지 본다.

## 7. 진행 규칙

- **작업 브랜치:** `spec/stage2-issues`. 이 명세서를 쓴 브랜치에서 이어서 구현한다. main 머지는 사용자 확인 뒤 사용자가 승인하면 squash merge로 한다(CLAUDE.md). push하지 않는다.

### 사전 승인

- 실제 `data/tidwyn.db`를 읽어 `.test-data/` 아래로 복사하거나, `refs/heads/data`의 백업을 읽어 `.test-data/` 아래에 복원한다(읽기만 한다).
- `.test-data/` 아래 시험 폴더를 만들고, 그 안의 데이터를 바꾸거나 지운다(4.7-2의 날짜 지우기와 첫 수집일 기록 옮기기, 4.7-5의 합치기 점검일 바꾸기). 시험 폴더는 끝난 뒤 지우지 않아도 된다.
- 시험 실행에서 1.5단계 피드 주소에 읽기 요청(GET)을 보내고, 웹 검색과 웹 페이지 읽기 도구를 쓴다(1.5단계 사전 승인과 같은 범위).

### 멈추고 물을 것

구현 중에는 사용자에게 묻지 않는다. 아래에 해당하면 그 부분은 하지 않고 보고서에 적고 끝낸다.

- 실제 `data/`에 쓰거나 `refs/heads/data`를 바꿔야만 확인할 수 있는 것이 생긴다(하지 않는다).
- 유료 서비스, 계정, API 키가 필요해진다.
- plan의 결정(D1~D14), 앞 단계 명세서의 결정(S1~S14, R1~R7), 이 명세서의 I1~I8을 바꿔야 한다.
- 1단계 브리프 작업 파일 형식이나 검사 규칙을 바꿔야 한다(4.1-4).
