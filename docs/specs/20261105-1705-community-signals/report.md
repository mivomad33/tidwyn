## 만든 것

- **커뮤니티 받기**(`node src/cli.ts demand-community`, `/brief` 14-1-1단계): 그날 공식 소스에서 오른 단위의 이름(Wikimedia 문서 이름, 1372 품목 중분류)을 검색어로 고른다. 하루 20개까지이고, 외부인 글 소스와 분류 이름 소스는 빼며, 같은 이름은 한 번만 쓴다. 그 검색어로 GitHub Issues 검색(`total_count`)과 Bluesky `searchPosts`(`hitsTotal`)의 최근 7일·앞 28일 건수를 센다. 건수와 상태만 전용 DB(`demand.db`의 `community_terms`·`community_counts`·`community_status`)에 쌓고, 글·제목·작성자는 받지 않는다. 명령 전체에 6분 상한이 있고, robots·간격·다시 하기 규칙을 지킨다.
- **판정**: 최근 값이 하한 이상이면서 앞 창의 비율로 2배 이상(또는 새로 나타남)이면 오른 것으로 본다. 하한은 GitHub 10, Bluesky 50이다. 첫 쪽에서 한 저장소·계정이 절반을 넘으면 쏠림으로 빼고, Bluesky 상한(1만)에 닿은 값도 뺀다.
- **흐름 인정**(S1): 예전처럼 공식 묶음 둘 이상이거나, 공식 묶음 하나와 그 공식 단위를 검색어로 한 오른 커뮤니티 단위가 있으면 인정한다. 공식 하나 + 커뮤니티인 흐름은 수준이 최고 '중'이다. 공식 묶음이나 커뮤니티 단위가 하한의 2배 미만이면 '약'이다. 기준 부족과 받지 못함은 S1대로 가른다. 같은 흐름에 14일 안에 새 커뮤니티 소스가 더해지면 같은 id로 다시 싣는다(S8).
- **꺾임**(S7): 마지막 3일의 같은 요일 비가 앞 4일보다 낮으면 '꺾임'을 표시한다.
- **사이트**: 수요 탭의 흐름에 커뮤니티 근거 줄(소스, 검색어였던 공식 단위 이름, 두 창 숫자, 창 기간)과 꺾임을 보여 준다. 커뮤니티를 받지 못한 날은 안내한다. 소개에 소스별 표본 설명과 분야×소스 사각지대 표(`src/demandCoverage.ts`)를 더했다.
- **백업**: 본 DB 마이그레이션 14와 공개 백업 형식 10에 커뮤니티 근거 줄과 꺾임 표시가 들어간다. 형식 9 백업도 복원된다. 받은 건수는 공개 백업에 넣지 않는다.
- **문서**: `docs/demand-sources.md`(소스·질의·기준), `docs/operations.md`, `/brief` 스킬, `docs/design.md`, README 두 파일.
- 끄기: `TIDWYN_DEMAND_OFF`에 `github:issues`·`bluesky:posts`를 넣거나 묶음(`github`, `bluesky`)을 넣으면 그 소스를 받지 않는다. 그러면 흐름 규칙은 9.97과 같아진다.

- 실린 흐름은 12건이다. 모두 '관심' 갈래이고 모두 커뮤니티 확인 흐름(공식 한 곳 + 커뮤니티)이다. 분야는 엔터테인먼트 5, 미디어 3, 스포츠 2, 소프트웨어 2다. 수준은 중 10, 약 2다. 꺾임은 4건이다. 커뮤니티 근거는 12건 모두 Bluesky이고, GitHub는 2건에 함께 들었다. 버린 흐름은 없고 이어진 흐름은 0건이다.
- **0건인 날**: 2/10이다. 9.97 실측은 10/10이었다. **4건 이상 인정된 날**: 0/10이다.
- **갈래 치우침**: 12건 모두 관심 갈래다. 검색어가 Wikimedia 문서 이름과 1372 품목에서 나오고, 커뮤니티는 그 이름이 많이 이야기되는지만 확인한다. 그래서 '불만·요구' 갈래는 나오지 않았다.
- **검색어**: 193개 중 흐름 근거에 쓰인 것은 12개다. 쓰이지 않은 비율은 93.8%다. Bluesky 앞 28일 창의 상한 닿음은 9/193(4.7%), 최근 창은 16/193이다. GitHub 상한 닿음은 0이다. 6분 상한에 닿은 날은 0이고, 가장 길었던 날은 250초다.
- **호출**: GitHub 598번, Bluesky 603번(모두 700번 이내), `claude -p` 11번(40번 이내)이다. 비용은 없다.
- **꺼짐 대조**: 같은 10일을 커뮤니티 꺼짐으로 기계 단계까지 돌렸다. 비교 묶음은 같은 5곳이고, 오른 공식 단위는 30~69개다. 후보 복사본은 12~25KB로 작아진다. 9.97 규칙은 공식 둘 이상이 필요하고, 9.97 실측의 격리 결과는 10/10이 0건이었다.

**판단**

- **커뮤니티 기준(하한 10·50, 비 2)**: 지금은 바꾸지 않는다. 실린 날이 8/10이고 하루 1~2건이라 너무 많지도 적지도 않다. 4건 이상인 날도 없다. 첫 일주일 운영을 보고 다시 본다.
- **검색어 20개 상한**: 바꾸지 않는다. 6분 상한에 닿은 날이 없어 시간 여유는 있다. 하지만 검색어의 93.8%가 근거에 쓰이지 않으므로, 상한을 올려도 얻는 것이 적고 호출만 는다.
- **공식 단위의 결을 바꾸는 다음 단계**: 여전히 필요하다. 0건인 날은 줄었지만, 실린 흐름이 모두 관심 갈래라 불만·요구 흐름은 여전히 못 잡는다. 이것은 공식 단위가 문서 이름·품목 이름이라서다. 다만 급하지는 않다. 제안 1에 적는다.

**한계**

- 커뮤니티의 지난 창을 지금 세어서, 그 사이 지워진 글이 빠졌다.
- 한꺼번에 받아서, 1372처럼 늦게 채워지는 소스가 운영 때보다 덜 비어 있다(9.97과 같다).
- 민원빅데이터를 받지 않아, 검색어가 Wikimedia와 1372에서만 나왔다.
- 권익위 공개제안은 시험 받기 20번 한도 안에 끝나지 않았다. 10번째 부름에서 형식 오류가 났고 11번째부터는 한도였다. 그래서 남은 범위를 뺐다. 공개제안은 외부인 글 소스라 검색어로 쓰이지 않으므로, 검색어와 커뮤니티 판정에는 영향이 없다.
- Bluesky 상한을 피하려고 창을 나누는 것은 하지 않았다. 앞 창 상한 닿음이 4.7%라서 지금은 필요하지 않다.
- 10-29는 첫 프로세스가 '다시 부름'이 되었다. 그런데 실측 스크립트가 같은 실행 기록으로 다시 부르지 않아, 10-30 뒤에 새 실행 기록으로 다시 돌렸다. 그래서 두 날 사이의 S8(같은 흐름 다시 싣기)은 실측으로 재지 못했다. S8은 자동 테스트로 확인했다.
- 마지막 검증에서 고친 코드(cc20358 단순화, 23c0b20 재실행 고정)로 실측을 다시 돌리지는 않았다. 23c0b20은 같은 대상 날짜를 다시 돌 때만 동작이 바뀌는데, 실측에서는 날마다 한 번만 돌았다. cc20358은 동작을 바꾸지 않았다.

3. **Bluesky 창 나누기**: 상한 닿음이 늘면(지금 앞 창 4.7%) 창을 나눠 센다.
4. **`community` 선택 칸 정리**: 내부 타입을 필수 칸으로 두고 9.97 형식을 읽는 곳에서만 채우면, 곳곳의 `?? []`가 없어진다.
5. **검색어 표 읽기 실패의 상태 기록**: `runCommunity`가 `selectedTerms`를 공식 단위 세기의 try 밖에서 읽는다(`src/communityFetch.ts:275`). 이 읽기가 실패하면 소스 상태가 '받지 못함(units)'으로 적히지 않는다. 명령은 중단으로 기록되고 정상 종료한다(`src/cli.ts`의 catch). 그래서 그날 흐름 단계는 커뮤니티를 '기록 없음'(꺼짐과 같음)으로 본다. 동작은 cc20358과 같다. 고친다면 이 읽기를 try 안으로 옮긴다.
