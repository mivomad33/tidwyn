# R1단계 명세서: 기능 줄이기

- 작성일: 2026-11-24
- 요약: Tidwyn에서 부수 기능 세 묶음을 코드째 지워 매일 실행과 사이트를 가볍게 한다. 수요(9.95 수요 스냅샷, 9.96 공식 수요, 9.97 수요 흐름, 9.98 커뮤니티 신호), 빌더(9.8 도구 변화, 9.9 새 제품과 뜨는 저장소), 추천 영상(7 받기·고르기, 8 내용 메모·요약, 9.6 기록 유지, 9.7 구간 정리)이다. 뉴스·이슈·인물과 용어·일정·지표는 남긴다.
- 종류: 변경 건 (수집 스킬, CLI, DB, 백업 형식, 공개 사이트, 문서를 바꾼다)
- 단계: [`docs/plan.md`](../../plan.md)의 R1. 남은 단계(9.99·10·10.5·11)를 접은 뒤(2026-11-24) 새로 더한 정리 단계다. 다음 단계는 없다.
- 이 문서는 기획과 요구사항만 담는다. 설계와 작업 계획은 구현하는 AI가 정한다.
- 공개 여부: 원본 저장소와 사이트는 이미 공개다. 바뀐 사이트는 머지 뒤 다음 `/brief`의 배포로 공개된다.

## 1. 목표

- **지금 상태(2026-11-24, main 8285913 기준 측정):**
  - 매일 `/brief`는 19단계(하위 단계를 따로 세면 31개)다. 그중 지울 기능이 차지하는 단계는 6-1(영상 새로 받기), 12-5·12-6(영상 받기·고르기), 12-6-1(저장소 스냅샷), 12-7·12-8(빌더 받기·쓰기), 14-1·14-1-1·14-2(수요 스냅샷·커뮤니티·흐름), 18-1(공식 수요)이다. 이 단계들의 Bash 시간 제한은 6~10분이고, 몇몇은 여러 번 다시 부른다(저장소 스냅샷 3번, 수요 흐름 3번, 공식 수요 2번).
  - 유료로 쓰는 외부 서비스는 Gemini(영상 메모·구간, 한 실행 상한 $1.50·$2.50, 월 약 $65)뿐이다. 빌더의 새 제품·저장소 글은 `claude -p` 격리 프로세스로 써서 구독 한도를 쓴다.
  - 지울 기능만 쓰는 키는 `YOUTUBE_API_KEY`, `GEMINI_API_KEY`, `PRODUCT_HUNT_TOKEN`, `DART_API_KEY`, `DATA_GO_KR_KEY`, `ASSEMBLY_API_KEY` 여섯이다. 남는 키는 `ECOS_API_KEY`, `FRED_API_KEY`다.
  - 실제 DB(`data/tidwyn.db`)의 지울 기능 데이터: 빌더 표 14개(`builder_*`, 항목 27·새 제품과 저장소 37·가격·한도 행 945 등), 저장소 스냅샷 표 3개(모두 0건), 수요 흐름 표 5개(흐름 1건·날짜 상태 8건), 영상 표 3개(모두 0건, 폴더를 잃으면서 없어졌다). 빌더 항목만 근거인 일정이 10개이고(`builder_item_schedules`, 뉴스 근거 없음), 뉴스 근거도 빌더 근거도 없는 일정은 0개다.
  - 수요 전용 DB(`data/demand.db`)·사본, 빌더 문서 원문(`data/builder-raw/`), 시험 데이터 폴더(`.test-data/<시각>/`)는 지금 없다.
  - 이름에 demand·community가 든 소스만 `src/`·`site/` 약 4,800줄, 테스트 약 9,300줄이다. 빌더는 소스 약 4,500줄·테스트 약 5,000줄, 영상은 소스 약 3,000줄·테스트 약 3,700줄이다(서브에이전트 조사, 대략).
- **바꾸려는 이유:** 사용자가 Tidwyn에 부수 기능이 너무 많아 과하다고 보고 확 줄이기로 했다(2026-11-24). 기능이 많으면 매일 실행이 길고, 외부 소스·키·약관·비용이 늘어 깨질 곳이 많고, 폴더를 잃었을 때처럼 되살릴 것도 많다. 원래 목표는 "매일 브리핑을 보고 지금 무슨 일이 벌어지는지와 흐름을 쉽게 파악한다"(plan 1장)이다.
- **쓰는 사람:** 매일 브리프를 보는 프로젝트 주인과, 검색으로 들어오는 공개 방문자.
- **충분한 수준:** 지운 기능의 코드·테스트·스킬 단계·문서·사이트 화면·DB 표가 남지 않고, 남은 기능은 지금처럼 돌며, 시험 실행이 남은 단계를 끝까지 돌고, 머지 뒤 배포만 실행(T9)이 끝까지 돌아 가벼워진 사이트가 운영에 올라간다.

## 3. 범위

### 3.1 넣는 것

- 세 묶음(T1)의 수집 명령, 격리 쓰기 프로세스(`claude -p`), 외부 서비스 호출, 키 읽기, DB 처리, 작업 파일, 백업·복원 파일, 정정 종류, 실행 기록·요약 칸, 사이트 탭·페이지·칸·검색 결과, 공개 전 점검과 배포 뒤 점검의 해당 검사, 테스트·시각 회귀 스냅샷·지어낸 데이터를 지운다.

### 3.2 넣지 않는 것

- 주요 지표, 인물·기관·국가와 용어, 일정(뉴스 근거), 읽은 표시, 방문 통계, 검색, RSS·SEO, 원문 이미지, 뉴스 정정 빼기: 사용자가 고르지 않았다(T1).

- 새 기능, 남는 기능의 개선, 남는 화면의 다시 디자인: 이 단계는 지우기만 한다.

## 4. 요구사항

### 4.0 용어

- **지운 기능:** T1의 세 묶음. 수요(수요 스냅샷, 공식 수요, 커뮤니티 신호, 수요 흐름), 빌더(도구 변화, 가격·한도 사본, 지원 종료·시행일 일정, 새 제품, 뜨는 저장소, 저장소 스냅샷), 영상(받기, 고르기, 메모·요약, 구간 정리, 영상 페이지, 새로 받기, 30일 지우기).
- **남는 기능:** 뉴스 후보 목록·조사·검사·저장·마크다운, 이슈 연결·합치기, 인물·기관·국가와 용어 뽑기·합치기, 일정 뽑기·합치기(뉴스 근거), 지표 판단·받기, 지난 날짜 이미지, 백업, 사이트 빌드·배포·`data` push, 뉴스 정정, 사이트의 브리프·이슈·인물·용어·일정·지표·검색·소개·처리방침·날짜 목록, 읽은 표시, 방문 통계, RSS·사이트맵.
- **지운 기능 낱말:** 코드·문서 검색에 쓰는 낱말. `video`, `youtube`, `gemini`, `builder`, `discover`, `product hunt`·`producthunt`, `repo snapshot`·`repoSnapshot`, `demand`, `community`, `영상`, `빌더`, `수요`, `새 제품`, `뜨는 저장소`, `커뮤니티`, `흐름 항목`. 대소문자는 가리지 않는다. 요일 '수요일'은 낱말 `수요`에 걸리지 않게 뺀다. `flow`·`흐름`은 뉴스의 흐름(섹션 흐름 문단, 이슈의 흐름)에도 쓰여 자동 검사에 넣지 않고, 사람이 읽는 대조(4.5)에서만 본다.
- **실제 DB 사본:** 메인 폴더 `data/tidwyn.db`를 읽기만 해서 `.test-data/` 아래에 복사한 파일. 실제 데이터 폴더에는 쓰지 않는다.

### 4.1 수집 스킬과 CLI

- **4.1-1** 브리프 스킬에 지운 기능의 단계, 규칙(0장의 금지 규칙 포함), 작업 파일, 명령, 키 줄 설명이 없다. 남은 단계는 번호가 이어지고(하위 번호 정리 포함), 실행 순서 표와 본문 절이 서로 맞으며, 남은 단계 사이의 "앞 단계가 실패해도" 관계가 지운 단계를 가리키지 않는다. 스킬 설명(`description`)에도 지운 기능이 없다.
  - 확인: 자동 테스트(단위, 스킬 문서를 읽는 기존 문서 테스트 방식)로 스킬 파일에 지운 기능 낱말이 없고, 실행 순서 표의 명령이 모두 CLI에 있는 명령이며, 표의 단계 번호가 본문 절 제목과 맞는지 검사한다. 낱말을 일부러 넣은 문서로 테스트가 실패하는 것도 본다.
- **4.1-2** CLI에 지운 기능의 명령이 없다. 지운 명령 이름으로 부르면 다른 알 수 없는 명령과 같은 사용법 안내와 종료 코드로 끝나고, 아무 파일도 쓰지 않는다. 남은 명령은 그대로 있다.
  - 확인: 자동 테스트(통합)로 지운 명령 이름 몇 개(`video-fetch`, `builder-write`, `demand-flow`, `demand-official`)가 알 수 없는 명령으로 거부되고, 남은 명령 몇 개(`feeds`, `validate`, `indicator-fetch`, `backup`)는 사용법이 그대로인지 본다.
- **4.1-3** `start`·`check`의 실행 설정, `start`의 키 줄·예정 줄, `summary`의 결과에 지운 기능의 줄이 없다. 키 줄은 ECOS와 FRED만 보인다.
  - 확인: 자동 테스트(통합, 임시 데이터 폴더)로 `start test`와 `summary`의 출력에 지운 기능 낱말이 없고 ECOS·FRED 키 줄이 있는지 본다.
- **4.1-4** 코드 어디에도 `claude` 실행 파일을 부르는 길이 없다(격리 쓰기 프로세스는 빌더·수요만 썼다). YouTube, Gemini, Product Hunt, GitHub Search·별 이력·README, 수요 소스로 가는 요청 주소가 코드에 없다.
  - 확인: 저장소 검색(명령)으로 `src/`·`site/`에 그 실행과 주소가 없음을 보이고, 결과를 보고서에 적는다. 자동 테스트로 두지 않는 이유: 주소 목록은 지운 코드에만 있어 테스트가 지킬 대상이 남지 않는다.
- **4.1-5** 키 읽기는 ECOS·FRED만 다룬다. 단, 비밀 값이 새는지 보는 모든 검사(공개 전 점검, 결과물 검사, 정정 검사 등 지금 키 값을 찾는 곳)는 `.env.local`에 남은 지운 기능의 키 여섯 값도 계속 찾는다.
  - 확인: 자동 테스트(단위)로, 지운 기능의 키 이름과 값이 든 가짜 `.env.local`을 두고 그 값이 든 결과물이 검사에서 실패하고 값이 없는 결과물은 통과하는지, 같은 값이 든 커밋 대상 파일로 공개 전 점검(`precheck`)이 실패하고 없으면 통과하는지 본다.

- **4.1-6** `src/`·`site/`·`test/`·`playwright.config.ts`·`package.json`에 지운 기능의 코드(모듈, 타입, 칸, 상수, 사이트 데이터 칸, 테스트·지어낸 데이터)가 남지 않는다. 남아도 되는 것은 이 문서가 요구하는 것뿐이다: 옛 탭 값·옛 주소 처리(T7, 4.3-2), 옛 백업 형식 읽기(4.2-3), 표를 지우는 DB 업그레이드(4.2-1), 비밀 값 검사의 키 이름(4.1-5)과 일반 비밀 값 모양 검사(예: `src/precheck.ts`의 Google API 키 모양 검사. 주석의 지운 기능 언급만 고친다), 정정 거부(4.2-4), 브라우저에 남은 옛 기록 다루기(4.3-5), 그리고 그것들의 테스트.
  - 확인: 저장소 검색(명령)으로 위 경로에서 지운 기능 낱말(4.0)이 든 파일 이름과 줄을 모아, 남은 줄이 모두 위 예외인지 보고서에 적는다. 자동 테스트로 두지 않는 이유: 예외가 뜻으로 정해져 있어 낱말 목록으로 가를 수 없다.

### 4.2 DB와 데이터

- **4.2-1** DB 업그레이드가 빌더 일정(T11)을 지운 뒤 지운 기능의 표(이름이 `builder_`, `repo_snapshot`, `demand_flow`, `video`로 시작하는 표)를 지운다. T11이 건드리지 않는다고 한 일정과 다른 표의 행은 바뀌지 않는다(`sqlite_sequence`는 지운 표의 줄만 빠진다). 업그레이드는 실행 전 사본을 만든 뒤에 돈다(지금 `start` 순서 그대로). 두 번 돌려도 같은 결과다.
  - 확인: 자동 테스트(통합)로 지운 기능 표, 빌더 일정, 그리고 남아야 하는 닮은 일정(지운 일정, 흡수된 일정, 뉴스와 빌더 근거가 함께 있는 일정)이 든 지어낸 DB를 업그레이드해 표가 없어지고 빌더 일정만 행째 지워지며 남아야 하는 일정·다른 표의 행 수가 그대로인지, 다시 돌려도 바뀌지 않는지 본다. 실제 DB 사본으로도 업그레이드를 돌려 표마다 전·후 행 수를 보고서에 적는다(남는 표는 같고, `schedules`는 72에서 62).
- **4.2-2** 백업은 지운 기능의 파일(`builder.json`, `demand.json`)을 쓰지 않고, 백업 형식 버전을 하나 올린다. 백업 커밋 뒤 `data` 브랜치 끝에 그 파일이 남지 않는다(지난 커밋에는 남는다).
  - 확인: 자동 테스트(통합, 임시 git 저장소)로 그 파일이 든 백업 브랜치에 새 백업을 커밋하면 끝 커밋에서 그 파일이 없어지고 다른 백업 파일은 남는지 본다.
- **4.2-3** 복원은 지금까지의 모든 백업 형식을 받는다. `demand.json`은 읽지 않고 넘어가고, `builder.json`에서는 일정 연결만 읽어 빌더 일정(T11)을 가려내 지운다. 복원한 DB에는 지운 기능의 표와 빌더 일정이 없고, T11이 건드리지 않는다고 한 일정은 남는다.
  - 확인: 자동 테스트(통합)로 `builder.json`·`demand.json`·빌더 일정과 남아야 하는 닮은 일정이 든 바로 앞 형식의 지어낸 백업을 복원해 오류 없이 끝나고 위 조건이 맞는지 본다. 실제 `data` 브랜치 끝(`refs/heads/data`)을 임시 폴더로 꺼내 복원하고, 4.2-1의 업그레이드한 실제 DB 사본과 백업이 다루는 표(`sqlite_sequence`·`meta` 제외)의 행 수가 같은지 보고서에 적는다. 다르면 원인을 보고서에 적고 계속한다(백업 밖 데이터 때문이면 문제가 아니다).
- **4.2-4** 뉴스 정정(`correct`)은 뉴스 항목만 받는다. 빌더·새 제품·저장소·수요 흐름 항목을 가리키는 정정 파일은 그 종류를 받지 않는다는 위반으로 거부된다.
  - 확인: 자동 테스트(통합)로 지운 종류의 키(`demand-1` 등)를 가리키는 정정 파일이 거부되고 뉴스 정정은 지금처럼 통과하는지 본다.
- **4.2-5** 코드는 지운 기능의 데이터 경로(`demand.db`, `demand-copies/`, `builder-raw/`, 영상·빌더·수요 작업 파일)를 만들거나 읽지 않는다. 지금 실제 데이터 폴더와 `.test-data/`에 그런 파일은 없다(2026-11-24 확인). 머지 전에 사용자가 옛 코드로 `/brief`를 돌려 생겼으면 배포만 실행(T9) 뒤에 AI가 데이터 폴더 밖의 날짜 붙은 폴더(`D:\projects\tidwyn-leftovers-<날짜>`)로 옮기고, 지울지는 최종 정리 안내(T8)에 넣어 사용자가 정한다(영구 삭제는 AI가 하지 않는다).
  - 확인: 자동 테스트(통합)로 `start test`부터 `site`까지 남은 명령을 임시 데이터 폴더에서 돌린 뒤 그 경로가 생기지 않았는지 본다.

### 4.3 공개 사이트

- **4.3-1** 브리프의 섹션 탭은 뉴스 탭(전체·한국·세계·IT·AI)만 있다. 정적 HTML 브리프에도 영상·빌더·수요 구역과 그 구역 이동 칩이 없다. 남은 탭의 동작(거르기 칩, 접힘, 읽음, '‹ 브리프' 되돌아가기)은 그대로다.
  - 확인: 자동 테스트(E2E, 지어낸 데이터)로 탭 목록, 정적 HTML의 구역, 남은 탭의 기존 동작 E2E가 통과하는지 본다.
- **4.3-2** 옛 주소는 T7대로 다룬다. 브리프(`/`와 `/<날짜>`)를 `#videos`, `#builder`, `#builder-2`, `#product-1`, `#repo-1`, `#demand`, `#demand-3`으로 열거나, 브라우저 저장소의 마지막 탭 값(`tidwyn.briefTab`)이 영상·빌더·수요 탭일 때 오류 없이 뉴스의 기본 탭으로 열린다. `/videos/<날짜>/<id>`는 사이트의 404 페이지를 404 상태로 돌려준다.
  - 확인: 자동 테스트(E2E)로 각 경우의 열린 탭, 콘솔 오류 없음, 404 상태를 본다. 정상 값(뉴스 키 해시 `#<섹션>-<번호>`는 그 뉴스를 펼쳐 열고, 남은 탭 저장값은 그 탭으로 연다)이 그대로인지도 본다. 옛 탭 값과 해시는 "지금 있는 탭이나 뉴스 키가 아니면 기본 탭"으로 다루고 옛 탭 이름을 코드에 문자열로 두지 않는다(그래서 4.3-3의 결과물 검사가 JS 번들에도 그대로 적용된다). 운영 호스팅 규칙은 로컬 서버와 따로 정의되므로, 자동 테스트(단위)로 결과물의 `vercel.json` rewrites에 `/videos`로 시작하는 source가 없는지도 본다.
- **4.3-3** 이슈 페이지에 관련 영상이 없고, 일정 화면·이번 주 상자·펼친 카드에 빌더 일정과 '빌더 항목 ›'이 없으며, 검색 결과·사이트맵·RSS·사이트 데이터 파일에 지운 기능의 항목·주소·파일이 없다.
  - 확인: 자동 테스트(통합, 지어낸 데이터로 빌드)로 빌드 결과물 전체에 지운 기능 낱말 중 화면 글(`영상`, `빌더`, `수요`(요일 제외), `새 제품`, `뜨는 저장소`)과 지운 파일 이름이 없는지 본다. 남은 기능이 우연히 같은 낱말을 쓰는 곳(예: 뉴스 본문)은 지어낸 데이터에 넣지 않는다. 낱말을 일부러 넣은 결과물로 검사가 실패하는 것도 본다.
- **4.3-4** 소개·처리방침에서 지운 기능의 안내, YouTube·Gemini·Product Hunt·GitHub·수요 소스 문구, YouTube 약관 링크, 브라우저 저장 목록의 지운 키가 빠지고, 처리방침의 바뀐 날짜(`site/src/lib/policy.ts`의 `PRIVACY_UPDATED`)가 머지 날로 바뀐다. 구현 중에는 구현한 날로 두고, 머지 날이 그보다 뒤면 `review-done`이 머지 직전에 작업 브랜치에서 값과 테스트 기대값을 고친다(배포만 실행 전에 끝난다). 남은 고지(FRED 고지, 방문 통계, 읽은 기록, 연락 메일)는 그대로다.
  - 확인: 자동 테스트(통합)로 두 페이지에 지운 서비스 이름이 없고 남은 고지가 있는지 본다.
- **4.3-5** 브라우저에 남은 지운 기능의 기록(빌더·흐름 항목 읽음 표시, 지운 탭 저장값)이 남은 화면의 수(예: 날짜 목록의 읽은 정도)나 동작을 바꾸지 않는다.
  - 확인: 자동 테스트(E2E)로 그런 값을 미리 넣은 브라우저 저장소에서 브리프와 날짜 목록의 읽은 수가 뉴스만으로 세어지는지 본다.
- **4.3-6** 바뀐 화면(브리프 375·1280 뉴스 탭, 정적 브리프, 이슈 페이지, 일정 화면, 검색, 소개, 처리방침, 404)이 디자인 기준을 지킨다. 지운 탭 때문에 생긴 빈자리·어색한 간격이 없다.
  - 확인: `browser-check`와 `design-check` 깨끗한 회차. 지운 화면의 시각 회귀 스냅샷은 지우고, 바뀐 화면의 스냅샷은 다시 찍는다.

### 4.4 남는 기능 유지

- **4.4-1** 검증 명령 `pnpm verify`와 `pnpm e2e`가 이 윈도우 PC에서 통과한다(T10). 지운 기능만 확인하던 테스트는 지우고, 남은 기능의 테스트 기대값은 이 문서가 바꾸는 동작(지운 탭·칸·키·명령·파일)에 기대는 것만 고친다.
  - 확인: 두 명령의 결과를 보고서에 적는다. 바꾼 기존 테스트의 기대값마다 어느 요구사항 때문인지 진행 기록에 적는다. 지우기 전 코드로 찍은 윈도우 기준 이미지와 지운 뒤 화면을 비교해, 달라진 화면이 모두 이 문서가 바꾼 것인지 보고서에 적는다(T10).
- **4.4-2** 시험 실행이 남은 단계를 끝까지 돈다: 브리프 스킬을 시험 모드로 한 날짜(KST 어제) 돌려 `start test`부터 `summary`까지 모든 단계가 돌고, 요약에 실패한 단계가 없다(시험 모드라 배포와 push는 "건너뜀"). 실제 RSS, ECOS·FRED를 부른다.
  - 확인: 명령. 지운 기능 단계를 건너뛸 길이 없는지(요약에 그 줄이 없음)와 걸린 시간을 보고서에 적는다. 스킬은 모델이 스스로 부를 수 없게 막혀 있어(`disable-model-invocation`), 구현하는 AI는 스킬 파일을 읽고 그대로 따라 돈다(`docs/operations.md`의 "`/brief`가 스킬 대신 다른 것으로 열릴 때"와 같은 방식).
- **4.4-3** 공개 전 점검(`node src/cli.ts precheck`)이 worktree에서 통과한다.
  - 확인: 명령.
- **4.4-4** 배포만 실행(T9)의 순서가 수집 단계 없이 끝까지 돈다. 배포만 실행은 `start`에서 명시적으로 고른 표시로 실행 기록에 남고, 그 표시가 없는 평소 실행의 요약은 지금 그대로다(결과가 없는 대상 날짜는 실패). `start`가 실행 전 사본을 만든 뒤 업그레이드하고, `backup`·`site`가 수집하지 않은 실행 기록으로도 성공하며, 표시가 있으면 `summary`는 대상 날짜를 실패가 아니라 "이번 실행에서 수집하지 않음"으로, 연결·뽑기·지표·합치기·이미지 줄을 "배포만 실행이라 하지 않음"으로 보이고 실패한 단계를 보이지 않는다. 다음 `/brief`는 그 날짜들을 빠진 날짜로 다시 잡는다.
  - 확인: 자동 테스트(통합, 임시 데이터 폴더·임시 git 저장소)로 지운 기능 표가 든 지어낸 DB에서 이 순서를 데이터 폴더 지정 실행으로 돌려(배포·push는 건너뜀으로 기록) 사본이 업그레이드 전 상태인지, 요약 문구, 다음 `start`의 대상 날짜를 본다. 표시 없이 같은 상태로 돌린 평소 실행의 요약은 그 날짜를 실패로 보이는 것도 본다. 실제 DB 사본으로도 같은 순서를 돌려 결과를 보고서에 적는다.

### 4.5 문서

- **4.5-1** `docs/plan.md`: 단계 표에서 지운 단계(7, 8, 9.6, 9.7, 9.8, 9.9, 9.95, 9.96, 9.97, 9.98)의 상태가 "R1에서 지움"으로 바뀌고, 큰 방향의 결정 중 지운 기능에만 해당하는 것(D13, D15, D16과 D1의 해당 예외)이 지웠다고 표시된다. 다른 결정 안의 지운 기능 문장(D7의 Gemini, D4·D6의 영상·자막 등)은 그 문장만 지웠다고 표시하고 결정은 남긴다(D7의 월 비용 상한은 프로젝트 전체의 것이라 남는다). 2.3에 한 줄로 이유를 적고, 바뀐 기록에 줄을 더한다. 남은 단계의 상세 중 지운 단계 절은 지운다. 머리말 요약과 1장 목표의 지운 기능 문장(영상 추천, 수요 흐름 등)도 고친다. 단계 R1의 상태는 `review-done`이 바꾼다.
  - 확인: 문서를 읽어 대조하고 보고서에 적는다(자동화하지 않는 이유: 계획 문서의 뜻을 보는 일이다).
- **4.5-2** `docs/operations.md`, `docs/design.md`, `README.md`·`README.en.md`에 지운 기능의 절·줄·명령·키·탭 설명이 없고, 남은 내용과 맞다. 두 README는 같은 섹션·명령·링크를 가진다. 지운 기능만 다루는 `docs/` 문서는 지운다(끝난 명세서 폴더가 링크하는 경우도 지운다, 그때의 기록은 git 이력에 있다). `docs/operations.md`에 배포만 실행(T9)의 명령 순서와, `site`를 실제 데이터 폴더에 바로 부르지 않는 이유를 적는다.
  - 확인: 저장소 검색(명령)으로 이 파일들에 지운 기능 낱말이 남은 줄을 모아, 남은 것은 모두 "지웠다"는 기록이거나 남은 기능의 뜻(예: 뉴스 흐름)인지 보고서에 적는다. 스킬 문서 테스트(`test/skillDoc.test.ts`)는 남아 스킬을 계속 검사한다(지운 기능의 `*Docs.test.ts`는 지운다).
- **4.5-3** `docs/memory.md`에서 지운 기능에만 해당하는 항목은 지우거나 한 줄로 줄이고, 남은 항목이 지운 기능을 가리키면 고친다(CLAUDE.md 기록 규칙: 해결된 항목은 짧게 유지). 2026-11-24 기능 줄이기 항목에 이 단계에서 지운 범위를 더한다.
  - 확인: 문서를 읽어 대조하고 보고서에 적는다.

## 5. 완료 정의

### AI가 확인하고 끝낸다

- 4장 요구사항의 확인을 모두 실행해 통과한다(화면은 `browser-check`와 `design-check` 깨끗한 회차까지).
- 결과 보고서에 전·후 비교가 있다: 브리프 스킬 단계 수와 줄 수, `src/`·`site/`·`test/` 줄 수, 쓰는 키 수, 실제 DB 사본의 표별 행 수(4.2-1), 사이트 결과물 크기와 파일 수, 시험 실행 시간(4.4-2).
- `package.json`의 의존성이 늘지 않았다(줄어든 것은 보고서에 적는다).
- 결과 보고서에 "최종 정리 안내" 절이 있다(T8). 항목마다 무엇을, 어디서(서비스와 화면 또는 명령), 하지 않으면 어떻게 되는지를 적는다: Google Cloud 프로젝트 `tidwyn`의 `YOUTUBE_API_KEY`·`GEMINI_API_KEY` 키 삭제와 API 끄기, Gemini 선불 자동 충전 끄기와 남은 잔액, Product Hunt 앱 `Tidwyn`과 `PRODUCT_HUNT_TOKEN`, OpenDART(`DART_API_KEY`)·공공데이터포털(`DATA_GO_KR_KEY`, 활용 신청)·열린국회정보(`ASSEMBLY_API_KEY`) 키, 메인 폴더 `.env.local`에서 여섯 줄 지우기. 정리 결과는 다음 작업 때 작업 브랜치에서 `docs/memory.md`에 적는다는 것도 적는다(main에 직접 커밋하지 않는다).
- 머지 전까지 메인 폴더, 실제 데이터 폴더(`data/`), `data` 브랜치, 운영 배포가 그대로다.

### 사용자가 마지막에 확인한다

1. 머지를 승인한다(배포 승인을 겸한다, T9). 머지 날이 구현한 날보다 뒤면 먼저 작업 브랜치에서 4.3-4대로 처리방침 날짜와 테스트 기대값을 고쳐 커밋하고 `pnpm verify`와 공개 전 점검을 다시 돌린다. 머지는 7장의 때에 메인 폴더에서 squash merge, 공개 전 점검, main push를 하고, 이어서 AI가 배포만 실행(T9)을 한다. 이 실행이 DB 업그레이드(T2·T3)를 하고 `data` 브랜치에서 `builder.json`·`demand.json`을 빼며 사이트를 배포한다. 끝나면 worktree와 브랜치를 지운다. 단계 접기 브랜치(`docs/drop-remaining-stages`)는 따로 머지하지 않는다: R1 브랜치가 그 위에 있어 R1 squash 머지에 두 변경이 함께 실린다. 머지 뒤 그 worktree(`../tidwyn-drop-stages`)를 지우고 브랜치는 `git branch -D`로 지운다.
2. 배포된 운영 사이트(`tidwyn.vercel.app`)에서 뉴스 탭만 보이고 지난 브리프·이슈·일정·지표가 그대로인지 본다. 빠진 날짜는 원할 때 `/brief`로 채운다(이 단계의 조건이 아니다).
3. 단계가 모두 끝난 뒤(1 뒤) `review-done`이 보고서의 "최종 정리 안내"를 보이면, 키 여섯·Gemini 자동 충전·관련 계정을 정리할지 정하고 직접 한다(T8, 이 단계의 머지 조건이 아니다).

## 7. 진행 규칙

- 작업 폴더는 worktree `../tidwyn-stageR1`이다. Bash 명령은 worktree 절대 경로로 `cd`한 뒤 실행하고, 파일 도구는 그 절대 경로를 쓴다. 서브에이전트 지시에도 넣는다. 메인 폴더의 `data/`는 4.2-1의 DB 사본 복사와 4.2-3의 `refs/heads/data` 꺼내기만 하고(읽기), 쓰지 않는다.
- **머지하는 때:** 메인 폴더에서 `/brief`가 돌고 있지 않을 때. 메인 폴더 `data/runs/`가 없거나 가장 늦은 실행 기록에 `push` 결과(성공·실패·건너뜀)가 기록되어 있으면 돌고 있지 않은 것으로 보고 진행한다. 그 밖에 알 수 없으면 사용자에게 묻는다. 머지는 메인 폴더에서 하고, 배포만 실행(T9)도 메인 폴더로 `cd`해서 한다(실제 데이터 폴더의 `start`는 worktree 안에서 거부된다). `start`가 거부(종료 코드 3)하면 조건을 맞추려 하지 않고 멈춰서 묻는다. 뒤에 worktree와 브랜치를 지운다. 작업 브랜치는 push하지 않는다.
- 커밋되는 파일과 메시지에 홈 절대 경로를 쓰지 않는다. 측정 결과, DB 사본, 스크린샷 원본은 `.test-data/` 아래(무시됨)나 세션 임시 폴더에 두고, 보고서에 넣을 스크린샷만 명세서 폴더의 `screenshots/`(무시됨)에 둔다.
- `security-review`는 세션의 작업 폴더에서 diff를 모아 worktree 브랜치를 보지 못한다(U1 놓친 점). 서브에이전트가 같은 기준으로 worktree의 `main...HEAD` diff를 직접 본다.

### 사전 승인

묻지 않고 해도 되는 것(2026-11-24, 이 명세서의 진행 규칙):

- worktree 안의 코드·테스트·스킬·문서 지우기와 수정, 커밋. 지운 기능의 테스트 파일·시각 회귀 스냅샷·지어낸 데이터 지우기, 바뀐 화면의 스냅샷 다시 찍기.
- `package.json`에서 지운 기능만 쓰던 의존성 빼기와 잠금 파일 갱신.
- 처리방침·소개 문구 고치기(공개는 머지 뒤 배포).
- 실제 DB를 `.test-data/` 아래로 복사하고 그 사본으로 업그레이드·복원 확인하기, `refs/heads/data`의 파일을 임시 폴더로 꺼내기. `.test-data/` 아래 AI가 만든 것 정리.
- 시험 모드 실행(4.4-2): 공개 RSS 피드, ECOS·FRED 호출, 웹 검색. 시험 데이터 폴더는 확인이 끝나면 지운다.
- 머지 승인 뒤: squash merge, 공개 전 점검, `git push origin main`(CLAUDE.md 작업 규칙), 이어서 메인 폴더에서 배포만 실행(T9): 실제 DB 업그레이드, `data` 브랜치 백업 커밋과 push, Vercel 운영 배포. 공개 전 점검이 실패하면 push와 배포를 하지 않는다. 배포만 실행 뒤 실제 데이터 폴더에 지운 기능의 경로(`demand.db`, `demand-copies/`, `builder-raw/`, `work/`의 영상·빌더·수요 작업 파일)가 있으면 4.2-5대로 데이터 폴더 밖으로 옮긴다. 머지 뒤 단계 접기 worktree(`../tidwyn-drop-stages`)와 브랜치 지우기: 그 worktree에 커밋하지 않은 변경이 없고 브랜치 끝이 머지한 R1의 조상(`git merge-base --is-ancestor`)일 때만 한다.
- E2E 서버 띄우기 방식 바꾸기, 시각 회귀 기준 이미지를 윈도우용으로 찍고 맥용을 지우기(T10).

### 멈추고 물을 것

- 배포만 실행의 어느 단계든 실패했을 때: 남은 단계를 하지 않고 요약을 보인 뒤 묻는다. main에서 고치거나 실행 전 사본으로 되돌리거나 이전 배포로 되돌리기를 묻지 않고 하지 않는다.
- 머지 승인 전의 배포와 push, 사이트 번들에 들어가는 새 패키지, 지운 기능의 외부 서비스 호출(시험 실행도 부르지 않아야 한다).
- 실제 데이터 폴더, 실제 DB, `data` 브랜치, `.env.local`을 바꿔야 할 때.
- 지운 기능을 빼면서 남는 기능의 동작이 이 문서가 정하지 않은 방식으로 바뀌어야 할 때(예: 이번 주 일정 상자의 구성, 이슈 연결·합치기 규칙, 백업에서 남는 파일의 형식).
- 요구사항끼리 충돌해 둘 다 만족할 수 없을 때.

아래는 멈추지 않는다. 그 부분만 처리하고 계속한다.

- 시험 실행에서 남는 기능의 외부 소스(RSS, ECOS, FRED)가 그날 실패할 때: 이 단계 때문이 아님을 기록하고 다시 돌리거나, 같은 단계를 임시 데이터로 확인해 보고서에 적는다.
- 기존 테스트가 이 문서가 정한 동작 때문에 깨질 때: 4.4-1대로 고친다. 이 문서가 정하지 않은 동작 때문에 깨지면 기존 테스트를 바꾸지 않고 원인을 고친다.

### AI 재량

- 지우는 순서와 커밋 단위, DB 업그레이드의 모양, 공통 코드(접는 줄 부품, 칩, 정정 공통부)에서 남은 기능이 쓰는 부분을 남기는 방법, 남은 스킬 단계의 번호 매기기, 실행 기록 형식에서 지운 칸을 다루는 방법(지난 실행 기록을 읽는 코드가 남으면 깨지지 않게), 테스트 묶음 구성, 문서 문장. 지난 일정 합치기 기록(DB·백업)의 빌더 칸(`itemsAbsorbed`, `itemsAdded`, `reminderMoved`, `reminderDropped` 등)은 읽을 때와 되돌릴 때 무시한다(실측 합치기 기록 0건).
