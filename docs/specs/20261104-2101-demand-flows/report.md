## 재량으로 정한 것

- 국회 목록은 그날 상태 스냅샷의 전날 대비 차이로 날마다 센다. 그날 상태 그대로는 7일 대 28일 비교가 오름을 보이지 못하기 때문이다.
- 분야는 21개다(`FLOW_FIELDS`). 공식 소스가 걸치는 영역을 덮도록 명세서 예시 10개에 11개를 더했다.
- 끄기 값 `TIDWYN_DEMAND_FLOW_OFF=1`, 후보 복사본 상한 160KB, 본 DB 마이그레이션 13, 백업 형식 9.
- 단위 규칙 값은 시험 폴더의 수 통계(대상 날짜 다섯, 하한·기준 격자)로 측정 전에 정했다: 공개제안 하한 5, 1372 15, DART 20, 나머지는 처음 값. 국회와 민원빅데이터는 시험에서 잴 수 없어 처음 값으로 뒀다. 테스트 데이터도 하한을 `UNIT_RULES`에서 읽게 바꿨다.
- 시험 격리 10일은 구간에 고르게 고르되, 이어진 사흘(10-28~30)을 넣었다.
- 시험에서 실제 DB를 복사하지 않았다(관련 이슈 후보는 재지 않음).
- 1372 공개 지연은 14일로 가정했다.

   - `--measure`가 날짜 범위를 받아 같은 스냅샷을 한 번만 풀기
   - `demandCrashReason` 문구 비교를 종류로
   - 소스 찾기 중복 정리

## 놓친 점

- `[명세서]` 4.4-3의 "수요 데이터 파일에 주소·메일·홈 경로를 심은 결과물에서 결과물 검사가 실패"의 '주소'를 메일·홈 경로·키로 읽었다. 수요 데이터 파일에는 출처 링크(공식 주소)가 정상으로 들어가 URL 전체를 막을 수 없다. 글 칸의 주소는 흐름 파일 검사(4.2-2)와 정정 검사가 막는다.
- `[명세서]` 4.1-2 상한은 상위 수를 1까지 줄이고 재료를 비워도 넘으면 넘긴 채 끝난다. 160KB와 지금 상위 수로는 생기지 않아 두었다.
- `[명세서]` 민원빅데이터 응답의 칸 이름이 9.96 기록에 없다(단발 호출로 칸 이름을 보지 않았다). 시험에서도 받지 않아, 단위 이름 칸은 칸 이름 규칙으로 고르는 방어적 해석으로 두고 실제 응답으로 확인하지 못했다.
- `[명세서]` 실측 격리 10일이 모두 0건이었다. 명세서는 0건을 허용하지만, 굵은 분류 단위와 문서 하나 단위를 같은 이야기로 잇는 구조라 0건이 기본이 될 수 있다는 점을 명세서 단계에서 따져 보지 않았다. 대조 실험으로 경로가 동작하는 것만 확인했다.
- `[프로세스]` 공개 전 점검을 마지막에야 돌려, 테스트에 넣은 허용 밖 가짜 메일 주소 둘(서브에이전트가 쓴 것)을 늦게 찾고 브랜치 이력을 고쳤다. 테스트를 쓰는 서브에이전트 지시에 공개 전 점검의 허용 도메인을 넣거나, 커밋 단위마다 점검을 돌렸으면 이력을 고칠 일이 없었다.
