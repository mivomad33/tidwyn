# 9.6단계 명세서: 영상 기록 유지

- 작성일: 2026-11-01
- 요약: 영상 기록을 받은 지 30일이 되기 전에 YouTube API로 새로 받아 계속 보관한다. 응답에 없는 영상과 끝내 새로 받지 못해 30일이 지난 영상은 지운다. 영상 데이터를 첫 화면 파일에서 분리해, 기록이 쌓여도 지난 브리프와 이슈 페이지에 영상이 보이고 첫 화면 크기 한도를 지킨다. 공개 백업에는 계속 넣지 않는다.
- 종류: 변경 건 (7·8단계의 영상 저장, `/brief`, 사이트를 바꾼다. 실제 데이터가 매일 쌓이고 사이트가 공개되어 있다)
- 단계: [`docs/plan.md`](../../plan.md)의 9.6단계. 7·8단계를 잇는다. 구간별 정리와 영상별 페이지는 9.7단계다.
- 이 문서는 기획과 요구사항만 담는다. 설계와 작업 계획은 구현하는 AI가 정한다.
- 공개 여부: 원본 저장소와 사이트는 이미 공개다. 영상 데이터는 사이트 결과물에만 실린다. 공개 백업과 저장소에는 들어가지 않는다.

## 1. 목표

- **지금 상태:** 영상 기록은 받은 날부터 30일이 지나면 지워진다(7단계 V1). 2026-11-01 기준 실제 DB(스키마 버전 8)에 영상 30개가 있고 받은 날은 2026-10-30~31이다. 그래서 **2026-11-29 실행부터 기록이 지워지기 시작하고, 지워진 기록은 되살릴 수 없다.** 사이트는 날짜별 영상을 달 목록 파일에 넣는다. 30일 × 하루 16개에서 브리프 첫 화면이 이미 gzip 279.9KB로, 한도 300KB에 가깝다(8단계).
- **바꾸려는 이유:** 사용자가 지난 추천 영상이 사라지지 않기를 원한다. 정책 원문이 30일 뒤 삭제 외에 새로 받기도 허용한다(III.E.4.d, 2026-11-01 plan D13).
- **쓰는 사람:** 프로젝트 주인 한 사람. 사이트는 공개라 누구나 볼 수 있다.
- **충분한 수준:** 머지한 뒤 예약 `/brief`가 묻지 않고 매일 기록을 새로 받고, 2026-11-29를 지나도 지난 브리프와 이슈 페이지에 영상이 그대로 있다. 5년치 영상을 넣어도 영상 때문에 첫 화면과 영상 화면의 크기 한도를 넘지 않는다(4.3-2).

## 3. 범위

### 넣는 것

- 영상 기록을 새로 받는 일, 응답에 없는 영상 지우기, 지우기 규칙 변경 → 4.1, 4.2
- 이미 추천한 영상 빼기를 전체 기록으로 넓히기 → 4.1
- 영상 데이터 분리와 크기 한도, 지난 브리프·이슈 화면 → 4.3
- 처리방침·소개·문서의 30일 문구 고치기, 되돌리는 방법 → 4.4
- 시험 실행과 미리보기 → 4.5

### 넣지 않는 것

- 구간별 정리, 영상별 페이지: 9.7단계
- 공개 백업에 영상 넣기, 로컬 DB를 잃었을 때 복원: D1, plan 3.10
- 2026-10-29 이전처럼 영상이 없는 지난 브리프 채우기: 7단계 V9
- 지운 영상에 "영상이 있었다"는 흔적 남기기: 7단계와 같다. 영상 ID를 남기지 않는다
- 보관 상한(L1), 영상 검색, 영상 전체 목록 페이지, 사이트 안 재생: 요청이 없었다(V8)
- 새로 받을 때 통계나 설명 저장: 정책 III.E.4.b, 7단계 4.1-1
- 지난 추천 이유·요약 다시 쓰기: L7
- 정적 HTML, RSS, sitemap에 영상 넣기: 9.5단계 R7
- 첫 화면 크기 외의 일반 성능 개선, 영상 고르기 기준 변경: 범위 밖

### 해당 없음

- 인증과 권한, 입력 제한: 로그인과 입력이 없다.
- 서버, 원격 DB: 로컬 수집과 정적 사이트 그대로다.
- 사용 분석: 3단계 P10 그대로다.
- 새 비용: YouTube API 무료 할당량 안이다. Gemini를 새로 부르지 않는다.

## 4. 요구사항

"자동 테스트"는 `pnpm verify`에 들어가는 테스트다. 네트워크를 쓰지 않고(YouTube는 가짜 응답), 실제 `data/`와 `.env.local`을 쓰지 않는다. 지어낸 데이터만 쓴다. 날짜는 시각을 넣어 준다. "E2E"는 `pnpm e2e`다.

**용어 정의**

- **받은 날:** 그 기록을 YouTube API에서 마지막으로 받은 날(KST)이다. 7단계 `fetched_on`의 뜻을 넓힌다. 처음 받은 날과 새로 받은 날을 나눌 필요는 없다.
- **새로 받기:** 저장된 영상 기록을 `videos.list`로 다시 받아 YouTube 데이터를 바꾸고 받은 날을 그 실행의 날짜로 바꾸는 일이다.
- **30일 지우기:** 받은 날이 실행한 날보다 30일 이상 앞인 YouTube 데이터를 지우는 일이다(7단계 정의 그대로, 받은 날을 0일로 세어 29일째까지 남는다).
- 영상 기록, 묶음, 대상 날짜, 데이터 폴더, 실행 전 사본, 시험 폴더, 결과물, 첫 화면 크기는 앞 단계와 같다.

### 4.1 새로 받기 (L2, L3, L5, L6, L7)

1. **대상과 순서:** 실행마다 받은 날이 7일 이상 앞인 기록을 오래된 것부터 한 번에 50개씩 `videos.list`로 새로 받는다. 같은 영상이 여러 날짜에 있으면(옛 기록) 모두 바꾼다. 한 실행의 상한은 500단위이고, 넘는 기록은 다음 실행이 한다. 쓴 단위를 실행 기록과 요약에 남긴다.
   - 확인: 자동 테스트로 6일 전 기록은 부르지 않고 7일 전 기록은 부른다. 120개가 3번의 호출이 되고, 상한을 낮춰 넣으면 가장 오래된 것부터 상한만큼만 부른다.
2. **바꾸는 것:** 응답의 제목, 채널, 길이, 썸네일, 올린 시각과 받은 날만 바꾼다. 덮어쓴 옛 값이 SQLite 파일 바이트에 남지 않게 한다. `secure_delete`만으로는 쌓일 때 페이지가 나뉘며 남은 복사본을 못 지우므로(3회차 검토에서 재 봄), 실제로 바꾸거나 지운 실행은 지운 행 수와 관계없이 `VACUUM`까지 한다. 추천 이유, 요약, 묶음, 받은 곳, 관련 이슈, 붙은 브리프 날짜, 순서는 그대로 둔다. Gemini를 부르지 않는다. 설명과 통계를 저장하지 않는다.
   - 확인: 자동 테스트로 `secure_delete` 없이 행 100개 이상을 넣은 DB에 바뀐 응답을 넣어 위 항목만 바뀌고, DB 파일 바이트에 옛 제목과 응답의 설명·조회수 문자열이 없다.
3. **응답에 없는 영상(L5):** 호출이 성공했는데 응답에 없는 영상은 기록과 이슈 연결을 지우고 지운 수를 남긴다. 지운 바이트가 SQLite 파일에 남지 않게 한다(2번과 같은 `VACUUM`). 그 영상이 없어진 뒤 그 브리프 날짜의 "고르기 끝남"은 남는다.
   - 확인: 자동 테스트로 행 100개 이상의 DB에서 응답에 없는 영상의 ID가 DB 파일 바이트에서 나오지 않고, 나머지는 남는다.
4. **이상한 응답(L5):** 위 3번의 지우기와 2번의 바꾸기는 호출마다 판정한 뒤 적용한다. 물은 수와 없는 수는 서로 다른 영상 ID로 센다. 호출이 실패하면 판정에 넣지 않는다. 이상으로 본 호출의 영상은 받은 날을 포함해 그대로 두고 요약에 이상으로 남긴다. 이 판정과 관계없이 30일 지우기는 돈다. 응답 항목의 필드가 없거나 깨져 읽을 수 없으면 그 영상은 지우지 않고 바꾸지 않으며 실패로 센다. JSON이 아니거나 `items`가 배열이 아닌 200 응답과, ID를 읽을 수 없는 항목이 있는 응답은 호출 실패로 센다.
   - 확인: 자동 테스트로 빈 응답 하나에서 기록과 받은 날이 그대로이고 요약에 경고가 나온다. 3번의 호출 중 가운데만 빈 응답이면 그 50개만 그대로이고 나머지 두 호출은 적용된다. 경계 경우(4개 없음, 10개 중 5개 없음)에는 지운다. 읽을 수 없는 항목은 지워지지 않고, `{}` 응답과 ID 없는 항목이 있는 응답은 물은 영상이 4개 이하여도 아무것도 지우지 않는다.
5. **순서(L3):** 새로 받기 시도 뒤 30일 지우기를 같은 묶음으로 한다. 40일 전 기록이 있고 호출이 성공하면 그 기록은 살아남는다. 새로 받기는 그날의 영상 받기가 "이미 끝남"이어도 돈다. 시험 모드 실행도 자기 DB를 새로 받는다. `start`는 동기 명령으로 두고, 스킬 순서상 `start` 바로 다음에 새 명령을 둔다(이름은 구현 재량). 지우기(DB, 사본, 작업 파일, 사이트 폴더, 시험 폴더)는 `start`에서 이 명령으로 옮겨 반드시 돌고, 호출이 필요 없는 날에도 돈다. `start`의 "지움" 출력 줄도 이 명령으로 옮긴다. 그 명령 전에 실행이 끊긴 날은 다음 실행이 한다(V14). 실행 전 사본은 실행 시작 상태이고, 사본 안의 30일 지난 기록은 사본 쪽 규칙대로 지운다(그 기록이 DB에서 새로 받기로 살아남아도 그렇다).
   - 확인: 자동 테스트(데이터 폴더 지정 흐름)로 40일 전 기록이 호출 성공 뒤 남고 받은 날이 오늘이며, 호출 실패·키 없음 뒤에는 지워진다. 새로 받을 대상이 없는 실행에서도 지우기가 돈다.
6. **실패 처리(L4):** 키 없음, 인증 오류, 할당량 초과, 네트워크, 시간 초과는 새로 받기를 멈추고 실패와 이유를 남기며, 실행의 나머지(수집, 백업, 빌드, 배포, 요약)를 막지 않는다. 호출마다 시간 제한과 재시도는 7단계 영상 받기와 같은 공통 코드를 쓴다. 일부 호출이 성공하면 성공한 호출은 적용한다. 실패한 기록은 다음 실행이 다시 한다. 새로 받기 실패는 `video-fetch`처럼 요약에 남기고 다음 단계로 간다. 지우기 자체가 실패하면(DB 잠금 등) `start`가 실패할 때처럼 그 실행을 멈춘다. 스킬 문서에 두 경우를 적는다.
   - 확인: 자동 테스트로 키 없음, 모든 호출 실패, 일부 실패에서 뒤 단계가 끝까지 돌고 성공한 것만 바뀐다. 새 명령의 종료 코드가 새로 받기 실패에서는 0, 지우기 실패에서는 0이 아니다. 7단계 4.8-1처럼 가짜 키를 되풀이하는 오류 응답이 실행 기록, 요약, 출력에 나오지 않는다.
7. **이미 추천한 영상(L6):** 영상 받기의 거르기는 받은 날과 관계없이 DB에 남은 모든 영상 기록으로 한다.
   - 확인: 자동 테스트로 받은 날이 40일 전인 기록을 지우기 전에 넣어도 거르기 목록에 들어가고(지금의 날짜 조건을 두면 실패), 붙은 브리프 날짜가 100일 전인 기록의 영상이 후보에서 빠진다.
8. **기존 동작 유지:** 7·8단계의 받기, 확인 후보, 메모, 고르기, 이슈 합치기·되돌리기, 백업 제외가 그대로 동작한다. 기존 테스트에서 고쳐도 되는 줄은 이 명세서가 바꾸는 동작을 직접 단언한 줄뿐이다: 지우기가 `start` 직후라는 단언(L3), 영상이 달 목록·이슈 묶음에 있다는 단언과 그 데이터를 읽는 준비 코드, 파일 목록(L8), 30일로 좁힌 거르기(L6), 처리방침·소개·README와 표시 문구(`EXCLUDE_LABELS` 등)의 30일 표현, 그에 따른 시각 회귀 기준 이미지, 스킬 문서 순서 단언, 새 명령을 부르는 준비 코드(비동기 전환, 가짜 실패 응답 주입 포함), 마이그레이션을 더했을 때의 스키마 버전 값, 지어낸 데이터의 영상 기간 넓히기. 뜻은 유지한다: 이슈 합치기·되돌리기 뒤 관련 영상 단언은 나눈 데이터로 같은 내용을 본다.
   - 확인: 기존 테스트가 통과하고, `git diff main -- test/`의 기존 줄 변경이 위 범위뿐이다. 바꾼 줄은 보고서에 적는다.

### 4.2 지우기와 출력 (L1, L4, V14, V17)

1. **30일 지우기 유지:** 7단계 4.1-2의 대상(DB, 실행 전 사본, 작업 파일, 사이트 입력·결과물, 시험 폴더)과 바이트 기준은 그대로다. 달라지는 것은 판단 기준이 받은 날(4장 용어)이라는 것과 돌아가는 위치(L3)뿐이다. 보관 상한은 두지 않는다(L1): 받은 날이 최근이면 붙은 브리프 날짜가 아무리 오래되어도 지우지 않는다.
   - 확인: 7단계 4.1-2 테스트가 L3의 위치로 통과한다. 자동 테스트로 붙은 브리프 날짜가 3년 전이고 받은 날이 5일 전인 기록이 지워지지 않는다. 실제 빌드 결과물의 나눈 영상 파일에 30일 지난 기록이 있으면 사이트 폴더가 지워진다(`dirHasExpiredVideos`가 새 형식을 놓치지 않는다).
2. **화면 숨기기 유지(V14):** 사이트는 받은 날부터 30일이 지난 영상을 방문자 브라우저 날짜로 숨긴다. 그래서 `/brief`가 오래 멈춰도 운영 화면에 30일 지난 데이터가 보이지 않는다.
   - 확인: 7단계 4.7-7 테스트가 나눈 데이터로도 통과한다.
3. **공개 백업 제외 유지:** 백업과 복원, 공개 전 점검의 영상 검사는 그대로다. 새로 받은 기록도 백업에 들어가지 않는다.
   - 확인: 7단계 4.4 테스트가 통과한다. 새 사이트 데이터 파일 이름이 있으면 결과물 검사와 공개 전 점검이 그 파일도 빠뜨리지 않는다(`data` 브랜치 백업에 영상 파일이 있으면 실패, HTML에 새 파일 주소가 있으면 실패).
4. **`start`와 실행 출력:** "새로 받기: 대상 N, 바꿈 N, 응답에 없어 지움 N, 쓴 단위 N, 남음 N"과 실패 이유를 실행 요약에 더한다. 영상 제목과 ID는 나오지 않는다.
   - 확인: 자동 테스트로 요약에 위 줄이 나오고 영상 ID가 출력과 실행 기록에 없다.
5. **지워지기 전 경고:** 실행이 끝났을 때 받은 날이 23일 이상 앞인 기록이 남아 있으면 요약에 "새로 받기가 밀림: N개, 가장 오래된 기록이 D일 뒤 지워짐"을 남긴다. 다른 알림은 두지 않는다(2026-10-31 사용자 결정). 무인 실행의 요약을 보지 않으면 놓칠 수 있는 것을 감수한다.
   - 확인: 자동 테스트로 23일 전 기록이 남으면 나오고 22일이면 나오지 않는다.

### 4.3 사이트 (L8)

1. **데이터 분리:** 영상의 제목, 채널, 썸네일, 추천 이유, 요약은 달 목록 파일에 넣지 않는다. 달 목록과 이슈 묶음의 기존 `videos` 키는 쓰지 않고, 필요한 정보는 새 키 이름으로 둔다(옛 화면이 깨지지 않게). 영상 파일은 `site-data/` 아래에 둔다(noindex 범위). 브리프 첫 화면을 열 때 영상 탭을 열지 않으면 영상 파일을 받지 않는다. 같은 DB에서 두 번 빌드하면 결과가 같다(시계로 거르지 않는다, 7단계 4.6-2).
   - 확인: 자동 테스트로 달 목록 파일에 지어낸 영상 제목·추천 이유 문자열이 없고, 달 목록과 이슈 묶음에 `videos` 키가 없으며, 영상 파일 경로에 noindex 규칙이 있다. E2E로 첫 화면에서 영상 파일 요청이 없고 영상 탭을 열면 요청이 있다.
2. **크기 한도:** 조건은 `test/siteVideos.test.ts` "4.6-3"의 5년 조건에 영상 5년 × 하루 16개(추천 이유 150자, 요약 350자, 영상마다 관련 이슈 2개)와, 영상이 몰린 이슈 하나(관련 영상 300개)를 더한 것이다. 이 조건에서 각각 gzip 300KB 이하다: 브리프 첫 화면, 영상 탭이 처음 받는 사이트 데이터, 이슈 페이지 본문의 사이트 데이터(`issue-list`와 이슈 묶음), 관련 영상이 처음 받는 사이트 데이터(몰린 이슈 기준). 그래서 이슈의 관련 영상도 이슈 묶음 파일에 그대로 두지 않는다. 영상 데이터가 더하는 파일은 2,000개 이하다(영상마다 파일 하나인 구조는 하루 업로드 한도 5,000건에 걸리므로 쓰지 않는다). 값을 보고서에 적고 `site/size.ts`의 측정에 넣는다. 결과물 전체의 파일 수와 크기는 재서 적기만 한다: 5년 지어낸 데이터는 페이지별 HTML 때문에 이미 34,801개, 615MB이고(9.5단계 R5가 감수) 이 단계의 한도가 아니다. 15,000개 검사는 기존 365일 회귀 테스트(`test/siteStatic.test.ts`)에 영상 365일치를 넣어 유지한다.
   - 확인: 자동 테스트. 측정이 영상 파일을 실제로 재는지는 몰린 이슈의 영상을 뺀 값과 비교해 보고서에 적는다. 4.3-1의 단언은 영상 본문을 달 목록에 되돌리면 실패하는 것을 한 번 본다.
3. **브리프 영상 탭:** 지난 날짜를 포함해 영상이 있는 모든 브리프에 '영상 N' 탭이 그대로 보인다. N은 보이는 영상 수다(30일 지난 영상을 뺀 수). 영상 파일을 받기 전에도 탭이 보이고 N이 맞는다. 보이는 영상이 0개인 날은 탭이 없다. 칩, 요약 펼침, `#videos` 주소로 바로 열기, 날짜 바꾸기, 정정 표시 등 앞 단계 동작이 그대로다. 영상 줄의 모양은 그대로다.
   - 확인: E2E(기존 `stage7`, `stage8`, 새 지난 달 날짜 영상 탭, N과 실제 줄 수 일치, 30일 지난 영상만 있는 날의 탭 없음).
4. **대기와 오류:** 영상 파일을 받는 동안 기존 대기 표시를 쓰고, 실패하면 기존 오류 표시와 다시 시도를 쓴다(공통 컴포넌트). 실패해도 뉴스 탭은 동작한다.
   - 확인: E2E로 응답을 늦추거나 실패시켜 대기, 오류, 다시 시도 뒤 정상 표시를 본다.
5. **이슈 관련 영상:** 지난 달에 붙은 영상도 '관련 영상'에 보이고 최근 순, 5개 + '더 보기'가 그대로다. 이슈 뉴스 표시는 영상 로드를 기다리지 않는다. 대기와 오류는 4번을 따른다. 영상이 없는 이슈(모두 숨겨진 경우 포함)는 관련 영상 절도 대기·오류 표시도 없고, 영상이 전혀 없는 이슈는 영상 파일을 요청하지 않는다.
   - 확인: E2E(기존 `stage7`, 새로 여러 달에 걸친 관련 영상 7개, 영상 없는 이슈의 요청 없음과 절 없음).

### 4.5 검증 (실제 데이터 보호)

1. **전체 검사:** `pnpm verify`, `pnpm e2e`가 통과한다.

2. **시험 실행:** 실제 DB를 `cp`로 worktree의 `.test-data/stage96-trial/`에 복사해 `TIDWYN_DATA_DIR`로 쓴다. 복사는 00:00~05:49이거나, 메인 폴더 `data/runs/`에 오늘 시작한 실행 기록이 있고 그 `push`가 null이 아닐 때 한다. 복사 뒤 양쪽 sha256을 비교한다. 조건이 맞지 않으면 복사하지 않고 나머지를 먼저 끝낸 뒤 다시 본다. 다음 00:00까지 기다려도 되며, 그래도 맞지 않으면 이 항목을 보류로 넘기고 멈추지 않는다. 복사본에서만 받은 날을 앞당기고(예: 9일 전 영상 20개, 40일 전 영상 5개) 지어낸 없는 ID 기록 하나를 넣어 실제 YouTube API로 새로 받기를 돌린다. 쓸 단위는 호출 5번 이내다. `/brief` 수집, Gemini, 차트·검색은 부르지 않는다. 실제 호출이 할당량이나 키 오류로 실패하면 재시도로 상한을 쓰지 않고, 초기화 뒤(17시 뒤) 한 번 다시 한다. 그래도 막히면 복사본 빌드까지만 하고 이 항목을 보류로 넘겨 보고서 맨 위에 적는다. 결과: 모두 바뀌고, 받은 날이 오늘이며, 40일 전 기록이 살아남고, 요약 줄이 나오고, 없는 ID는 응답에 없어 지워진다.

3. **실제 데이터 보호:** 구현 중 실제 `data/`, `refs/heads/data`, 운영 배포에 쓰지 않는다. 예약 `/brief`가 바꾸는 것은 예외이므로, 시작과 끝을 비교할 때는 `data/runs/`에 그 사이 실행 기록이 있는지 함께 본다.
   - 확인: 시작·끝의 DB sha256, `refs/heads/data`, 운영 배포 ID(Vercel 조회가 안 되면 메인 폴더 최신 실행 기록의 배포 주소)를 보고서에 적고, 달라졌으면 그 사이 예약 실행 기록을 근거로 적는다.

## 5. 완료 정의

### AI가 확인하고 끝낸다

- 4장 요구사항의 확인을 모두 실행해 통과한다.
- 시험 실행의 수치와 미리보기 주소가 보고서에 있다. 4.5-2의 대체 경로를 쓰면 그 사실을 보고서 맨 위에 적는 것으로 갈음한다.
- `package.json`의 `dependencies`가 비어 있다.
- 머지 전까지 운영 배포가 그대로다(예약 실행의 배포는 예외).
- 시험 폴더는 AI가 지운다(복사본에 영상 데이터가 있다). 사용자에게 넘기지 않는다.

### 사용자가 마지막에 확인한다

1. 폰에서 보고서의 미리보기를 연다(Vercel `mivomad33`로 로그인). 지난 브리프의 영상 탭과 이슈의 관련 영상을 본다. 영상 탭을 처음 열 때 대기가 거슬리지 않는지 본다. 미리보기 주소가 없으면 보고서 맨 위에 그 이유가 있고, 막힌 것을 푼 뒤 `review-done`에서 다시 복사해 올린 뒤 같은 확인을 한다.
2. 처리방침의 새 문구를 읽는다.
3. 머지를 승인한다. 2026-11-29 전에 머지해야 한다. `/review-done`에는 보고서의 worktree 경로를 준다. 머지하면 메인 폴더에서 squash merge, 공개 전 점검, main push를 하고 worktree와 브랜치를 지운다. 운영 사이트는 머지 뒤 첫 `/brief`가 바꾼다.

머지 뒤에 한다(머지 승인의 조건이 아니다): 2026-11-06 뒤 실행 요약에서 "새로 받기" 줄을 한 번 본다. 첫 영상이 받은 지 7일이 되는 날이다.

## 7. 진행 규칙

- 작업 브랜치는 `spec/stage9.6-video-retention`이고 작업 폴더는 `../tidwyn-stage96`이다(L9). Bash 명령은 `git worktree list`로 확인한 worktree 절대 경로로 `cd`한 뒤 실행하고, 파일 도구는 그 절대 경로를 쓴다. 서브에이전트 지시에도 넣는다. `node src/cli.ts`로 DB를 여는 모든 호출에 `TIDWYN_DATA_DIR=<worktree 절대 경로>/.test-data/stage96-trial`을 붙이고 `TIDWYN_BACKUP_REPO`는 쓰지 않는다(읽기 명령도 마이그레이션을 한다).
- 머지는 메인 폴더에서 예약 실행이 돌지 않을 때 한다: 00:00~05:49에는 해도 되고, 05:50 뒤에는 메인 폴더 `data/runs/`에 오늘(KST) 시작한 실행 기록이 있고 그 `push`가 null이 아닐 때만 한다. 아니면 미루고 사용자에게 알린다. 머지 전에 git이 무시하는 스크린샷을 메인 폴더의 같은 경로로 옮기고, 머지 뒤 worktree와 브랜치를 지운다. 작업 브랜치는 push하지 않는다.
- 기한: plan 3.10대로 4.1·4.2를 먼저 끝낸다. 4.3이 막혀도 4.1·4.2의 구현을 되돌리지 않는다. 4.3을 끝내지 못하면 보류로 넘기고 그 사유를 보고서 맨 위에 적어 사용자가 나눠 머지할지 정하게 한다.
- 커밋되는 파일과 메시지에 홈 절대 경로를 쓰지 않는다. 실제 영상 제목·ID, 뉴스 글, 인물 이름을 진행 기록, 보고서, 테스트에 쓰지 않는다.

### 사전 승인

묻지 않고 해도 되는 것:

- 실제 YouTube API를 4.5-2 범위로 호출(`videos.list` 5번 이내).
- Vercel 프로젝트 `tidwyn`에 미리보기 배포(5번 이내). 운영 배포는 하지 않는다.
- 로그인된 브라우저로 미리보기를 열어 응답 읽기.
- 읽기 전용 Vercel 조회.
- `.test-data/` 아래 시험 폴더 만들기와 정리(AI가 만든 것만).
- `devDependencies` 설치.
- 공개 문서 읽기.

### 멈추고 물을 것

- 위 승인 밖의 비용, 외부 변경, 운영 배포.
- 실제 DB, `data` 브랜치, 공개 데이터를 바꿔야 할 때.
- YouTube 공식 문서가 이 명세서의 정책 전제와 달라졌을 때(새로 받기 금지, 수량 기준 등).
- 시험 실행에서 응답에 없는 영상이 물은 실제 영상의 절반을 넘을 때.
- 미리보기가 로그인 없이 열릴 때(보호가 꺼진 것이다).
