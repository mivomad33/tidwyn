# 8단계 명세서: 영상 내용 확인과 요약

- 작성일: 2026-10-30
- 요약: `/brief`의 영상 고르기를 두 번으로 나눈다. Claude가 제목·설명으로 확인 후보를 추리면, 스크립트가 Gemini API에 YouTube 주소를 넣어 영상 내용 메모를 받고, Claude가 메모로 최종 선별과 한국어 요약을 쓴다. 사이트의 영상 줄에 접어 둔 요약을 더한다. Gemini가 막혀도 7단계 흐름은 그대로 돈다.
- 종류: 변경 건 (7단계의 영상 고르기, 저장, 사이트를 바꾼다. 실제 데이터가 매일 쌓이고 사이트가 공개되어 있다)
- 단계: [`docs/plan.md`](../../plan.md)의 8단계(영상 자막 확인과 요약). 7단계를 참조한다.
- 이 문서는 기획과 요구사항만 담는다. 설계(스키마, 라이브러리, 폴더 구조)와 작업 계획은 구현하는 AI가 정한다.
- 공개 여부: 원본 저장소와 사이트는 이미 공개다. 요약은 영상 기록과 함께 사이트에만 실리고(최근 30일) 공개 백업과 저장소에는 들어가지 않는다.

## 1. 목표

- **지금 상태:** `/brief`가 YouTube API로 후보를 받아 Claude가 제목·설명(앞 120자)만 보고 하루 최대 16개를 고르고 추천 이유를 쓴다. 영상 내용은 보지 않는다. 2026-10-30 기준 실제 DB는 스키마 버전 7이고 영상 기록 15개가 있다.
- **바꾸려는 이유:** 제목·설명만으로는 내용이 약한 영상을 거를 수 없고, 추천 이유가 제목을 바꿔 말한 수준에 그치기 쉽다(7단계 보고서 제안 2). 시드 "자막 요약"과 plan 8단계다.
- **쓰는 사람:** 프로젝트 주인 한 사람. 사이트는 공개라 누구나 볼 수 있다.
- **충분한 수준(T9):** 실제 DB의 복사본, 실제 YouTube API, 실제 Gemini API로 시험 실행한 결과가 다음을 보인다. 선별과 요약이 좋은지는 사용자가 마지막에 본다(5장).
  - 확인 후보를 Gemini로 확인해 메모를 받고, 그 메모로 최종 선별과 요약을 써서 가장 늦은 브리프 날짜에 적용한다.
  - 그 결과로 빌드한 사이트가 Vercel 미리보기로 배포되어, 폰 폭(375px)에서 영상 줄의 '요약 보기'가 동작한다.
  - Gemini 키가 없거나 호출이 모두 실패해도 영상이 요약 없이 올라가고 뒤 단계가 끝까지 도는 것이 자동 테스트로 확인된다.
  - 받은 지 30일 지난 요약이 DB, 실행 전 사본, 작업 파일, 사이트 데이터 어디에도 남지 않는 것이 자동 테스트로 확인된다.

## 2. 확정된 결정과 제약

### 2.1 계획과 앞 단계에서 가져온 결정 (다시 묻지 않는다)

- plan D1~D14와 2.2 제약, 앞 단계 결정(1~7단계 명세서의 결정)을 따른다. 특히 다음이다.
  - **D1:** 다시 돌려도 안전해야 한다. 백업은 D13의 YouTube 데이터를 빼고 복원할 수 있어야 한다.
  - **D6:** 직접 인용은 15단어 미만이다. 자막 전문은 올리지 않고 요약만 싣는다.
  - **D13, V1, V14, V17:** 영상 기록과 거기 붙은 직접 쓴 글은 받은 날부터 30일이 지나면 모두 지우고, 공개 백업에 넣지 않으며, 화면은 30일 지난 영상을 숨긴다. 요약도 영상 기록이므로 같다(plan 8단계).
  - **D14, S12:** 매일 실행은 main 코드로만 한다. 개발과 확인은 실제 DB의 복사본이나 테스트 DB로만 한다. DB 구조는 마이그레이션(`PRAGMA user_version`)으로 바꾼다.
  - **V3~V5, V8, V9, V11, V15:** 후보 받기, 묶음별 최대 개수(16개), 영상을 사이트 안에서 재생하지 않음, 실행한 날 한 번, 관련 이슈, 생방송 기록 처리는 7단계 그대로다. 미국 영상 제목은 영어 그대로다(V8, plan 8단계). 요약만 한국어로 직접 쓴다.
  - **4.3-1(7단계):** 영상 고르기는 서브에이전트에 맡기지 않고 메인 Claude가 한다.
  - **E12:** 시험 결과는 Vercel 미리보기로 사용자가 폰에서 본다. 운영 주소는 구현 중에 바꾸지 않는다.
  - **3단계 화면 규칙:** 4.3-5(오류와 대기), 4.3-6(375px 우선, 다크 모드, 키보드, 대비 AA, `lang="ko"`), 4.3-7(첫 화면 gzip 300KB), `dependencies` 비움.
  - **6단계 4.8:** 키는 `.env.local`에 두고, 값은 어디에도 쓰지 않으며, 공개 전 점검과 결과물 검사가 키 값을 찾는다.
- **CLAUDE.md:** 여러 곳에서 쓸 로직과 UI는 공통 코드로 만든다. 영상 줄은 `site/src/components/videoView.ts` 하나를 넓혀 쓴다. 키는 `src/keys.ts`를 넓혀 쓴다.
- **docs/memory.md:** 명세서 폴더의 스크린샷은 git에 넣지 않는다. 테스트용 가짜 마이그레이션에는 큰 숫자를 쓴다. `/browser-check` 점검 목록은 `.test-data/browser-check/`에 두고 지어낸 데이터로 빌드해 본다. 이 프로젝트의 gcloud 명령은 `CLOUDSDK_ACTIVE_CONFIG_NAME=tidwyn`으로 돌린다. 자율 구현은 샌드박스를 끈 채로 한다.

- 지난 영상의 요약을 되돌려 채우기, 실패한 날의 요약만 나중에 채우기: V9, T11
- 사이트 안에서 영상 재생, 조회수 표시: V8, 7단계
- 요약을 검색(Pagefind), 로컬 마크다운, 브리프 '전체' 탭에 넣기: 요청이 없었다
- 펼친 상태 기억: 요청이 없었다
- 디자인 기준 문서와 `design-check`: T10
- 데이터에 질문하기, 흐름 리포트: 9·10단계
- Gemini 키를 Vercel이나 결과물에 넣기: 사이트는 정적이고 키는 로컬 수집에서만 쓴다
- 사용자가 볼 무인 예약 실행: `docs/memory.md`의 보류 이슈로 따로 한다

### 해당 없음

- 인증과 권한: 로그인이 없다.
- 남용 방지와 입력 제한: 사이트에 새 입력이 없다. 메모는 영상에서 나온 데이터이고 지시로 따르지 않는다(4.7-1).
- 서버, 원격 DB, 예약 작업: 사용자가 `/brief`를 직접 실행한다. Gemini API는 로컬 스크립트만 부른다.
- 사용 분석: 3단계 P10 그대로다.

## 4. 요구사항

요구사항마다 확인 방법을 붙인다. "자동 테스트"는 `pnpm verify`에 들어가는 테스트다. 자동 테스트는 네트워크를 쓰지 않고(Gemini와 YouTube API는 가짜 응답으로 바꾼다), 실제 `data/`, `.env.local`, 실제 저장소의 `.test-data/`를 읽거나 쓰지 않는다. 예시 데이터는 지어내서 만든다(저장소가 공개다). "E2E"는 `pnpm e2e`다. "화면 확인"은 7단계와 같다.

**용어 정의**

- **확인 후보:** Claude가 후보 목록에서 추려 Gemini로 확인할 영상이다. **확인 후보 파일:** Claude가 쓰는 파일로, 후보 번호와 묶음을 담는다.
- **메모:** Gemini가 영상 하나에 대해 돌려준 구조화된 내용이다. **메모 파일:** 스크립트가 쓰는 작업 파일이다. 둘 다 영상 ID나 제목이 함께 있으므로 영상 작업 파일로 다룬다.
- **요약:** Claude가 메모를 바탕으로 쓴 한국어 글이다. 영상 기록의 일부다.
- **Gemini 키:** `GEMINI_API_KEY`. 프로젝트 폴더의 `.env.local`에 있다(6장).
- 그 밖의 용어(영상 기록, YouTube 데이터, 묶음, 받은 날, 30일 지우기, 대상 날짜, 고르기 끝남, 영상 작업 파일, 실행 기록)는 7단계 명세서와 같다.

### 4.1 Gemini 호출 (T1, T2, T4, T5, T6)

1. **명령과 위치:** 새 명령(영상 확인, 기존 명령처럼 `node src/cli.ts <명령> --run <실행 기록>`)이 확인 후보 파일을 검사하고, 영상마다 Gemini를 불러 메모 파일을 쓴다. 실행 조건(S12)을 따른다. `/brief`의 영상 고르기 단계 안에서 돈다. 시험 모드에서도 돈다.
   - 확인: 자동 테스트로 실제 데이터 폴더 모드에서 실행 조건에 맞지 않으면 거부되고, 스킬 문서의 명령 이름이 실제 명령과 같다.
2. **호출:** Gemini API(`generativelanguage.googleapis.com`)의 `generateContent`에 YouTube 주소(`https://www.youtube.com/watch?v=<ID>`)를 파일 입력으로 넣고 키는 `x-goog-api-key` 헤더로만 보낸다. 요청마다 `store: false`를 넣는다. 영상당 시간 제한과 몇 번의 다시 시도를 둔다. 동시 호출은 3개 이하다. 비용이 줄면 낮은 해상도나 에이전틱 처리를 써도 된다(AI 재량, 실제 호출로 메모 품질을 보고 정한다). 명령 전체는 8분 안에 끝낸다: 메모는 영상 하나가 끝날 때마다 파일에 더하고, 8분에 닿으면 진행 중인 호출도 끊어 그 영상을 시간 초과 실패로 두고 받은 만큼으로 끝낸다(실행 요약에 "시간 제한 도달"). 재시도 대기를 포함해 명령은 9분 안에 끝난다.
   - 확인: 자동 테스트로 가짜 응답(정상, 시간 초과, 일시 오류 뒤 성공, 429 뒤 성공)에서 메모와 실패가 맞고, 키가 헤더로만 가며, 요청 본문에 `store: false`가 있다. 가짜 시계를 넣은 테스트로 8분에 닿으면 진행 중 호출이 끊기고 남은 호출이 없으며 받은 메모가 남는다.
3. **메모 내용:** 정해 둔 형식의 구조화 응답으로 받는다: 쓰인 언어, 형식(해설, 강의·강연, 다큐, 정보성 대담, 정치 토크, 뉴스 클립, 방송·라이브 다시보기, 홍보, 그 밖), 실제 주제, 핵심 내용 여러 개(한국어), 제목이 내용과 맞는지, 홍보 비중. 프롬프트는 전문이나 긴 원문을 옮기지 말라고 한다. 스크립트가 항목 수와 글자 수 상한(값은 AI 재량)을 검사한다. 형식이 맞지 않거나 상한을 넘는 응답은 그 영상의 실패로 본다.
   - 확인: 자동 테스트로 잘못된 형식의 응답과 지나치게 긴 응답이 실패로 남고 메모 파일에 들어가지 않는다.
4. **영상별 실패와 전체 멈춤:** 오류는 응답의 HTTP 상태와 본문(상태·사유)으로 다음과 같이 나눈다.
   - **일시 오류:** 5xx, 분·초 단위 속도 제한의 429는 응답의 지연 값이나 물러남을 따라 다시 시도한다. 다시 시도해도 계속되면 429는 전체 멈춤, 그 밖은 그 영상의 실패다.
   - **전체 멈춤:** 키 없음, 키 거부, 잔액·결제 문제(402, 결제 사유의 400 `failed_precondition`과 403), 일일 할당량이나 소비 한도로 읽히는 429. 응답으로 구분되지 않는 429는 일시 오류로 다룬다. 남은 호출을 하지 않고 실행 요약에 이유를 남긴다("Gemini 키 확인 필요", "Gemini 크레딧 확인 필요", "Gemini 한도 초과").
   - **영상별 실패:** 그 밖의 오류(비공개·삭제·연령 제한 등으로 안 됨, 시간 초과, 빈 응답, 안전 차단, 형식 오류, 200 응답인데 사용량에 영상 토큰이 없음). 없는 영상 ID는 2026-10-30 시험에서 403 `PERMISSION_DENIED`로 왔으므로, 키나 결제 사유가 없는 403은 키 거부가 아니라 영상별 실패다. 그 영상만 메모 없음으로 두고 계속한다. 분류 밖 오류가 연속 3개 나오면 전체 멈춤으로 본다(모델 ID 오류 등으로 헛돌지 않게).
   - 개발 중 실제 호출로 틀린 키, 없는 영상 ID(비공개 영상 ID를 얻을 수 있으면 그것도)의 응답을 받아 보고 그 모양으로 분류와 가짜 응답을 만든다(비용이 거의 없다). 가짜 응답 테스트에 영상 토큰이 없는 200 응답을 넣는다. 실제로 보지 못한 응답(결제, 소비 한도, 비공개 영상)은 공식 문서의 모양을 따르고 보고서에 그렇게 적는다.
   - 실행 기록에 남기는 이유는 정해진 분류로만 쓰고 응답 본문을 옮기지 않는다(주소와 영상 ID가 들어올 수 있다).
   - 확인 후보 검사가 통과한 뒤에는 어느 경우든 명령이 메모 파일(빈 것 포함)을 쓰고, 뒤 고르기·합치기·백업·빌드·배포·요약을 멈추지 않는다(T11).
   - 확인: 자동 테스트(데이터 폴더 지정 흐름)로 키 없음, 키 거부, 402, 소비 한도 429, 계속되는 429, 연속 분류 밖 오류, 모두 실패에서 남은 호출이 없거나 실패로 끝나고, 영상이 요약 없이 적용되며 뒤 단계가 끝까지 돈다. 보고서에 실제로 받아 본 응답의 상태 코드를 적는다.
5. **비용 기록과 상한:** 응답의 토큰 사용량(생각 토큰과 도구 사용 토큰 포함, 실패한 응답의 사용량도)을 합해 실행 기록과 실행 요약에 입력·출력 토큰과 예상 달러를 남긴다(가격은 코드 한 곳). 끊겼다가 이어서 해도 누계가 이어진다. 한 실행의 예상 비용이 $1.50에 닿으면 남은 호출을 하지 않고 그 사실을 남긴다.
   - 확인: 자동 테스트로 가짜 사용량에서 합과 예상 달러가 맞고, 상한을 낮춰 넣으면 그 뒤 호출이 없다.
6. **다시 부르기:** 메모 파일에 끝남 표시를 둔다(표시 방법은 AI 재량). 모든 확인 후보를 처리했거나, 전체 멈춤, 비용 상한, 시간 제한 도달로 정상 종료하면 끝남이다. 끝남이면 같은 실행에서 다시 불러도 Gemini를 부르지 않는다. 프로세스가 끊겨 끝남 표시가 없으면 다시 불렀을 때 메모도 실패 기록도 없는 영상만 부른다. 영상별 실패는 같은 실행에서 다시 부르지 않는다. 스킬 문서의 규칙은 하나다: 명령이 비정상으로 끊겼으면 한 번 다시 부르고, 그 뒤에는 받은 만큼으로 고르기로 간다. 대상 날짜가 고르기 끝남이면 영상 확인도 하지 않는다.
   - 확인: 자동 테스트로 끝남 표시가 있는 파일에서 호출 0건, 전체 멈춤 뒤 호출 0건, 끝남 표시 없는 부분 파일에서 남은 영상만 호출한다.

### 4.2 확인 후보 (T3, T4)

1. **파일과 검사:** Claude가 `work/` 아래 확인 후보 파일에 후보 번호와 묶음을 쓴다. 스크립트가 다음을 거부한다: 후보 목록에 없는 번호, 같은 영상 두 번, 그 후보가 고를 수 없는 묶음, 묶음별 최대(T4) 초과, 합계 24개 초과, 합계 길이 8시간 초과, 3시간 넘는 영상. 위반이면 Gemini를 부르지 않고 메모 파일도 쓰지 않는다. 합계 위반이면 지금 합계와 초과분을 함께 알린다. 고쳐서 다시 검사는 최대 2번이다. 명령이 실행 기록으로 위반 횟수를 세어(7단계 `video-apply`와 같은 방식) 세 번째 위반에서 스크립트가 끝남 표시가 있는 빈 메모 파일을 쓰고 메모 없이 7단계 흐름으로 넘어간다.
   - 확인: 자동 테스트로 거부 경우마다 거부되고 가짜 API가 불리지 않으며, 맞는 파일이 통과하고, 위반 파일로 세 번 부르면 호출 0건에 빈 메모 파일이 생기고 이어서 메모 없는 고르기가 적용된다.
2. **0개:** 확인 후보가 0개이면 Gemini를 부르지 않고 끝남 표시가 있는 빈 메모 파일을 쓰고 고르기로 넘어간다.
   - 확인: 자동 테스트.

### 4.3 최종 고르기와 저장 (T3, T6, T11)

1. **고르기 파일:** 7단계 고르기 파일에 요약 항목을 더한다. 검사에 다음을 더한다: 메모가 있는 영상은 요약이 있어야 한다. 메모가 없는 영상에 요약이 있으면 거부한다(내용을 보지 않은 글을 막는다). 요약은 150자 이상 350자 이하이고 주소(`http`, `www.`)와 메일 주소 모양이 없다(결과물 검사가 메일 주소에서 실패하기 때문이다). 그 밖의 7단계 검사는 그대로다. 메모가 없는 영상을 고를 수 있다(후보 목록 전체에서 고를 수 있는 것도 그대로다).
   - 확인: 자동 테스트로 위 거부 경우가 거부되고 DB가 바뀌지 않으며, 메모 있는 영상과 없는 영상이 섞인 파일이 적용된다.
2. **선별 기준(스킬 문서):** 메모의 형식·주제·홍보 비중·제목 일치로 7단계 기준을 그대로 다시 적용한다: 일반 뉴스 클립, 정치 토크, 방송·라이브 다시보기, 오락·브이로그, 제품 홍보는 빼고, 정보성 대담과 강연은 고를 수 있다. 묶음별 최대와 "좋은 영상이 없으면 채우지 않는다"는 그대로다. 메모를 받은 영상에서 고른다. 메모를 받지 못한 확인 후보(전체 멈춤, 시간 제한, 비용 상한, 그 영상의 실패)도 고를 수 있다. 확인 후보 밖의 영상은 그날 메모를 하나도 받지 못했을 때만 고른다(이 기준은 스킬 문서로 지키고 스크립트가 막지는 않는다).
   - **요약:** 한국어 3~5문장, 150자 이상 350자 이하로 Claude의 말로 쓴다. 영상이 무엇을 말하는지, 핵심 주장과 근거를 담는다. 메모에 없는 사실을 지어내지 않고, 메모의 문장을 옮기지 않으며, 인용은 15단어 미만이다. 영상이 안전하다·적합하다·믿을 만하다고 판정하는 말, 다른 영상·채널을 권하는 말을 쓰지 않는다. 추천 이유도 메모로 쓴다.
   - 확인: 스킬 문서에 기준이 있다(읽어서 확인). 결과의 적절함은 사용자가 본다.
3. **저장과 마이그레이션:** 요약을 영상 기록에 둔다(없을 수 있다). 지금 버전 7의 DB를 열면 새 버전으로 마이그레이션되고 기존 데이터와 기존 영상 기록(요약 없음)이 그대로 남는다. 버전 4~6에서도 올라간다. 실행 전 사본이 마이그레이션 전에 남는 순서는 그대로다.
   - 확인: 자동 테스트로 버전 7(영상 기록 포함)과 4의 DB를 열어 데이터가 그대로이고, 같은 고르기를 두 번 적용해도 영상이 한 번씩이다.
4. **기존 동작:** 7단계의 받기, 거르기, 관련 이슈, 합치기·되돌리기, 고르기 끝남은 바꾸지 않는다.
   - 확인: 7단계 테스트가 통과한다(4.8-1).

### 4.4 30일 지우기, 백업, 유출 막기 (D13, V1, V17)

1. **30일 지우기:** 요약은 영상 기록과 함께 지워지고, 확인 후보 파일과 메모 파일은 영상 작업 파일로 다룬다: 적용하면 지우고, 실패하면 남겼다가 다음 실행의 `start`가 지운다. 시험 폴더의 30일 지우기와 결과물 검사의 금지 이름에도 넣는다. 예전 버전의 실행 전 사본(요약 칸 없음)도 그대로 처리된다.
   - 확인: 7단계 4.1-2 테스트를 요약 문자열까지 넓혀, 30일·31일 전 기록의 요약이 DB, 사본, 작업 파일, 사이트 입력·결과물의 바이트에서 나오지 않는다. 적용 뒤 작업 파일이 없고, 결과물에 메모 파일 이름이 있으면 검사가 실패한다.
2. **백업:** 요약을 백업에 넣지 않는다. 요약 항목 이름은 이슈의 `summary`와 구별되게 정하고 공개 전 점검의 영상 기록 표시 검사에 더한다.
   - 확인: 자동 테스트로 요약이 있는 DB를 백업하면 파일 어디에도 요약 문자열이 없고, 복원한 DB에 영상 기록이 없으며, 요약 항목이 든 백업 파일을 넣은 커밋에서 점검이 실패한다.
3. **키:** `GEMINI_API_KEY`를 `KEY_NAMES`에 더해 6단계 키 읽기와 키 값 점검을 지킨다. 키 값은 실행 기록·요약·출력·작업 파일에 없다. 오류를 남길 때 가린다.
   - 확인: 자동 테스트로 가짜 키를 넣고 인증·네트워크·한도 오류를 낸 실행에서 그 문자열이 어디에도 없고, 가짜 키가 든 결과물과 커밋에서 검사가 실패한다.
4. **실행 기록과 대화창:** 실행 기록(`data/runs/`)과 대화창 요약에 영상 ID, 제목, 메모, 요약을 쓰지 않고 수만 쓴다.
   - 확인: 자동 테스트(가짜 오류 본문에 가짜 영상 ID와 주소를 넣음)로 실행 기록과 실행 요약에 가짜 영상 ID·메모·요약 문자열이 없다.

### 4.5 `start` 출력과 실행 요약

1. **`start`:** 키 줄에 "Gemini 있음/없음"을 더한다(값은 보이지 않는다).
   - 확인: 자동 테스트.
2. **실행 요약:** 확인 후보 수, 메모를 받은 수, 실패 수와 이유, 부르지 않은 수(전체 멈춤, 비용 상한, 시간 제한), 입력·출력 토큰과 예상 달러, 요약을 붙인 영상 수를 더한다.
   - 확인: 자동 테스트로 실행 요약 출력에 위 줄이 나온다.

### 4.6 사이트 (T7, T8)

화면은 7단계 확정 시안의 영상 줄을 넓힌다. 3단계 4.3-5, 4.3-6을 지킨다.

1. **사이트 데이터:** 브리프와 이슈의 영상에 요약을 담는다. 요약이 없는 영상은 그 항목을 뺀다. 같은 DB면 같은 결과다(4.1-2, 3단계).
   - 확인: 자동 테스트.
2. **'요약 보기':** 요약이 있는 영상 줄의 추천 이유 아래에 '요약 보기' 버튼이 있다. 누르면 요약이 열리고 글이 '요약 접기'로 바뀌며, 다시 누르면 닫힌다. 버튼은 `aria-expanded`와 연결된 영역을 가진다. 칩을 바꾸거나 새로 고치면 닫힌 상태로 돌아간다. 브리프 영상 탭과 이슈 '관련 영상'이 같은 공통 컴포넌트를 쓴다. 이 버튼은 영상 링크 밖에 있어 눌러도 YouTube로 가지 않는다.
   - 확인: E2E로 두 화면에서 열고 닫고 키보드로 쓰며, 요약 없는 영상에 버튼이 없고, 칩을 바꾸면 남은 줄도 닫힌다. 화면 확인(375px 라이트·다크, 1440px, 긴 요약, 요약 없는 줄과 섞임). 가로 스크롤이 없고 새 글자 색 대비가 AA 이상이다(`textPairs`에 더한다). 지어낸 데이터(`site/dev/videoFixtures.ts`)에 요약 있는 영상과 없는 영상을 섞는다.
3. **문구:** 출처 줄을 T7로 바꾼다. 사이트 소개의 "Claude가 제목과 설명을 보고 … 고른다"와, 사이트 소개·처리방침의 "추천 이유는 Tidwyn이 쓴 글"을 새 흐름에 맞게 고친다(`test/siteVideos.test.ts`의 문구 단언도 고친다). 사이트 소개 '추천 영상' 절과 처리방침에 다음을 더한다: 확인할 수 있는 영상은 내용을 Google의 Gemini API로 확인해 고른다는 것, 요약은 AI가 영상 내용을 바탕으로 쓴 글이라 틀릴 수 있다는 것, 방문자 정보는 보내지 않는다는 것. 처리방침의 바뀐 날짜를 고친다. 7단계 보고서의 제안대로 "Tidwyn을 만들 때"를 "매일 브리프를 만들 때"로 바꾼다.
   - 확인: 자동 테스트와 E2E(7단계 4.7-4·4.7-5를 고친다).
4. **크기:** 측정 조건에 "30일 × 하루 16개 영상에 요약 350자"를 더해도 파일 수 한도와 브리프 첫 화면 gzip 300KB를 지킨다. 측정용 요약은 영상마다 서로 다른 한국어 글로 만들고 반복으로 늘리지 않는다(반복은 gzip이 없애 거짓으로 통과한다). 넘치면 요약을 첫 화면 밖 파일로 나눠도 된다. 그때 '요약 보기'는 처음 열 때 불러오고, 대기 표시와 실패·다시 시도를 둔다(3단계 4.3-5, E2E 확인 포함).
   - 확인: `test/siteVideos.test.ts` 측정을 넓히고 보고서에 7단계 값과의 차이를 적는다.

## 5. 완료 정의

### AI가 확인하고 끝낸다

- `pnpm verify`와 `pnpm e2e`가 통과한다.
- 4장의 모든 확인이 통과한다.
- `package.json`의 `dependencies`가 없거나 비어 있다.
- 공개 전 점검(`node src/cli.ts precheck`)이 작업 브랜치에서 통과한다.
- 운영 주소가 구현 전과 같은 배포다.
- 명세서 폴더에 `report.md`를 쓴다. 새 명령 사용법, 시험 실행 결과, 파일 크기 값, 실제 데이터 확인 결과, 토큰 기준 예상 비용과 하루 예상 비용, 마지막으로 실제 YouTube API를 쓴 시각, 머지 뒤 첫 실제 `/brief`에서 일어날 일을 담는다.

### 사용자가 마지막에 확인한다

1. 폰에서 보고서의 미리보기 주소를 연다(Vercel `mivomad33`로 로그인). '요약 보기'가 쓸 만한지 본다.
2. 검토 파일을 보고, 메모로 뺀 영상이 맞는지, 요약이 영상과 맞고 읽기 좋은지, 추천 이유가 나아졌는지 본다(T9). 머지 뒤 첫 실제 `/brief`의 결과는 검토 없이 운영에 올라가므로 그 실행 뒤 영상 탭을 한 번 본다.
3. AI Studio 지출 화면에서 실제 청구액을 보고 보고서의 예상 비용과 비교한다(AI는 청구 화면을 쓰지 않는다).
4. 보고서의 지울 날짜까지 시험 폴더, 개발 결과 폴더, 검토 파일, 실제 데이터 스크린샷을 지운다(그 전에 `review-done`을 하면 거기서 지워도 된다).
5. 머지를 승인한다. 머지한 세션이 공개 전 점검 → main push를 한다. 운영 사이트는 머지 뒤 첫 실제 `/brief`가 바꾼다.
