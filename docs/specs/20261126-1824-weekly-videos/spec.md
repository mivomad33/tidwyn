# B2단계 명세서: 영상 탭의 볼만한 영상

- 작성일: 2026-11-26
- 요약: 매일 `/brief`가 사용자의 다른 프로젝트 youtube-insight가 모으고 거른 유튜브 영상 중, 전에 실린 적 없는 것을 분야별로 하루 평균 조회수 순 최대 10개 골라 브리프의 새 섹션 탭 '영상'에 싣는다. Tidwyn 안에는 수집·키·API를 두지 않고 그쪽 DB를 읽기 전용으로 읽기만 한다. AI가 글을 쓰는 단계가 없다.
- 종류: 변경 건 (`/brief` 스킬, CLI, DB, 백업, 공개 사이트, 문서를 바꾼다. 실제 데이터가 매일 쌓이고 사이트가 공개되어 있다)
- 단계: [`docs/plan.md`](../../plan.md)의 B2. B1 뒤에 사용자가 새로 정한 단계다. 다음 단계는 없다.
- 이 문서는 기획과 요구사항만 담는다. 설계와 작업 계획은 구현하는 AI가 정한다.
- 공개 여부: 원본 저장소와 사이트는 이미 공개다. 실린 영상 항목(영상 ID, 제목, 채널, 길이, 조회수, 분야, 순위)은 사이트와 공개 백업(`data` 브랜치)에 실린다. youtube-insight의 DB 파일, 판정 이유, 고르지 않은 영상은 Tidwyn의 커밋·백업·사이트에 들어가지 않는다.

## 1. 목표

- **지금 상태(2026-11-26, main f0d449b 기준):** 브리프의 섹션 탭은 뉴스 탭(전체·한국·세계·IT·AI)과 빌더다. R1(2026-11-24)에서 추천 영상(YouTube Data API, Gemini, 영상 표, 영상 페이지)을 무겁다는 이유로 코드째 지웠다. 사용자는 별도 프로젝트 youtube-insight(`D:\projects\youtube-insight`, 같은 윈도우 PC)로 한국어 검색어 122개의 최근 일주일 롱폼 인기 영상을 yt-dlp로 모으고, `/daily-filter` 스킬이 분야별 상위 영상을 판정해 정보성 있는 것만 통과시킨다. 그 결과는 사용자만 로컬 화면(`ytinsight view`)으로 본다.
- **바꾸려는 이유:** 방문자에게 "오늘 볼만한 영상"을 가볍게 무료로 보여 주고 싶다(사용자, 2026-11-26). 전체 데이터가 아니라 분야별 10개만 싣는다.
- **쓰는 사람:** 브리프를 보는 방문자와 프로젝트 주인. 모든 방문자에게 같다.
- **충분한 수준:** 머지 뒤 `/brief`가 묻지 않고 youtube-insight DB에서 영상을 골라 영상 탭에 싣는다. 한 번 실린 영상은 다시 나오지 않는다. 그날 준비된 데이터가 없으면 없다고 나오고, 뉴스 등 다른 단계는 그대로 돈다. 화면은 사용자가 구현 직후 보고 정한다(V12).

## 2. 확정된 결정과 제약

### 2.1 가져온 결정 (다시 묻지 않는다)

- **영상 탭 다시 넣기와 약관 위험 감수(2026-11-26, 사용자 결정, `docs/memory.md`):** youtube-insight DB에서 분야별 상위 10개만 읽어 공개한다. Tidwyn 안에 수집·키·API를 두지 않는다. API 없이 자동 수집한 결과를 공개하는 것이 YouTube 약관의 회색지대인 것을 알고 감수한다. 광고를 달 때나 YouTube가 문제를 삼을 때 다시 본다.
- **수집 시각(2026-11-26, 사용자):** 사용자가 youtube-insight 수집·판정을 앞당겨 오전 6시 `/brief` 전에 끝나게 한다(6장 사용자 할 일).
- **기능 줄이기(2026-11-24, 사용자 결정):** AI가 새 기능을 제안하지 않는다. 이 단계는 사용자가 직접 요청했다.
- **운영(`docs/memory.md`):** 매일 `/brief`는 메인 폴더(`D:\projects\tidwyn`)의 main, 깨끗한 작업 트리에서 예약 작업으로 오전 6시에 돌고 Sonnet 5.5로 돈다. 단계 작업은 worktree에서 한다. CI는 없다. 사이트 말투는 습니다체다(2026-11-25).
- **스크린샷은 git에 넣지 않는다, 점검은 지어낸 데이터로 한다, 테스트용 가짜 마이그레이션은 큰 숫자를 쓴다, AI가 할 수 있는 정리를 사용자에게 넘기지 않는다(`docs/memory.md`).**
- **CLAUDE.md:** 공통 코드를 먼저 쓰고, 화면은 `docs/design.md`를 따른다. README 두 파일을 함께 고친다.
- **디자인:** 새 방향이 없다. 화면은 `docs/design.md`를 따르고, 기준에 없는 부분(영상 항목)은 기준의 토큰과 부품으로 만든다(`write-spec` 5장, 시안 없음).
- **B1 방식(2026-11-25):** 브리프 날짜에 붙는 기록, 날짜마다 상태 셋, 실패가 다른 단계를 막지 않음, 정적 HTML·검색에 넣고 RSS·사이트맵에 넣지 않음, 항목별 페이지·읽은 표시·정정 없음은 B1(`docs/specs/20261125-1531-trending-repos/spec.md` G9~G11)과 같게 한다.

## 3. 범위

### 3.1 넣는 것

- youtube-insight DB 읽기와 고르기, 저장: 새 명령(이름은 구현 재량) → 4.1
- 백업과 복원 → 4.2
- 사이트 영상 탭, 정적 HTML, 검색, 소개, 처리방침 → 4.3
- 스킬·운영 문서·README·디자인 기준 → 4.4
- 검증과 시험 실행 → 4.5

### 3.2 넣지 않는 것

- youtube-insight 저장소 고치기(그쪽 `docs/project_overview.md`의 "다른 사람에게 공개하는 서비스로 만들지 않는다" 고치기 포함): V2. 그 문서 고치기는 그 저장소의 규칙(작업 브랜치, 그쪽 CI)으로 따로 한다.
- youtube-insight 수집·판정 예약을 앞당기기: 사용자가 한다(6장).
- 설명 글, 판정 이유, 업로드 시각, 채널 링크: V6.
- 라이브 다시보기: V5.
- 영상 항목의 RSS·사이트맵·항목별 페이지·읽은 표시·정정, 영상 끼워 넣기(embed) 재생: 2.1의 B1 방식. 끼워 넣기는 YouTube 스크립트와 쿠키가 들어와 처리방침과 무게가 크게 바뀐다.
- 지난 날짜 소급(빠진 날짜에 영상 채우기): V11.
- 마크다운 브리프(`briefs/*.md`)에 영상 넣기: 마크다운은 뉴스 기록이고 영상 단계가 저장(`save`)보다 뒤다(B1과 같다).
- 이슈·인물 페이지에 영상 보이기, 영상과 뉴스 연결: R1에서 지운 7단계 기능이고 사용자가 요청하지 않았다.
- 영어 영상, YouTube Data API, Gemini, 영상 고르기에 AI 판단 더하기: V2(판정은 youtube-insight가 한다).
- 실린 영상을 내리는 명령: 지금은 두지 않는다(B1과 같다. 필요하면 사용자가 정한다).
- `design-check`: run-stage에서 잠정 제외(사용자 결정 2026-11-10). 사용자가 구현 직후 화면을 직접 본다(V12).

### 3.3 해당 없음

- 인증과 권한, 입력 제한: 로그인과 입력이 없다.
- 서버, 원격 DB, 비용: 로컬 수집과 정적 사이트 그대로이고 유료 호출이 없다.
- AI가 쓰는 글과 프롬프트 공격: 이 단계에는 Claude가 읽고 쓰는 작업 파일이 없다. 영상 제목·채널은 명령이 데이터로만 옮긴다.
- 사용 분석: 바뀌지 않는다. 새 브라우저 저장 키도 없다(탭 저장값 `tidwyn.briefTab`에 '영상' 값이 하나 늘고, 영상 탭의 분야 칩은 기존 거르기 칩이 저장하는 방식을 따른다).

### 3.4 R1과 부딪히는 곳 (2026-11-26 조사)

R1은 영상을 지우면서 다시 생기지 않게 막는 검사와 예약 이름을 남겼다. 이 단계는 그중 아래만 의도적으로 푼다. 나머지(수요·Product Hunt·도구 변화·YouTube Data API·Gemini를 막는 검사, 지운 키 이름 목록 `RETIRED_KEY_NAMES`)는 그대로 둔다.

- 스킬 문서에서 `video`·`youtube`·`영상` 낱말을 막는 검사와 지운 명령 목록 `video-fetch`(`test/r1Trim.test.ts`), 결과물·소개·처리방침에서 '영상'·`YouTube`·`videos-`·`video-sections-`와 youtube.com 링크를 막는 검사(`test/r1TrimSite.test.ts`), 정적 HTML의 `id="videos"`와 '영상' 글, 옛 해시 `#videos`를 지운 것으로 보는 E2E(`test/e2e/stageR1.spec.ts`), 데이터 파일 이름 검사(`/video|.../i`), 백업 형식 버전을 단언하는 검사. 이 단계가 다시 쓰는 낱말·링크·구역·탭 값·해시만 허용하도록 고친다. YouTube 이용약관 링크와 Gemini 문구를 막는 처리방침 검사는 남긴다. 새 명령 이름으로 `video-fetch`는 쓰지 않는다(지운 명령으로 남긴다).
- 옛 이름은 새로 쓰지 않는다: DB 표 이름에 `video` 앞머리를 쓰지 않는다(`RETIRED_TABLE_PREFIXES`, 옛 표로 보고 지운다). 영상 페이지 주소 `/videos/...`는 404 그대로다(V13).

## 4. 요구사항

"자동 테스트"는 `pnpm verify`에 들어가는 테스트다. 네트워크를 쓰지 않고, 실제 `data/`와 실제 youtube-insight DB를 쓰지 않으며, 지어낸 데이터(지어낸 youtube-insight 모양의 SQLite 파일 포함)만 쓴다. "E2E"는 `pnpm e2e`다.

### 4.0 용어

- **원천 DB:** youtube-insight의 SQLite 파일. 기본 경로는 Tidwyn 저장소 폴더 기준 `../youtube-insight/data/youtube.sqlite`이고, 환경 변수 하나(이름은 구현 재량, `TIDWYN_` 앞머리)로 바꿀 수 있다.
- **기준 시각:** V9의 영상 명령 실행 시각.
- **영상 항목:** 한 브리프 날짜에 실린 영상 하나(영상 ID, 제목, 채널, 길이, 조회수, 분야, 분야 안 순위).
- **영상 기록:** 한 브리프 날짜의 영상 상태(실음 / 새 영상 없음 / 받지 못함)와 그날의 항목.
- **대상 날짜(영상):** V11의 날짜.

### 4.1 읽기, 고르기, 저장 (V2, V3, V5, V8~V11)

- **4.1-1** 새 명령 하나(이하 '영상 명령')가 대상 날짜를 정한다. 그 날짜의 영상 기록이 이미 '실음'이나 '새 영상 없음'이면 원천 DB를 열지 않고 '이미 끝남'을 출력한다. 저장된 브리프가 하나도 없으면 '대상 없음'을 출력한다. 그 밖이면 원천 DB를 읽기 전용으로 열어 V9대로 고르고(연결 하나, 읽기 트랜잭션 하나, 잠금 대기는 몇 초로 짧게, 읽기가 끝나면 바로 닫는다. youtube-insight의 쓰기는 잠금을 60초까지만 기다리므로(`LOCK_WAIT_SECONDS`) 연 시간이 그보다 훨씬 짧아야 한다. 잠금 대기가 끝나도 열 수 없으면 '받지 못함'), 한 트랜잭션에 그 날짜의 영상 기록으로 저장한다. V10의 각 경우는 '받지 못함'으로 저장하고 이유를 실행 기록(로컬)에 남기며 종료 코드 0으로 끝난다. 다시 돌려도 중복되지 않고, '실음'이나 '새 영상 없음'인 날짜를 덮지 않는다.
  - 확인: 자동 테스트(통합, 임시 데이터 폴더, 지어낸 원천 DB)로 정상 저장, '이미 끝남'에 원천 DB를 열지 않음, '대상 없음', 대상 날짜가 가장 늦은 저장된 날짜인 것(앞 날짜에 기록이 생기지 않음), '받지 못함'인 날짜를 다시 고르는 것, 다시 돌려도 행 수가 같은 것을 본다.
- **4.1-2** 고르기 규칙(V9, V8, V5, V3): 분야마다 하루 평균 순, 최대 10개, 라이브 다시보기 제외, 업로드 7일 경계, 전에 실린 영상 제외(모든 날짜), 두 분야 통과 영상은 순위가 높은 분야 하나(같으면 분야 순서), 후보 부족 시 있는 만큼, 결과물 검사에 걸리는 제목·채널은 건너뛰고 다음으로 채움, `current_passed`에 없는 영상(제외·취소·판정 안 됨)은 고르지 않음, 분야 순서.
  - 확인: 자동 테스트(통합, 지어낸 원천 DB)로 규칙마다 걸리는 것과 닮았지만 남는 것을 본다: 11번째는 빠지고 10번째는 남음, `was_live` 1은 빠지고 0은 남음, 7일 경계 직전은 빠지고 경계 시각은 남음, 전에 실린 ID는 빠지고 처음 보는 ID는 남음, 두 분야 통과 영상이 한 번만 나오고 다른 분야가 다음 영상으로 채워짐(순위가 같을 때 분야 순서), 제외·취소된 판정은 빠짐, 스냅샷이 여럿이면 가장 늦은 것을 씀(수집일이 같으면 관측 시각이 늦은 것), 스냅샷이 없는 통과 영상은 빠짐, 7일 경계는 바꿔 넣은 기준 시각으로 잼, 업로드 시각이 기준 시각보다 늦은 통과 영상도 남음, 하루 평균의 1일 하한과 소수 날 수(1.5일이면 내림하지 않음), 결과물 검사에 걸리는 제목 또는 채널 이름 대신 다음 영상, 모르는 분야 이름이 뒤에 옴.
- **4.1-3** 준비 확인(V10, V2): 원천 DB 없음, 열 수 없음(잠김 등), 필요한 표·보기·칸이 없음은 '받지 못함'이고 이유가 각각 다르게 남는다. 후보 0개면 '새 영상 없음'이다. `runs`에 완주 실행이 없거나 마지막 수집이 오래돼도, 업로드 7일 안의 통과 영상이 있으면 '실음'이다. 원천 DB는 어떤 경우에도 바뀌지 않는다(파일 해시가 같다).
  - 확인: 자동 테스트(통합)로 각 경우의 상태와 이유, `runs`가 비었거나 마지막 수집이 오래된 원천 DB에서도 통과 영상을 고르는 것, 판정이 일부만 있을 때 통과 영상만 고르는 것, 칸 하나를 지운 원천 DB가 '받지 못함'인 것과 쓰지 않는 칸을 더한 원천 DB가 정상인 것, 실행 전후 원천 DB의 sha256이 같은 것을 본다.
- **4.1-4** 영상 단계의 어떤 실패도 뉴스, 이슈, 일정, 지표, 저장소, 백업, 빌드, 배포, push를 막지 않는다. 영상 명령이 비정상 종료해도 스킬은 다음 단계로 간다. 실행 요약에 영상 결과(대상 날짜, 기준 시각, 상태, 분야별 실은 수, 받지 못한 이유)가 나온다. 영상 단계를 돌지 않은 실행의 요약은 '이번 실행에서 하지 않음'으로 쓴다.
  - 확인: 자동 테스트(통합)로 '받지 못함'인 실행에서 `backup`·`site`가 성공하고 요약에 영상 줄이 나오는 것, 영상 명령을 부르지 않은 실행의 요약을 본다. 스킬 문서에서 새 단계의 "실패해도 다음 단계로" 문구를 대조한다.
- **4.1-5** 시험 모드(`/brief test`)와 데이터 폴더 지정 실행에서도 원천 DB를 읽는다(읽기 전용이라 실제 원천 DB를 읽어도 된다. 경로는 4.0의 환경 변수로 바꿀 수 있다). 자동 테스트는 늘 지어낸 원천 DB를 가리키고, 실제 원천 DB를 가리키면 실패한다.
  - 확인: 자동 테스트(통합)로 시험 모드에서 영상 명령이 지정한 원천 DB를 읽는 것, 테스트 도우미가 기본 경로를 쓰지 않는 것, 도우미에 기본 경로(저장소 기준 `../youtube-insight/data/youtube.sqlite`)를 주면 그 테스트가 실패하는 것(실제 파일을 열지 않고 경로로만 비교)을 본다.
- **4.1-6** 원천 DB의 판정 이유, 고르지 않은 영상, 실행 중에 쓴 원천 DB 경로는 Tidwyn DB의 영상 항목, `data` 브랜치 백업, 사이트 결과물에 들어가지 않는다. 코드의 기본 상대 경로(4.0)와 `docs/operations.md`의 경로 안내는 예외다(README·소개·처리방침에는 쓰지 않는다, 4.3-4·4.4-2). 받지 못한 이유(경로가 들어갈 수 있다)는 실행 기록과 요약 출력에만 있다.
  - 확인: 자동 테스트(통합)로 지어낸 판정 이유 문자열과 고르지 않은 영상 제목, 지어낸 원천 DB 경로(홈 경로 모양)가 백업 파일과 사이트 결과물 어디에도 없는 것을 본다.

### 4.2 백업과 복원

- **4.2-1** 영상 기록(날짜별 상태와 항목)을 공개 백업에 넣고 복원한다(새 파일 이름, 3.4). 백업 형식 버전을 하나 올리고(지금 12), 바로 앞 형식 백업도 복원된다(영상 기록 없이). DB 업그레이드는 쌓인 기록을 보존한다. 백업에는 상태와 항목만 싣고 받지 못한 이유는 싣지 않는다. 새 백업 파일 이름을 결과물 검사의 백업 파일 이름 목록(`BACKUP_NAME_RE`)에 더한다.
  - 확인: 자동 테스트(통합)로 백업 → 복원 → 다시 백업의 내용이 같은 것, 지어낸 받지 못한 이유가 백업에 없는 것, 새 백업 파일을 결과물에 넣으면 결과물 검사가 실패하는 것(단위), 형식 12의 지어낸 백업이 오류 없이 복원되는 것, 옛 DB를 업그레이드해 기존 값이 그대로이고 두 번 업그레이드해도 같은 것을 본다.

### 4.3 사이트 (V6, V7, V13)

- **4.3-1** 브리프 섹션 탭에서 IT·AI 뒤, 빌더 앞에 '영상' 탭이 있다. 그 날짜에 영상 기록이 있을 때만 보인다. 탭 글은 건수 없이 '영상'이다. '전체' 탭과 날짜 목록의 뉴스 읽은 수에 영상이 섞이지 않는다. 탭을 고르면 기존 탭처럼 `tidwyn.briefTab`과 기록 상태로 기억된다. `#videos`로 들어오면 그날 영상 탭을 연다(V13). 영상 기록이 없는 날짜로 가면 기존 탭 대체 동작(그날 있는 첫 섹션 탭)을 따른다. 영상 탭에는 뉴스 대분류 칩과 '안 읽은 것만'을 두지 않고, 그날 요약·키워드와 이번 주 일정|지표 상자의 규칙은 뉴스 탭 기준 그대로다(빌더와 같다).
  - 확인: E2E(지어낸 데이터)로 영상만 있는 날, 영상과 빌더가 모두 있는 날, 둘 다 없는 날의 탭 목록과 순서, '전체' 탭에 영상이 없는 것, 영상 탭을 고른 뒤 기록 없는 날짜로 가면 그날 첫 섹션 탭인 것, 새로 고치면 영상 탭이 다시 열리는 것, `#videos`로 열면 영상 탭인 것, `/videos/<날짜>/abc`가 404인 것을 본다.
- **4.3-2** 영상 탭 머리에 굵은 제목 '이번 주 볼만한 영상'과 분야 칩('모든 분야'와 그날 있는 분야만, 건수)이 있다. 처음에는 '모든 분야'이고 분야 순서(V9)대로, 분야 안에서는 순위대로 보인다. 항목마다 썸네일, 제목(영상 주소 `https://www.youtube.com/watch?v=<ID>`를 새 탭으로 여는 링크), 채널 이름, 조회수(만·억 단위 어림 표기, 문구는 재량), 길이(시:분:초 또는 분:초)가 보인다. '모든 분야'에서는 항목의 분야도 알 수 있다(모양은 재량). 썸네일은 V6의 고정 주소이고(지어낸 데이터로 띄우는 개발·점검용 빌드에서만 썸네일 주소 앞부분을 로컬 이미지로 바꾸는 개발 전용 선택지를 둘 수 있다. 운영 빌드에는 그 선택지가 없고, E2E의 `src` 검사는 고정 주소로 한다), 늦게 받고(`loading="lazy"`), 뉴스 이미지처럼 `referrerPolicy="no-referrer"`이며, 크기를 미리 잡아 화면이 튀지 않으며, 받지 못하면 빈 자리만 남는다(깨진 이미지 표시 없음). 상태가 '새 영상 없음'이면 공통 빈 상태로 새로 실을 영상이 없다고 쓰고, '받지 못함'이면 오늘은 영상을 준비하지 못했다고 쓴다(습니다체). 받지 못한 이유는 사이트에 싣지 않는다.
  - 확인: E2E로 순서, 각 칸, 링크 `href`와 새 탭, 썸네일 `src`가 고정 주소 모양이고 `loading="lazy"`·`referrerPolicy="no-referrer"`인 것, 분야 칩의 건수와 거르기, 긴 제목(100자)과 긴 채널 이름에서 375px 가로 스크롤이 없는 것, 두 빈 상태 문구, 지어낸 받지 못한 이유가 결과물에 없는 것을 본다. E2E는 썸네일 요청을 가로채 외부로 나가지 않게 하고, 실패 응답일 때 빈 자리인 것도 본다. 자동 테스트(통합)로 개발 전용 선택지(환경 변수나 인자)를 준 채 운영 경로(`node src/cli.ts site`)로 빌드해도 썸네일 주소가 고정 주소인 것을 본다.
- **4.3-3** 브리프 정적 HTML에 영상 구역(분야별 제목, 링크, 채널, 조회수, 길이. 썸네일 `<img>`는 넣지 않는다: 정적 HTML의 이미지를 막는 기존 검사 `test/siteStatic.test.ts`·`test/siteBuild.test.ts`는 그대로 둔다)과 구역 이동 칩이 있다(기록이 있는 날만). 사이트 검색에서 영상 제목과 채널 낱말로 찾아지며 결과를 누르면 그 날짜의 영상 탭이 열린다. RSS(`rss.xml`)와 사이트맵은 그대로다.
  - 확인: 자동 테스트(통합, 지어낸 데이터로 빌드)로 정적 HTML의 지어낸 제목, RSS와 사이트맵에 그 제목이 없는 것, 기록 없는 날의 정적 HTML에 영상 구역과 칩이 없는 것을 본다. E2E로 검색 결과를 눌러 영상 탭으로 가는 것을 본다.
- **4.3-4** 사이트 소개 페이지에 영상 탭 안내를 더한다: 유튜브 검색으로 모은 최근 일주일 한국어 영상 중 분야에 맞고 정보성 있다고 AI가 판정한 것을 하루 평균 조회수 순으로 분야별 최대 10개 싣는다는 것, 한 번 실린 영상은 다시 싣지 않는다는 것, 라이브 다시보기는 뺀다는 것, 추천이나 보증이 아니라는 것. 처리방침에 영상 탭 썸네일은 방문자 브라우저가 YouTube(Google) 이미지 서버에서 직접 받는다는 것(그 서버가 방문자의 IP 주소 등 요청 정보를 받는다는 것)을 더하고, `tidwyn.briefTab` 설명(`site/src/lib/browserKeys.ts`)에 '영상'을 더하며, 바뀐 날짜(`PRIVACY_UPDATED`)를 이 고침을 커밋하는 날로 고친다. 소개와 처리방침에 youtube-insight 경로·저장소 주소는 쓰지 않는다(비공개 저장소다).
  - 확인: 자동 테스트(통합)로 소개 문구, 처리방침의 썸네일 문구와 탭 값 문구와 바뀐 날짜, 두 페이지에 `youtube-insight` 낱말이 없는 것을 본다.
- **4.3-5** 화면은 `docs/design.md`를 따른다. 영상 항목은 기준의 토큰과 공통 부품(`.text-link`, `NewTabMark`, `Empty`, 거르기 칩, 구역 제목)으로 만들고, 새 규칙(영상 항목, 썸네일 비율)은 `docs/design.md`에 적는다. 375px·1280px, 라이트·다크, 키보드, 폰 누를 곳 44px를 지킨다. 썸네일에는 빈 `alt`를 둔다(제목 링크가 바로 옆에 있다).
  - 확인: 시각 회귀 테스트(E2E)에 영상 탭(실음·새 영상 없음·받지 못함, 375·1280, 썸네일은 테스트용 로컬 이미지)을 더한다. 구현 단계에서는 시각 회귀 테스트와 4.5-2 화면까지 하고 끝난다. 그 뒤 사용자가 화면을 보고(V12), `browser-check` 깨끗한 회차는 run-stage의 다음 단계에서 한다.
- **4.3-6** 크기 한도(`site/size.ts`의 첫 화면 300KB 조건)를 지킨다. 영상 항목은 하루 최대 70개라 쌓이면 크다(5년이면 약 12만 개). 첫 화면 데이터에 날짜별 영상 항목을 다 싣지 않는다(날짜를 열 때 받는 등, 방식은 재량). 5년, 하루 70개, 제목 100자의 지어낸 최악 조건으로 첫 화면 크기와 날짜 하나의 영상 데이터 크기(gzip 300KB 이하)를 잰다. Vercel Hobby 한도(총 100MB, 파일 15,000개, `docs/operations.md`의 "Vercel 한도")에 미치는 영향도 잰다: 기존 5년치 최악 조건 측정에 영상을 더해 늘어나는 전체 크기와 파일 수. 나누는 방식은 파일 수가 덜 느는 쪽을 고른다. `docs/operations.md`의 한도 표를 고친다.
  - 확인: 자동 테스트(첫 화면 300KB, 날짜 하나 300KB, 기존 파일 수 회귀 테스트에 영상 포함), 값을 보고서에 적는다.

## 5. 완료 정의

### AI가 확인하고 끝낸다

- 4장 요구사항의 확인을 모두 실행해 통과한다. `browser-check` 깨끗한 회차는 V12의 사용자 확인 뒤 run-stage의 다음 단계에서 하며, `implement-spec`이 끝날 때는 사용자 확인 항목으로 본다.
- `site/` 코드가 새로 가져오는(import) 외부 패키지가 없다(`devDependencies` 차이와 `site/src`의 import 목록으로 본다).
- 머지 전까지 메인 폴더, 실제 데이터 폴더, `data` 브랜치, 운영 배포, youtube-insight 저장소가 그대로다(사용자의 `/brief`·youtube-insight 실행은 예외).

### 사용자가 마지막에 확인한다

1. 구현 직후(`browser-check` 전) AI가 띄운 화면(지어낸 데이터, 그리고 4.5-2의 실제 데이터로 만든 화면)을 보고 정보와 디자인이 적절한지 본다. 고칠 것이 있으면 알리고, AI가 고친 뒤 `browser-check`로 간다.
2. youtube-insight 문서(`docs/project_overview.md`의 "다른 사람에게 공개하는 서비스로 만들지 않는다")를 이 결정에 맞게 고치는 일은 이 단계 밖이다(3.2). 이번 실행에서는 하지 않고 결과 보고서의 후속 일에만 적는다. 사용자가 요청하면 별도 세션에서 그 저장소 규칙(작업 브랜치, 사용자 확인 뒤 머지)으로 한다.
3. 머지는 V12대로 run-stage 5장을 따른다. 머지하면 메인 폴더에서 squash merge, 공개 전 점검, main push를 하고 worktree와 브랜치를 지운다. 운영 사이트는 머지 뒤 첫 `/brief`가 바꾸고, 그날 영상 탭이 처음 생긴다. 그 아침 영상 탭이 '받지 못함'이나 '새 영상 없음'이면 원천 DB와 youtube-insight 수집·판정을 본다.

## 7. 진행 규칙

- 작업 폴더는 worktree `../tidwyn-stageB2`이다. Bash 명령은 worktree 절대 경로로 `cd`한 뒤 실행하고, 파일 도구는 그 절대 경로를 쓴다. 서브에이전트 지시에도 넣는다. 메인 폴더의 `data/tidwyn.db`는 4.5-2의 사본 복사만 하고 쓰지 않는다. 사본은 파일 복사로만 뜨고, 메인 폴더의 가장 늦은 실행 기록에 `push` 결과가 있을 때(돌고 있는 `/brief`가 없을 때) 복사하며, 사본에서 `PRAGMA integrity_check`로 확인한다. 조건이 맞지 않으면 그 실행 기록의 실행 전 사본(`snapshots/`)을 쓰고, 그것도 없으면 지어낸 브리프 날짜를 저장한 시험 DB로 4.5-2를 돌리고 보고서에 적는다. `node src/cli.ts`로 DB를 여는 모든 시험 호출에 `TIDWYN_DATA_DIR=<worktree 절대 경로>/.test-data/<시험 폴더>`와 원천 DB 경로 환경 변수(사본)를 붙인다.
- 실제 원천 DB(`D:\projects\youtube-insight\data\youtube.sqlite`)는 4.5-2의 온라인 백업 복사로만 읽고, 다른 연결을 열지 않는다. youtube-insight 저장소의 파일을 고치지 않는다.
- **멈추는 곳(V12):** `implement-spec`이 끝나면 `browser-check` 전에 멈추고, 지어낸 데이터와 4.5-2의 결과물을 로컬 서버로 띄워 앱 안 브라우저로 보여 주고 사용자 답을 기다린다. 멈추기 직전 `run_stage_state.py wait`를 적고, 답을 받으면 `resume`한다.
- 머지는 메인 폴더에서 `/brief`가 돌고 있지 않을 때 한다(메인 폴더 `data/runs/`의 가장 늦은 실행 기록의 `push` 칸이 null이 아니면 돌고 있지 않다. null이고 시작한 지 3시간이 넘었으면 끊긴 실행으로 본다. null이고 3시간이 안 됐으면 기다렸다가 다시 본다). 작업 브랜치는 push하지 않는다.
