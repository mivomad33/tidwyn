# 9.95단계 명세서: 되살릴 수 없는 수요 스냅샷

- 작성일: 2026-11-04
- 요약: 매일 `/brief`가 Google Trends 급상승 RSS(30개국)와 Mastodon 인스턴스 12곳의 트렌드 태그·링크를 받아, 작성자 칸만 버리고 수요 데이터 전용 로컬 DB에 쌓는다. 지난 날짜를 나중에 받을 수 없는 소스라 이력부터 쌓는다. AI는 이 데이터를 읽지 않고, 사이트와 공개 백업에 넣지 않는다.
- 종류: 변경 건 (`/brief`, 로컬 데이터, 운영 문서를 바꾼다. 실제 데이터가 매일 쌓이고 사이트가 공개되어 있다)
- 단계: [`docs/plan.md`](../../plan.md)의 9.95단계. 수요 신호 단계(9.95~9.99) 중 첫 단계다. 9.96(공식 수요 데이터)이 이 단계의 저장·끄기·약관 판정 장치를 함께 쓰고, 9.97(수요 흐름)과 9.98(커뮤니티 신호)이 이 데이터를 보조 근거로 쓴다.
- 이 문서는 기획과 요구사항만 담는다. 설계와 작업 계획은 구현하는 AI가 정한다.
- 공개 여부: 원본 저장소와 사이트는 이미 공개다. 받은 데이터는 로컬에만 둔다(사이트, 공개 백업, git에 넣지 않는다). 소스 판정 문서와 코드는 공개 저장소에 들어간다.

## 1. 목표

- **지금 상태:** 수요 신호를 모으는 장치가 없다. 급상승 검색어와 Mastodon 트렌드는 그날 받지 않으면 지난 날짜를 나중에 받을 수 없다.
- **바꾸려는 이유:** 9.97이 흐름을 만들 때 쓸 보조 근거의 이력을 일찍 쌓는다(D16, plan 3.15). 화면과 AI 판단이 없어 작게 먼저 한다.
- **쓰는 사람:** 프로젝트 주인 한 사람. 이 단계에서는 아무것도 보이지 않는다. 실행 요약에 소스별 상태와 수만 나온다.
- **충분한 수준:** 머지 뒤 예약 `/brief`가 묻지 않고 매일 받아 쌓는다. 받지 못한 소스가 있어도 나머지가 쌓이고, 뉴스 브리프와 다른 탭이 그대로 올라간다. 9.96이 같은 장치에 소스를 더할 수 있다.

## 2. 확정된 결정과 제약

### 2.1 계획과 앞 단계에서 가져온 결정 (다시 묻지 않는다)

- **D16:** 공식 API·피드·파일 중 무료인 것만 쓴다. 약관이나 robots가 AI 입력·자동 수집을 막거나, 확인하지 못했거나 애매한 소스는 쓰지 않는다. robots는 `*`나 Anthropic 계열 봇을 막을 때만 막힌 것으로 본다. 판정은 저장·AI 입력·요약 게시·공개 백업 네 가지다. 작성자 이름·계정·닉네임은 받을 때 버리고, 그 밖에는 가공하지 않고 지우지 않는다(약관이 삭제를 요구하면 따른다). 급상승어와 트렌드는 공개 백업에 넣지 않고 로컬에만 둔다. 로컬 DB를 잃으면 이력을 잃는 것은 감수한다. 글 칸은 격리 프로세스만 읽는다(이 단계에서는 아무 AI도 읽지 않는다). 수요 수집이 실패해도 뉴스와 다른 탭은 올라간다.
- **plan 3.15:** 급상승 RSS는 받기 직전 한 시간 안팎의 10건쯤만 주고 단독으로 흐름을 만들지 못하며 '서로 다른 소스 두 곳'에 세지 않는다(9.97이 지킨다). 국가·분야는 소스가 허용하는 한 넓게 받는다. 하루 저장 증가량을 실측해 보고서에 적는다. 뒤 단계는 이 단계의 약관 판정을 따른다.
- **D1:** 다시 돌려도 안전하다(같은 날 중복 저장 없음). 지난 날짜를 되돌려 받을 수 없는 데이터는 실행한 날 기준으로만 모은다. 수요 신호의 공개 백업 범위는 D16 예외를 따른다. **D14:** 개발과 확인은 실제 데이터 폴더의 복사본이나 시험 폴더로만 한다.
- **9.9단계:** 소스 끄기 값은 코드 한 곳에 두고 끈 소스는 호출하지 않는다(B·N 규칙). 시험 모드(`/brief test`)에서 스냅샷은 꺼짐이고 `custom`(데이터 폴더 지정)은 켜짐이다. 수집 실패는 종류별로 가두고 다음 단계로 간다.
- **`docs/memory.md`:** 예약 `/brief`가 06시경 메인 폴더 main에서 돈다. 작업은 worktree에서 하고 작업 브랜치는 push하지 않는다. CI와 폰 알림이 없다. 테스트용 가짜 마이그레이션은 큰 숫자를 쓴다. AI가 할 수 있는 정리를 사용자에게 넘기지 않는다. 막힌 페이지를 우회하지 않는다.
- **CLAUDE.md:** 공통 코드를 쓴다. README 두 파일을 함께 고친다. 결정은 `docs/memory.md`에 바로 적는다.

## 4. 요구사항

"자동 테스트"는 `pnpm verify`에 들어가는 테스트다. 네트워크를 쓰지 않고(소스는 가짜 응답), 실제 `data/`를 쓰지 않으며, 지어낸 데이터만 쓴다.

**용어 정의**

- **소스:** 받는 단위 하나. Google은 나라 하나, Mastodon은 인스턴스 하나다(태그와 링크를 함께 받는다).
- **스냅샷:** 한 소스를 한 날짜(KST)에 받은 응답 원문(S6)과 그 메타데이터.
- **전용 DB:** S4의 수요 데이터 DB 파일. **본 DB:** `tidwyn.db`.
- **상태:** 소스마다 그날의 결과. 받음 / 받지 못함(사유) / robots 막힘 / 꺼짐.
- **받기 명령:** 이 단계가 더하는 명령(이름은 구현 재량).

### 4.1 받기와 저장 (S2, S3, S4, S6)

1. **받기:** 받기 명령이 켜진 소스를 차례로 받아 그날(KST) 스냅샷으로 전용 DB에 저장한다. Google은 나라마다 피드 하나를 받는다. Mastodon은 인스턴스마다 트렌드 태그와 링크를 받고, 한 번에 20건씩 주므로 빈 응답이나 상한(각 100건)까지 페이지를 넘긴다. 요청 간격은 같은 호스트에 2초 이상이고, 호스트가 다르면 서로 기다리지 않고 동시에 받는다(Mastodon 큰 인스턴스는 태그·링크가 각 100건까지 차 인스턴스 하나에 요청이 11번쯤이라, 차례로 받으면 5분을 넘긴다). 요청마다 시간 상한을 둔다. 명령 전체는 5분 안에 끝나고, 넘으면 남은 소스를 받지 못함으로 두고 끝낸다. 리디렉션은 따라가지 않는다. Mastodon 인스턴스는 태그와 링크를 모두 받았을 때만 스냅샷으로 저장하고, 하나라도 실패하면 그 인스턴스는 받지 못함이다(같은 날 다시 돌면 둘 다 다시 받는다). 페이지 상한 100건은 5분 상한과 하루 크기 때문이고(2026-11-04 큰 인스턴스 3곳이 100건까지 20건씩 줬다), 상한에 닿은 횟수를 실행 기록과 보고서에 적는다. 다시 시도 규칙(4.2-3의 한 번 재시도)은 Mastodon에도 같다.
   - 확인: 자동 테스트로 소스 목록의 Google 나라 수만큼의 요청과 그 주소가 목록과 같은 것, 다른 호스트끼리 서로 기다리지 않는 것(요청 수가 다른 여러 가짜 호스트에서 가짜 시계의 전체 시간이 가장 오래 걸리는 호스트의 시간과 같고 합보다 작은 것), Mastodon 페이지 넘기기(빈 응답, 100건 상한), 같은 호스트 간격 2초, 시간 상한에서 멈춤과 남은 소스의 상태, 응답이 오지 않는 가짜 요청 하나가 요청 상한에서 끊기고 그 소스만 받지 못함인 것, 100건 상한에 닿은 가짜 인스턴스의 닿은 횟수가 실행 기록에 나오는 것, 리디렉션을 따라가지 않는 것.
2. **원문 그대로:** Google 스냅샷은 받은 피드 본문과 같다. Mastodon 스냅샷은 응답에서 작성자 칸만 지운 것이고 나머지 칸과 값이 같다. 작성자 칸은 `author_name`, `author_url`, `authors`이고, 구현하는 AI가 시험 실행 전에 실제 응답 모양을 보는 단발 호출로 같은 종류의 칸(작성자 이름·계정·닉네임)이 더 있는지 확인해 더한다. 지운 칸 목록과, 다른 칸 값 안의 이름은 두는 것을 운영 문서에 적는다.
   - 확인: 자동 테스트로 지어낸 피드의 바이트가 그대로 저장되는 것, 지어낸 링크 응답의 작성자 칸에 넣은 지어낸 이름·계정이 전용 DB 어디에도 없고 다른 칸은 그대로인 것.
3. **하루 한 번:** 같은 날 다시 돌면 받은 소스는 부르지 않고, 받지 못한 소스만 다시 받는다. 받은 소스의 스냅샷은 하루에 하나다. 날짜는 받은 시각의 KST 날짜이고 브리프 대상 날짜와 상관없다. 빠진 날은 채우지 않는다(D1).
   - 확인: 자동 테스트로 두 번 실행해 행 수가 같고 두 번째 요청 수(robots 포함)가 0인 것, 태그만 받고 링크가 실패한 인스턴스가 저장되지 않고 다음 실행에서 둘 다 다시 받는 것, 첫 실행에서 실패한 소스만 두 번째에 요청되는 것, 23:59와 00:01 KST 실행이 다른 날짜가 되는 것.
4. **지우지 않음:** 이 단계의 어떤 명령도 전용 DB의 스냅샷을 지우거나 고치지 않는다. 마이그레이션은 쌓인 스냅샷을 보존한다. 전용 DB의 실행 전 사본은 그 실행에서 받을 소스가 있을 때만 받기 직전에 하나 만들고 최근 3개만 둔다(S5). 사본은 본 DB 사본 폴더(`snapshots/`)와 `tidwyn-*.db` 이름 규칙 밖에 둔다(본 DB 사본의 14일 정리와 영상 30일 지우기가 그 폴더의 열 수 없는 `.db`를 지우기 때문이다). 전용 DB가 없으면 만들고, 이때 사본은 없다.
   - 확인: 자동 테스트로 지어낸 스냅샷이 든 전용 DB에 테스트 안의 가짜 마이그레이션(큰 번호)을 적용해도 행이 그대로인 것, 사본이 4번째에 가장 오래된 것부터 지워져 3개인 것, 첫 실행에 사본이 없는 것, 받을 소스가 없는 같은 날 두 번째 실행에서 사본이 늘지 않는 것, 깨진 사본을 둔 채 `video-refresh`의 지우기와 본 DB 사본 정리를 돌려도 전용 DB 사본이 그대로인 것.
5. **공통 장치:** 소스 목록(종류, 주소, 판정 문서 위치), 끄기 값, 상태 기록, 저장을 코드 한 곳에 두어 9.96이 같은 장치에 소스를 더할 수 있게 한다. 9.96의 소스는 지난 날짜를 받을 수 있으므로 저장은 '받은 날짜'와 별개로 '값의 기준 날짜'를 둘 수 있어야 한다(이 단계의 소스는 둘이 같다). 형태는 구현 재량이다.
   - 확인: 결과 보고서에 9.96이 소스를 더할 때 고칠 곳을 적는다(문서 서술이라 자동화하지 않는다). 자동 테스트로 소스 하나를 목록에 더하면 받기, 상태, 끄기가 그 소스에 적용되는 것(테스트 안의 가짜 소스).

### 4.2 끄기와 robots (S7, S8)

1. **끄기:** 소스와 소스 묶음(Google 전체, Mastodon 전체)을 코드의 끄기 값으로 끈다. 끈 소스는 호출하지 않고 상태는 꺼짐이며 스냅샷을 지우지 않는다. 시험 모드(`test`)에서는 모두 꺼짐이고 `custom`은 켜짐이다.
   - 확인: 자동 테스트로 끈 소스와 묶음의 요청 0, 상태 꺼짐, 행 수 유지, `test`와 `custom`.
2. **robots:** 실행마다, 그 실행에서 받을 소스가 있는 호스트만 robots.txt를 한 번 받아 D16 기준(`*`, ClaudeBot, Claude-User, Claude-SearchBot, anthropic-ai, Claude-Web)으로 받는 경로가 막혔는지 본다. 막히면 그 호스트의 소스는 받지 않고 robots 막힘이다. 다른 봇만 막는 것은 막힌 것이 아니다. robots를 받지 못하거나(404는 막지 않은 것으로 본다) 형식을 읽을 수 없으면 그 호스트의 소스는 받지 못함이다. 판정은 그룹, 가장 긴 규칙, Allow·Disallow 우선순위, `*`와 `$`를 따르고, 특정 봇 그룹이 있으면 `*` 그룹 대신 그것을 쓴다.
   - 확인: 자동 테스트로 지어낸 robots: GPTBot만 막음(받음), `*` Disallow `/api/`(막힘), ClaudeBot 그룹이 여러 User-agent 줄과 함께 막음(막힘), 더 긴 Allow가 이김(받음), 404(받음), 5xx(받지 못함), 경로 `/trending/rss` 판정.
3. **Google 막힘:** Google 요청이 S8의 막힘(403, 429, `/sorry`로 가는 302)을 받으면 그 실행의 남은 Google 요청을 하지 않고 남은 나라를 받지 못함(Google 막힘)으로 둔다. Mastodon은 계속 받는다. 400, 404와 `/sorry`가 아닌 곳으로 가는 302는 그 나라만 받지 못함(지원 안 함)이다. 200이고 항목이 0개인 피드는 받음으로 저장한다. 그 밖의 오류는 그 소스만 받지 못함이고 한 번 다시 시도한다.
   - 확인: 자동 테스트로 같은 날 앞 실행이 Google 막힘이면 두 번째 실행의 Google 요청(robots 포함)이 0인 것, 3번째 나라가 `/sorry` 302일 때 4번째부터 요청 0이고 Mastodon은 요청되는 것, 429와 403도 같은 것, 다른 곳으로 가는 302와 400은 그 나라만 받지 못함이고 다음 나라를 받는 것, 500 뒤 한 번 재시도, 요청의 User-Agent가 고정 문자열인 것.

### 4.3 `/brief` 연결과 실패 격리

1. **단계:** `.claude/skills/brief/SKILL.md`에 받기 단계를 더한다. 위치는 뉴스 후보 목록을 받는 단계보다 뒤이고(Google 막힘이 그날 뉴스 RSS에 번지지 않게) 백업보다 앞이다. 앞 단계가 실패해도 돈다. 백그라운드로 돌리지 않고, Bash 시간 제한은 명령 상한에 1분을 더한다. 끝나지 않거나 비정상으로 끝나도 다음 단계로 간다. 다시 부르지 않는다(남은 것은 다음 실행이 받는다). 앞뒤 단계의 건너뛰기 문장이 새 단계를 거치게 고친다. 운영 문서의 진행 순서도 고친다.
   - 확인: 자동 테스트로 문서 속 명령 이름이 실제 명령과 같은 것, 새 단계가 뉴스 후보 단계 뒤·백업 단계 앞에 있는 것, 앞 단계의 건너뛰기 문장이 새 단계를 가리키는 것.
2. **실패 격리:** 받기 명령은 소스마다 예외를 가두고, 일부나 전부가 실패해도 종료 코드 0으로 끝난다. 전용 DB를 열지 못하는 등 명령 자체가 실패하면 0이 아닌 코드로 끝나고, 스킬은 다음 단계로 간다. 어떤 경우에도 본 DB, 뉴스, 이슈, 영상, 빌더, 백업, 빌드, 배포를 막거나 바꾸지 않는다.
   - 확인: 자동 테스트로 모든 소스 실패에도 종료 코드 0, 전용 DB 경로가 쓸 수 없을 때 0이 아닌 코드와 본 DB의 바이트가 그대로인 것, 스킬 문서 문구 대조.
3. **실행 요약:** 실행 기록과 `/brief` 끝의 요약에 묶음별(Google, Mastodon) 받음·받지 못함·robots 막힘·꺼짐 수, 받지 못한 소스 이름(나라 코드, 인스턴스 이름)과 사유 종류, 묶음별 요청 수(robots 포함)와 100건 상한에 닿은 횟수, 저장한 바이트 수, 전용 DB 크기, 걸린 시간이 나온다. 연속으로 받지 못한 일수가 3일 이상인 소스는 따로 적는다(받지 못함만 세고, robots 막힘과 꺼짐인 날은 세지 않으며 이어 온 일수를 끊지도 않는다. 받음이 끊는다). 받은 글(검색어, 태그, 링크 제목·주소)은 나오지 않는다. 실패 사유는 종류(시간 초과, HTTP 코드, 형식 오류 등)만 쓰고 오류 메시지나 응답 조각을 넣지 않는다(JSON·XML 파싱 오류 메시지는 입력 일부를 담는다).
   - 확인: 자동 테스트로 요약 줄의 값, 연속 실패 3일(사이에 robots 막힘·꺼짐이 낀 경우와 받음이 끊는 경우), 지어낸 글이 든 잘린 JSON과 깨진 피드를 받았을 때 사유에 종류만 나오고 그 글이 출력과 실행 기록에 없는 것, 지어낸 검색어·태그·링크 제목이 명령 출력, 실행 기록, 요약에 없는 것.

### 4.4 비공개 보장 (D16)

1. **AI가 읽지 않음:** 메인 `/brief`는 받기 명령의 출력(4.3-3)만 본다. 스킬 문서 0장의 금지 줄에 두 가지를 더한다: 전용 DB와 그 사본을 읽지 않는다, 수요 소스(Google Trends, Mastodon 트렌드)를 직접 받거나 웹에서 찾지 않고 받기 명령만 쓴다. 이 단계의 어떤 명령도 받은 글을 출력하지 않는다.
   - 확인: 자동 테스트로 4.3-3의 출력 검사, 스킬 문서 문구 대조.
2. **사이트에 나가지 않음:** 사이트 빌드는 전용 DB를 읽지 않는다. 결과물 검사와 공개 전 점검이 전용 DB 파일 이름과 사본 이름이 결과물·커밋 대상에 있으면 거부한다.
   - 확인: 자동 테스트로 전용 DB에 지어낸 스냅샷이 있을 때 사이트 결과물에 그 글이 없고 결과물이 전용 DB 없을 때와 바이트가 같은 것, 일부러 넣은 전용 DB 파일이 결과물 검사와 공개 전 점검에 각각 걸리는 것.
3. **백업에 나가지 않음:** 공개 백업(`data` 브랜치)과 복원은 전용 DB를 다루지 않는다. 본 DB를 복원해도 전용 DB는 그대로다. 운영 문서의 복원 절차에 이것을 적는다.
   - 확인: 자동 테스트로 전용 DB에 지어낸 스냅샷이 있을 때 백업 파일들에 그 글이 없고 백업이 전용 DB 없을 때와 같은 것, 본 DB 복원 뒤 전용 DB의 바이트가 같은 것.
4. **기존 동작 유지:** 뉴스, 이슈, 일정, 지표, 영상, 빌더, 백업, 사이트의 동작이 그대로다. 기존 테스트에서 고쳐도 되는 줄은 이 명세서가 바꾸는 값을 직접 단언한 줄뿐이다: 스킬 문서 순서, 작업 파일·비공개 파일 목록, 실행 요약 줄.
   - 확인: 기존 테스트 통과, `git diff main -- test/`의 기존 줄 변경을 보고서에 적는다.

6. **시험 실행:** `.test-data/stage995-trial/`을 데이터 폴더로 쓴다(`TIDWYN_DATA_DIR`). 본 DB는 실제 DB를 복사해 쓰고, 복사 조건과 sha256 비교는 9.7단계 4.6-2와 같다. 받기 명령에 넘길 실행 기록은 `TIDWYN_DATA_DIR`을 준 `start`로 만든다(받기 횟수에 세지 않는다). 먼저 Google에 피드 하나만 요청해 막힘이 풀렸는지 본다. 막힘(S8)이면 한 시간 뒤 다시 보고(사전 승인 횟수 안. 기다리는 동안 다른 작업을 하거나 백그라운드로 기다린다), 구현이 끝날 때까지 풀리지 않으면 Google 부분을 보류로 넘겨 보고서 맨 위에 적고 Mastodon과 나머지를 계속한다. 받기 명령을 실제 소스로 끝까지 돌리고, 같은 날 한 번 더 돌려 요청이 받지 못한 소스에만 가는지 본다. S2의 지원 안 함 코드를 확인해 목록을 고친다(항목 0개인 나라는 목록에 두고 보고서에 적는다).    - 확인: 수치를 보고서에 적는다.
7. **실제 데이터 보호:** 구현 중 실제 `data/`, `refs/heads/data`, 운영 배포에 쓰지 않는다. 실제 데이터 폴더에 전용 DB를 만들지 않는다(머지 뒤 첫 `/brief`가 만든다).

## 5. 완료 정의

### AI가 확인하고 끝낸다

- 4장 요구사항의 확인을 모두 실행해 통과한다.
- 시험 실행의 수치(4.5-6)가 보고서에 있다. 보류하면 보고서 맨 위에 적는다.
- `package.json`의 `dependencies`가 비어 있다.
- 머지 전까지 실제 데이터 폴더와 운영 배포가 그대로다(예약 실행이 바꾼 것은 예외).

### 사용자가 마지막에 확인한다

1. [source-terms.md](source-terms.md)의 판정(특히 S1의 '학습만 막는 문장' 해석과 쓰지 않는 곳)을 보고 그대로 둘지 정한다. 빼기로 정한 곳은 끄기 값과 판정 문서를 worktree에서 고쳐 커밋하고 `pnpm verify`를 다시 돈 뒤 머지한다.
2. 머지를 승인한다. 머지하면 메인 폴더에서 squash merge, 공개 전 점검, main push를 하고 worktree와 브랜치를 지운다. 사이트는 바뀌지 않는다. 머지 뒤 첫 `/brief`가 전용 DB를 만들고 첫 스냅샷을 쌓는다.

머지 뒤에 한다(머지 승인의 조건이 아니다): 첫 실행 요약에서 묶음별 상태와 저장 바이트를 본다. Google 막힘이 이어지면 운영 문서대로 끈다.

## 7. 진행 규칙

- 작업 브랜치는 `spec/stage9.95-demand-snapshots`이고 작업 폴더는 `../tidwyn-stage995`이다(S9). Bash 명령은 worktree 절대 경로로 `cd`한 뒤 실행하고, 파일 도구는 그 절대 경로를 쓴다. 서브에이전트 지시에도 넣는다. `node src/cli.ts`로 데이터 폴더를 쓰는 모든 호출에 `TIDWYN_DATA_DIR=<worktree 절대 경로>/.test-data/stage995-trial`을 붙이고 `TIDWYN_BACKUP_REPO`는 쓰지 않는다.
- 머지는 메인 폴더에서 예약 실행이 돌지 않을 때 한다: 00:00~05:49에는 해도 되고, 05:50 뒤에는 메인 폴더 `data/runs/`에 오늘(KST) 시작한 실행 기록이 있고 그 `push`가 null이 아닐 때만 한다. 머지 뒤 worktree와 브랜치를 지운다. 작업 브랜치는 push하지 않는다.
- 커밋되는 파일과 메시지에 홈 절대 경로를 쓰지 않는다.
