# 9.5단계 명세서: 공개 준비

- 작성일: 2026-10-31
- 요약: 지금 모든 주소가 같은 빈 화면 틀을 돌려줘 검색엔진과 공유 링크가 내용을 읽지 못한다. 페이지마다 제목·설명·본문이 든 HTML을 빌드하고, 메타·OG·canonical·구조화 데이터, `robots.txt`, `sitemap.xml`, 진짜 404, 파비콘·공유 이미지, RSS를 더한다. 오류 제보 메일과 뉴스 정정 명령·표시를 더하고, 호스팅 한도 도달 시점을 다시 계산한다.
- 종류: 변경 건 (운영 중인 공개 사이트, 매일 쌓이는 DB, 백업을 바꾼다)
- 단계: [`docs/plan.md`](../../plan.md)의 9.5단계(공개 준비). 3단계를 참조한다.
- 이 문서는 기획과 요구사항만 담는다. 설계(스키마, 라이브러리, 폴더 구조)와 작업 계획은 구현하는 AI가 정한다.
- 공개 여부: 원본 저장소와 사이트는 이미 공개다. 이번에 메일 주소 `mivomad33@gmail.com`이 사이트에 공개된다(사용자 결정).

## 1. 목표

- **지금 상태:** 사이트는 Vite + React SPA다. 모든 주소가 같은 `index.html`(제목 `Tidwyn`, 빈 `#root`)을 돌려주고, 없는 주소도 200이다. `robots.txt`, `sitemap.xml`, 파비콘(`data:,`), 공유 이미지, RSS가 없다. 오류 제보는 사이트 소개의 GitHub 이슈 링크뿐이고 뉴스 글을 고치는 명령이 없다. 2026-10-31 기준 실제 DB는 스키마 버전 8, 브리프 4일, 뉴스 128건, 이슈 93개, 대상 180개, 용어 110개, 일정 19개이고 결과물은 파일 78개, 약 1.9MB다.
- **바꾸려는 이유:** 외부 공개를 준비한다(plan 9.5, 11). 자바스크립트를 돌리지 않는 수집기(네이버, 다음, 링크 미리보기)는 지금 사이트에서 아무 내용도 읽지 못한다. 공개하면 틀린 내용을 알릴 길과 고칠 길도 필요하다.
- **쓰는 사람:** 사이트 방문자, 검색엔진과 링크 미리보기 수집기, RSS 구독자, 운영자 한 사람.
- **충분한 수준:** 실제 DB 복사본으로 빌드한 미리보기에서 다음이 확인된다. 검색 결과에 실제로 잡히는지는 등록 뒤 11단계에서 본다.
  - 자바스크립트 없이 받은 HTML만으로 페이지별 제목, 설명, 본문을 읽을 수 있고, 없는 주소는 404다.
  - 자바스크립트를 켠 방문자에게 지금 화면과 동작이 그대로이고 내용이 깜빡이지 않는다.
  - 정정 명령으로 뉴스를 고치면 화면, HTML, 검색, RSS, 백업에 함께 반영되고 '정정됨'이 보인다.

## 2. 확정된 결정과 제약

### 2.1 계획과 앞 단계에서 가져온 결정 (다시 묻지 않는다)

- plan D1~D14, 2.2 제약과 앞 단계 결정을 따른다. 특히 다음이다.
  - **D1:** 로컬 DB가 원본이고 사이트·백업은 DB에서 만든다. 다시 돌려도 안전하다. 데이터를 더하면 백업과 복원에도 넣는다.
  - **D2·2.2:** 호스팅은 Vercel Hobby, 로컬 빌드 결과를 CLI로 올린다. 결과물은 어디에나 올릴 수 있는 순수 정적 파일이다. 호스팅 전용 설정은 `vercel.json` 한 파일에만 둔다. 한도에 가까워지면 옮기거나 유료로 바꾼다.
  - **D3:** 뉴스마다 HTML을 만들지 않는다. 이번 단계의 페이지 단위는 plan 9.5가 정한 브리프·이슈·대상·지표·소개다(뉴스는 날짜 브리프 안에 있다). D3의 "SPA, 월별 JSON, Pagefind"는 그대로 두고 정적 HTML을 앞에 더한다.
  - **D6:** 기사 문장은 바꿔 쓴 글만 싣고, 이미지 파일을 올리지 않으며, 자막 전문을 올리지 않는다.
  - **X3(6단계):** 코스피·코스닥은 그래프에만 싣는다(R12).
  - **D13, V1:** 영상 기록은 30일이 지나면 지운다. 화면은 방문자 날짜로 30일 지난 영상을 숨긴다.
  - **D14, S12:** 매일 실행은 main 코드로만 한다. 개발과 확인은 실제 DB의 복사본이나 테스트 DB로만 한다. DB 구조는 마이그레이션으로 바꾼다.
  - **3단계 화면 규칙:** 4.3-5(오류와 대기), 4.3-6(375px 우선, 다크 모드, 키보드, 대비 AA, `lang="ko"`), 4.3-7(첫 화면 gzip 300KB), `dependencies` 비움.
  - **E12:** 시험 결과는 Vercel 미리보기로 사용자가 폰에서 본다. 운영 주소는 구현 중에 바꾸지 않는다.
- **plan 2.3 없음, `docs/memory.md`:** 공개 주소는 `tidwyn.vercel.app`이고 도메인을 사지 않는다. 명세서 스크린샷은 git에 넣지 않는다. 테스트용 가짜 마이그레이션에는 큰 숫자를 쓴다. `/browser-check` 점검 목록은 `.test-data/browser-check/`에 두고 지어낸 데이터로 빌드해 본다. 자율 구현은 샌드박스를 끈 채로 한다. CI는 두지 않는다. Vercel 화면 작업은 팀 `mivomad33`으로 로그인된 Chrome 프로필로 한다.
- **CLAUDE.md:** 공통 코드를 쓰고, 여러 곳에서 쓸 것은 공통 코드로 만든다. 주소는 `site/src/lib/routes.ts`, 호스팅 규칙은 `site/hosting.ts`, 문의 문구는 `site/src/lib/policy.ts`, 결과물 검사는 `src/siteCheck.ts`, 메일 허용 목록은 `src/precheck.ts`를 넓혀 쓴다.

## 3. 범위

### 넣는 것

- 페이지별 정적 HTML → 4.1
- 메타, OG, canonical, 구조화 데이터 → 4.2
- `robots.txt`, `sitemap.xml`, 진짜 404, 호스팅 규칙 → 4.3
- 파비콘, 앱 아이콘, 공유 이미지 → 4.4
- RSS → 4.5
- 메일 통로와 정정 안내 → 4.6
- 뉴스 정정 명령, 저장, 백업, 표시 → 4.7
- 결과물 검사, 배포 뒤 점검, 호스팅 한도 재계산 → 4.8
- 문서 → 4.9
- 기존 기능 유지와 시험 실행 → 4.10

### 넣지 않는 것

- 검색엔진 등록, 소유 확인 값: R9
- 도메인 구매: `docs/memory.md`
- 호스팅 이전, Vercel 유료 전환: 한도에 가까워질 때 한다(R5)
- 사이트 방식을 SSR·서버 렌더링으로 바꾸기, Vite·React 교체: 순수 정적 구조(D2)를 지킨다
- 뉴스마다 페이지(D3), 용어·일정마다 페이지: plan 9.5 범위 밖이고 파일이 늘어난다. 용어 사전과 일정은 목록 페이지 하나씩이다
- 페이지마다 다른 공유 이미지: 파일이 늘어난다. 사이트 전체에 한 장이다
- 뉴스 글 삭제, 이슈 글과 브리프 단위 글(`headline`, 섹션 `flow`, `unverified`) 정정: 이번 정정은 뉴스 글만 다룬다. 대상·용어·일정 지우기는 기존 명령이 있다
- 영어 페이지, 다국어: 사이트는 한국어다
- PWA, 앱 설치 안내: `docs/memory.md`
- 흐름 리포트 페이지: 10단계. 10단계가 이번 구조를 넓혀 쓴다
- 제작기와 외부 공유: 11단계

### 해당 없음

- 인증과 권한: 로그인이 없다.
- 남용 방지와 입력 제한: 사이트에 새 입력이 없다. 메일 스팸은 감수한다(R1).
- 서버, 원격 DB: 순수 정적이다.
- 새 외부 서비스, 새 비용: 없다.
- 사용 분석: 3단계 P10 그대로다. 없는 페이지와 정적 HTML은 바꾸지 않는다.
- 새 예약 작업: `/brief`의 빌드 단계 안에서 함께 만들어진다.

## 4. 요구사항

요구사항마다 확인 방법을 붙인다. "자동 테스트"는 `pnpm verify`에 들어가는 테스트다. 네트워크를 쓰지 않고, 실제 `data/`, `.env.local`, 실제 저장소의 `.test-data/`를 읽거나 쓰지 않는다. 예시 데이터는 지어내서 만든다(저장소가 공개다). "E2E"는 `pnpm e2e`다.

**용어 정의**

- **정적 HTML:** 빌드가 만든, 주소마다 하나인 HTML 파일이다. 서버에서 받은 그대로의 내용을 말한다.
- **색인 페이지:** 검색엔진이 수집할 주소다: `/`, `/<날짜>`(저장된 날짜마다), `/dates`, `/issues`, `/issues/<번호>`(남아 있는 이슈마다), `/entities`, `/entities/<번호>`(남아 있는 대상마다), `/terms`, `/schedules`, `/indicators`, `/indicators/<식별자>`(공개 지표마다), `/about`, `/privacy`.
- **앱 전용 주소:** 앱이 처리하지만 색인하지 않는 주소다: `/search`, `/terms/<번호>`, `/schedules/<번호>`, 흡수된 이슈·대상 주소.
- **공개 주소:** `https://tidwyn.vercel.app`. 코드 한 곳에 둔다.
- **정정:** 운영자가 명령으로 저장된 뉴스 글을 고치고 날짜와 사유를 남기는 것이다.
- 그 밖의 용어(대상, 흡수, 영상 기록, 실행 조건, 결과물 검사, 공개 전 점검)는 앞 단계 명세서와 같다.

### 4.1 페이지별 정적 HTML (R5, R7)

1. **만들기:** 사이트 빌드가 사이트 데이터(`site-data/`)로 색인 페이지마다 정적 HTML을 만든다. 같은 입력이면 같은 결과다. 새 사이트 데이터가 없는 페이지는 빈 목록 상태로 만들어지고 빌드는 실패하지 않는다.
   - 확인: 자동 테스트로 지어낸 데이터에서 모든 색인 페이지의 파일이 나오고, 두 번 빌드한 HTML이 같으며, 데이터가 빈 빌드가 통과한다.
2. **본문:** 페이지마다 `<h1>`과 화면에 있는 글을 읽을 수 있는 HTML로 담는다.
   - 브리프와 `/`: 날짜, 섹션, 뉴스마다 제목·요약·왜 중요한지·배경 등 글 항목, 출처 이름과 원문 링크, 이슈 링크, 정정 표시와 사유(날짜, 바뀐 내용). 뉴스마다 지금 화면의 `#<뉴스 키>`로 갈 수 있는 앵커를 둔다.
   - 이슈: 이름, 요약, 상태, 타임라인과 뉴스 링크, 관련 이슈.
   - 대상: 이름, 설명, 관련 이슈, 뉴스 링크.
   - 지표: 이름, 설명, 최신 값과 날짜, 출처 고지. 5년 값 전체를 표로 싣지 않는다. 코스피·코스닥은 값과 날짜를 뺀다(R12).
   - 목록(`/dates`, `/issues`, `/entities`, `/terms`, `/schedules`, `/indicators`): 항목 이름, 짧은 설명, 항목 주소 링크. `/terms`는 용어 설명까지 담는다. `/indicators`도 지금 화면의 출처 고지를 담고 코스피·코스닥 값을 싣지 않는다. 목록은 전체 항목을 싣는다(4.1-3). 목록 페이지는 4.1-6의 크기 기준 밖이다.
   - 소개와 처리방침: 화면의 문구와 같은 공통 문구를 쓴다. 두 벌로 관리하지 않는다.
   - 영상, 기사 이미지, 방문자 날짜에 따라 바뀌는 것(지난 일정 판정의 오늘 기준 등)은 넣지 않거나 빌드 날짜 기준임이 드러나지 않게 처리한다(R7).
   - 확인: 자동 테스트로 지어낸 데이터의 각 종류 페이지 HTML에서 표식 문자열이 위 항목별로 나오고, 영상 제목·썸네일 주소·기사 이미지 주소가 어떤 HTML에도 없으며, 코스피·코스닥 표식 값이 HTML·메타·JSON-LD에 없고, 소개 문구가 화면과 같다.
3. **탐색 링크:** 모든 정적 HTML에 머리글 메뉴와 바닥글 링크가 `<a href>`로 있어, 자바스크립트 없이 링크만 따라가도 모든 색인 페이지에 닿는다. 이전·다음 날짜 링크를 브리프에 둔다.
   - 확인: 자동 테스트로 `/`에서 정적 HTML의 링크만 따라가 모든 색인 페이지에 닿는다.
4. **자바스크립트를 켠 방문자:** 앱은 지금과 같은 화면을 그린다. 정적 본문이 보였다가 사라지는 깜빡임, 레이아웃 밀림, 콘솔 오류가 없다. 방법은 AI 재량이다(하이드레이션이든 숨김이든). 숨기는 방식이면 앱 코드를 받지 못했을 때 정적 본문이 다시 보여야 한다.
   - 확인: E2E로 첫 페인트 전부터 앱이 그릴 때까지 정적 본문이 보이지 않고(또는 앱 화면과 같고), 콘솔 오류가 없으며, 앱 JS 요청을 막으면 정적 본문이 보인다. 앞 단계 E2E가 통과한다.
5. **자바스크립트를 끈 방문자:** 모든 색인 페이지를 읽을 수 있고 스타일이 입혀져 있다. 지금 `<noscript>` 안내는 정적 본문이 있는 페이지에서는 없앤다. 앱에서만 되는 기능(카드 펼침, 검색)은 정적 페이지에서 깨져 보이지 않는다.
   - 확인: E2E(자바스크립트 끔)로 브리프, 이슈, 대상 페이지의 본문이 보이고 스타일이 입혀져 있으며, `<noscript>` 안내가 없고 375px에서 가로 스크롤이 없다. 누를 곳 44px 보정(R10)은 `design-check` 객관 관문으로 본다.
6. **크기:** 브리프 첫 화면 전송 크기(3단계 4.3-7, gzip 300KB)를 HTML 본문을 합쳐서 지킨다. 뉴스 42건, 이슈·대상이 많은 측정 조건을 쓴다. 앞 측정의 여유가 약 20KB뿐이므로, 먼저 첫 화면이 받는 데이터를 줄인다(영상 요약을 다른 파일로 빼기 등, 필요하면 데이터 구조를 바꿔도 된다). 본문은 줄이지 않는다(R5). 그래도 넘으면 `FIRST_SCREEN_BUDGET`을 가장 큰 측정값보다 10% 큰 값으로 올린다(R13). 측정값과 새 상한을 보고서 맨 위에 적어 마지막 질문에서 보인다.
   - 확인: `test/siteBuild.test.ts`, `test/siteIndicators.test.ts`, `test/siteVideos.test.ts`의 측정이 모두 HTML을 포함해 상한 이하이고, 상한을 올렸으면 값이 보고서 맨 위에 있다.

### 4.2 메타, OG, canonical, 구조화 데이터

1. **제목과 설명:** 페이지마다 다른 `<title>`과 `meta description`이 있다. 제목은 앱의 `useTitle` 결과와 같다. 앱의 제목도 함께 바꾼다: `/`는 `Tidwyn · 최신 뉴스 브리프`, 날짜 브리프는 `Tidwyn · 10월 30일 브리프` 모양(`docs/design.md`)이다. 같은 월·일의 저장 날짜가 둘 이상이면 그 날짜들의 제목에 연도를 넣는다(`Tidwyn · 2027년 10월 30일 브리프`). 이슈·대상 이름이 겹치면 구분하는 방법은 AI 재량이다. 앱과 정적 HTML이 같은 함수를 쓴다. 나머지 페이지의 제목 모양은 그대로다. 설명은 그 페이지의 글에서 만들고 길이 상한(AI 재량, 약 160자)을 지키며 태그와 줄바꿈이 없다.
   - 확인: 자동 테스트로 색인 페이지 전체의 제목이 겹치지 않고(`/`와 최신 날짜 페이지는 다르게 쓴다), 설명이 비지 않고 상한 안이며, E2E로 앱을 그린 뒤의 문서 제목이 정적 제목과 같다.
2. **canonical:** 색인 페이지마다 공개 주소 기준 절대 주소의 canonical이 있다. `?kind=`, `?view=` 같은 쿼리는 canonical에 없다. 앱 전용 주소는 `noindex`이거나 남는 주소·목록을 canonical로 가진다.
   - 확인: 자동 테스트. 미리보기 빌드도 공개 주소를 쓴다.
3. **OG·Twitter:** `og:title`, `og:description`, `og:url`, `og:image`(절대 주소), `og:image:width`, `og:image:height`, `og:image:alt`, `og:type`, `og:site_name`, `og:locale`(`ko_KR`), `twitter:card`(`summary_large_image`)를 색인 페이지마다 둔다.
   - 확인: 자동 테스트.
4. **구조화 데이터:** JSON-LD로 `/`에 `WebSite`, 브리프·이슈에 `Article` 계열, 그 밖의 페이지에 맞는 유형을 둔다. 작성자는 조직 `Tidwyn`이고, 사람인 체하지 않는다. 날짜는 ISO 8601이고 정정이 있으면 `dateModified`가 정정일이다. `<`를 이스케이프해 글이 스크립트를 깨지 않는다. 유형과 필드는 [Google 문서](https://developers.google.com/search/docs/appearance/structured-data/article)를 구현 때 확인한다.
   - 확인: 자동 테스트로 모든 JSON-LD가 파싱되고 필수 필드가 있으며, `</script>`가 든 지어낸 제목이 깨지지 않는다.
5. **그 밖:** `lang="ko"`, `theme-color`, RSS `<link rel="alternate">`를 둔다. 글의 `<`, `&`, 따옴표를 이스케이프한다.
   - 확인: 자동 테스트.

### 4.3 수집 규칙과 404

1. **`robots.txt`:** 모든 수집기를 허용하고(R4) `/search`를 막으며 `Sitemap:` 줄이 있다. `assets/`, `site-data/`, `pagefind/`를 막지 않는다(Google이 앱을 그릴 때 필요하다). 뒤에 `/register-search`가 줄을 더할 수 있게 한 곳에서 만든다. 그 스킬이 더할 다음 소유 확인 주석 줄은 4.8-1 검사에 걸리지 않고, Google·Bing·네이버 소유 확인 메타 태그를 더할 `<head>` 생성 지점도 한 곳이다.
   - 확인: 자동 테스트.
2. **`sitemap.xml`:** 색인 페이지만 절대 주소로 담고, `lastmod`는 그 페이지의 마지막 내용 날짜다(정정 포함, 빌드 날짜가 아니다). 앱 전용 주소가 없다. 프로토콜 한도(5만 개, 50MB)를 넘으면 나눈다.
   - 확인: 자동 테스트로 XML이 파싱되고, 주소 집합이 색인 페이지 파일 집합과 정확히 같으며, 흡수된 이슈·지운 대상·비공개 지표가 없고, 5만 개를 넘는 지어낸 입력이 나뉜다.
3. **진짜 404:** 없는 주소(`/nope`, `/2026-02-30`, 저장되지 않은 날짜, 없는 이슈·대상 번호, 비공개 지표)는 HTTP 404와 없는 페이지 내용을 돌려준다. 없는 페이지는 `noindex`이고 정적 HTML만으로 읽을 수 있으며 앱도 같은 화면을 보인다. 끝의 `/`가 붙은 주소는 지금처럼 같은 페이지로 간다. 정적 404에는 `docs/design.md`의 요청 주소 줄이 없어도 된다(앱이 그릴 때 보인다). 흡수된 이슈·대상 번호를 200으로 돌려주는 방식은 AI 재량이고, 그로 늘어나는 파일이나 규칙을 4.8-3 계산에 넣는다.
   - 예외: `/terms/<번호>`, `/schedules/<번호>`는 숫자 모양이면 앱 화면을 돌려주고 없는 번호는 앱이 없는 페이지를 보인다(파일을 늘리지 않기 위해 감수한다). 이 주소는 `noindex`다.
   - 확인: `site/dev/serve.ts`와 `resolveStatic`이 같은 규칙을 쓰고, 자동 테스트와 E2E가 상태 코드를 본다. 4.10-2에서 미리보기의 실제 Vercel 응답을 본다(자동화하지 않는 이유: 호스팅 동작이다).
4. **앱 전용 주소:** 지금 동작(검색, 용어 위치로 이동, 일정 강조, 흡수 안내)이 그대로다. 새로 고침해도 된다. 흡수된 이슈·대상 주소는 200이고 canonical이 남는 주소이며 앱이 지금처럼 남는 이슈를 보인다.
   - 확인: 앞 단계 E2E와 새 E2E(직접 열기), 자동 테스트로 흡수 주소의 정적 HTML canonical이 남는 주소다.
5. **호스팅 설정:** 호스팅 전용 규칙은 `vercel.json` 한 곳이다. 확장자 없는 주소가 HTML 파일로 가는 규칙, 404, 앱 전용 주소를 담는다. 사이트 데이터와 검색 색인 응답에 `X-Robots-Tag: noindex`를 붙인다.
   - 확인: 자동 테스트로 설정 값을 보고, 헤더 규칙의 `source`가 `site-data/`와 `pagefind/` 주소에만 맞고 색인 페이지 주소 표본에는 맞지 않음을 본다(Vercel이 모든 미리보기에 같은 헤더를 붙여 미리보기 응답으로는 구분되지 않는다). 운영 응답은 4.8-2가 본다. `docs/operations.md`의 "옮길 때" 설명을 고친다.

### 4.4 아이콘과 공유 이미지 (R3)

1. **파일:** `design/final/`의 확정 표시로 파비콘(`icon.svg`, 16·32·48px PNG), `apple-touch-icon`(180px), 공유 이미지(`share.png`, 1200×630, 300KB 이하)를 결과물에 넣고 모든 페이지가 가리킨다. `data:,` 링크를 없앤다. 파일은 저장소의 원본에서 복사하며, 빌드할 때 네트워크를 쓰지 않는다.
   - 확인: 자동 테스트로 파일 크기와 치수, 링크가 있다. 미리보기에서 공유 이미지 주소가 200이다.
2. **모습:** 16px 탭 표시, 라이트·다크 탭, 공유 이미지의 잘림을 확인한다.
   - 확인: 화면 확인과 `design-check` 깨끗한 회차.

### 4.5 RSS (R6)

1. **피드:** `/rss.xml`(RSS 2.0)에 최근 30개 저장 날짜의 브리프를 최신순으로 담는다. 항목마다 제목, 그 날짜 브리프 링크, 고유 `guid`, `pubDate`, 주요 뉴스 제목 목록이 있다. 정정된 뉴스의 고친 제목을 쓴다. 주소를 바꾸면 안 된다. 사이트 소개에서 링크한다.
   - 확인: 자동 테스트로 소개의 링크가 있고 XML이 파싱되고 항목 수·순서·이스케이프가 맞으며, 본문 글(`summary` 표식)이 없고 저장 날짜가 0개면 빈 채널이 유효하다.
   - 확인: 30개보다 많은 지어낸 날짜에서 30개만 나온다.

### 4.6 메일 통로와 안내 (R1)

1. **문구:** 사이트 소개에 '오류 정정과 연락' 절을 두고, 메일 주소(`mailto:` 링크), 무엇을 적어 주면 좋은지, 정정 방침(확인하면 고치고 '정정됨'으로 알린다)을 적는다. 사이트 소개와 처리방침의 GitHub 이슈 안내를 메일로 바꾼다. 바닥글에서 그 절로 갈 수 있다. 메일 주소는 `site/src/lib/policy.ts` 한 곳에 둔다.
   - 펼친 카드와 목록 끝(짧은 소식용)에 `docs/design.md`대로 '틀린 내용 알리기' 메일 링크를 둔다. 메일 제목과 본문에 날짜, 뉴스 제목, 뉴스 주소가 미리 채워진다. 짧은 소식은 제목이 없으므로 날짜와 브리프 주소를 채운다.
   - 확인: E2E와 자동 테스트로 절, `mailto:`(채운 값 디코딩), 바닥글 링크가 있고 화면에 `github.com/mivomad33/tidwyn/issues`가 없다.
2. **처리방침:** 메일을 보내면 보낸 사람의 주소와 내용을 답장과 정정에만 쓰고 공개하지 않는다는 것, 보관 기간을 따로 정하지 않고 메일함에 두며 요청하면 지운다는 것을 더한다. '모으는 정보'의 첫 문장을 사이트 자체는 모으지 않고 메일을 보낸 경우만 예외라는 뜻으로 고친다. 바뀐 날짜를 고친다.
   - 확인: 자동 테스트.
3. **검사 허용:** `src/precheck.ts`의 허용 메일에 이 주소를 더한다. 다른 메일 주소는 지금처럼 결과물 검사와 공개 전 점검이 막는다.
   - 확인: 자동 테스트로 이 주소가 든 결과물은 통과하고 다른 주소는 실패한다.

### 4.7 뉴스 정정 (R2)

1. **명령:** `node src/cli.ts`의 새 명령으로 뉴스 하나의 글 항목을 고친다. 고칠 수 있는 항목은 저장된 글(제목, 요약, 왜 중요한지, 배경 등, 짧은 소식은 요약)이고, 값이 비어 있는 선택 항목을 새로 채우지 않는다. 출처 이름·링크와 분류는 고치지 않는다(`docs/operations.md`의 한계에 적는다). 명령은 뉴스 식별자(날짜와 키), 고칠 항목과 새 글, 정정 사유를 파일이나 인자로 받는다(AI 재량). 값 없는 사유, 없는 뉴스, 없는 항목, 빈 글, 저장 때의 검사(`src/validate.ts`의 글 항목 규칙: 글 길이, 인용 등)를 어기는 글을 거부하고 DB를 바꾸지 않는다. 새 글과 사유는 `scanText`와 같은 기준으로도 검사해, 저장을 통과한 값이 결과물 검사나 공개 전 점검에 걸리지 않게 한다. 사유는 길이 상한(AI 재량)을 두고, 주소, 전화번호 모양, 메일 모양(공개 메일 포함)을 거부한다. 사유는 공개되고 공개 이력에서 지울 수 없으므로 무엇을 어떻게 고쳤는지만 쓰고 제보자와 제보 내용을 쓰지 않는다. 명령이 이 안내를 출력하고, 끝날 때 그 뉴스에 붙은 이슈 번호를 출력해 같은 오류를 함께 보게 한다. `/brief`는 이 명령을 부르지 않는다.
   - 확인: 자동 테스트로 거부 경우마다(메일, 공개 메일, 홈 경로, 키 모양, 주소, 전화번호가 든 사유 포함) DB가 그대로이고, 맞는 입력이 적용된다.
2. **실행 조건과 사본:** 실제 데이터 폴더를 쓸 때는 `/brief`와 같은 실행 조건을 따르고, 바꾸기 전에 DB 사본을 `data/snapshots/`에 남긴다.
   - 확인: 자동 테스트로 실행 조건을 어기면 거부되고 DB가 그대로이며, 통과하면 `snapshots/`에 사본이 생긴다.
3. **기록:** 뉴스마다 정정 기록(날짜(KST), 사유, 바뀐 항목 이름)을 쌓는다. 고치기 전 글은 DB에 두지 않아도 된다(백업 이력에 남는다). 같은 뉴스를 여러 번 정정할 수 있다. 재실행으로 같은 정정이 두 번 쌓이지 않게 하는 방법은 AI 재량이다.
   - 확인: 자동 테스트.
4. **마이그레이션과 백업:** 버전 8 DB가 새 버전으로 올라가고 데이터가 그대로다. 버전 4~7에서도 올라간다. 정정 기록이 백업과 복원에 들어간다. 옛 형식 백업도 복원된다. 정정 기록을 새 백업 파일로 내면 `BACKUP_NAME_RE`에도 더한다. 공개 저장소에 고치기 전 글이 남는다는 한계를 문서에 적는다.
   - 확인: 자동 테스트로 버전 8과 4의 DB, 왕복 백업, 옛 형식 복원을 본다.
5. **파생 반영:** 정정한 뉴스의 글이 다음 빌드에서 브리프 화면, 정적 HTML, 마크다운, 검색, RSS, 구조화 데이터, `sitemap.xml` `lastmod`에 나온다. 명령 끝에 마크다운을 다시 만들고, 사이트는 다음 `/brief`나 손 배포가 올린다.
   - 확인: 자동 테스트로 지어낸 데이터를 정정한 뒤 각 파생에서 새 글이 나오고 옛 글이 없다.
6. **표시:** 정정된 뉴스의 목록 줄과 펼친 카드에 `design/final/` 시안대로 '정정됨 · M월 D일'이 보이고, 펼치면 '바뀐 내용'이 보인다. 짧은 소식은 펼침이 없어 사유를 늘 보인다. 여러 번 정정하면 최신순으로 쌓인다. 정정 기록이 있는 카드를 펼칠 때 누른 줄이나 '바뀐 내용'이 화면 밖으로 밀리면 `docs/design.md`대로 줄 윗선이 머리글 아래에 오게 스크롤한다. 이슈 타임라인·대상 페이지·검색 결과 줄에는 표시하지 않아도 된다. 정정이 없는 뉴스는 4.6-1의 제보 링크 말고는 지금과 같다. 색 대비는 AA 이상이다(`textPairs`에 더한다).
   - 확인: E2E와 화면 확인(375·1440px, 라이트·다크, 긴 사유, 표시 없는 카드와 섞임), `design-check` 깨끗한 회차.

### 4.8 검사, 점검, 한도

1. **결과물 검사:** 사이트 빌드 뒤 검사에 다음을 더한다: 모든 색인 페이지 HTML에 제목·설명·canonical이 있음, `sitemap.xml`의 주소마다 파일이 있음, 색인 페이지에 `noindex`가 없음, `robots.txt`가 수집을 막지 않음. 영상 데이터 파일 이름이나 영상 필드가 HTML에 들어가면 실패한다. 검사는 새 HTML도 기존 비밀 값·메일·경로 검사를 받는다.
   - 확인: 자동 테스트로 일부러 깨뜨린 결과물마다 실패한다.
2. **배포 뒤 점검:** 운영 주소의 `robots.txt`, `sitemap.xml`, 최근 날짜 페이지(200, 그 날짜가 제목에 있음), 없는 주소(404), `site-data/dates.json`의 `X-Robots-Tag: noindex`, `/`와 최근 날짜 페이지에 그 헤더가 없음을 더 본다. 날짜는 ISO 날짜가 아니라 실제 문서 제목 모양(`10월 30일`)으로 비교한다. 실패 처리는 지금과 같다(되돌리지 않고 요약에 남긴다).
   - 확인: 자동 테스트(가짜 응답, 헤더를 포함하게 넓힌다).
3. **호스팅 한도 재계산:** 실제 DB 복사본 빌드(4.10-2)와 지어낸 5년치 측정으로, 1년 증가량(파일 수와 크기)과 Hobby CLI 한도(100MB, 15,000개)에 닿는 시기를 계산한다. 시기는 실제 날짜별 증가량으로 계산하고, 지어낸 5년치는 크기와 빌드 시간 측정에만 쓴다. 2026-06-17 Vercel 공지("CLI-specific deployment limits" 제거)와 공식 한도 문서가 어긋나 보이므로 지금 적용되는 값을 다시 확인하고, 확인되지 않으면 문서의 값으로 계산한다. 하루 배포에서 새로 올라가는 파일 수와 전체 HTML 수가 Hobby의 하루 업로드 5,000건을 넘는 시기도 계산한다(CLI는 바뀐 파일만 올린다. 코드 해시나 공통 머리글이 바뀌면 HTML 전부가 바뀐다). 이 일로 멈추지 않는다(R5). `docs/operations.md`에 코드 머지 뒤 배포가 실패할 수 있다는 점과 대응을 적는다. 기존 80MB·12,000개 경고는 그대로다. 2년 안에 닿으면 보고서에 그 시기와 옮길 곳 비교(Vercel Pro, Cloudflare Pages 등, 값은 공식 문서로 다시 확인)를 적고, 어느 한도든 6개월 안에 닿으면 보고서 맨 위에 적는다.
   - 확인: 보고서와 `docs/operations.md`의 한도 절에 측정 값이 있다. 상위 문서 수정 제안에 plan 2.2 값을 넣는다.
4. **빌드 시간:** 사이트 빌드가 지어낸 5년치 데이터에서 5분 안에 끝난다.
   - 확인: `test/siteVideos.test.ts`의 5년치 조건으로 단독 빌드해 5분 이하인지 보고 값을 보고서에 적는다.

### 4.10 기존 기능 유지와 시험 실행

1. **기존 테스트:** `pnpm verify`와 `pnpm e2e`가 통과한다. 고쳐도 되는 기존 줄은 이 명세서의 요구사항이 바꾸는 동작이나 값을 직접 단언한 줄과, 새 필수 파일·주소·헤더를 채워야 하는 가짜 결과물·가짜 응답(그에 따라 바뀌는 수와 호출 목록 포함)뿐이다. 예: 없는 주소의 상태 코드, 결과물 최상위 목록, 스키마·백업 버전, GitHub 이슈 문구와 링크 수, 처리방침 바뀐 날짜, 허용 메일, 호스팅 규칙, 없는 페이지 문구, `/`와 브리프 제목, 파일 수 상한, 데이터 구조와 상한 상수(4.1-6), 빈 `#root`, 바닥글 링크. 요구사항으로 설명되지 않는 변경은 하지 않는다. `test/siteBuild.test.ts`의 두 금지 단언은 뜻을 지켜 좁힌다: `.txt` 금지는 `robots.txt`만 빼고, HTML의 외부 주소 금지는 자원을 부르는 곳(`<script src>`, `<link rel="stylesheet|preload|modulepreload">`, `<img src>`)의 외부 주소 금지로 바꿔 모든 새 HTML에 적용한다. 그 밖의 기존 금지 단언은 약하게 하지 않으며, `res.files.length <= 10_000` 단언은 5년치에서 값을 보고서에 적는 것으로 바꾼다. 대신 365일, 이슈·대상 각 3,000개 조건에서 15,000개 이하를 본다(회귀 방지용이다. 한도 시기 판단은 4.8-3의 실측이 맡는다). 사이트 데이터 모양 단언은 정정 필드를 정정이 있을 때만 넣어 그대로 둔다.  고친 줄과 이유를 보고서에 적는다.
   - 확인: 두 명령 통과, `git diff main -- test/`의 기존 줄 변경이 허용 범위뿐이다.
2. **시험 실행:** `../tidwyn/data/tidwyn.db`를 `cp`로 `.test-data/stage95-trial/` 아래에 복사해 `TIDWYN_DATA_DIR`로 쓴다. 실제 `data/`와 `refs/heads/data`에는 쓰지 않는다. 새 날짜 수집과 외부 API 호출은 하지 않는다.
   - 설정: `TIDWYN_DATA_DIR` 없이 `node src/cli.ts`를 부르면 worktree에서도 실제 `data/`를 열고, 일부 명령(`backup` 등)은 실행 조건을 보지 않는다. 그래서 DB를 여는 모든 호출의 명령 앞에 `TIDWYN_DATA_DIR=<worktree 절대 경로>/.test-data/stage95-trial`을 붙이고 `TIDWYN_BACKUP_REPO`는 쓰지 않는다. `site`는 같은 폴더를 `--data-dir`로도 준다.
   - 복사는 예약 실행이 쓰지 않을 때 한다. 00:00~05:49이거나, 오늘 시작한 실행 기록의 `push`가 null이 아니면 복사한다. 그 밖에는 시험 실행을 뒤로 미루고 다른 요구사항을 먼저 끝낸다. 12:00까지 기다리고, 12:00 뒤에도 그대로이면 실제 DB와 `../tidwyn/data/runs/`가 30분 넘게 바뀌지 않았음을 보고 복사하며 그 사실을 보고서에 적는다. 복사본 해시가 원본과 같은지 본다.
   - 복사본에서 마이그레이션, 뉴스 하나 정정(복사본에만, 글은 실제 내용과 같은 뜻의 시험 문구), 백업, 빌드, 결과물 검사를 돌린다.

   - 복사본에 흡수된 이슈가 없으면 복사본에서만 기존 합치기 명령으로 두 이슈를 합쳐 시험한다(외부 호출 없음).

3. **실제 데이터 보호:** 구현을 시작할 때 `../tidwyn/data/tidwyn.db`의 해시, `refs/heads/data`, 운영 배포 ID를 진행 기록에 적고 끝날 때 다시 본다. 메인 폴더가 main이고 `git status --porcelain`이 비어 있는지도 시작과 끝에 본다. 예약 실행이 돌아 바뀌면 `../tidwyn/data/runs/`로 그 실행 때문인지 확인해 보고서에 적는다.

## 7. 진행 규칙

- 작업 브랜치는 `spec/stage9.5-public-ready`이고 작업 폴더는 `../tidwyn-stage95`다(R8). 세션과 서브에이전트가 메인 폴더에서 시작해도 Bash 명령은 `git worktree list`로 확인한 worktree 절대 경로로 `cd`한 뒤 실행하고(`git`, `pnpm`, `node src/cli.ts`, 시험 폴더 지우기 포함), 파일 도구는 그 절대 경로를 쓴다. 서브에이전트 지시에도 넣고, `node src/cli.ts`로 DB를 여는 호출에 4.10-2의 `TIDWYN_DATA_DIR`을 붙인다는 규칙도 함께 넣는다(읽기 명령도 마이그레이션을 한다). CLAUDE.md의 "작업 브랜치에서 한다"는 그대로이고, 위치만 worktree다. 머지는 메인 폴더에서 예약 실행이 돌지 않을 때 한다: 00:00~05:49에는 해도 되고, 05:50 뒤에는 메인 폴더 `data/runs/`에 오늘(KST) 시작한 실행 기록이 있고 그 `push`가 null이 아닐 때만 한다. 아니면 미루고 사용자에게 알린다. `pnpm-lock.yaml`이 바뀌었으면 머지 뒤 메인 폴더에서 `pnpm install`을 하고 검사한다. 사용자 검토를 통과하면 main에 squash merge하고 worktree와 브랜치를 지운다. 지우기 전에 git이 무시하는 `screenshots/`와 `design/explore/`를 메인 폴더의 같은 경로로 옮긴다(`docs/design.md`가 가리키는 그림이 있다). 작업 브랜치는 push하지 않는다.
