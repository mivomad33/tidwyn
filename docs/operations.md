# 운영 문서

매일 뉴스 브리프를 수집하는 `/brief`의 사용법, 공개 사이트와 원본 저장소 운영, 문제가 생겼을 때 할 일을 적는다. 명령은 모두 프로젝트 폴더(이 저장소의 최상위)에서 실행한다.

## 전제

- **권한 건너뛰기 모드:** `/brief`는 Claude Code의 권한 건너뛰기 모드(bypassPermissions)로 실행한다는 전제로 만들었다. 프로젝트 허용 목록(`.claude/settings.json`)은 두지 않는다. 다른 모드에서는 실행 중 승인 요청이 뜰 수 있다.
- **Node 24와 pnpm:** Node 버전은 `.node-version`(24)에 고정되어 있다. 의존성은 `pnpm install`로만 설치한다. 실행 경로(`src/`)는 Node 내장 기능만 쓴다. 그래서 실행 조건 확인과 복원은 의존성 설치 없이도 돈다.

## 매일 실행: `/brief`

1. 메인 작업 폴더(처음 클론한 폴더)에서 main을 체크아웃하고 변경 사항이 없는 상태로 둔다.
2. 그 폴더에서 Claude Code를 권한 건너뛰기 모드로 열고 `/brief`를 실행한다.
3. 묻지 않고 끝까지 진행한다. 진행 순서는 다음과 같다.
   1. 인자와 실행 조건 확인
   2. 의존성 맞추기
   3. 실행 설정 표시
   4. 실행 전 사본
   5. 빠진 날짜 계산
   6. 소급 연결: 이슈가 없는 뉴스가 있는 저장된 날짜를 오래된 날부터 이슈에 연결
   7. 날짜마다 후보 목록·조사·검사·저장·마크다운, 저장한 직후 그 날짜를 이슈에 연결
   8. 영상 받기와 고르기(가장 늦은 브리프 날짜에 한 번, 아래 "추천 영상")
   9. 합치기(마지막 점검에서 7일이 지났을 때만)
   10. 지난 날짜 이미지 채우기
   11. 백업 커밋
   12. 사이트 빌드, Vercel 배포, `data` 브랜치 push
   13. 결과 출력
4. 끝나면 대화창에 저장한 날짜, 실패한 날짜와 이유, 날짜마다 우선 출처 비율, 받지 못한 피드, 이슈 연결 결과, 영상 받기·고르기 결과(수와 대상 날짜만, 영상 제목은 나오지 않는다), 합치기 결과, 이슈 목록 경로, 백업 결과, 원문 이미지 수, 사이트 빌드·배포·push 결과, 가장 최근 날짜의 브리프 전체(이어지는 이야기 포함)가 나온다.

대상 날짜는 처음에는 KST 어제 하루다. 그 뒤에는 첫 수집일부터 어제까지 DB에 없는 날짜를 모두 채운다. 대상일 다음 날보다 늦게 수집한 날짜에는 "늦게 수집" 표시가 붙는다.

**실행 중에는 이 폴더에서 브랜치를 바꾸지 않는다.** 실행 조건은 시작할 때 한 번만 확인한다. 도중에 브랜치를 바꾸면 다른 코드가 실제 DB를 쓰게 된다. 잘못됐으면 실행 전 사본으로 되돌린다(아래 "실행 전 사본").

### 후보 목록과 출처

- 날짜마다 조사 전에 `node src/cli.ts feeds --run <실행 기록> --date <날짜>`가 RSS로 우선 출처 후보 목록을 만든다. 결과는 데이터 폴더의 `work/<날짜>.candidates.md`(Claude가 읽는 짧은 목록)와 `.candidates.json`(전체)이다.
  - 받는 피드: 구글 뉴스 RSS 검색(Reuters, AP, 연합뉴스, BBC를 날짜로 좁힘), 연합뉴스 공식 RSS(종합·분야별), BBC 세계 RSS.
  - 범위: 대상일 KST 0시부터 미국 서부 시간으로 대상일이 끝날 때까지.
  - 매체 페이지를 직접 읽지 않는다. 원문 주소는 웹 검색으로 찾는다. 구글 뉴스 중간 주소(`news.google.com`)는 출처로 쓸 수 없다(검사에서 거부).
- 검사는 한 매체가 주요 뉴스 대표 출처의 절반을 넘으면 거부한다(쏠림).
- 실행 요약의 "우선 출처 비율"은 대표 출처 중 통신사·주요 일간지·방송사·공식 발표의 비율이다. 절반 미만이면 경고만 붙고 저장은 된다.
- 코드 위치: 피드 주소 목록은 `src/feeds.ts`, 우선 출처 목록(도메인)은 `src/outlets.ts`. 매체를 더하거나 빼려면 작업 브랜치에서 이 파일을 고친다.

### 실행 설정 표시

모든 실행은 시작할 때 다음을 보여 준다. 실제 실행인지 시험인지 여기서 확인한다.

- 모드(실제 실행 / 시험 모드 / 데이터 폴더 지정)
- 데이터 폴더
- 코드: 브랜치와 커밋, 변경 사항이 있으면 그 표시
- 백업 저장소: 커밋하지 않으면 "커밋 안 함"과 이유

### 실행 조건과 거부됐을 때 할 일

실제 데이터 폴더를 쓰는 실행은 **메인 작업 폴더가 main을 체크아웃하고 변경 사항(`git status`에 나오는 것, 무시되는 파일 제외)이 없을 때만** 돈다. 아니면 아무것도 쓰지 않고 이유와 할 일을 알리고 멈춘다. 실행하는 Claude는 조건을 맞추려 하지 않는다(stash, checkout 등을 하지 않는다). 아래 할 일은 직접 한다.

| 거부 이유 | 할 일 |
| --- | --- |
| main이 아닌 브랜치 | 작업을 커밋한 뒤 `git switch main` |
| 변경 사항 있음 | 작업 브랜치에 커밋하거나 되돌린다. 도구가 만든 추적되지 않은 파일(예: `.serena/memories/`)이 원인일 수 있다 |
| git worktree 안에서 실행 | 메인 작업 폴더에서 worktree 없이 Claude Code 세션을 열고 실행한다 |
| DB가 없는데 `data` 브랜치에 백업이 있음 | 아래 "복원"대로 DB를 먼저 복원한다 |

조건만 미리 확인하려면 다음을 실행한다. 아무것도 쓰지 않는다.

```bash
node src/cli.ts check
```

### `/brief`가 스킬 대신 다른 것으로 열릴 때

`/brief`가 이 프로젝트 스킬 대신 Claude Code 내장 명령(brief-only 모드)으로 열리면 이름이 겹친 것이다. 그때는 스킬 목록에서 프로젝트 스킬 `brief`를 골라 실행한다. 또는 Claude에게 "`.claude/skills/brief/SKILL.md`대로 브리프를 수집해줘"라고 요청한다.

## 시험 실행: `/brief test`

- `/brief test`는 새 임시 데이터 폴더(`.test-data/<시각>/`)를 쓰고, 백업은 그 폴더 안에 내보내기만 하며 커밋하지 않는다.
- 어느 브랜치에서든, 커밋하지 않은 변경이 있어도 돈다. 지금 작업 폴더의 코드로 돈다.
- `/brief test YYYY-MM-DD`는 그날부터 KST 어제까지 수집한다. 시작일은 시험 모드에서만 받는다.
- 다른 인자(오타 포함)나 잘못된 시작일은 사용법을 알리고 멈춘다.
- `.test-data/`는 git이 무시한다. 쌓인 시험 데이터 폴더는 필요 없으면 직접 지워도 된다.
- 시험 모드도 실제 YouTube API로 영상을 받는다. 같은 키의 하루 검색 할당량을 쓰므로, 같은 날 시험을 여러 번 돌리면 그날 실제 `/brief`의 영상 받기가 할당량 초과로 실패할 수 있다(아래 "추천 영상").
- 모든 실행의 시작 단계가 시험 모드가 만든 `.test-data/<시각>/` 폴더들에서도 받은 지 30일 지난 영상 데이터를 지운다(아래 "30일 규칙"). 그 밖의 시험 데이터는 그대로 둔다.

## 데이터 폴더와 환경 변수

실제 데이터 폴더는 메인 작업 폴더의 `data/`다. git이 무시한다. worktree에서 계산해도 메인 작업 폴더의 `data/`를 가리킨다.

| 경로 | 내용 |
| --- | --- |
| `data/tidwyn.db` | 실제 DB(SQLite). 원본이다 |
| `data/snapshots/` | 실행 전 사본. 최근 14일치만 남는다 |
| `data/briefs/YYYY-MM-DD.md` | 날짜별 마크다운 브리프 |
| `data/issues/<식별자>.md`, `data/issues/index.md` | 이슈마다 마크다운 하나와 전체 이슈 목록 |
| `data/backup/` | 마지막으로 내보낸 월별 JSON |
| `data/work/`, `data/runs/` | 실행 중 작업 파일(후보 목록, 연결 파일, 합치기 파일, 영상 후보 목록·상세·확인 후보·메모·고르기 파일(`videos.*`) 포함)과 실행 기록 |

| 환경 변수 | 뜻 |
| --- | --- |
| `TIDWYN_DATA_DIR` | 데이터 폴더를 다른 곳으로 바꾼다. `data/`를 가리키면(상대 경로, 심볼릭 링크 포함) 실제 데이터 폴더로 보고 실행 조건을 똑같이 받는다 |
| `TIDWYN_BACKUP_REPO` | 백업을 커밋할 git 저장소. 기본은 이 프로젝트 저장소다 |
| `ECOS_API_KEY` | 한국은행 ECOS Open API 키(지표 받기). 없으면 메인 작업 폴더의 `.env.local`에서 읽는다 |
| `FRED_API_KEY` | FRED API 키(지표 받기). 없으면 메인 작업 폴더의 `.env.local`에서 읽는다 |
| `YOUTUBE_API_KEY` | YouTube Data API 키(영상 받기). 없으면 메인 작업 폴더의 `.env.local`에서 읽는다 |
| `GEMINI_API_KEY` | Gemini API 키(영상 내용 확인). 없으면 메인 작업 폴더의 `.env.local`에서 읽는다 |

- 데이터 폴더를 바꾸고 백업 저장소를 지정하지 않으면 커밋하지 않고 내보내기만 한다.
- 데이터 폴더가 실제 데이터 폴더가 아닌데 백업 저장소가 이 프로젝트 저장소면 커밋하지 않는다. 시험 데이터가 실제 `data` 브랜치에 들어가지 않게 하기 위해서다.

## `data` 브랜치(백업)

- 실행 끝에 DB 전체를 월별 JSON(`YYYY-MM.json`)과 `meta.json`(형식 버전, 첫 수집일, 첫 연결 적용일, 마지막 합치기 점검일)으로 내보낸다.
- 이슈 데이터(이슈, 뉴스-이슈 연결, 이슈 관계, 합치기 기록과 합치기 전 상태, "합치지 않음" 쌍)는 `issues.json`에 들어간다. 이슈 데이터가 없으면 이 파일은 없다.
- 형식 버전은 2다. 형식 1 백업(2단계 전)도 복원되고, 그때는 모든 뉴스가 이슈 없음이 되어 다음 실행이 다시 연결한다.
- 내보낸 파일을 이 저장소의 `data` 브랜치에 커밋한다. 바뀐 것이 없으면 커밋하지 않는다.
- `data` 브랜치에는 백업 파일만 있다. main에 머지하지 않고 지우지 않는다. 실제 실행 끝에 원본 저장소(`origin`)로 push한다(아래 "원본 저장소").
- 커밋은 작업 트리와 체크아웃된 브랜치를 건드리지 않는다.
- 백업만 따로 실행하려면 다음을 실행한다. 환경 변수가 없으면 실제 데이터 폴더와 이 저장소를 쓴다. 실제 데이터 폴더일 때는 main 체크아웃 상태에서 실행한다.

```bash
node src/cli.ts backup
```

- git 브랜치 이름과 작업 트리의 `data/` 폴더가 헷갈리지 않게, git 명령에서는 `refs/heads/data`로 가리킨다. 예: `git log refs/heads/data`.

## 실행 전 사본

- 매 실행은 DB에 쓰기 전에 `data/snapshots/tidwyn-YYYYMMDD-HHMMSS.db`(KST)를 남긴다. 14일보다 오래된 사본은 지운다.
- 되돌리려면 Claude Code를 닫은 상태에서 지금 DB를 다른 이름으로 옮기고, 원하는 사본을 `data/tidwyn.db`로 복사한다.
- 백업과 다르다. 사본은 DB 파일 그대로의 단기 되돌리기용이고, 백업(`data` 브랜치)은 DB를 다시 만들 수 있는 장기 보관용이다.

## 복원

`data/`가 지워졌거나 새 컴퓨터에 클론했으면 백업에서 DB를 만든다. 의존성 설치 없이 돈다.

```bash
node src/cli.ts restore
```

- 이 저장소의 `refs/heads/data`에서 백업을 읽어 `data/tidwyn.db`를 만든다.
- 이미 DB가 있으면 거부한다. 덮어쓰려면 `--force`를 붙인다.
- 다른 곳에서 읽거나 다른 곳에 만들려면 옵션을 쓴다.
  - `--repo <저장소>`: 다른 저장소의 `data` 브랜치에서 읽는다
  - `--from <폴더>`: 백업 JSON이 있는 폴더에서 읽는다
  - `--out <DB 경로>`: 다른 경로에 만든다
- 마크다운(브리프와 이슈)은 백업에 없다. 복원한 뒤 아래 `render --all`로 모두 다시 만든다. 다음 `/brief` 실행이 연결이나 합치기를 하면 그때도 모두 다시 만들어진다.

## 마크다운 다시 만들기

```bash
node src/cli.ts render --all
```

DB에서 모든 날짜의 브리프(`data/briefs/`)와 이슈 마크다운(`data/issues/`)을 다시 만든다. DB에 없는 이슈 파일은 지운다. 한 날짜의 브리프만 다시 만들려면 다음을 실행한다.

```bash
node src/cli.ts render --date YYYY-MM-DD
```

`TIDWYN_DATA_DIR`이 있으면 그 폴더에서 한다.

## 이슈(이어지는 이야기)

- 모든 뉴스는 이슈 하나(주 이슈)에 속하고, 다른 이슈에도 추가로 붙을 수 있다. 이슈는 몇 주~몇 달 이어지는 이야기 하나다.
- `/brief`가 저장한 직후 그 날짜를 연결한다. 이슈가 없는 뉴스(지난 실행에서 연결이 실패한 날짜, 2단계 전에 쌓인 날짜)는 다음 실행이 새 날짜를 조사하기 전에 오래된 날부터 연결한다.
- 연결 결과는 `data/issues/`에서 본다. `index.md`는 진행 중 이슈(최근 업데이트 순)와 종료된 이슈, 최근 합치기 기록을 보인다. 이슈 파일에는 별칭, 분류, 상태, 기간, 지금까지 요약, 타임라인, 관련 이슈가 있다.
- 브리프의 주요 뉴스마다 "이어지는 이야기"(주 이슈 링크)와 이전 전개 최대 3건(없으면 "새 이슈")이 나온다. 짧은 소식에는 이슈 이름만 붙는다.
- 이슈는 뉴스가 끝을 알릴 때만(협상 타결, 판결 확정 등) 종료되고, 후속 뉴스가 붙으면 다시 진행 중이 된다.
- 이슈를 찾으려면 다음을 실행한다(이름·별칭·요약의 낱말).

```bash
node src/cli.ts issue-search --q "낱말"
```

### 합치기

- `/brief`는 마지막 합치기 점검(처음에는 첫 연결 적용일)에서 7일이 지난 실행의 끝, 백업 전에 비슷한 이슈 쌍을 뽑아 같은 이야기인 것을 합친다.
- 흡수된 이슈는 지우지 않고 남는 이슈를 가리킨다. 이슈 파일도 남는 이슈로 가는 링크만 남는다. 흡수된 이슈의 이름과 별칭은 남는 이슈의 별칭이 된다.
- 합친 결과는 실행 요약과 `data/issues/index.md`의 "최근 합치기"에 나온다. 전체 기록은 다음 명령으로 본다.

```bash
node src/cli.ts merges
```

### 잘못 합친 것 되돌리기

합치기 기록의 번호(`merges` 출력이나 `index.md`의 "되돌리기" 값)로 그 합치기 하나만 되돌린다. `/brief`는 이 명령을 실행하지 않는다. 직접 실행한다.

```bash
node src/cli.ts unmerge --id 번호
```

- 실제 데이터 폴더를 쓸 때는 `/brief`와 같은 실행 조건(main 체크아웃, 변경 사항 없음)을 따른다. 아니면 아무것도 바꾸지 않고 멈춘다. `TIDWYN_DATA_DIR`로 다른 폴더를 지정하면 그 폴더에서 한다.
- 바꾸기 전에 DB 사본을 `data/snapshots/`(실행 전 사본과 같은 곳, 14일 보관)에 남긴다.
- 흡수된 이슈를 합치기 전 이름, 별칭, 분류, 상태, 요약, 연결, 관계로 되살린다. 남는 이슈는 합치기 전 별칭, 연결, 관계로 돌아가되, 그 합치기 뒤에 더해진 것(새로 붙은 뉴스, 다른 합치기로 들어온 것)은 그대로 둔다. 남는 이슈의 요약과 상태는 그 뒤에 더해진 것이 없을 때만 합치기 전 값으로 돌아간다.
- 되돌린 두 이슈는 "합치지 않음"이 되어 다음 합치기 후보에서 빠진다.
- 그 합치기 뒤에 남는 이슈가 다시 다른 이슈에 흡수되었으면 거부하고, 먼저 되돌릴 합치기 번호를 알린다. 이미 되돌린 합치기도 거부한다.
- 끝나면 마크다운을 다시 만든다. 백업은 다음 `/brief` 실행이 한다.

### 2단계 머지 뒤 첫 실제 실행

- 첫 실제 `/brief`가 실제 DB 구조를 바꾸고(마이그레이션), 쌓인 뉴스 전체를 소급 연결한다. 연결할 날짜가 많아 평소보다 오래 걸린다.
- 마이그레이션 전에 실행 전 사본이 남는다(`data/snapshots/`).

### 2단계 이전 코드로 돌아가야 할 때

- 머지 뒤 첫 실제 실행의 실행 전 사본(마이그레이션 전 DB)을 `data/tidwyn.db`로 되돌린다(위 "실행 전 사본"). 그 뒤 모은 날짜는 이전 코드의 다음 실행이 다시 모은다.
- 이전 코드로 백업하면 `data` 브랜치 최신 백업에서 이슈 데이터(`issues.json`)가 빠진다. `data` 브랜치 이력에는 남는다.
- 실행 전 사본은 14일만 남는다. 14일이 지났으면 `git log refs/heads/data`에서 2단계 머지 전의 백업 커밋을 찾아, 그 커밋의 파일을 저장소 밖 폴더로 꺼낸 뒤 복원한다(저장소 안에 두면 변경 사항이 생겨 실행 조건에 걸린다).

```bash
git log --oneline refs/heads/data
```

```bash
mkdir -p ../tidwyn-old-backup && git archive <커밋> | tar -x -C ../tidwyn-old-backup
```

```bash
node src/cli.ts restore --from ../tidwyn-old-backup --force
```

- 이 경우에도 머지 전 백업 뒤에 모은 날짜는 다음 실행이 다시 모은다.

## 인물·기관·국가와 용어

- `/brief`는 날짜마다 이슈 연결 직후, 그날 뉴스에서 이야기의 중심이 되는 인물·기관·국가(대상)와 어려운 용어를 뽑아 뉴스에 연결한다(뽑기). 대상에는 한 줄 설명(직함·소속·역할), 용어에는 쉬운 설명이 붙는다. 이미 쌓인 날짜와 뽑기가 실패한 날짜는 다음 실행이 새 날짜를 조사하기 전에 오래된 날부터 뽑는다(`start`의 "뽑기할 저장된 날짜" 줄).
- 뽑기는 DB에 저장된 뉴스 글만 읽는다(웹을 다시 조사하지 않는다). 공적 역할로 나온 공인만 뽑고, 사건의 일반인은 뽑지 않는다(스킬 문서의 뽑기 기준).
- 뽑기가 검사를 2번 고쳐도 통과하지 못하면 그 날짜는 아무것도 적용하지 않고 실패로 남는다. 뉴스와 이슈 연결은 그대로이고 다음 실행이 다시 뽑는다.
- 결과는 사이트의 "인물·기관·국가"(`/entities`), 대상 페이지(`/entities/<번호>`), "용어 사전"(`/terms`, 용어 주소 `/terms/<번호>`)과 펼친 카드의 칩·밑줄로 나온다.
- 대상·용어를 찾으려면 다음을 실행한다(이름·별칭·설명의 낱말). 지운 이름과 같으면 "지운 이름과 같음"이 나온다.

```bash
node src/cli.ts ref-search --q "낱말"
```

### 대상·용어 합치기와 되돌리기

- 7일 합치기(위 "합치기")에서 이슈와 함께 비슷한 대상 쌍(같은 종류끼리)과 비슷한 용어 쌍을 뽑아, 같은 것을 합친다. 흡수된 것은 남는 것을 가리키고(옛 주소는 남는 것으로 간다), 이름과 별칭은 남는 것의 별칭이 된다. 합친 결과는 실행 요약과 `merges` 출력에 나온다.
- 잘못 합친 것은 그 기록 번호로 되돌린다. `/brief`는 이 명령을 실행하지 않는다. 규칙(실행 조건, 바꾸기 전 사본, 되살리는 범위, "합치지 않음", 연달아 합친 경우 거부)은 이슈의 `unmerge`와 같다.

```bash
node src/cli.ts ref-unmerge --id 번호
```

### 대상·용어 지우기

잘못 뽑힌 일반인이나 틀린 설명이 공개되었을 때 대상 하나나 용어 하나를 지운다. `/brief`는 이 명령을 실행하지 않는다. 직접 실행한다.

```bash
node src/cli.ts ref-delete --entity 번호
```

```bash
node src/cli.ts ref-delete --term 번호
```

- 실제 데이터 폴더를 쓸 때는 `/brief`와 같은 실행 조건을 따르고, 바꾸기 전에 DB 사본을 `data/snapshots/`에 남긴다.
- 그 대상·용어의 연결을 모두 끊고, 이름·별칭·설명을 DB에서 지운다(식별자는 다시 쓰지 않는다). 그것에 흡수되어 있던 것도 함께 지우고, 그것이 든 합치기 기록은 합치기 전 상태와 이유를 가린다(그 기록은 되돌리기를 거부한다). 흡수된 번호를 주면 거부하고 남는 것의 번호를 알린다.
- 이름과 별칭은 "지운 이름"으로 기록해 다음 뽑기에서 같은 이름(띄어쓰기·대소문자만 다른 표기 포함)의 새 대상·용어를 거부한다. 지운 이름은 비밀 키로 만든 해시로만 저장하고 백업한다. 키는 데이터 폴더의 `deleted-names.key`(백업하지 않는다, 처음 지울 때 만든다)다. 키 파일은 비밀 값이다: 저장소, 백업, 결과물, 대화창에 넣지 않는다.
- 키 없이 백업에서 복원한 데이터 폴더에서는 지운 이름으로 막지 못하고, `start`와 요약에 "지운 이름 일부를 막지 못한다" 줄이 나온다. 그 뒤 새로 지우면 새 키가 생기지만, 옛 키로 만든 기록은 여전히 막지 못한다. 키 파일을 데이터 폴더와 함께 따로 보관해 두면 이 경고가 나오지 않는다. 잘못 뽑힌 이름이 다시 나오면 다시 지운다.
- 다음 `/brief` 실행이 백업하고 배포한다. 그때부터 사이트와 검색에서 빠지고 그 주소는 없는 페이지가 된다. 바로 내리려면 main에서 위 "손으로 빌드·배포하기"(`site --data-dir data` 뒤 `deploy --dir data/site --db data/tidwyn.db`)를 한다.
- **지우기의 한계:** 이미 push된 `data` 브랜치의 지난 백업 이력에는 이름이 남는다(공개 저장소). 뉴스 본문(제목·요약·본문)과 이슈 이름·별칭·요약에 나온 이름도 바꾸지 않는다.
- 지우기는 되돌리지 않는다. 지운 이름을 다시 쓰거나 지우기를 물리려면, 지우기 전에 남긴 사본(`data/snapshots/`, 14일 보관)을 위 "실행 전 사본"의 방법으로 `data/tidwyn.db`에 되돌린다. 그 사본 뒤에 모은 날짜는 다음 실행이 다시 모은다.

### 4단계 머지 뒤 첫 실제 실행

- 첫 실제 `/brief`가 실제 DB 구조를 바꾸고(마이그레이션, 버전 4), 쌓인 날짜 전체를 뽑는다. 뽑을 날짜가 많아 평소보다 오래 걸린다. 마이그레이션 전에 실행 전 사본이 남는다.
- 이 실행은 검토 없이 운영 사이트에 대상·용어를 올린다. 실행 뒤 사이트의 인물·기관·국가 목록을 한 번 보고, 일반인이나 틀린 설명이 있으면 위 "대상·용어 지우기"로 지운다.

### 4단계 이전 코드로 돌아가야 할 때

- 기본은 머지 뒤 첫 실제 실행의 실행 전 사본(마이그레이션 전 DB)을 `data/tidwyn.db`로 되돌리는 것이다(위 "실행 전 사본"). 그러면 그 뒤에 지운 대상·용어의 지운 이름 기록도 사라진다. 다시 4단계로 올리면 그 이름이 다시 뽑힐 수 있으니, 그 실행 뒤 다시 지운다.
- 사본 없이 이전 코드를 돌리면 이전 코드가 버전 4 DB를 거부하지 않아 그대로 돈다. 하지만 그 코드의 백업에서 대상·용어와 지운 이름 기록(`refs.json`)이 빠지고, 사이트의 대상·용어 주소(`/entities`, `/terms`)가 깨진다. `data` 브랜치 이력에는 남는다.

## 일정

- `/brief`는 날짜마다 인물·용어 뽑기 직후, 그날 뉴스에서 날짜가 정해졌다고 보도된 공식 일정(회의, 발표, 선거, 선고, 시행, 출시 등)을 뽑아 근거 뉴스에 연결한다(일정 뽑기). 예정일은 일 단위(`YYYY-MM-DD`)나 달 단위(`YYYY-MM`)이고, 해외 일정은 현지 날짜다. 이미 쌓인 날짜와 일정 뽑기가 실패한 날짜는 다음 실행이 새 날짜를 조사하기 전에 오래된 날부터 뽑는다(`start`의 "일정 뽑기할 저장된 날짜(채우기·재시도)" 줄).
- 일정 뽑기는 DB에 저장된 뉴스 글만 읽는다(새로 수집하는 날짜는 조사하며 읽은 기사도 쓴다). 일정을 찾으려고 웹을 따로 조사하지 않는다. 판단 기준은 스킬 문서의 "일정 뽑기 기준"이다.
- 같은 일정은 다른 날짜 뉴스에도 근거로 붙는다. 알려진 날은 가장 이른 근거 뉴스의 날짜다.
- **결과 연결과 기다리는 기간:** 예정일이 된 일정은 기다리는 기간(일 단위는 예정일부터 14일 뒤까지, 달 단위는 그 달 1일부터 다음 달 14일까지) 동안 날마다 결과 후보에 들고, 그날 뉴스에 결과(결정, 발표, 선고 등)가 있으면 그 뉴스가 결과로 이어진다. 연기·취소가 보도되면 연기(새 일정을 가리킨다)나 취소가 된다. 예정일 전에도 연기·취소가 될 수 있다. 기간이 지나도 결과가 없으면 사이트에 "결과 못 찾음"으로 나온다(DB의 가장 최근 저장 날짜 기준으로 빌드할 때 계산한다. 늦게 재시도한 날짜가 결과를 찾으면 바뀐다).
- 일정 뽑기가 검사를 2번 고쳐도 통과하지 못하면 그 날짜는 아무것도 적용하지 않고 실패로 남는다. 뉴스, 이슈 연결, 인물·용어 뽑기는 그대로이고 다음 실행이 다시 뽑는다.
- 결과는 사이트의 일정 화면(`/schedules`, 목록과 달력), 일정 주소(`/schedules/<번호>`, 목록에서 그 일정을 강조한다), 브리프 위의 '이번 주 일정', 펼친 카드의 일정 칩, 이슈 페이지의 일정으로 나온다.
- 일정을 찾으려면 다음을 실행한다(이름의 낱말, 예정일 범위는 빼도 된다). 지운 일정과 이름·예정일이 같으면 "지운 일정과 같음"이 나온다.

```bash
node src/cli.ts schedule-search --q "낱말" --from 2026-11-01 --to 2026-11-30
```

### 일정 합치기와 되돌리기

- 7일 합치기(위 "합치기")에서 이슈·대상·용어와 함께 비슷한 일정 쌍(예정일이 같거나 이틀 안, 달 단위와 그 달 안의 일 단위 포함, 이름이 비슷함)을 뽑아 같은 일정을 합친다. 흡수된 일정의 근거·결과 연결은 남는 것으로 옮겨지고, 흡수된 일정 주소는 남는 일정으로 간다. 합친 결과는 실행 요약과 `merges` 출력에 나온다.
- 잘못 합친 것은 그 기록 번호로 되돌린다. `/brief`는 이 명령을 실행하지 않는다. 규칙(실행 조건, 바꾸기 전 사본, 되살리는 범위, "합치지 않음", 연달아 합친 경우와 이미 되돌린 기록 거부)은 이슈의 `unmerge`와 같다. 합친 뒤 남는 것에 붙은 근거는 남는 것에 그대로 둔다.

```bash
node src/cli.ts schedule-unmerge --id 번호
```

### 일정 지우기

잘못 뽑힌 일정(추측을 일정으로 뽑았거나 일반인 이름이 든 이름 등)이 공개되었을 때 일정 하나를 지운다. `/brief`는 이 명령을 실행하지 않는다. 직접 실행한다.

```bash
node src/cli.ts schedule-delete --id 번호
```

- 실제 데이터 폴더를 쓸 때는 `/brief`와 같은 실행 조건을 따르고, 바꾸기 전에 DB 사본을 `data/snapshots/`에 남긴다.
- 그 일정의 근거·결과 연결을 모두 끊는다(식별자는 다시 쓰지 않는다). 그 일정에 흡수되어 있던 일정도 함께 지운다. 흡수된 번호를 주면 거부하고 남는 것의 번호를 알린다. 그 일정을 연기 대상으로 가리키던 일정은 "연기(새 날짜 모름)"로 보인다.
- 이름과 예정일은 "지운 일정"으로 DB와 백업에 남아, 다음 뽑기에서 같은 이름(띄어쓰기·대소문자·가운뎃점만 다른 표기 포함)·같은 예정일의 새 일정을 거부한다. 예정일이 다르면 새로 만들 수 있다.
- 다음 `/brief` 실행이 백업하고 배포한다. 그때부터 사이트에서 빠지고 그 일정 주소는 없는 페이지가 된다. 바로 내리려면 main에서 위 "손으로 빌드·배포하기"(`site --data-dir data` 뒤 `deploy --dir data/site --db data/tidwyn.db`)를 한다.
- **지우기의 한계:** 이미 push된 `data` 브랜치의 지난 백업 이력에는 일정이 남는다(공개 저장소). 지운 일정의 이름과 예정일은 이후 백업에도 "지운 일정"으로 남는다. 뉴스 본문(제목·요약·본문·전망)에 나온 일정 내용도 바꾸지 않는다.
- 지우기는 되돌리지 않는다. 지우기를 물리려면, 지우기 전에 남긴 사본(`data/snapshots/`, 14일 보관)을 위 "실행 전 사본"의 방법으로 `data/tidwyn.db`에 되돌린다. 그 사본 뒤에 모은 날짜는 다음 실행이 다시 모은다.

### 5단계 머지 뒤 첫 실제 실행

- 첫 실제 `/brief`가 실제 DB 구조를 바꾸고(마이그레이션, 버전 5), 쌓인 날짜 전체의 일정을 뽑는다(7-2단계). 뽑을 날짜가 많아 평소보다 오래 걸린다. 마이그레이션 전에 실행 전 사본이 남는다.
- 이 실행은 검토 없이 운영 사이트에 일정을 올린다. 실행 뒤 사이트의 일정 화면을 한 번 보고, 잘못 뽑힌 일정이 있으면 위 "일정 지우기"로 지운다.

### 5단계 이전 코드로 돌아가야 할 때

- 기본은 머지 뒤 첫 실제 실행의 실행 전 사본(마이그레이션 전 DB)을 `data/tidwyn.db`로 되돌리는 것이다(위 "실행 전 사본"). 그 뒤에 쌓인 일정과 그 뒤에 모은 날짜는 사라지고, 다시 5단계로 올리면 다음 실행이 다시 모으고 뽑는다.
- 사본 없이 이전 코드를 돌리면 이전 코드가 버전 5 DB를 거부하지 않아 그대로 돈다. 하지만 그 코드의 백업에서 일정 데이터(`schedules.json`과 월별 파일의 일정 뽑기 완료 표시)가 빠지고, 사이트의 일정 주소(`/schedules`, `/schedules/<번호>`)가 깨진다. `data` 브랜치 이력에는 남는다.

## 주요 지표

- **무엇을 어디서 받는지:** 12개 지표를 공식 API 두 곳에서 받는다. 한국은행 ECOS Open API: 원/달러 환율, 코스피, 코스닥, 한국 기준금리, 국고채 3년 금리, 한국 소비자물가. FRED API(St. Louis Fed): 미국 기준금리(상단), 미국채 10년 금리, WTI 유가, 브렌트유, 미국 소비자물가, 달러 지수. 정의(식별자, 출처 코드, 표시 방식, 공개 여부)는 `src/indicators.ts`에 있다. 값은 스크립트(`indicator-fetch`, `/brief` 12-4단계)만 받고 Claude가 찾거나 고치지 않는다.
- **키 두는 곳:** 메인 작업 폴더의 `.env.local`(git이 무시한다)에 `ECOS_API_KEY=…`, `FRED_API_KEY=…`로 둔다. 같은 이름의 환경 변수가 있으면 그것을 먼저 쓴다. worktree에서 돌려도 메인 작업 폴더의 파일을 읽는다. 키 값은 실행 기록, 출력, 백업, 결과물에 쓰지 않고, 공개 전 점검과 결과물 검사가 키 값을 찾으면 실패한다.
- **ECOS 키 기한:** ECOS 키는 발급일부터 2년간 쓸 수 있다(ECOS 이용약관 제4조). 지금 키는 2026-10-29에 받아 2028-10 말쯤 끝난다. 끝나기 전에 ECOS 누리집에서 연장하거나 새로 받아 `.env.local`을 고친다.
- **받는 범위:** 일별 지표는 값이 없으면 2021-10-27부터, 있으면 마지막 저장 값 날짜의 60일 전부터 오늘(KST)까지 다시 받는다. 출처가 늦게 고친 값도 이렇게 반영된다. 월별 지표(소비자물가)는 매번 2020-10부터 받아 저장 값을 통째로 바꾼다. 응답이 비었거나, 첫 달이 저장 값보다 늦거나, 행 수가 저장 값의 90% 미만이면 실패로 보고 저장 값을 그대로 둔다. 휴장일처럼 값이 없는 날은 비워 둔다.
- **실패:** 지표 하나가 실패해도 나머지 지표, 백업, 빌드, 배포, 요약은 계속한다. 실패한 지표는 다음 실행이 받는 범위 규칙으로 빠진 만큼 채운다.
- **백업:** 지표 값(코스피·코스닥 빼고, 지표마다 출처 표시와 함께), 이슈-지표 연결과 판단 여부, 지표 합치기 기록은 백업의 `indicators.json`에 들어간다. 코스피·코스닥 값은 한국거래소 자료라 공개 백업에 넣지 않는다. 그래서 백업에서 복원하면 코스피·코스닥은 값이 없고(사이트에서 카드와 상자에서 빠진다), 다음 `/brief`가 처음(2021-10-27)부터 다시 받는다.
- **공개 끄기:** 지표 하나를 사이트에서 내리려면 작업 브랜치에서 `src/indicators.ts`의 그 지표의 `public`을 `false`로 바꿔 main에 머지한다. 다음 `/brief`(또는 위 "손으로 빌드·배포하기")부터 그 지표가 사이트 데이터, 브리프 위 상자, 지표 페이지, 이슈 페이지 어디에도 없고 그 주소는 없는 페이지가 된다. 값 받기·저장과 이슈 판단은 계속하므로 다시 켜면 바로 보인다.
- **소비자물가 기준년 개편:** 국가데이터처가 2026-12-31부터 소비자물가 기준년을 2020=100에서 2025=100으로 바꾼다. 개편 뒤 첫 `/brief`에서 한국 소비자물가 값이 통째로 바뀌었는지(요약의 "바뀐 값" 수), 사이트의 상승률이 발표와 같은지 확인한다. ECOS 통계표 코드(`901Y009`)가 바뀌어 받기가 계속 실패하면 ECOS의 통계표 목록에서 새 코드를 찾아 `src/indicators.ts`를 작업 브랜치에서 고친다.

### 키 문제일 때 할 일

요약에 "키 확인 필요"가 나오면 키가 없거나, 틀렸거나, 기한이 끝난 것이다. `/brief`는 키 문제로 멈추지 않는다(그 출처의 지표만 받지 못한다).

1. `.env.local`에 `ECOS_API_KEY`·`FRED_API_KEY` 줄이 있는지 본다(값을 대화창이나 기록에 붙여 넣지 않는다). `start` 출력의 "키:" 줄이 "있음"인지도 본다.
2. ECOS는 ECOS 누리집에서 키 상태와 기한을 본다. 끝났으면 연장하거나 새로 받는다. FRED는 FRED 계정 화면에서 키를 본다.
3. 새 키를 `.env.local`에 넣으면 다음 `/brief`가 빠진 만큼 다시 받는다.

키가 공개된 곳(커밋, 백업, 결과물)에 들어갔다면 공개 전 점검이 막지만, 이미 push됐다면 그 키는 출처 화면에서 폐기하고 새로 받는다.

### 이슈 지표 판단

- `/brief` 12-3단계에서 "지표 판단 안 함"인 이슈마다 Claude가 그 이슈와 직접 관계있는 지표를 0~3개 고른다(기준은 스킬 문서의 "지표 판단 기준"). 대부분의 정치·사회·IT 이슈는 0개다. 한 번 판단한 이슈는 다시 판단하지 않는다.
- 이슈를 합치면 흡수된 이슈의 지표를 남는 이슈에 더한다. 합친 수가 3개를 넘거나 둘 중 하나가 판단 안 함이면 남는 이슈가 "판단 안 함"으로 돌아가 다음 실행이 다시 고른다.
- `unmerge`는 두 이슈의 지표 연결과 판단 여부를 합치기 전으로 되돌린다. 같은 남는 이슈에 나중에 한 합치기로 들어온 지표는 남는다(그래서 3개를 넘으면 "판단 안 함"). 6단계 전에 한 합치기를 되돌리면 두 이슈 모두 "판단 안 함"이 되어 다음 실행이 다시 고른다.
- 판단이 틀린 연결을 손으로 고치는 명령은 없다. 틀린 연결이 보이면 다음 명세서에서 다룬다.

### 6단계 머지 뒤 첫 실제 실행

- 첫 실제 `/brief`가 실제 DB 구조를 바꾸고(마이그레이션, 버전 6. 그 전에 실행 전 사본이 남는다), 12개 지표의 5년치를 받고, 모든 이슈를 판단한다. 평소보다 오래 걸린다.
- 이 실행은 검토 없이 운영 사이트에 지표를 올린다. 실행 뒤 지표 페이지와 몇몇 이슈의 '관련 지표'를 한 번 본다.

### 6단계 이전 코드로 돌아가야 할 때

- 기본은 머지 뒤 첫 실제 실행의 실행 전 사본(마이그레이션 전 DB)을 `data/tidwyn.db`로 되돌리는 것이다(위 "실행 전 사본"). 지표 값은 다시 6단계로 올리면 다음 실행이 다시 받는다.
- 사본 없이 이전 코드를 돌리면 이전 코드가 버전 6 DB를 거부하지 않아 그대로 돈다. 하지만 그 코드의 백업에서 지표 데이터(`indicators.json`)가 빠지고, 사이트의 지표 주소(`/indicators`, `/indicators/<식별자>`)가 깨진다. `data` 브랜치 이력에는 남는다.

## 추천 영상

- **무엇을 하는지:** `/brief`가 실행한 날(KST) 한 번, DB의 가장 늦은 브리프 날짜(대상 날짜)에 볼 만한 정보성 롱폼 영상을 붙인다. 스크립트(`video-fetch`, 스킬 12-5단계)가 YouTube Data API v3에서 받아 거르고, Claude가 후보 목록에서 확인 후보(하루 최대 24개)를 추리고, 스크립트(`video-notes`)가 Gemini API로 영상 내용 메모를 받으면, Claude가 메모로 최종 선별해 추천 이유, 요약, 관련 이슈(0~2개)를 쓴다(12-6단계, 기준은 스킬 문서의 "영상 고르기 기준"). 묶음마다 최대 한국 5개, 미국 5개, AI 한국어 3개, AI 영어 3개이고, 좋은 영상이 없으면 채우지 않는다. 조회수는 보지 않는다.
- **무엇을 어디서 받는지:**
  - 인기 차트: 한국(`KR`)과 미국(`US`)마다 그 실행에서 받은 카테고리 목록(`videoCategories`) 중 정해 둔 카테고리의 차트만 페이지 끝까지 받는다. 정해 둔 카테고리는 정보성 4개(뉴스·정치 25, 교육 27, 과학·기술 28, 비영리·사회운동 29)와 엔터테인먼트 24·코미디 23이다(`src/youtube.ts`의 `CHART_CATEGORIES`). 음악·게임·스포츠 등 그 밖의 카테고리와 카테고리를 지정하지 않은 전체 차트는 받지 않는다(2026-10-30 사용자 결정. 시험에서 그 차트들이 후보의 큰 몫을 차지했지만 고른 영상은 없었다). 엔터테인먼트·코미디를 남긴 것은 지식 채널(슈카월드, 지식한입 등)이 그 카테고리로 올리기 때문이다. 카테고리는 올리는 사람이 고르므로, 그 밖의 카테고리로 올라온 좋은 영상은 주제·AI 검색(카테고리를 보지 않는다)이 잡는다. 차트가 없다는 오류(`videoChartNotFound`, `notFound`)가 나는 카테고리는 건너뛴다(실패가 아니다).
  - 주제·AI 검색: 11개 분야(경제·금융, 산업·기업, 국제 정세, 과학, 우주, 의학·건강, 기술, 역사, 사회·다큐, 기후·환경·에너지, 인문·교양)와 AI를 한국어(`ko`, 지역 `KR`)와 영어(`en`, 지역 `US`)로 각각, 길이 구간 `medium`(4~20분)과 `long`(20분 넘음)으로 나눠 검색한다. 한 실행에 검색 48번(12 × 2 × 2)이다. 조건은 영상만, 실행한 시각 48시간 전 이후 업로드, 관련도 순이고, 검색마다 관련도 앞쪽 20개만 받는다. 분야와 키워드 목록은 `src/youtube.ts`의 `SEARCH_TOPICS` 한 곳에 있다.
  - 묶음: 한국 차트와 한국어 분야 검색은 한국(`kr`), 미국 차트와 영어 분야 검색은 미국(`us`), AI 한국어 검색은 `ai-ko`, AI 영어 검색은 `ai-en` 후보다.
  - 거르기: 합쳐 중복을 뺀 뒤 상세를 받아 4분 미만, 세로 영상, 지금 생방송 중이거나 예정인 영상, 최근 30일 안에 이미 추천한 영상을 뺀다. 생방송 기록이 있는 영상(라이브 다시보기, 프리미어)은 "생방송 기록 있음"으로 표시해 두고 Claude가 가른다(라이브 다시보기는 빼고, 프리미어로 올린 다큐·해설은 고를 수 있다).
- **언제 받는지:** 대상 날짜가 이미 "고르기 끝남"이면(0개를 고른 것도 끝남) YouTube를 부르지 않는다. 받기나 고르기가 실패하면 그 날짜는 끝나지 않은 채로 남아 다음 실행이 다시 받는다(그때의 가장 늦은 브리프 날짜에 붙인다). 지난 브리프 날짜를 되돌려 채우지 않는다.
- **작업 파일:** 받기와 고르기가 데이터 폴더의 `work/`에 여섯 파일을 둔다(스크립트가 쓰는 `videos.notes.json`은 메모 파일, Claude가 쓰는 `videos.check.json`은 확인 후보 파일이다. 메모를 쓰는 동안 임시 파일 `videos.notes.tmp.json`이 잠깐 생긴다). 후보 쪽 파일은 다음과 같다. `videos.candidates.md`(Claude가 먼저 읽는 목록, 후보마다 한 줄과 끝에 관련 이슈 후보), `videos.details.md`(후보마다의 상세: 받은 곳, 채널, 길이, 생방송 기록, 카테고리, 올린 시각, 언어, 설명 앞부분 120자), `videos.candidates.json`(전체), 그리고 Claude가 쓰는 `videos.pick.json`(고르기 파일). 후보가 하루 천여 개라 Claude는 한 줄 목록에서 추린 번호만 상세 파일에서 찾아 읽는다. 모든 영상 작업 파일에 YouTube 데이터가 들어 있어 고르기를 적용하면 그 실행 안에서 지우고, 실패하면 살펴볼 수 있게 남겼다가 다음 실행의 시작 단계가 지운다. 결과물 검사는 이 이름의 파일이 결과물에 들어가면 실패한다.
- **결과:** 사이트 브리프의 '영상' 탭(한국·미국·AI 칩으로 거름)과 이슈 페이지의 '관련 영상'에 나온다. 영상은 사이트에서 재생하지 않고 YouTube 영상 페이지로 연결한다. 제목·채널·길이·썸네일은 YouTube가 준 그대로이고 번역하지 않는다.

### 키와 할당량

- **키 두는 곳:** 메인 작업 폴더의 `.env.local`(git이 무시한다)에 `YOUTUBE_API_KEY=…`로 둔다. 읽는 규칙(같은 이름의 환경 변수 먼저, worktree에서도 메인 작업 폴더의 파일)과 키 값을 쓰지 않는 규칙은 지표 키와 같다(위 "주요 지표"). 요청할 때 키는 `x-goog-api-key` 헤더로 보내고 주소에 넣지 않는다.
- **키를 만든 곳:** Google 계정 `mivomad33`의 Google Cloud 프로젝트 `tidwyn`. YouTube Data API v3만 켰고, 키(이름 `tidwyn-youtube`)는 YouTube Data API만 부를 수 있게 제한했다. YouTube API는 지금도 비용이 없다. 8단계에서 같은 프로젝트에 Gemini 결제를 연결했다(아래 "영상 내용 확인"). YouTube 키의 동작은 그대로다.
- **gcloud:** 이 맥의 gcloud 기본 설정은 다른 개인 계정이다. 이 프로젝트의 gcloud 명령은 전용 설정으로 돌린다: `CLOUDSDK_ACTIVE_CONFIG_NAME=tidwyn gcloud …`. 기본 설정을 바꾸지 않는다.
- **할당량:** 검색(`search.list`)은 하루 100번, 그 밖의 호출은 하루 10,000단위다. 한 실행은 검색 90번, 그 밖의 호출 2,000단위를 넘지 않게 상한을 둔다(보통 검색 48번). 상한에 닿으면 그때까지 받은 것으로 후보 목록을 쓰고, 받지 못한 차트·분야가 요약에 나온다. 쓴 양은 요약의 "쓴 양" 줄에 나온다. 할당량은 태평양 시간 자정(한국 시간 오후 5시, 미국 서머타임 중에는 오후 4시)에 풀린다.
- **시험 모드도 같은 할당량을 쓴다:** `/brief test`도 같은 키로 검색 48번 안팎을 쓴다. 하루에 실제 실행과 시험을 합쳐 두 번 정도가 한도다. 같은 날 시험을 여러 번 돌리면 실제 `/brief`의 영상 받기가 막힐 수 있다.

### 영상 내용 확인(Gemini)

- **흐름:** 공식 자막 API는 영상 편집 권한이 있어야 해서 남의 영상에 쓸 수 없고, 비공식 자막 도구는 쓰지 않는다. `video-notes`가 Gemini API(`generateContent`)에 YouTube 주소를 넣어 영상마다 구조화된 메모를 받는다. 영상 파일은 받지 않는다. 메모는 작업 파일로만 두고 적용하면 지우며, 사이트에 올리는 요약은 Claude가 쓴다.
- **키:** `.env.local`의 `GEMINI_API_KEY`다. Google Cloud 프로젝트 `tidwyn`의 키 `tidwyn-gemini`이고 Gemini API만 부를 수 있게 제한했다. 키는 `x-goog-api-key` 헤더로만 보낸다.
- **결제:** 선불이다. 자동 충전은 잔액 ₩8,000 미만이면 ₩8,000을 채우고, 월 자동 충전 한도는 ₩1,000,000이다. 한도에 닿으면 다음 달까지 자동 충전이 꺼진다. 결제 화면은 <https://aistudio.google.com/billing>, 지출 화면은 <https://aistudio.google.com/spend>다. 크레딧은 산 날부터 12개월 뒤 만료되고 환불되지 않는다.
- **비용과 상한:** 시간당 입력 약 32~36만 토큰, 8시간 약 $0.8~0.9로 잡는다. 코드의 한 실행 상한은 $1.50이다. 확인 후보는 묶음별 `kr` 7, `us` 7, `ai-ko` 5, `ai-en` 5개, 합계 24개, 합계 길이 8시간, 영상 하나 3시간까지다. 명령은 8분에 닿으면 받은 만큼으로 끝난다.
- **시험 모드도 같은 크레딧을 쓴다:** `/brief test`도 실제 Gemini를 부른다.
- **모델을 바꾸는 곳:** `src/gemini.ts`의 `GEMINI_MODEL`과 그 아래 가격이다. 공식 가격표로 함께 고친다. 작업 브랜치에서 고친다.
- **Gemini가 막혀도 영상은 올라간다:** 메모 없이 고른 영상은 요약 없이 저장되고 뒤 단계는 멈추지 않는다. 나중에 요약만 채우지 않는다.

### 키·할당량 문제일 때 할 일

`/brief`는 영상 받기가 실패해도 멈추지 않는다(영상만 붙지 않고, 대상 날짜는 다음 실행이 다시 받는다).

- **"키 확인 필요":** 키가 없거나, 틀렸거나, 막힌 것이다.
  1. `.env.local`에 `YOUTUBE_API_KEY` 줄이 있는지 본다(값을 대화창이나 기록에 붙여 넣지 않는다). `start` 출력의 "키:" 줄이 "YouTube 있음"인지도 본다.
  2. Google 계정 `mivomad33`으로 Google Cloud 콘솔의 프로젝트 `tidwyn` → API 및 서비스 → 사용자 인증 정보에서 키 `tidwyn-youtube`의 상태와 제한(YouTube Data API v3)을 보고, YouTube Data API v3가 켜져 있는지 본다.
  3. 새 키를 만들었으면 `.env.local`을 고친다. 다음 `/brief`가 다시 받는다.
- **"Gemini 키 확인 필요":** 키가 없거나 거부된 것이다. `start`의 "키:" 줄이 "Gemini 있음"인지 보고, Google Cloud 콘솔의 프로젝트 `tidwyn`에서 키 `tidwyn-gemini`와 Gemini API 사용 설정을 본다.
- **"Gemini 크레딧 확인 필요":** 잔액이나 결제 문제다. 결제 화면에서 잔액, 자동 충전, 월 한도를 본다. 다음 실행부터 다시 확인한다.
- **"Gemini 한도 초과":** 일일 할당량이나 소비 한도에 닿았거나 속도 제한이 계속된 것이다. 지출 화면을 보고, 매일 나오면 작업 브랜치에서 확인 후보 수나 상한을 줄인다.
- **"Gemini 오류 반복", "시간 제한 도달", "비용 상한 도달":** 그날은 받은 메모만 쓴다. 계속 나오면 모델 ID와 공식 문서의 변경 사항을 본다.
- **"할당량 초과, 태평양 시간 자정에 풀림":** 할 일 없음. 풀린 뒤의 다음 실행이 다시 받는다. 같은 날 시험 실행을 여러 번 했는지 본다. 매일 계속 나오면 Google Cloud 콘솔의 할당량 화면에서 쓴 양을 보고, 작업 브랜치에서 검색 수나 상한(`src/youtube.ts`)을 고친다.
- 키가 공개된 곳(커밋, 백업, 결과물)에 들어갔다면 공개 전 점검이 막지만, 이미 push됐다면 Google Cloud 콘솔에서 그 키를 지우고 새로 만든다.

- 이 실행은 검토 없이 운영 사이트에 영상을 올린다. 실행 뒤 브리프의 '영상' 탭과 개인정보 처리방침 페이지를 한 번 본다.
- `start`의 "키:" 줄이 "YouTube 있음"인지 본다. "없음"이면 영상 받기만 실패하고 나머지는 돈다.

### 7단계 이전 코드로 돌아가야 할 때

- 기본은 머지 뒤 첫 실제 실행의 실행 전 사본(마이그레이션 전 DB, 영상 기록 없음)을 `data/tidwyn.db`로 되돌리는 것이다(위 "실행 전 사본"). 그 뒤에 모은 날짜는 이전 코드의 다음 실행이 다시 모은다. 다시 7단계로 올리면 그때의 가장 늦은 브리프 날짜부터 영상을 다시 받는다.
- 사본이 14일이 지나 없으면 `node src/cli.ts restore --force`로 백업에서 복원한다. 백업에는 영상 데이터가 없으므로 영상 기록이 없는 DB가 된다(날짜별 "고르기 끝남" 상태도 없다).
- 이전 코드는 30일 지우기를 하지 않는다. 영상 기록이 든 DB로 이전 코드를 돌리면 영상 기록이 DB와 실행 전 사본에 30일을 넘겨 남아 30일 규칙과 어긋난다. 그래서 영상 기록이 든 DB를 그대로 쓰지 않는다. 되돌린 뒤 `data/snapshots/`에 남은 7단계 실행 전 사본과 시험 폴더(`.test-data/<시각>/`)에도 영상 기록이 들어 있으니, 필요 없으면 지운다.
- 이전 코드의 사이트에는 개인정보 처리방침 주소(`/privacy`)와 영상 탭이 없어 그 주소가 깨진다.

### 8단계 머지 뒤 첫 실제 실행

- 첫 실제 `/brief`가 DB를 버전 8로 마이그레이션한다(그 전에 실행 전 사본이 남는다). 기존 영상 기록은 요약 없이 그대로 남는다.
- `start`의 "키:" 줄이 "Gemini 있음"인지 본다. 그 실행의 대상 날짜가 아직 고르기 전이면 첫 Gemini 호출이 일어나고 실행 요약에 토큰과 예상 달러가 나온다.
- 이 실행은 검토 없이 운영 사이트에 요약을 올린다. 실행 뒤 브리프의 '영상' 탭을 한 번 보고, 지출 화면에서 실제 청구액을 본다.

### 8단계 이전 코드로 돌아가야 할 때

- 기본은 머지 뒤 첫 실제 실행의 실행 전 사본(마이그레이션 전 DB)을 `data/tidwyn.db`로 되돌리는 것이다.
- Gemini만 끄려면 `.env.local`에서 `GEMINI_API_KEY`를 빼면 된다. 코드를 되돌리지 않아도 메모 없는 흐름으로 돈다.
- 버전 8 DB를 이전 코드로 열면 코드가 거부하지 않고 그대로 돈다. 요약 칸은 쓰이지 않고 남으며, 영상 기록과 함께 30일 지우기로 지워진다.

## 공개 사이트

- 주소: <https://tidwyn.vercel.app>. Vercel 팀 `mivomad33`의 프로젝트 `tidwyn`이다. Git 저장소와 연결하지 않았다(Vercel이 저장소를 빌드하지 않는다).
- 매일 `/brief`의 실제 실행이 끝에 사이트를 빌드하고(`site`), 결과물을 운영 배포하고(`deploy`), 배포 뒤 점검을 한다. 시험 모드와 데이터 폴더 지정 실행은 빌드만 한다.
- 결과물은 `<데이터 폴더>/site/`에 매번 새로 만든다. 화면 틀(`index.html`), 화면 파일(`assets/`), 사이트 데이터(`site-data/`), 검색 색인(`pagefind/`), 호스팅 설정(`vercel.json`)만 들어간다. DB와 백업 파일은 들어가지 않는다.

### 손으로 빌드·배포하기

main을 체크아웃한 상태에서 실제 DB로 빌드하고 배포한다.

```bash
node src/cli.ts site --data-dir data
```

```bash
node src/cli.ts deploy --dir data/site --db data/tidwyn.db
```

- `site`는 빌드 뒤 결과물 검사(DB 파일, 백업 파일, 영상 작업 파일, 비밀 값 모양, 출처 API 키 값(ECOS·FRED·YouTube·Gemini), 홈 폴더 경로, 허용 목록 밖 메일 주소)를 한다. 걸리면 실패한다.
- `deploy --dir`는 실행 기록과 모드에 상관없이 배포한다. 배포 전에 결과물 검사를 다시 하고, 배포 뒤 운영 주소의 첫 화면과 최근 날짜가 그 DB와 같은지 점검한다(별칭이 새 배포로 바뀌는 시간을 기다려 5초 간격으로 6번까지 확인한다).
- Vercel CLI는 프로젝트 `devDependencies`(`node_modules/.bin/vercel`)를 쓴다. 로그인이 풀렸으면 `node_modules/.bin/vercel login`으로 다시 로그인한다(사용자가 한다).

### 미리보기 배포

운영 주소를 바꾸지 않고 결과물을 Vercel 프로젝트 `tidwyn`의 미리보기 주소로 올린다(새 화면을 폰에서 먼저 볼 때). `/brief`는 이 명령을 부르지 않는다.

```bash
node src/cli.ts deploy --dir <결과물 폴더> --preview
```

- 운영 배포와 같은 규칙(결과물 폴더만 올림, `--scope mivomad33 --project tidwyn`, Vercel에서 빌드하지 않음, 결과물 검사를 통과해야 올림)으로 `--prod` 없이 올린다. 운영 별칭(`tidwyn.vercel.app`)은 바뀌지 않는다. 출력에 미리보기 주소가 나온다.
- 폰에서 보려면 폰 브라우저에서 Vercel에 `mivomad33` 계정으로 로그인한 뒤 그 주소를 연다. 미리보기 주소는 Vercel 배포 보호(Vercel Authentication)로 로그인해야 열린다.
- **주의:** 프로젝트 설정에서 배포 보호가 꺼져 있으면 미리보기 주소를 아는 사람은 누구나 연다. 아직 검토하지 않은 데이터(예: 시험 실행의 대상 목록)를 올리기 전에 Vercel 화면의 Settings → Deployment Protection에서 켜져 있는지 본다.

### Vercel 한도와 넘을 때 할 일

- 무료(Hobby) 플랜의 CLI 배포 한도는 총 100MB, 파일 15,000개다(2026-10-28 공식 문서). 요약의 사이트 줄이 80MB나 12,000개를 넘으면 경고를 낸다.
- 지어낸 5년치 데이터(하루 뉴스 42건, 이슈 15,000개)로 재면 파일은 2,262개지만 크기는 약 106MB다. 크기가 먼저 한도에 닿는다. 1년에 약 20MB씩 늘어난다고 보면 4~5년 뒤다.
- 경고가 나오면 Pro로 올리거나 다른 정적 호스팅으로 옮긴다(`docs/memory.md` 2026-10-28 결정). 결과물은 순수 정적 파일이라 그대로 올릴 수 있다. 옮길 때 다른 호스팅에서도 `vercel.json`의 되쓰기 규칙(`site-data/`·`pagefind/`·`assets/` 밖의 주소는 `index.html`)을 같게 설정한다.

### 배포 뒤 점검이 실패했을 때

- 배포는 이미 올라가 있고 자동으로 되돌리지 않는다. 요약에 나온 이유를 본다.
- 운영 주소를 브라우저로 열어 첫 화면과 최근 날짜를 확인한다. 정상이면 별칭이 늦게 바뀐 것이다. 할 일은 없고 다음 실행이 다시 점검한다.
- 화면이 깨졌으면 위 "이전 배포로 되돌리기"로 되돌리고, 작업 브랜치에서 원인을 고친다.

- Vercel 대시보드의 `mivomad33` 팀 → `tidwyn` 프로젝트 → Analytics에서 본다. 무료 플랜은 월 50,000 이벤트, 보고 기간 30일이다. 넘으면 청구 없이 수집만 멈춘다.

## 원본 저장소

- GitHub `mivomad33/tidwyn`. main과 `data` 브랜치만 push한다. 작업 브랜치는 push하지 않는다.
- 커밋 이메일은 GitHub noreply 주소다(이 저장소의 로컬 `git config user.email`). 다른 주소로 커밋하면 공개 전 점검에 걸린다.
- `data`: 매일 `/brief`의 실제 실행이 원격보다 앞선 커밋에 공개 전 점검을 하고 push한다(강제 push 아님). 점검에 걸리면 push하지 않는다.
- main: 작업 브랜치를 사용자 승인 뒤 main에 squash merge하면, 머지한 세션이 공개 전 점검을 돌리고 main을 push한다(아래 "머지 뒤 할 일").

### 공개 전 점검

```bash
node src/cli.ts precheck
```

- 모든 로컬 브랜치의 이력 전체와 git이 추적하는 지금 파일을 검사한다. `--refs main,data`로 브랜치를 고를 수 있다.
- 걸리는 것: noreply 주소가 아닌 작성자·커미터 이메일, 실행하는 사람의 홈 폴더 절대 경로, 비밀 값 모양(GitHub·Vercel 토큰 접두사, Google API 키 모양(`AIza`로 시작하는 39자), 개인 키 머리, `.env` 파일), 출처 API 키 값(`.env.local`과 환경 변수 `ECOS_API_KEY`·`FRED_API_KEY`·`YOUTUBE_API_KEY`의 값. 값은 출력하지 않고 "키 값이 들어 있음"과 파일 이름만 보인다. 키가 어디에도 없으면 이 검사는 건너뛰었다고 보인다), SQLite 파일과 실행 전 사본, 백업 파일 속 영상 기록(영상 기록 항목 이름), 허용 목록 밖 메일 주소 모양(허용: 이 저장소의 noreply 주소, `noreply@anthropic.com`, `example.com`·`example.org` 같은 예시 주소).
- 걸린 파일과 종류만 나오고 값은 가린다. 통과하면 "통과."가 나오고 종료 코드가 0이다.

### 머지 뒤 할 일

1. 공개 전 점검을 돌린다: `node src/cli.ts precheck`. 실패하면 push와 공개를 하지 않고 사용자에게 알린다.
2. main을 push한다: `git push origin main`. 강제 push는 하지 않는다.
3. 3단계 머지 때만: 저장소를 공개로 바꾸고(`gh repo edit mivomad33/tidwyn --visibility public --accept-visibility-change-consequences`), 로그인 없이 열리는지 본다(`curl -s -o /dev/null -w '%{http_code}' https://github.com/mivomad33/tidwyn`이 200).
4. 공개로 바꾼 뒤에는 main과 `data`를 강제 push하지 않는다.

### 이력 번들

- 3단계에서 커밋 이메일을 noreply 주소로 바꾸려고 이력을 다시 썼다(2026-10-29). 다시 쓰기 전의 모든 브랜치를 저장소와 같은 상위 폴더의 `../tidwyn-history-backup-20261029.bundle`에 남겼다.
- 옛 이력이 필요하면 `git clone ../tidwyn-history-backup-20261029.bundle <새 폴더>`로 꺼낸다. 이 번들에는 옛 개인 이메일이 들어 있으니 공개 저장소에 올리지 않는다.

### 메일 주소 모양에 걸렸을 때

뉴스 글(요약, 배경 등)에 허용 목록 밖의 메일 주소 모양(예: 기사에 나온 연락처)이 들어가면 사이트 빌드의 결과물 검사와 `data` push의 공개 전 점검이 멈춘다. 걸린 파일만 나오고 값은 가린다.

1. 걸린 파일(`site-data/list-YYYY-MM.json`이나 `YYYY-MM.json` 등)로 달을 알아낸다. 그 달의 백업 파일(`data/backup/YYYY-MM.json`)에서 `@`를 찾아 어느 날짜·뉴스의 어느 글인지 확인한다.
2. Claude Code를 닫거나 `/brief`가 돌지 않는 때에, `data/snapshots/`에 지금 DB 사본을 하나 더 남긴다(`cp data/tidwyn.db data/snapshots/tidwyn-수동-<날짜>.db`).
3. DB의 그 글에서 메일 주소를 지우거나 "(메일 주소 생략)"처럼 바꾼다. `sqlite3 data/tidwyn.db`로 그 뉴스의 행을 찾아 `UPDATE`한다. 다른 값은 바꾸지 않는다.
4. 아직 push하지 않은 `data` 커밋에 그 글이 들어 있으면 그 커밋들을 다시 만든다: `git fetch origin data` 뒤 `git update-ref refs/heads/data refs/remotes/origin/data`로 `data`를 원격과 같게 되돌리고, main 체크아웃 상태에서 `node src/cli.ts backup`을 돌려 지금 DB로 새 커밋을 만든다. 이미 push한 커밋에 들어 있으면 공개 이력이라 강제 push로 지우지 않는다. 사용자가 따로 판단한다.
5. 마크다운을 다시 만든다: `node src/cli.ts render --all`.
6. `node src/cli.ts precheck --refs data`가 통과하는지 보고, "손으로 빌드·배포하기"로 사이트를 다시 올린 뒤 `git push origin data`.

## 개발

```bash
pnpm install
```

```bash
pnpm verify
```

- `pnpm verify`는 타입 검사, 린트, 전체 테스트를 한 번에 돌린다.
- 테스트는 임시 폴더와 임시 git 저장소만 쓴다. 실제 `data/`와 이 저장소의 `data` 브랜치를 건드리지 않는다.
- 개발 중 확인은 `/brief test`나 `TIDWYN_DATA_DIR`로 다른 데이터 폴더를 지정해서 한다.
